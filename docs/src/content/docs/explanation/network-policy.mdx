---
title: "Network policy"
description: "Because Kix knows which workloads talk to which Services, it can generate matching ingress and egress network policies automatically."
---

Writing default-deny Kubernetes network policies by hand is tedious and fragile. To let one web service talk to one database, you normally have to write an egress rule in the caller's namespace, a matching ingress rule in the database's namespace, and a DNS rule so the caller can resolve the hostname. In Kix, when you turn on `networkPolicy.enable = true`, the compiler generates both ends of those firewall rules automatically from the service connections your packages already declare.

## Which policy objects Kix writes

To generate network policies, your cluster must include an instance whose package claims the `network-policy-enforcer` role. Setting `networkPolicy.enable = true` without an enforcer instance fails evaluation. Today, `packages.experimental.cilium` is the only enforcer package: Kix generates Cilium policy resources only and cannot emit standard Kubernetes `NetworkPolicy` objects or policies for other CNIs such as Calico.

On platforms that own the pod network (`cluster.roles.cni.binding = "exclusive"`, such as GKE Dataplane V2, EKS with the Amazon VPC CNI, and k3s with Flannel), Kix cannot install Cilium. None of the three serves `CiliumNetworkPolicy`: GKE Dataplane V2 always enforces standard `NetworkPolicy`, the Amazon VPC CNI enforces it only after enforcement is turned on in the add-on (`enableNetworkPolicy`, which is off by default), and k3s enforces it with its embedded network policy controller unless started with `--disable-network-policy`. Setting `networkPolicy.enable = true` on these clusters fails evaluation and tells you to set `networkPolicy.enable = false` until Kix supports that pod network.

Most generated policies are namespaced `CiliumNetworkPolicy` objects (`apiVersion: cilium.io/v2`). Kix writes cluster-wide `CiliumClusterwideNetworkPolicy` objects in three cases:

| Policy | Kind | Scope | Written when |
| --- | --- | --- | --- |
| Workload and connection policies (caller egress, callee ingress, DNS and API server egress, ingress-controller and LoadBalancer ingress, StatefulSet peer traffic, Prometheus and VMAgent scrapes, and `kix.operandPolicy`) | `CiliumNetworkPolicy` | Namespaced | `networkPolicy.enable = true` |
| `<namespace>-default-deny` | `CiliumNetworkPolicy` | Namespaced | `networkPolicy.enable = true` and `networkPolicy.defaultDeny = true` (default) |
| `networkPolicy.platformIntents.<name>` | `CiliumNetworkPolicy` | Namespaced | `networkPolicy.enable = true` and `scope = "namespaced"` (default) |
| `networkPolicy.platformIntents.<name>` | `CiliumClusterwideNetworkPolicy` | Cluster-wide | `networkPolicy.enable = true` and `scope = "clusterwide"` |
| `cilium-cluster-dns-egress` | `CiliumClusterwideNetworkPolicy` | Cluster-wide | The `cilium` instance configures Cilium, effective `policyEnforcementMode` is `"always"`, and `clusterDnsEgress = true` (default) |
| `cilium-health-probes` | `CiliumClusterwideNetworkPolicy` | Cluster-wide | The `cilium` instance configures Cilium and effective `policyEnforcementMode` is `"always"` |

When `networkPolicy.defaultDeny = true` (the default once `networkPolicy.enable = true`), Kix writes a `<namespace>-default-deny` `CiliumNetworkPolicy` in every namespace (except `_`-prefixed keys such as `_cluster`) that holds at least one active deployed instance or is declared under `namespaces`. Namespaces that hold only imports (`kix.mkImport`, such as `kube-system/platform-dns`) or inactive `optional` instances are skipped because Kix deploys no pods there; to add a default-deny policy to an import-only namespace, declare `namespaces.<name> = { };`.

Kix also skips any namespace listed in `networkPolicy.platformNamespaces`. The `gke`, `gke-autopilot`, `eks`, and `aks` flavors set this to `[ "kube-system" ]` so a default-deny policy does not block cloud-managed pods whose traffic Kix cannot see; workloads Kix deploys in a platform namespace still get their own policies, which isolate only those pods. Where `<namespace>-default-deny` is written, it selects every pod in the namespace (`endpointSelector: {}`) and adds an empty rule (`{}`) for each direction in `networkPolicy.directions`, blocking all unmatched traffic in that direction:

```yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: immich-default-deny
  namespace: immich
  labels:
    app.kubernetes.io/managed-by: kix
    kix.run/derived: "true"
    kix.run/policy-type: default-deny
spec:
  endpointSelector: {}
  ingress:
    - {}
  egress:
    - {}
```

When the `cilium` instance configures Cilium (either by installing the Helm chart or, on RKE2, by writing a `HelmChartConfig` for RKE2's bundled Cilium) and `networkPolicy.enable = true`, Kix sets Cilium's `policyEnforcementMode` to `"always"` unless `values.policyEnforcementMode` overrides it. In `"always"` mode, Cilium blocks unmatched traffic on every pod in the cluster, even in namespaces Kix does not manage and on pods that no policy selects.

To keep core cluster networking working in `"always"` mode, the `cilium` instance adds two `CiliumClusterwideNetworkPolicy` objects:

- **`cilium-cluster-dns-egress`:** Allows every pod (`endpointSelector: {}`) to reach the cluster's DNS pods on UDP and TCP port 53 (see [DNS peers](#dns-peers)), so pods outside Kix-managed namespaces can still resolve DNS names. Set `clusterDnsEgress = false` on the `cilium` instance if you write your own cluster-wide DNS policy.
- **`cilium-health-probes`:** Allows Cilium's node health endpoints to probe each other across nodes (`health` and `remote-node` entities).

When the platform manages Cilium's configuration externally (the `cilium` instance uses a `platform-cilium` import with `out.helmChartConfig = null`), Kix leaves Cilium's enforcement mode unchanged and omits both cluster-wide policies.

### Replacing existing clusterwide policies

Kix writes `<namespace>-default-deny` policies only in namespaces it manages, though Cilium's `"always"` mode still blocks unmatched traffic in unmanaged namespaces (except DNS when `cilium-cluster-dns-egress` is active).

If your cluster relies on existing `CiliumClusterwideNetworkPolicy` rules applied with `kubectl` (for example, allowing egress to `world` from every pod), Kix does not generate equivalents automatically. Bring those rules into Kix in either of two ways:

- Add an entry under `networkPolicy.platformIntents` with `scope = "clusterwide"` (using `podSelector`, `targetNamespace`, `ingress`, and `egress`).
- Build a `CiliumClusterwideNetworkPolicy` directly in a package with `scope.mkCR cilium.out.crds.CiliumClusterwideNetworkPolicy { ... }`.

Every policy Kix generates carries the label `kix.run/derived: "true"` in `kix build <cluster>` output, so you can check Kix's generated coverage before deleting existing policies.

## Default-deny baseline and paired rules

With `networkPolicy.defaultDeny = true` (the default when network policy is enabled), Kix emits a baseline default-deny policy in every Kix-managed namespace for the configured `networkPolicy.directions` (`"both"`, `"ingress"`, or `"egress"`). Nothing in those namespaces can dial out or accept traffic unless a specific rule allows it.

For every service dependency in the graph, Kix opens a narrow path on both ends:

- **Caller egress:** A policy in the calling workload's namespace allowing egress to the target Service's pod selector and numeric ports, plus egress to the cluster DNS provider.
- **Callee ingress:** A paired policy in the target Service's namespace (`emit.inNamespace`) allowing ingress from the caller's pod selector and namespace on those ports.

Because Kix compiles the whole cluster at once, it knows the pod labels, namespaces, and container ports of both the caller and the callee. The enforcer package (such as `packages.experimental.cilium`, which claims the `network-policy-enforcer` role) supplies the policy builder (`out.netpol.mkPolicy`). If `networkPolicy.enable = true` is set without an enforcer in the cluster, evaluation fails immediately rather than generating policies that nothing would enforce.

## How Kix discovers connections from endpoint facts

Kix distinguishes between naming a resource (for deploy ordering) and dialing a Service over the network.

When a Service is sealed by `scope.mkResource`, its address-shaped outputs (`out.fqdn`, `out.url`, and custom `outputs`) carry an **endpoint fact** in their Nix string context alongside the Service's identity path. That fact records the Service's namespace, pod selector, and ports.

- **Conducting versus terminating facts:** Non-workload resources such as ConfigMaps and Secrets conduct endpoint facts onward. If a package writes `backend.out.fqdn` into a ConfigMap and mounts that ConfigMap into a Deployment, the Deployment absorbs the endpoint fact from the ConfigMap. Workload constructors (`scope.mkDeployment`, `scope.mkStatefulSet`, `scope.mkDaemonSet`, and `scope.mkJob`) terminate the fact and turn it into a network connection.
- **Structural references:** Reading `out.name` carries only the resource's identity path, not an endpoint fact. That orders the consumer after the target without opening a firewall hole.

Beyond cross-package Service references, Kix automatically derives rules for four other structural patterns:

1. **DNS egress:** Every workload with an egress policy gets a rule allowing DNS queries to the cluster's [DNS peers](#dns-peers), and any workload that connects to a Service is ordered after the DNS provider during deploy.
2. **Kubernetes API server egress:** During instance evaluation, Kix walks the instance's `RoleBinding` and `ClusterRoleBinding` resources. If a workload's `ServiceAccount` is bound to a role, Kix emits an egress rule allowing that workload to reach `kube-apiserver`.
3. **External ingress and exposure:** A workload fronted by a `LoadBalancer` Service (unless served by an internal provider load-balancer class) gets an ingress rule from `world`. Similarly, `kix.expose` automatically emits an ingress rule on the backend admitting the configured Ingress or Gateway controller's pods.
4. **StatefulSet peer traffic and metric scrapes:** `StatefulSet` workloads receive self-ingress and self-egress rules so peer replicas can form a cluster. At the cluster level, Kix joins each Prometheus or VMAgent custom resource with the `ServiceMonitor` and `PodMonitor` objects it selects, opening scrape egress from the monitoring server and scrape ingress on each target's numeric pod ports.

### DNS peers

The DNS egress rule allows UDP and TCP port 53 to the cluster's DNS peers. By default, these are pods labeled `k8s-app: kube-dns` in `kube-system`, where kubeadm, kind, k3s, RKE2, and EKS run CoreDNS. A `dns` import (such as a flavor's `platform-dns`) can override this list in `out.dnsPeers`. Each entry selects either pods by label in a single namespace (`{ namespace; podSelector; }`) or an IP range (`{ cidr; }`). The `gke` and `gke-autopilot` flavors set `out.dnsPeers` to `kube-dns`, `node-local-dns`, `169.254.169.254/32`, and `169.254.20.10/32`, covering standard `kube-dns`, NodeLocal DNSCache, and Cloud DNS.

Kix reads `out.dnsPeers` only from `kix.mkImport` instances. When a managed package such as `coredns` provides the `dns` role, Kix uses the default peers, so with `networkPolicy.enable = true` that package must run in `kube-system` with the label `k8s-app: kube-dns`. Because Cilium cannot combine pod selectors and IP ranges in one DNS rule, the `cilium` enforcer accepts only `{ namespace; podSelector; }` entries and fails evaluation when `out.dnsPeers` includes `{ cidr; }`.

### Cloud credentials

When a workload's ServiceAccount uses a [cloud identity](/docs/reference/composition-helpers/#cloudidentity), Kix automatically adds the outbound rules needed to fetch credentials to that workload's egress policy: TCP port 443 to external addresses (`world`) for IRSA (AWS STS) and Microsoft Entra Workload ID, TCP port 80 to the node-local EKS Pod Identity agent (`169.254.170.23/32` and `fd00:ec2::23/128`), and TCP ports 80 and 8080 to the node-local GKE metadata server (`169.254.169.254/32`). Workloads without a cloud identity do not receive these rules.

## Three-phase policy assembly

Different network facts become available at different stages of evaluation. Kix attaches its network policy plugin across three phases so each policy is built as soon as its inputs exist:

| Phase | What Kix knows | Policies emitted |
| --- | --- | --- |
| **Workload phase** (inside `sealWorkload`, pre-seal) | One workload's pod spec, absorbed endpoint facts, and package intents | Per-connection caller egress, callee ingress, DNS egress, StatefulSet self-rules, and declarative package intents |
| **Instance phase** (post-fixpoint processor) | All resources belonging to one package instance | API server egress (from the `ServiceAccount` to `RoleBinding` walk), `LoadBalancer` world ingress, and policies for custom resources that declare `factBehavior.endpoint = "terminate"` |
| **Cluster phase** (whole-cluster processor) | All active instances, namespaces, and monitors | Per-namespace default-deny walls, Prometheus and VMAgent scrape policies, and `networkPolicy.platformIntents` |

Running the workload phase *before* the workload resource is sealed is critical for rollout safety. Kix splices the generated policies into the workload's `requires` list before computing its store hash. As a result, `kix deploy` applies the `CiliumNetworkPolicy` resources and waits for them to become ready before applying the Deployment itself, ensuring pods never start in a window where their firewall rules are missing.

## Declarative intents and operand policies

A dependency graph only sees connections between resources in the build. Two kinds of traffic fall outside that graph:

- **External traffic (`meta.network.intents`):** The internet, external APIs, or the Kubernetes API server dialing an admission webhook are not resources in the Kix build. A package declares these connections once under `meta.network.intents` using targets like `"world"`, `"apiserver"`, `"dns"`, or `"all-pods"`.
- **Operator-created pods (`kix.operandPolicy` and `platformIntents`):** When an operator creates data-plane pods at runtime from a custom resource (such as database replicas or proxy pods), Kix does not build their Deployment directly. Packages that author those custom resources use `kix.operandPolicy` (or CRD `factBehavior`) to emit policies selecting the operator's pod labels, while cluster operators can use `networkPolicy.platformIntents` to open traffic for pods managed outside Kix.
