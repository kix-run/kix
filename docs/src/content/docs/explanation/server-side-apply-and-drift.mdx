In a live Kubernetes cluster, your deployment tool is rarely the only thing modifying objects. HorizontalPodAutoscalers adjust `spec.replicas`, operators inject webhook conversion blocks into CRDs, and the Kubernetes API server fills in default values on every pod spec. Kix uses Kubernetes **Server-Side Apply** to track exactly which fields Kix owns, so it can detect real configuration drift without fighting in-cluster controllers or flagging harmless API server defaults.

## Per-field ownership in Server-Side Apply

When `kix deploy` applies a manifest, it uses Kubernetes Server-Side Apply with the field manager name `kix/<cluster>`, where `<cluster>` is the name of the Kix cluster, such as `kix/production`. Instead of storing a giant "last-applied-configuration" JSON blob in an annotation, the Kubernetes API server records which manager owns each individual field inside `metadata.managedFields`.

Because ownership is tracked per field rather than per object, Kix and an in-cluster controller can safely co-own the same Deployment:

- Kix can own the Deployment's container image, environment variables, and resource requests.
- A HorizontalPodAutoscaler can own `spec.replicas` on that same Deployment.
- Fields that Kix never included in its manifest (such as `status` or API server defaults) stay outside Kix's owned field set.

When Kix tries to change a field that another manager currently owns, the Kubernetes API server returns a **field ownership conflict** instead of silently overwriting the value. That conflict is a useful safety check: it tells you that your Nix manifest and a live controller (or a manual `kubectl edit`) are both trying to control the same setting.

## Two ways to resolve an ownership conflict

How you resolve a conflict depends on who *should* control the field going forward:

1. **Kix should own the field:** When someone changes a field that Kix applied, for example with `kubectl edit`, the next `kix deploy` labels the object as changed on the cluster and takes the field back (see [Drift detection](#drift-detection-uses-the-same-ownership-boundary) below). For a field Kix has never owned, such as when you move a resource from Helm to Kix, use `--force-conflicts` on `kix deploy` for that transition. A forced Server-Side Apply transfers ownership of the conflicting fields to Kix and writes the values from your build. Avoid leaving `--force-conflicts` enabled on every routine deploy, because it would also steamroll legitimate conflicts from controllers.
2. **A controller should own the field (`ownership.cede`):** Sometimes a resource must include an initial value when it is first created, even though an in-cluster controller will take over that field afterward (for example, `spec.replicas` on an autoscaled workload, or webhook `spec.conversion` fields on a CRD). In those cases, the package declares the field path under `ownership.cede` on `scope.mkResource`. Kix sends the field when creating the object, and if a later apply conflicts *only* on declared ceded paths, Kix automatically retries without those fields so the controller keeps ownership. A ceded field never counts as drift, and Kix never takes it back.

Making `ownership.cede` an explicit list of field paths keeps conflicts honest: expected controller takeovers happen smoothly, while a change by anything else to a field Kix applied shows up as drift and asks you to decide.

## Drift detection uses the same ownership boundary

Most diff and drift tools compare your desired YAML against the entire live object returned by the cluster, which creates constant noise whenever controllers update status fields or the API server adds default fields.

Kix compares only the fields its own field manager owns. After each apply, Kix hashes the live fields it owns, leaving out the fields the object cedes, and records that applied hash in the status of a [`PackageInstanceRevision`](/docs/reference/annotations-crds-and-receipts/#packageinstancerevision): a record, kept in the cluster, of the objects one build makes for one package instance. The object itself carries only its build hash, `kix.run/identity-hash`, which says what the build wants.

With those two hashes, `kix plan` and `kix deploy` decide what to do with each object of the build, in this order:

1. **The object is missing, or its build hash differs from the new build's.** Kix applies it. This is a change the build makes.
2. **The build hashes match, but Kix has no applied hash for the object.** Kix applies it again and records the hash. This happens once after a deploy stopped between an apply and the write of the hash, or after a backup was restored without the revisions' status.
3. **The applied hash differs from the hash of the fields Kix owns on the live object.** Something changed a field Kix applied. The plan labels the object as changed on the cluster, names the field manager and the fields, and `kix deploy` applies the build again with force, which takes those fields back. If the object changes again after the plan, the deploy stops instead of overwriting a change you have not seen.

Otherwise the object is unchanged, and Kix does not write to it.

`kix status` runs the same comparison without a build, so it reports drift on any machine. If a controller updates `status`, or a field was ceded via `ownership.cede`, Kix ignores it. If someone changes a Kix-owned field out of band (even through a subresource like `kubectl scale`), Kix names the field and the field manager that changed it.

The [Kix operator](/docs/reference/cli/operator-mode/) never takes fields from another field manager. When drift has another owner, it leaves the object as it is and posts a `DriftNotReverted` Warning Event. It repairs drift that no manager owns, such as a removed field.

## Several Kix clusters on one Kubernetes cluster

Several Kix clusters can deploy to one Kubernetes cluster, and two of them can deploy the same object, such as a shared Namespace or ClusterRole. Each Kix cluster applies under its own field manager, so the object's `metadata.managedFields` shows which Kix clusters apply it.

- **When both render the object the same way,** both own the same fields and neither apply changes the object.
- **When they set a field to different values,** Kubernetes refuses the second apply, and the deploy stops with `[K5636]`, naming the other Kix cluster and the fields. Make the two definitions agree, or deploy the object from one Kix cluster only. `--force-conflicts` takes the fields for the cluster you deploy, and the other one's next deploy is refused in the same way. `kix plan` shows the refusal before anything is applied.
- **When a field another Kix cluster applied reads as drift,** Kix does not take it back with force, as it would from `kubectl` or a controller. It applies the object without force, and the plan counts it apart from the drift it reverts. Kubernetes adds this cluster's entry when the values agree and refuses with `[K5636]` when they differ.
- **When one of them stops deploying the object,** its prune keeps the object, because the other Kix cluster still deploys it, and sends one empty apply under its own field manager. That apply gives up its fields, so the object belongs to the other Kix cluster alone, and that cluster's prune deletes it once it stops deploying it too. If the empty apply fails, the object stays on the first cluster's list of kept orphans, and its next deploy tries again.

Each prune reads the records and revisions of every other Kix cluster before it deletes an object, and deletes only with the `resourceVersion` it read. The first apply by a second Kix cluster adds its field manager to the object and changes that `resourceVersion`, so a prune that read the object earlier has its delete refused.

## The first deploy after upgrading

Earlier versions of Kix applied every object under the one field manager name `kix`, and wrote two annotations onto every object after applying it: `kix.run/activations`, the deployment records that used the object, and `kix.run/applied-hash`. That second write changed every object on every deploy, which restarted Pods of operators that copy annotations and raced with operators that update the same object.

The first deploy of a Kix cluster with this version moves it to revisions in two steps.

1. **It converts the records.** Under the deploy lock, before it writes any object, Kix gives revisions to each deployment record the earlier version wrote that a later deploy still needs: the current record, and each `Failed` or `Partial` record. It finds what each record deployed in the record's package index, or from the live objects whose `kix.run/activations` annotation names the record, and copies each object's `kix.run/applied-hash` into the revisions' status. For the current record it also writes a revision of the orphans earlier deploys kept. It names the revisions on each record in one write, after they all exist. From then on, every reader reads those records from their revisions.
2. **It tidies the objects.** It rewrites the metadata of each object once, in one write that renames the `kix` entry in `metadata.managedFields` to `kix/<cluster>` and removes both annotations. The rewrite runs right before an object's first apply under the new name, because Kubernetes would refuse a changed value while `kix` still owned the field. Objects the deploy does not apply are rewritten after the apply. The plan says how many objects it rewrites in a line that starts with `Upgrade:`. Controllers that copy annotations into Pods may restart those Pods once, and after that a deploy writes only the objects it changes.

The Kix operator's deploy and its drift repair convert the records the same way, and `kix deploy --only` does too.

The conversion writes no object, and a record gets its revisions in one write after all of them exist, so a deploy that stops at any point leaves the records readable. The notes stay on the objects it had not tidied yet, and the next deploy finishes the job. If an earlier version of Kix deploys the Kix cluster afterwards, it writes the annotations again, and the next deploy with this version converts its new record.

### Kix clusters on two versions of Kix

A project can keep its Kix clusters on [several versions of Kix](/docs/how-to/start-and-inspect/hold-clusters-on-different-kix-versions/). An earlier version decides that an object is still in use by another Kix cluster from the `kix.run/activations` annotation. If this version removed it from a shared object, the earlier version's prune could delete the object.

So while another Kix cluster on the same Kubernetes cluster is still deployed with an earlier version, Kix leaves the `kix` entries and both annotations on each object that both Kix clusters deploy, and adds its own record to `kix.run/activations`. Its own apply adds a `kix/<cluster>` entry beside `kix` and takes nothing from it. A deploy of either Kix cluster that changes a value the other one set is refused with a field ownership conflict that names `kix`.

Kix adds its record to the annotation in a write that does not stop the deploy when it fails. If that write fails on a shared object, the annotation names only the older Kix cluster's records, so when that cluster stops deploying the object, its prune can delete it, as it could before either cluster upgraded. The next deploy of this Kix cluster writes the annotation again. The first deploy of the other Kix cluster with this version finishes the move on those objects.

## Why deploy inputs are committed

Just as Kix avoids hidden state in the cluster, it avoids hidden inputs at deploy time. Every input that affects a compiled manifest, including frequently updated values like container image digests, lives in a committed file in your repository and is read during evaluation:

- **Content-addressed identity hashes:** During evaluation, Kix computes each resource's `kix.run/identity-hash` from its serialized JSON in Kix's local store, and `kix deploy` compares them with the build hash on each live object to determine which objects the build changes. Reading all inputs during evaluation guarantees that the hashes in your build match the manifests applied to the cluster.
- **Committed JSON image pins (`pins.json`):** To make automated image updates easy without letting a CI bot rewrite Nix code, Kix stores image versions in a structured `pins.json` file managed by `kix pin`. Running `kix pin set <key> --tag <tag>` queries the container registry, records the immutable `sha256` digest alongside the tag, and writes the update to `pins.json`.
- **Verifiable deploy receipts (`status.receipt`):** When `kix deploy` finishes applying an `Activation`, it records a deploy receipt on the `Activation` status subresource containing the activation hash, timestamp, Git commit, locked flake inputs, and container image digests. Because every input was committed before evaluation, `kix compliance attest --from-cluster` can generate a verifiable SLSA provenance statement directly from the live cluster receipt.
