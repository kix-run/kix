---
title: "Handle server-side-apply conflicts safely"
description: "Identify the field manager that changed a field Kix applied, and decide whether Kix takes it back or leaves it with that manager."
---

import Command from '/src/components/Command.astro';
import drift from '/src/command-output/how-to/adoption-ssa-conflicts/drift.json';
import resolve from '/src/command-output/how-to/adoption-ssa-conflicts/resolve.json';
import clean from '/src/command-output/how-to/adoption-ssa-conflicts/clean.json';

Kubernetes records which field manager owns each field of an object. When
another manager changes a field Kix applied, it becomes that field's owner.
Kix shows this as drift before it changes anything. Decide who should own the
field, then either let Kix take it back or leave it with the other manager.

The example below starts with a Kix-managed Deployment. A separate manager
named `autoscaler` then takes ownership of `spec.replicas` and changes it from
two to three.

## See what changed without changing the cluster

Run a plan:

<Command {...drift} />

The plan labels the change `(reverts drift)` and lists it under `Drift:`. It
names three things:

- the resource, `Deployment.apps/legacy-web@takeover`;
- the other field manager, `autoscaler`;
- the field and its two values, `spec.replicas`: `3` live and `2` in the
  deployed build.

The `↺` line under `Objects:` counts the objects that changed on the cluster
since Kix applied them. A plain `kix deploy` applies each of them again and
takes the changed fields back from the other manager. You don't need
`--reconcile` or `--force-conflicts` for that.

## Inspect the other manager

Fetch the resource with its managed fields:

<Command
  commands={[
    "kubectl get deployment legacy-web -n takeover -o yaml --show-managed-fields",
  ]}
/>

Find the named manager under `metadata.managedFields`, then determine what owns
it. Common managers include an operator, an autoscaler, `kubectl`, Helm, and
another deployment system.

Also inspect the current field value and the Kix definition. Drift is not
evidence that the other value is wrong.

## Choose the field owner

If the other controller should continue managing the field, change the Kix
package or its configuration so it no longer emits that field. When the
package cannot omit it, because the field is required on create or the whole
object comes from upstream, declare the field as ceded on the resource:

```nix
scope.mkResource {
  # ...
  ownership.cede = [ "spec.replicas" ];
}
```

Kix stamps the paths as `kix.run/cede-fields`. A ceded field never counts as
drift, and Kix never takes it back, so the other manager keeps it. See
[Cede fields to a controller](/docs/how-to/adopt-existing-resources/cede-fields-to-a-controller/).
Choose one manager either way, rather than letting both repeatedly take
ownership from each other.

If Kix should manage the field, first disable or reconfigure the other manager
for this resource. Otherwise it changes the field again after the deploy, and
the next plan shows the same drift.

## Take the field back

Run a plain deploy:

<Command {...resolve} />

The deploy applies the drifted Deployment again with force, which moves
`spec.replicas` back to the Kix cluster's field manager and restores the
replica count from the Kix definition. It writes nothing to the resources that
did not change. Kix takes back only what the plan showed: the
same field, from the same manager, at the same value. A status update by the
Deployment controller does not stop it. If the field, its manager, or its value
changed after the plan, the deploy stops, names the object, and asks you to
plan again.

Plan again to confirm that nothing is left to do:

<Command {...clean} />

## Where a conflict still stops the deploy

Kix forces only the objects the plan labels as reverting drift. Other
ownership disputes still stop the plan and the deploy with a field ownership
conflict:

- **An object Kix never applied.** On a first deploy over a resource that
  `kubectl`, Helm, or another tool created, those tools own the fields, and
  Kix has nothing to revert. The plan lists the conflict with the owning
  manager and fields. Pass `--force-conflicts` once, after review, to take
  the fields. See
  [Take ownership of kubectl-managed resources](/docs/how-to/adopt-existing-resources/take-ownership-of-kubectl-managed-resources/)
  and [Take ownership of Helm-managed resources](/docs/how-to/adopt-existing-resources/take-ownership-of-helm-managed-resources/).
- **A field another Kix cluster applies.** Kix never takes it back. When the
  two Kix clusters set different values, the deploy stops with `[K5636]`.
  Make the two definitions agree.

`--force-conflicts` forces every apply of the run, so keep it out of routine
commands. It can hide a new ownership dispute that needs a separate decision.

:::note[Use it for a migration]
See [Take ownership of kubectl-managed resources](/docs/how-to/adopt-existing-resources/take-ownership-of-kubectl-managed-resources/)
for the full first-deployment checklist, including selector preservation and a
backup of the live object.
:::
