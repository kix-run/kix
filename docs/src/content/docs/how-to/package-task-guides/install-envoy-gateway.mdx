Install Envoy Gateway with two Kix packages. `gateway-api` installs the
Gateway API CRDs. `envoy-gateway` installs the Envoy Gateway controller, its
own CRDs, and a `GatewayClass` and `Gateway` that application packages route
through. The controller then runs Envoy proxies for the Gateway.

Both packages are experimental. Check the
[Envoy Gateway compatibility matrix](https://gateway.envoyproxy.io/docs/install/version-compatibility/)
for the Kubernetes versions the pinned release supports.

## Add the Gateway API CRDs

Add a `gateway-api` instance:

<Snippet {...gatewayApiInstance} />

A cluster has one set of Gateway API CRDs, so the instance claims the
`gatewayApi` role. Every Gateway API implementation in the cluster, such as
`envoy-gateway` or `traefik`, uses these CRDs. If your Kubernetes provider
installs the Gateway API CRDs itself, bind the role `exclusive` and declare
the provider's CRDs with
[`kix.mkImport`](/docs/reference/helm-and-imports/#mkimport) instead of
adding this instance.

## Add Envoy Gateway

Add an `envoy-gateway` instance with the listeners your applications need:

<Snippet {...gatewayInstance} />

The instance's namespace holds the controller and the Envoy proxies it starts.
A cluster runs one `envoy-gateway` instance.

`listeners` takes Gateway API `Listener` fields with their upstream names
(`name`, `port`, `protocol`, `hostname`, `tls`, `allowedRoutes`); a
misspelt field fails evaluation. The example permits routes from every
namespace. Restrict `allowedRoutes.namespaces` if only selected
namespaces should attach routes. `kix.expose` reads these listeners to
pick each application's URL scheme and port, and fails when no listener
accepts an application's host and namespace. An HTTPS listener without
`tls.certificateRefs` is not rendered.

The package gives the proxies a `LoadBalancer` Service. When the cluster has
no load balancer (`cluster.roles.loadBalancer.binding = "absent"`, which the
kind flavour sets), it uses a `NodePort` Service instead, so the Gateway can
become ready. To change the proxies' Service, replica count, or other
settings, set `config.proxySpec` to fields of Envoy Gateway's `EnvoyProxy`
spec.

When the cluster enforces network policy, the package lets clients reach the
proxies on the listener ports, and `kix.expose` lets the proxies reach each
application it routes to.

Deploy the Kix cluster:

<Command
  commands={["kix deploy how-to-platform-gateway"]}
  cwd="kix-examples/"
/>

Kix applies the CRDs first, then runs a Job that creates the certificates the
controller and the proxies use, then starts the controller. The deploy waits
until the controller accepts the `GatewayClass` and reports the `Gateway`
programmed.

## Verify the installation

Check the `GatewayClass` and the `Gateway`:

<Command {...gatewayResources} />

The `GatewayClass` should report `Accepted`, and the `Gateway` should report
`Programmed`. On kind, Envoy Gateway reports a kind node address for the
Gateway.

If either resource stays unready, inspect its conditions and the controller
logs:

<Command
  commands={[
    "kubectl describe gatewayclass gateway",
    "kubectl describe gateway gateway -n gateway-system",
    "kubectl logs -n gateway-system deployment/gateway --since=10m",
  ]}
/>

## Move from a Helm installation

Earlier releases of the `envoy-gateway` package installed only the
`GatewayClass` and `Gateway`, and the controller came from Envoy Gateway's
Helm chart. Two controllers must not serve the same `GatewayClass`, so remove
the Helm release before you deploy this version:

<Command
  commands={[
    "helm uninstall eg --namespace envoy-gateway-system",
  ]}
/>

Helm keeps the CRDs, and the running proxies keep serving their last
configuration. Then change the cluster definition:

- Add the `gateway-api` instance shown above.
- Delete `controllerName`, `proxyNamespace`, `gatewayClassName`, and
  `gatewayName` from the `envoy-gateway` instance. The package refuses them.
- Delete a `proxySpec` that only sets a `NodePort` Service for kind. The
  package now sets it.

Helm still owns fields of the CRDs, so the first deploy stops on a field
ownership conflict. Deploy once with `--force-conflicts` to give those
fields to Kix:

<Command
  commands={["kix deploy <cluster> --force-conflicts"]}
/>

Use ordinary `kix deploy` commands after that.

The controller now starts the proxies in the instance's namespace. When that
is not the namespace Helm used, the Gateway gets new proxies with a new
Service, and on a cloud load balancer a new address. Point DNS at the new
address, or keep the old one with the instance's `addresses` option. Then
delete the old proxies, which nothing removes for you:

<Command
  commands={[
    "kubectl delete deployment,service,serviceaccount,configmap,hpa,pdb --namespace envoy-gateway-system --selector app.kubernetes.io/managed-by=envoy-gateway",
  ]}
/>

:::tip[Use it in a task]
Continue with [Expose a service with Gateway API](/docs/how-to/platform-capabilities/expose-a-service-with-gateway-api/)
to add an HTTPRoute from an application package to this Gateway.
:::
