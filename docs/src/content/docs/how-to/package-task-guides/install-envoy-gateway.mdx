Install Envoy Gateway with two experimental Kix packages: `gateway-api`
installs the Kubernetes Gateway API CRDs, and `envoy-gateway` installs the
Envoy Gateway controller, its own CRDs, a `GatewayClass`, and a `Gateway`
for application routes. Once running, the controller deploys Envoy proxy
pods for the Gateway.

Check the
[Envoy Gateway compatibility matrix](https://gateway.envoyproxy.io/docs/install/version-compatibility/)
to confirm your cluster's Kubernetes version is supported by the Envoy
Gateway release in `envoy-gateway`.

## Add the Gateway API CRDs

Add a `gateway-api` instance to your cluster definition:

<Snippet {...gatewayApiInstance} />

This instance claims the `gatewayApi` role so the cluster installs only one
set of Gateway API CRDs. Every Gateway API controller in the cluster, such as
`envoy-gateway` or `traefik`, shares them.

If your Kubernetes provider already installs compatible Gateway API CRDs, do
not add `gateway-api`. Instead, set
`cluster.roles.gatewayApi.binding = "exclusive"` and declare the CRDs with
[`kix.mkImport`](/docs/reference/helm-and-imports/#mkimport). In the import,
set `roles = [ "gatewayApi" ]`, set `out.version` to the installed Gateway API
version, and add a `crds` entry for each kind your controller uses:

- `envoy-gateway` requires Gateway API 1.6 or later and the `GatewayClass`,
  `Gateway`, `HTTPRoute`, and `ReferenceGrant` CRDs.
- `traefik` requires Gateway API 1.6.1 or later and those four CRDs, plus
  `GRPCRoute`, `TLSRoute`, and `BackendTLSPolicy`.

Include `readiness.condition` on `GatewayClass` (`type = "Accepted"`) and
`Gateway` (`type = "Programmed"`), both with `status = "True"`, so `kix deploy`
waits until the controller accepts the class and programs the Gateway:

```nix
cluster.roles.gatewayApi.binding = "exclusive";
instances.gateway-system.platform-gateway-api.package = kix.mkImport {
  roles = [ "gatewayApi" ];
  out.version = "1.6.1";
  crds = [
    {
      group = "gateway.networking.k8s.io";
      kind = "GatewayClass";
      plural = "gatewayclasses";
      version = "v1";
      crdScope = "Cluster";
      readiness.condition = { type = "Accepted"; status = "True"; };
    }
    {
      group = "gateway.networking.k8s.io";
      kind = "Gateway";
      plural = "gateways";
      version = "v1";
      readiness.condition = { type = "Programmed"; status = "True"; };
    }
    { group = "gateway.networking.k8s.io"; kind = "HTTPRoute"; plural = "httproutes"; version = "v1"; }
    { group = "gateway.networking.k8s.io"; kind = "ReferenceGrant"; plural = "referencegrants"; version = "v1"; }
  ];
};
```

If the import is missing a required CRD, a readiness condition, or a supported
`out.version`, evaluation fails and names what to fix.

## Add Envoy Gateway

Add an `envoy-gateway` instance with the listeners your applications need:

<Snippet {...gatewayInstance} />

Kix allows one `envoy-gateway` instance per cluster. Both the controller and
the Envoy proxy pods it creates run in this instance's namespace.

`listeners` takes Gateway API `Listener` fields with their upstream names
(`name`, `port`, `protocol`, `hostname`, `tls`, `allowedRoutes`); a
misspelt field fails evaluation. The example permits routes from every
namespace. Restrict `allowedRoutes.namespaces` if only selected
namespaces should attach routes. `kix.expose` reads these listeners to
pick each application's URL scheme and port, and fails when no listener
accepts an application's host and namespace. An HTTPS listener without
`tls.certificateRefs` is not rendered.

By default, the Envoy proxies get a `LoadBalancer` Service. On clusters
without a load balancer (`cluster.roles.loadBalancer.binding = "absent"`,
which `kix.flavors.kind` sets), the package switches to a `NodePort` Service
so the Gateway can still become ready. Use `config.proxySpec` (an Envoy
Gateway `EnvoyProxy` `spec`) to customize the proxy Service, replica count,
or pod settings.

When `networkPolicy.enable = true`, the package allows incoming traffic to
the proxy pods on the listener ports, and `kix.expose` allows the proxy pods
to reach each backend Service they route to.

Deploy the Kix cluster:

<Command
  commands={["kix deploy how-to-platform-gateway"]}
  cwd="kix-examples/"
/>

During deploy, Kix installs the CRDs, runs a Job to generate TLS
certificates for control-plane traffic between the controller and proxies,
and starts the controller. `kix deploy` waits until the `GatewayClass` is
`Accepted` and the `Gateway` is `Programmed`.

## Verify the installation

Check the `GatewayClass` and `Gateway`:

<Command {...gatewayResources} />

The `GatewayClass` should report `Accepted`, and the `Gateway` should report
`Programmed`. On kind, Envoy Gateway sets the Gateway's address to a kind node
IP.

If either resource stays unready, inspect its conditions and the controller
logs:

<Command
  commands={[
    "kubectl describe gatewayclass gateway",
    "kubectl describe gateway gateway -n gateway-system",
    "kubectl logs -n gateway-system deployment/envoy-gateway --since=10m",
  ]}
/>

## Migrate from a Helm installation

Earlier versions of `envoy-gateway` created only the `GatewayClass` and
`Gateway` and expected you to install the controller with Envoy Gateway's
Helm chart. Because two controllers must not reconcile the same
`GatewayClass`, uninstall the Helm release before deploying the upgraded
package. The commands below assume the Helm release is named `eg` in the
`envoy-gateway-system` namespace, matching Envoy Gateway's install guide.

Envoy Gateway's Helm chart installs the experimental Gateway API CRDs, while
`gateway-api` installs the standard channel. Check your routes and Gateways
before upgrading:

- Applying the standard CRDs drops experimental-only fields from existing
  routes and Gateways. Remove any experimental fields before you deploy
  `gateway-api`.
- The experimental-only CRDs (`xbackends`, `xbackendtrafficpolicies`, and
  `xmeshes` in `gateway.networking.x-k8s.io`) remain in the cluster. Delete
  them once nothing uses them.

Uninstall the Helm release:

<Command
  commands={[
    "helm uninstall eg --namespace envoy-gateway-system",
  ]}
/>

Uninstalling the Helm release leaves the CRDs in place, and the existing
Envoy proxy pods continue serving traffic with their last configuration.
Helm does not delete hook resources on uninstall, so it also leaves behind the
`eg-gateway-helm-certgen` ServiceAccount, Role (which still grants write access
to Secrets), RoleBinding, ClusterRole, ClusterRoleBinding, and Job, along with
the topology injector webhook. Delete them:

<Command
  commands={[
    "kubectl delete serviceaccount,role,rolebinding,job --namespace envoy-gateway-system --selector app.kubernetes.io/instance=eg",
    "kubectl delete clusterrole,clusterrolebinding,mutatingwebhookconfiguration --selector app.kubernetes.io/instance=eg",
  ]}
/>

Next, update your cluster definition:

- Add the `gateway-api` instance shown in [Add the Gateway API CRDs](#add-the-gateway-api-crds).
- Remove `controllerName`, `proxyNamespace`, `gatewayClassName`, and
  `gatewayName` from the `envoy-gateway` instance. Setting any of them now
  fails evaluation.
- If `config.proxySpec` only sets `envoyService.type = "NodePort"` for kind,
  remove it. The package now sets `NodePort` automatically when the cluster
  has no load balancer.

Because Helm still owns fields on the existing CRDs, the first deploy stops
with a server-side apply conflict. Run `kix deploy` once with
`--force-conflicts` to transfer field ownership to Kix:

<Command
  commands={["kix deploy <cluster> --force-conflicts"]}
/>

Subsequent deploys do not need `--force-conflicts`.

Envoy Gateway starts proxy pods in the `envoy-gateway` instance's namespace.
If your `envoy-gateway` instance is not in the namespace Helm used (such as
`envoy-gateway-system`), the controller creates a new proxy `Deployment` and
`Service` in the instance's namespace while the old ones keep running.

On a cloud load balancer, the new `Service` receives a new IP address:

- **Use the new IP address:** Point DNS at the new address, then delete the old
  proxy resources with the command below.
- **Keep the old IP address with `config.addresses`:** Delete the old proxy
  resources *before* running `kix deploy` so `kix deploy` can wait for the
  Gateway to become `Programmed` on that IP. Because the old `Service` holds
  the IP until you delete it, the Gateway serves no traffic between the
  deletion and the new `Service` claiming the address.

Delete the old proxy resources from Helm's namespace:

<Command
  commands={[
    "kubectl delete deployment,service,serviceaccount,configmap,hpa,pdb --namespace envoy-gateway-system --selector app.kubernetes.io/managed-by=envoy-gateway",
  ]}
/>
