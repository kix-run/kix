A normal `kix deploy` heals out-of-band changes. It recreates any resource in
the build that is missing from the cluster or being deleted, and it puts back
fields that someone changed on a resource Kix applied, taking them back from
the field manager that changed them. The plan labels those resources as
changed on the cluster before anything is applied. Use `kix deploy --reconcile`
only when you want Kix to reapply every resource of the build.

## Review what changed

Start by finding the objects that changed and the fields that changed on
them:

<Command commands={["kix status how-to-application --check drift"]} cwd="kix-examples/" />

```text
...
how-to-app/production
  Deployment how-to-app/production  changed since deploy (spec.replicas by kubectl)

16 resources: 15 ok, 1 changed.
Next: run `kix deploy how-to-application` to put back what is missing or changed. `kix plan how-to-application` shows what it would change first. The deploy takes back the fields that kubectl owns.
```

Run `kix plan how-to-application` to see what the deploy would change before
it changes anything. The plan counts the resources that changed on the cluster
in a line that starts with `↺`, and lists each changed field under `Drift:`
with the field manager that changed it.

Confirm that the checked-in cluster definition still describes the state you
want. Reconciliation applies that definition, so review intentional emergency
changes before continuing.

## Reapply the desired resources

The example output says kubectl changed `spec.replicas`. Deploy the cluster,
which takes that field back:

<Command expandable {...reconcileApplication} />

The example begins with a production Deployment that was scaled from two
replicas to one outside Kix. The deploy applies that Deployment again with
force and waits for it to become ready. It writes nothing to the resources
that did not change.

Use `--context` and `--flake` when the Kubernetes target or source directory
is not the current one:

<Command
  commands={[
    "kix deploy how-to-application -y --flake ./infrastructure --context kind-kix-demo",
  ]}
/>

Omit `-y` when running interactively if you want to review the confirmation
prompt.

## Confirm the result

Run the drift check again:

<Command commands={["kix status how-to-application --check drift"]} cwd="kix-examples/" />

```text
...
16 resources: 16 ok.
```

No object should be changed, and the command exits `0`. Run `kix status`
without `--check` to also confirm that the reapplied workloads are ready. See
[Check a cluster's status](/docs/how-to/operate-a-cluster/check-resource-status/).

A field the package cedes with `ownership.cede` never counts as changed, so
the deploy leaves it with the controller that owns it. A field another Kix
cluster applies is not taken back: the deploy stops with `[K5636]` when the
two Kix clusters set it to different values. `--reconcile` reapplies every
resource of the build, and `--force-conflicts` takes fields from other
managers on every apply. Neither is needed to heal drift.
