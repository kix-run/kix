Use `kix gc` to remove resources that an earlier Activation managed but the
current cluster definition no longer contains. Every mode also applies the
Activation retention policy.

## Review the normal garbage-collection plan

Run `gc` with the cluster name:

<Command commands={["kix gc how-to-application"]} cwd="kix-examples/" />

To see the plan without being asked to confirm, and without deleting
anything, add `--dry-run`:

<Command commands={["kix gc how-to-application --dry-run"]} cwd="kix-examples/" />

The normal mode compares the previously deployed Activation with a fresh build
of the cluster. It prints the resources found by that comparison and the
Activation records it plans to delete, then asks for confirmation.

The normal mode can also find stale cluster-level resources that belong to no
package. It currently deletes those after confirmation without listing them in
the plan. Use `--full-scan` when the confirmation plan must be a complete
inventory of live garbage.

It also deletes orphans that an earlier `kix deploy` without `--prune` listed
and kept. That deploy records the builds they came from on its Activation; the
plan lists them under **Orphans kept by earlier deploys (warn-only)** and
deletes them along with the rest of the garbage after confirmation.

Check the package, kind, namespace, and name of each resource before approving
the plan. Kix deletes dependants before their dependencies.

A Namespace or CustomResourceDefinition that has left the build is listed
under **Kept** and is not deleted, in either mode. Deleting a Namespace deletes
everything in it, and deleting a CustomResourceDefinition deletes every custom
resource of that kind on the cluster, including ones Kix does not manage.
`kix deploy --prune` keeps the same kinds. When you do want one removed, delete
it with `kubectl delete` after checking what it contains.

## Run without a prompt

After reviewing the plan, pass `--yes` in automation:

<Command {...gcPlan} />

This performs the same comparison and deletion without asking for
confirmation. The captured run follows an instance being renamed in the
cluster definition, so the resources deployed under the old name are the ones
Kix removes.

## Scan the live cluster for orphans

Use `--full-scan` when the local activation cache is unavailable or you need
to find Kix-managed resources outside the previous-to-current build
comparison:

<Command commands={["kix gc how-to-application --full-scan"]} cwd="kix-examples/" />

A full scan reads live resources carrying Kix ownership metadata and compares
them with the expected resources in the current build.

When one Kubernetes cluster hosts more than one Kix cluster, a full scan
judges only the named cluster's resources. It finds them through the
Activation records each resource names, skips the other clusters' resources,
and keeps a resource another cluster's current build also contains. A
resource that names no Activation record at all cannot be attributed to
either cluster, so a full scan lists it under "No deployment record on this
cluster" and keeps it. Review those and pass `--include unattributed` to judge
them against the build too.

Resources carrying a Kix label but no `kix.run/identity-hash` are listed under
"No Kix build annotation" and kept by default. Kix cannot establish that it originally applied
them. Include them only after checking each reported resource. `--include`
takes a comma-separated list, such as `--include unstamped,unattributed`:

<Command
  commands={["kix gc how-to-application --full-scan --include unstamped"]}
  cwd="kix-examples/"
/>

## When a delete does not finish

Kubernetes keeps a deleted object on the cluster until every finalizer on it is
removed. Usually, the controller or operator that added a finalizer removes it
after cleaning up external state, such as a database or cloud load balancer.
`kix gc` waits for each deleted object to be removed, stopping after 3 minutes
without a finalizer being removed or 5 minutes in total.

If an object is still on the cluster when the wait ends, `kix gc` fails with
`[K2794]`, lists any remaining finalizers, and exits with code `1`. Kix skips
deleting any resources recorded as dependencies of the stuck object and lists
them as kept. Those orphans stay tracked so the next `kix gc` or
`kix deploy --prune` can delete them once the stuck object is gone. Most
packages do not yet record that a custom resource depends on its operator, so
removing both at once can delete the operator before it clears the custom
resource's finalizer.

To resolve `[K2794]`:

1. **Wait if cleanup is still running.** Slow cleanups, such as pods with a
   long termination grace period or a cloud load balancer being deleted, can
   finish on their own after Kix stops waiting. Run `kix gc` again later.
2. **Check the controller or operator for the finalizer.** Make sure the
   workload that removes the finalizer is running. If you removed it in the
   same change, restore it and deploy so it can clean up its objects, then run
   `kix gc` again.
3. **Force-remove the finalizer to skip external cleanup.** Kix never removes
   finalizers itself. To make Kubernetes delete the object immediately, run the
   `kubectl patch` command printed in the error message. Anything the finalizer
   would have cleaned up outside the object, such as an external database or
   cloud resource, remains behind. Then run `kix gc` again to delete any
   dependencies Kix kept.

## Let the operator perform cleanup

For an operator-managed cluster, use operator mode:

<Command commands={["kix gc how-to-application --operator"]} cwd="kix-examples/" />

Kix deletes the Activation records selected by the retention policy. These are
all Superseded records, so the operator only removes its finalizer from each
one. It deletes no resources: the Active record owns them. The operator deletes
resources only when an Active, Deploying or Degraded record is deleted, and even
then it keeps every Namespace and CustomResourceDefinition. If any resource
fails to delete or is still being deleted when the wait ends, the operator
keeps its finalizer on the Activation record, records a Warning Event on it,
and retries every 30 seconds. See
[When an Activation record is deleted](/docs/reference/cli/operator-mode/#when-an-activation-record-is-deleted).

Use the same `--keep`, `--keep-max`, and `--keep-for` flags in any mode. For
example:

<Command
  commands={[
    "kix gc how-to-application --full-scan --keep 20 --keep-max 100 --keep-for 90d",
  ]}
  cwd="kix-examples/"
/>

:::note[Configure the history window]
See [Configure Activation retention](/docs/how-to/operate-a-cluster/configure-activation-retention/)
for the retention rules and scheduling example.
:::

See [`kix gc`](/docs/reference/cli/gc/) for all flags and mode behavior.
:::
