Use a snapshot when you want `kix diff` without a connection to the cluster:
on a laptop off the VPN, in a CI job that holds no cluster credentials, or
when several people need the same baseline for a review.

`kix snapshot` writes the fields Kix applied to each resource of the named
cluster, along with a `kix-snapshot.json` state file containing the cluster
state that `kix plan --read-only` reads. `kix diff --from` compares a build
against that directory using the same rules as `kix plan --read-only` against
the live cluster, so both commands produce the same report. `Secret` values
are redacted and never written to disk.

This guide assumes the cluster has been deployed at least once and that you
can reach it when saving. The examples use the `how-to-application` cluster
from `kix-examples`.

## Save a snapshot after deploying

Take the snapshot right after a successful deploy, while the cluster and the
source agree:

<Command {...save} />

Pass `--context` when the cluster is not the current kubectl context. The
command reports how many resources it fetched and wrote. The directory holds
one YAML file per resource (grouped by namespace), the `kix-snapshot.json`
state file, and a `README.md` with the
timestamp, cluster and context. Resources of other Kix clusters deployed to
the same Kubernetes cluster are left out.

## Diff a build against the snapshot

Compare the current source with the snapshot. No cluster access is needed:

<Command {...diffClean} />

Straight after the save this reports no differences and exits with status 0.

## Preview a change

Edit the source, then run the same command again. Changing the production
message in the example cluster gives a report like this:

<Command {...diffFromSnapshot} />

The ConfigMap is the resource you edited. The command exits with status 2
whenever it finds a difference.

## Keep the snapshot current

A snapshot describes the cluster at the moment it was taken. Once you deploy,
save again, or the next diff will keep showing the change you already shipped.
A simple rule: every command that deploys is followed by a save of the same
context.

When you can reach the cluster, run
`kix plan how-to-application --read-only`. It reads the same fields from the
live resources and needs no saved copy.

## Compare with a previous build instead

A bundled build works as the baseline too. Package the cluster from the old
revision with `kix bundle`, build a second bundle from the current revision,
and compare the two:

<Command
  commands={[
    "kix bundle how-to-application --out before.kixbundle",
    "kix bundle how-to-application --out after.kixbundle",
    "kix diff how-to-application --bundle after.kixbundle --from-bundle before.kixbundle",
  ]}
  cwd="kix-examples/"
/>

You can also export the old revision with `kix export --with-kix-metadata
--out ./before` and pass `--from ./before`. Both approaches compare two builds of the
source without contacting a cluster. Use them to check what a branch changes
relative to `main`.

## Troubleshooting

**Every package shows its `PackageInstance` as added, and the `Activation`
line shows `(none)`.** The directory comes from `kix export` without
`--with-kix-metadata`, which omits `PackageInstance` and `Activation`
resources. Save a snapshot with `kix snapshot` instead, or export with
`kix export --with-kix-metadata`.

**The diff reports changes you did not make.** The snapshot is older than the
last deploy, or an older version of Kix saved it without `kix-snapshot.json`.
Without that file, `Secret` values and fields modified by the API server
appear as differences. Save a fresh snapshot with `kix snapshot` and compare
again.
