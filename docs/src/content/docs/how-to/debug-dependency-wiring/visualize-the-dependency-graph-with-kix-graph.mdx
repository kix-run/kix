Use `kix graph` to inspect the dependencies Kix derived from the rendered
cluster: every reference a resource's manifest carries, plus anything named in
`requires` or `extraDeps`. The graph needs no access to Kubernetes.

## Print the tree

Tree output is the quickest way to inspect ordering in a terminal:

<Command expandable {...graphTree} />

The tree starts with resources that have no dependencies. Each indented entry
depends on the resource above it. In this example, the gateway ConfigMap
appears beneath `Service/backend@platform`, showing the edge across the
namespace boundary.

If an expected edge is absent, check that the consumer actually reads a value
from the dependency, such as `backend.out.url { }` or `backend.out.name`. The
reference is the edge. For a relationship with no value to read, name the
resource in `requires` or `extraDeps`.

`deps` on its own creates no edge. It binds a build argument so the package
can reach the provider; the edge appears only where the built manifest uses
something the provider produced.

## Write a DOT graph

Use DOT output for Graphviz or another graph viewer:

<Command expandable {...graphDot} />

Redirect it into a file and render it with Graphviz:

<Command
  commands={[
    "kix graph 08-namespace-deps --format dot > kix-graph.dot",
    "dot -Tsvg kix-graph.dot > kix-graph.svg",
  ]}
  cwd="kix-examples/"
/>

The second command requires Graphviz. The generated SVG is useful when a tree
is too deep to scan comfortably.

## Write graph data as JSON

Use JSON when another tool will inspect the nodes and edges:

<Command {...graphJson} />

The excerpt above counts the nodes and edges and shows one node. Every node
carries its kind, name, namespace, and identity hash, so another tool can
join the graph to the rendered manifests.

Choose JSON for automation, not as the default way to read the graph by hand.
