Scorecard rules run while Kix evaluates a cluster. Add built-in rule sets when
you want their existing checks, and add custom rules for policy specific to
your packages or organization.

This guide assumes the cluster is defined with `kix.buildCluster`.

## Enable a built-in rule set

Set `scorecard.enable`, then add a rule set under `scorecard.rules`:

```nix title="cluster.nix"
scorecard = {
  enable = true;
  rules.reliability = kix.rules.reliability;
};
```

The attribute name becomes the rule category. For example,
`kix.rules.reliability.hasProbes` is reported as `reliability.hasProbes`.

You can enable several built-in sets together:

```nix title="cluster.nix"
scorecard.rules = {
  inherit (kix.rules) security reliability governance architecture;
};
```

## Add a custom rule

Place custom rules under a category of your own. This tested package-level
rule applies only to packages that advertise the `reverse-proxy` capability,
then checks their evaluated configuration:

<Snippet {...packageRule} />

Add the rule inside `scorecard.rules`. Its full name is
`custom.proxyMaxBodySizeMustBeExplicit`.

Every rule declares a `level` that determines the value passed to its check:

- `manifest` runs once for each rendered Kubernetes resource.
- `package` runs once for each package instance.
- `namespace` runs once for each namespace.
- `cluster` runs once for the whole cluster.

Those four are the whole vocabulary, and so are the three severities, `info`,
`warning`, and `error`. Kix refuses anything else at evaluation. Without that
check a typo fails open: a rule at an unknown level matches none of the level
filters and is never evaluated, and a severity that is not `error` is reported
as a warning, so `severity = "critical"` reads as a promotion and lands as a
trace line. Either way the scorecard reports that everything passed.

The check returns one finding for each problem and an empty list when the
input passes. Use `appliesTo` when a rule is meaningful only for a subset of
its level.

## Check the rules

Run the cluster checks after adding or changing a rule:

<Command {...check} />

Kix reports the number of scorecard errors, warnings, and informational
findings. An error-severity finding does more than fail the check: it is a
failed assertion, so evaluation stops at the first one and the cluster does not
build. Only that first finding is reported. Warnings and info findings are
collected across the whole cluster and appear in the report together.

:::note[Reference]
See [Rule schema](/docs/reference/scorecard/rule-schema/) for the context
available at each level and the complete rule fields. The built-in rule pages
list the checks available in each category.
:::
