`kix rollback` switches a cluster back to one of its Superseded activations.
It does not build: it finds the target activation's build in Kix's local
store and applies it through the same engine as `kix deploy`. To see the
activations it can roll back to, run
[`kix history`](/docs/reference/cli/history/).

This page is hand-maintained. Check `cli/kix-cli/src/cli.rs` and
`cli/kix-cli/src/commands/rollback.rs` when in doubt.

## Synopsis

```text
kix rollback <CLUSTER> [-y] [--dry-run] [--prune] [--force-conflicts] [--accept-migrations] [--operator] [--flake <FLAKE>] [--context <CONTEXT>]
```

| Argument or flag | Meaning |
| --- | --- |
| `<CLUSTER>` | Cluster name, as recorded on its Activation records. |
| `-y`, `--yes` | Roll back to the most recent Superseded activation without prompting. |
| `--dry-run` | Print the plan and stop. |
| `--prune` | Delete resources the current activation has and the target does not, and orphans earlier deploys kept. Without it they are listed and kept, and the target Activation records where they came from, as a deploy does. |
| `--force-conflicts` | Take fields that another field manager owns, such as a replica count set with `kubectl scale`. Without it, a conflict stops the rollback before it writes anything. |
| `--accept-migrations` | Proceed when the rollback replaces a resource that holds data in a stateful package, matching `kix deploy --accept-migrations`. Without it, the rollback stops before changing the cluster, even with `-y`. Kix does not copy data between the old and new resources. |
| `--operator` | Ask the Kix operator to restore the target Activation record as the cluster's current deployment and mark the previous record `Superseded`. See [Operator mode](/docs/reference/cli/operator-mode/). |
| `--flake <FLAKE>` | Flake reference used to evaluate the cluster name when no Activation record in the context carries `<CLUSTER>`. See [Global flags](/docs/reference/cli/global-flags/). |
| `--context <CONTEXT>` | Kubeconfig context. See [Global flags](/docs/reference/cli/global-flags/). |

## Choosing the target

Only records that were once the cluster's running state are offered. A deploy
that stopped part way is never a target.

On a terminal without `--yes`, Kix lists the candidates, newest first, and
asks for a number; Enter picks the newest. Without a terminal it picks the
newest and then stops at the confirmation unless `--yes` is set.

The target's build must be in Kix's local store, found through the record's
source path or the local activation cache. A build made on another machine or
removed from the local store cannot be rolled back to from here. How many
records exist depends on `kix gc` retention.

A build from a Kix library before 2026-10-02 cannot be rolled back to if it
imports a CRD (`scope.mkCRDRef`, or `kix.mkImport` with `crds`). Its CRD ref
markers lack the `kix.run/crd-served-versions` annotation, and Kix refuses the
build before applying anything (with `--operator`, the operator refuses it).
Deploy a fresh build instead.

Before it writes anything, the rollback sends its writes to the apiserver as a
dry run, as `kix plan` does, and sorts the answers by the same rules. When the
apiserver would refuse one, such as for a field ownership conflict, Kix lists
the refused writes and stops, so the cluster is never left between two builds.
An object that `kix plan` would list as
[not checked](/docs/reference/cli/plan/#objects-not-checked), such as one in a
Namespace the rollback creates, does not stop it. `--dry-run` shows the same
list.

If the rollback replaces a resource that holds data in a stateful package (such
as a PersistentVolumeClaim renamed between the two builds), it stops with
`[K3354]` before changing the cluster, matching `kix deploy`. Kix lists each
replacement and whether the old resource will be kept as an orphan or deleted.
Back up or migrate the data first, then run the rollback again with
`--accept-migrations`.

The rollback waits up to 180 seconds for each resource to become ready and
stops at the first failure.

After you confirm, the rollback takes the cluster's
[deploy lock](/docs/reference/cli/deploy/#the-deploy-lock), as `kix deploy`
does: it refuses when another run holds the lock and is still running, or
when another run changed the cluster since the plan. The target record
becomes the one the cluster runs at the same single point as a deploy's.

## Exit status

| Code | Meaning |
| --- | --- |
| `0` | Rolled back, nothing to change, or the prompt was declined |
| `1` | A resource failed, including a failed or timed-out prune delete; confirmation was needed on a non-interactive terminal; no target is available; the target build is not in the local store; another run holds the deploy lock or changed the cluster since the plan; or a cluster error |
