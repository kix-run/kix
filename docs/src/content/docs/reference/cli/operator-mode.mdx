---
title: "Operator mode"
description: "How `deploy`, `rollback`, and `gc` behave with `--operator`, when the Kix operator applies Activation records inside the cluster."
---

In operator mode the CLI still builds and plans on your machine, but the
Kix operator running in the cluster makes the changes. The CLI writes an
Activation record that names the build's store path, then watches the
record's status until the operator finishes. The operator applies with the
same engine as `kix deploy` and, while an activation is Active, re-applies
resources that have drifted and deletes the record's cluster's resources that
the build no longer has. It reads only the resources of the record's Kix
cluster, named by the record's `kix.run/cluster` label (or `spec.cluster` when
the label is missing), found through the Activation records each resource
names in `kix.run/activations`. It keeps a resource another Kix cluster's
current build also contains, both when it prunes and when a deleted record's
finalizer removes that record's resources.

This page is hand-maintained. Check `cli/kix-cli/src/commands/operator.rs`,
`cli/kix-operator/src/main.rs`, and the command files when in doubt.

## Commands

| Command | With `--operator` |
| --- | --- |
| `kix deploy <CLUSTER> --operator` | Builds, shows the plan, asks for confirmation, and writes the Activation record with the build's store path, the deploy receipt, and a request token (`spec.request`). Waits for the operator to finish that request. If the build is already deployed, the operator redeploys it and keeps the record current. |
| `kix rollback <CLUSTER> --operator` | Selects a `Superseded` Activation record, shows the plan, asks for confirmation, and writes a request token (`spec.request`) to that record. The operator restores it as the current deployment and marks the previous record `Superseded`, matching `kix rollback`. Waits for the operator to finish that request. |
| `kix gc <CLUSTER> --operator` | Deletes the Activation records that retention retires. The operator's finalizer deletes each record's resources; the CLI waits up to 300 seconds per record. |

[`kix status <CLUSTER>`](/docs/reference/cli/status/) takes no `--operator`
flag. It reads the cluster's current Activation record the same way whoever
applied it, and does not need the operator to be running.

Flags that control the local engine have no effect in operator mode:
`--timeout`, `--on-error`, `--prune`, `--skip-orphan-check`, `--reconcile`,
`--force-conflicts`, `--group-by`, and `--log-format`. `--yes`,
`--offline`, and `--accept-migrations` still apply to the local
plan. `--dry-run` runs [`kix plan`](/docs/reference/cli/plan/) locally and
does not contact the operator.

## Waiting for the operator

The CLI polls the Activation record every 2 seconds and prints progress as
the operator reports it. It ignores the record's phase until
`status.startedRequest` matches `spec.request`, and treats `Active` or
`Degraded` as complete only after `status.finishedRequest` matches
`spec.request` too. That prevents an earlier phase (such as `Active` when
redeploying the current build) from ending the wait early.

| Record phase | CLI result |
| --- | --- |
| `Active` | Success (exit code `0`) |
| `Degraded` | Error (exit code `1`), after printing the failed resources or `status.failure.reason` |
| `Failed` | Error (exit code `1`), with the record's `status.failure.reason` (or `unknown error` if unset) |
| `Superseded` | Error: a newer activation took over |
| No terminal phase after 600 seconds | Error: timed out |

A timeout ends the CLI only. The operator keeps working on the record.

## Requirements

- The Activation CRD is installed, and the account can list Activation
  records. The `--operator` commands check this before changing anything.
- The operator is running and watches the `kix.run` API group.
- The operator runs a matching or newer version of Kix, its Kubernetes account
  can patch CustomResourceDefinition `activations.kix.run`, and your account
  can read that CRD. On startup, the operator writes `requests` to the
  `kix.run/operator-features` annotation on `activations.kix.run`.
  `kix deploy --operator` and `kix rollback --operator` check that annotation
  before changing anything and stop if `requests` is missing.
- The operator can read the store path the CLI wrote. It loads manifests from
  `spec.source.path`, so the build must be present in the store the operator
  reads, not only on the machine that ran the CLI.

## Exit status

Operator-mode commands exit `1` on any of the errors above, when confirmation
is needed on a non-interactive terminal, or when a record could not be
deleted. `deploy --operator` and `rollback --operator` also exit `1` when the
operator finishes the Activation as `Degraded`.
