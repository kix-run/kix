description: "Dedicated builders for Secrets, CustomResourceDefinitions, and RBAC permissions that catch mistakes at build time."
---

Mistakes in secret key names, custom resource schemas, or RBAC permission rules are notoriously easy to miss until a pod fails to start in the cluster. Instead of passing those objects to `scope.mkResource`, you build them with dedicated `scope` functions (`scope.mkSecret`, `scope.mkCRD`, `scope.rbac.*`) so Kix can verify key names, schema fields, and role bindings during compilation.

:::note[Helpful background]
- [Resources and `out`](/docs/reference/resources-and-out/): review how standard `scope` builders construct resources and expose `.out` attributes.
- [Manage secrets](/docs/how-to/platform-capabilities/use-kix-managed-secrets/): follow step-by-step instructions for wiring SOPS-encrypted or external Secrets into a package.
- [Using RBAC Authorization (Kubernetes docs)](https://kubernetes.io/docs/reference/access-authn-authz/rbac/): review how Kubernetes `ServiceAccount`, `Role`, and `RoleBinding` objects grant API permissions.
- [Custom Resources (Kubernetes docs)](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/): understand how Kubernetes operators extend the API with `CustomResourceDefinition` objects.
:::

## Secrets and secret refs

`scope.mkResource` refuses `v1/Secret` manifests directly. Instead, create secrets with `scope.mkSecret` (when Kix renders the `Secret` resource) or `scope.mkSecretRef` (when an operator or external controller populates the `Secret` in the cluster). All secrets defined in a package's `build` return set belong in the `secrets = { ... };` folder.

```nix
secrets.dbCredentials = scope.mkSecret {
  name = "myapp-db-credentials";
  source = ./secrets/db-credentials.sops.yaml;
  hash = "sha256:4f8b42c22dd3729b519ba6f68d2da7cc5b2d606d05daed5ad5128cc03e6c6358";
  keys = [ "username" "password" ];
  plainKeys = {
    host = self.postgres.out.fqdn;
  };
};
```

### `scope.mkSecret` arguments

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `name` | string | Required | `metadata.name` of the `Secret`. |
| `keys` | list of strings | Auto-derived from `stringData` or `plainKeys` | Declared secret key names. Required when `source` is set or when the secret is populated by a controller without inline `stringData`. |
| `type` | string | `"Opaque"` | Kubernetes Secret `type` (for example, `"Opaque"` or `"kubernetes.io/tls"`). |
| `stringData` | attrset of strings | `{ }` | Inline plaintext key-value entries. Marks each key's provenance as `"inline"` in `kix.run/secret-sources` (flagged by `security.noInlineSecrets` unless `meta.classification = "configuration"` or accepted in `cluster.secrets.accept`). |
| `source` | path or string or `null` | `null` | Path to a SOPS-encrypted file decrypted at deploy time by `kix apply`. Marks keys in `keys` as `"sops"`. |
| `hash` | `"sha256:<64-hex>"` or `null` | `null` | Expected SHA-256 content hash of the encrypted `source` file. Required whenever `source` is a path. |
| `plainKeys` | attrset of strings | `{ }` | Non-sensitive configuration keys merged into `stringData` alongside a SOPS `source`. Keys in `plainKeys` are recorded with provenance `"plain"` and must not overlap with `keys`. |
| `meta.classification` | `"configuration"` or `null` | `null` | Marks an inline `Secret` as non-credential configuration (used when an upstream application requires a `Secret` rather than a `ConfigMap` for its config file). |
| `meta.rotationPolicy` | `"manual"` \| `"automated"` \| `"ephemeral"` \| `"immutable"` or `null` | `null` | Documents how the secret is rotated (`kix.run/rotation-policy`). |
| `labels` | attrset | `{ }` | Extra `metadata.labels`. |
| `annotations` | attrset | `{ }` | Extra `metadata.annotations`. |
| `requires` | list of resources | `[ ]` | Explicit deployment dependencies. |
| `extra` | attrset | `{ }` | Extra top-level fields (`immutable = true`, etc.). Cannot set `data` or `stringData`. |

When `stringData`, `source`, and `plainKeys` are all omitted (for example, an empty `Secret` shell that an in-cluster operator populates at runtime), `keys` must be non-empty and Kix records the key provenance as `"controller"` while ceding `/data` and `/stringData` ownership in `kix.run/cede-fields`.

### `scope.mkSecretRef`

Use `scope.mkSecretRef` when an operator or external process creates the `Secret` object itself at runtime (for example, cert-manager creating a TLS `Secret` or CloudNativePG creating an application credentials `Secret`):

```nix
secrets.appUser = scope.mkSecretRef {
  name = "${self.pgCluster.out.name}-app";
  keys = [ "username" "password" "uri" ];
  requires = [ self.pgCluster ];
};
```

| `scope.mkSecretRef` argument | Type | Default | Description |
| --- | --- | --- | --- |
| `name` | string | Required | Runtime `Secret` name in `scope.namespaceName`. |
| `keys` | non-empty list of strings | Required | Keys expected to exist on the runtime `Secret`. |
| `type` | string | `"Opaque"` | Expected Secret type. |
| `requires` | list of resources | `[ ]` | Resources (such as the `Certificate` or database `Cluster` CR) that must be applied before the runtime `Secret` is created. |
| `reflect` | `{ fromNamespace: string }` or `null` | `null` | When set, copies the Secret from `fromNamespace` into `scope.namespaceName` via a reflector annotation (`kix.run/reflect-from`). |

`scope.mkSecretRef` emits a synthetic `PackageInstance` import marker (`secret-ref-<instance>-<name>`) with `kix.run/secret-keys` so `kix apply` verifies that both the `Secret` and all declared `keys` exist at deploy time.

### Secret `.out` consumption helpers

Both `scope.mkSecret` and `scope.mkSecretRef` return the same `.out` helpers. Every helper validates requested key names against the Secret's declared `keys` at Nix evaluation time and attaches the Secret's store-path context so the consuming workload automatically depends on the Secret:

| `.out` field or function | Signature | Returned value |
| --- | --- | --- |
| `out.name` | string | Secret `metadata.name` (with store context and namespace metadata). |
| `out.keys` | list of strings | Declared key names on the Secret. |
| `out.type` | string | Declared Secret `type`. |
| `out.keyRef` | `key -> attrset` | `{ valueFrom.secretKeyRef = { name = out.name; key = key; }; }`. Throws an evaluation error if `key` is not in `out.keys`. Ready to pass to `kix.mkEnvVars`. |
| `out.mkEnv` | `{ ENV_VAR = "key"; ... } -> list` | Maps environment variable names to Secret keys, validates every key against `out.keys`, and returns a sorted list of `{ name; valueFrom.secretKeyRef; }` entries. |
| `out.envFrom` | attrset | `{ secretRef.name = out.name; }` for container `envFrom` lists. |
| `out.volume` | `volName -> attrset` | `{ name = volName; secret.secretName = out.name; }` for pod `volumes` lists (or use [`kix.mount.secret`](/docs/reference/composition-helpers/#mount-helpers)). |

```nix
# Consuming a Secret via keyRef, mkEnv, and envFrom
env = kix.mkEnv {
  DB_HOST = self.postgres.out.fqdn;
  DB_PASS = self.secrets.dbCredentials.out.keyRef "password";
} (self.secrets.dbCredentials.out.mkEnv {
  DB_USER = "username";
});

envFrom = [ self.secrets.dbCredentials.out.envFrom ];
```

To validate keys on a Secret passed across packages as a `build` dependency, use [`kix.checkSecretKeys`](/docs/reference/package-anatomy/#kixchecksecretkeys).

## CRDs and CRD refs

Like Secrets, `CustomResourceDefinition` resources cannot be created with `scope.mkResource`. Use `scope.mkCRD` when your package renders the CRD manifest, or `scope.mkCRDRef` when the CRD is installed by an external component or operator at runtime. Place all CRDs in the `crds = { ... };` folder of `build` so Kix exports them to downstream consumers at `dep.crds.<Kind>`.

### `scope.mkCRD` arguments

```nix
crds.ServiceMonitor = scope.mkCRD {
  spec = (builtins.fromJSON (builtins.readFile ./crds/servicemonitors.json)).spec;
  readiness = null;
  holdsData = false;
};
```

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `spec` | attrset | Required | Full `CustomResourceDefinition` `.spec` (`group`, `names.kind`, `names.plural`, `scope`, and `versions` with at least one `storage = true` and `served = true` version). `metadata.name` is derived automatically as `"${spec.names.plural}.${spec.group}"`. |
| `labels` | attrset | `{ }` | Extra `metadata.labels`. |
| `annotations` | attrset | `{ }` | Extra `metadata.annotations`. |
| `ownership.cede` | list of strings | `[ ]` | Field paths ceded to controllers (for example, `[ "spec.conversion.webhook.clientConfig.caBundle" ]`). |
| `readiness` | attrset or `null` | `null` | Default readiness check stamped on custom resources of this CRD (`{ condition = { type; status; }; }`, `{ path; equals; }`, or `{ path; notEquals; }`). |
| `factBehavior` | `{ endpoint?: "conduct" \| "terminate" }` | `{ }` | Default network-policy endpoint fact behavior for custom resources of this CRD. |
| `usesAtLeast` | `(crSpec: { cpu; memory; })` or `null` | `null` | Function estimating the pod CPU and memory resources spawned by an operator for a given custom resource `spec` (used by cluster capacity checks). |
| `holdsData` | bool | `false` | Set to `true` when custom resources of this CRD manage stateful data (such as database clusters or object-store buckets). Propagates `kix.run/holds-data: "true"` onto custom resources for deletion-protection checks. |

### `scope.mkCRDRef` arguments

Use `scope.mkCRDRef` when a package creates custom resources for a CRD that is installed outside the package's own manifests (or dynamically by an operator):

```nix
crds.Certificate = scope.mkCRDRef {
  group = "cert-manager.io";
  kind = "Certificate";
  plural = "certificates";
  version = "v1";
  crdScope = "Namespaced";
  installedBy = deps.certManager;
  readiness = {
    condition = {
      type = "Ready";
      status = "True";
    };
  };
};
```

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `group` | string | Required | API group (for example, `"cert-manager.io"`). |
| `kind` | string | Required | PascalCase kind name (for example, `"Certificate"`). |
| `plural` | string | Required | Lowercase plural name (for example, `"certificates"`). |
| `version` | string | `"v1"` | Preferred storage API version. |
| `servedVersions` | list of strings | `[ version ]` | All served API versions accepted by the CRD. |
| `crdScope` | `"Namespaced"` \| `"Cluster"` | `"Namespaced"` | Whether custom resources of this CRD are namespaced or cluster-scoped. |
| `installedBy` | resource or `null` | `null` | Operator workload or dependency that installs this CRD. Attaches its store context so custom resources wait for the operator. Leaving `installedBy = null` emits a finding under `architecture.untrackedCrds`. |
| `readiness` | attrset or `null` | `null` | Default readiness predicate stamped on custom resources of this CRD. |
| `factBehavior` | attrset | `{ }` | Default network-policy endpoint behavior for custom resources of this CRD. |
| `usesAtLeast` | function or `null` | `null` | Resource estimation callback `(crSpec: { cpu; memory; })`. |
| `holdsData` | bool | `false` | Whether custom resources of this CRD hold stateful data. |

### Creating custom resources (`scope.mkCR`, `crd.out.mkCR`, and `crd.out.cr`)

Once a CRD is defined via `scope.mkCRD` or `scope.mkCRDRef` (or received from a dependency at `dep.crds.<Kind>`), construct custom resources using any of these three equivalent forms:

1. **`scope.mkCR crd args`**: Builds the custom resource in `scope`, automatically setting `apiVersion` (`"${crd.group}/${crd.version}"` or `args.version`), `kind`, cluster vs. namespaced scoping, `readiness`, `factBehavior`, `holdsData`, `usesAtLeast`, and the deployment dependency on `crd`.
2. **`crd.out.mkCR consumerScope args`**: Identical to `consumerScope.mkCR crd args`. Convenient when calling a CRD exported by a dependency (`prometheus.crds.ServiceMonitor.out.mkCR scope { name = "echo"; spec = { ... }; }`).
3. **`scope.mkResource (crd.out.cr args)`**: `crd.out.cr` returns the attribute set for `scope.mkResource` (or `scope.mkClusterResource` when `crdScope == "Cluster"`).

### Capacity estimation helpers (`kix.usage.*`)

When defining `usesAtLeast` on `scope.mkCRD` or `scope.mkCRDRef` for an operator that spawns pods from a custom resource, use `kix.usage`:

| Helper | Signature | Description |
| --- | --- | --- |
| `kix.usage.ofPod` | `resourcesAttr -> { cpu; memory; }` | Extracts `{ cpu = resourcesAttr.requests.cpu or "0"; memory = resourcesAttr.requests.memory or "0"; }`. |
| `kix.usage.times` | `count -> { cpu; memory; } -> { cpu; memory; }` | Multiplies `cpu` and `memory` quantities by integer `count`. |
| `kix.usage.add` | `usageA -> usageB -> { cpu; memory; }` | Sums two `{ cpu; memory; }` attribute sets. |

```nix
usesAtLeast =
  spec:
  kix.usage.times (spec.instances or 1) (kix.usage.ofPod (spec.resources or { }));
```

### CRD spec construction helpers (`kix.crd.*` and `scope.crd.*`)

When authoring a CRD schema in Nix instead of loading a vendored JSON file, use the composable transformers in `kix.crd` (also available at `scope.crd`), which build an attribute set you can pass to `scope.mkCRD`:

| Helper | Signature | Description |
| --- | --- | --- |
| `kix.crd.fromKind` | `{ group, kind, plural ? "${lib.toLower kind}s", singular ? lib.toLower kind, version ? "v1", schema ? { type = "object"; x-kubernetes-preserve-unknown-fields = true; } }` | Creates a base Namespaced CRD definition with one served storage `version`. |
| `kix.crd.clusterScoped` | `crdAttrs -> crdAttrs` | Sets `spec.scope = "Cluster"`. |
| `kix.crd.withShortNames` | `[ strings ] -> crdAttrs -> crdAttrs` | Sets `spec.names.shortNames`. |
| `kix.crd.withCategories` | `[ strings ] -> crdAttrs -> crdAttrs` | Sets `spec.names.categories`. |
| `kix.crd.withPrinterColumns` | `[ columns ] -> crdAttrs -> crdAttrs` | Sets `additionalPrinterColumns` on all versions in `spec.versions`. |
| `kix.crd.withSchema` | `openAPIV3Schema -> crdAttrs -> crdAttrs` | Replaces `schema.openAPIV3Schema` on all versions in `spec.versions`. |
| `kix.crd.withVersion` | `{ name, served ? true, storage ? false, schema ? null, subresources ? null, additionalPrinterColumns ? [ ] } -> crdAttrs -> crdAttrs` | Appends an additional API version to `spec.versions`. |
| `kix.crd.withLabels` | `labels -> crdAttrs -> crdAttrs` | Merges `labels` onto the CRD definition. |
| `kix.crd.withAnnotations` | `annotations -> crdAttrs -> crdAttrs` | Merges `annotations` onto the CRD definition. |

## RBAC helpers

### Creating a `ServiceAccount`

Create a `ServiceAccount` with `scope.mkResource` and pass it to a workload's `spec.template.spec.serviceAccount` shorthand:

```nix
serviceAccount = scope.mkResource {
  apiVersion = "v1";
  kind = "ServiceAccount";
  name = "my-operator";
};

deployment = scope.mkDeployment {
  name = "my-operator";
  spec = {
    selector.matchLabels = scope.selectorLabels;
    template.spec = {
      serviceAccount = self.serviceAccount; # Sets serviceAccountName and deployment dependency
      containers = [ ... ];
    };
  };
};
```

### Policy rule DSL (`kix.rbac.*` and `scope.rbac.*`)

Instead of writing verbose `apiGroups`, `resources`, and `verbs` arrays by hand, use `kix.rbac` (also aliased at `scope.rbac`) to construct RBAC policy rules by API group and intent:

```nix
rules =
  let
    inherit (kix.rbac) core group sub restrictTo watch reconcile finalize emit;
  in
  [
    # Watch and update status/finalizers on Certificates in cert-manager.io
    (reconcile (group "cert-manager.io" [ "certificates" "issuers" ]))

    # Read Secrets and ConfigMaps in the core ("") API group
    (watch (core [ "secrets" "configmaps" ]))

    # Update a specific ConfigMap by resourceName
    ( kix.rbac.readWrite (restrictTo [ "my-operator-leader" ] (core [ "configmaps" ])) )

    # Emit Kubernetes Events
    (emit (core [ "events" ]))
  ];
```

#### Target constructors and modifiers

| Function | Signature | Description |
| --- | --- | --- |
| `kix.rbac.group` | `apiGroup -> [ resources ] -> target` | Targets `resources` in `apiGroup` (accepts a string or list of API group strings). |
| `kix.rbac.core` | `[ resources ] -> target` | Shorthand for `kix.rbac.group "" resources` (core `v1` API group). |
| `kix.rbac.sub` | `[ subresources ] -> target -> target` | Expands `resources` to include `"${resource}/${subresource}"` (for example, `sub [ "status" ]`). |
| `kix.rbac.restrictTo` | `[ resourceNames ] -> target -> target` | Restricts the rule to specific `resourceNames`. |

#### Intent constructors (target -> policyRule)

| Intent function | Verbs granted | Subresources added automatically |
| --- | --- | --- |
| `kix.rbac.watch` | `[ "get" "list" "watch" ]` | None |
| `kix.rbac.reconcile` | `[ "get" "list" "watch" "update" "patch" ]` | `status` |
| `kix.rbac.finalize` | `[ "update" "patch" ]` | `finalizers` |
| `kix.rbac.watchAndFinalize` | `[ "get" "list" "watch" "update" "patch" ]` | `finalizers` |
| `kix.rbac.own` | `[ "get" "list" "watch" "create" "update" "patch" "delete" ]` | `status`, `finalizers` |
| `kix.rbac.readWrite` | `[ "get" "list" "watch" "create" "update" "patch" ]` | None |
| `kix.rbac.full` | `[ "get" "list" "watch" "create" "update" "patch" "delete" ]` | None |
| `kix.rbac.emit` | `[ "create" "patch" ]` | None (designed for `events`) |
| `kix.rbac.allow` | `[ verbs ] -> target -> rule` | Custom verb list |
| `kix.rbac.grant` | `{ groups ? [ "" ], resources, verbs, resourceNames ? null }` | Direct one-off rule constructor |

### Role and RoleBinding set builders (`mkRoleSet` and `mkClusterRoleSet`)

`kix.rbac.mkRoleSet` and `kix.rbac.mkClusterRoleSet` generate paired `Role` + `RoleBinding` (or `ClusterRole` + `ClusterRoleBinding`) parts in a single call and wire the `ServiceAccount` subject automatically:

```nix
rbac = kix.rbac.mkClusterRoleSet scope {
  subjects = [ self.serviceAccount ];
  roles = {
    "my-operator-controller" = with kix.rbac; [
      (reconcile (group "example.com" [ "widgets" ]))
      (watch (core [ "pods" "services" ]))
    ];
  };
};
```

| Builder | Signature | Returned parts attrset |
| --- | --- | --- |
| `kix.rbac.mkRoleSet` | `scope -> { subjects, roles, labels ? { } }` | For a single entry in `roles`, returns `{ role, roleBinding }`. For multiple entries in `roles`, returns `{ "role-<name>", "roleBinding-<name>", ... }`. |
| `kix.rbac.mkClusterRoleSet` | `scope -> { subjects, roles, labels ? { } }` | For a single entry in `roles`, returns `{ clusterRole, clusterRoleBinding }`. For multiple entries in `roles`, returns `{ "clusterRole-<name>", "clusterRoleBinding-<name>", ... }`. |

Each element of `subjects` can be a `ServiceAccount` resource (created by `scope.mkResource`) or an explicit `{ kind, name, namespace?, apiGroup? }` subject attribute set. When a `ServiceAccount` resource is passed, its `.out.name` is used so the binding automatically depends on the `ServiceAccount`.
