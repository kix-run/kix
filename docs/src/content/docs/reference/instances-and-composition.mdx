Once you have a cluster module, you populate it by declaring package instances under `instances.<namespace>.<name>`. Reach for this page when you are adding an application or database to a cluster, passing configuration values to a package, wiring a service to a dependency in another namespace, or sharing common configuration across staging and production environments.

- [08. Basic dependency resolution and namespace boundaries](/docs/tutorials/08-basic-dependency-resolution-and-namespace-boundaries/): learn how Kix matches dependencies within a namespace and how to wire cross-namespace links with `ref`.
- [10. Reuse packages across instances and environments](/docs/tutorials/10-reusing-packages/): see how to run multiple instances of the same package with different settings.
- [The dependency graph as the model](/docs/explanation/the-dependency-graph/): understand how instance dependencies control deployment ordering and network policies.
- [Namespaces (Kubernetes docs)](https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/): review how Kubernetes partitions resources inside a cluster by namespace.

## Instances

Each entry under `instances.<namespace>.<name>` places a managed package instance or an external resource marker (`kix.mkImport`) into `<namespace>` with the instance name `<name>`.

```nix
{ packages, ref, ... }:
{
  instances.apps.web = {
    package = packages.web;
    config = {
      replicas = 3;
      ingress.host = "web.example.com";
    };
    deps.database = ref.data.postgres;
  };
}
```

### Summary of instance fields

| Field | Type | Default | Merge behavior across modules | Purpose |
| --- | --- | --- | --- | --- |
| `package` | raw function or attrset | required | single definition (conflict on duplicate) | Package function, evaluated package attribute set, or `kix.mkImport` marker. |
| [`config`](#config) | `deferredModule` | `{ }` | NixOS module merge (`lib.mkDefault`, `lib.mkForce`) | Values evaluated against the package's `options`. |
| [`deps`](#deps) | `attrsOf anything` | `{ }` | collision on same key is an error | Explicit dependency bindings (`ref.<ns>.<inst>`, list of `ref`s, or direct values) keyed by build argument name. |
| [`aliases`](#aliases) | `nullOr (listOf str)` | `null` | list merge | Dependency-resolution names for this instance. A list replaces `meta.defaultAliases`. |
| [`optional`](#optional) | `bool` | `false` | boolean merge | Keeps the instance dormant unless an active instance transitively depends on it. |
| [`availability`](#availability) | `null \| "none" \| "pod" \| "node" \| "zone"` | `null` | single definition | Overrides `cluster.availability.default` for this instance. |
| [`partsOverlays`](#partsoverlays) | `listOf raw` | `[ ]` | lists concatenate in module order | Post-build functions (`scope: self: base: attrset`) that modify, add, or remove rendered parts. |
| `labelStyle` | `"kix" \| "helm"` | `"kix"` | single definition | Selector and metadata label convention: `"kix"` (`app.kubernetes.io/*`) or `"helm"` (`app` and `release`). |
| `selectorLabels` | `nullOr (attrsOf str)` | `null` | attribute set merge | Explicit `spec.selector.matchLabels` override for adopting workloads with immutable live selectors. |
| `extraDeps` | `listOf raw` | `[ ]` | lists concatenate | Additional deployment-ordering dependencies (`ref.<ns>.<inst>` or resource values) on a `kix.mkImport` instance's marker. |
| `platformIntents` | `attrsOf anything` | `{ }` | attribute set merge | Network connectivity intents for a `kix.mkImport` instance's pre-installed pods. |
| `version` | `nullOr str` | `null` | single definition | States the version the instance runs. Overrides the package's `out.version` and `meta.version`. |

### `package`, `labelStyle`, `selectorLabels`, `extraDeps`, `platformIntents`, and `version`

- **`package`**: Required for every instance. Takes a package function (`{ scope, lib, kix, ... }: { ... }`), an inline package attribute set (`{ meta?; options?; build = ...; }`), or a [`kix.mkImport`](/docs/reference/helm-and-imports/) marker. Built-in packages from `packages` (such as `packages.harbor` or `packages.experimental.coredns`) work like package functions and also carry a package ID (`.id`), which Kix writes to [`spec.package`](/docs/reference/annotations-crds-and-receipts/#packageinstance-spec-and-annotations) on the instance's `PackageInstance` resource. Do not redefine `package` when writing an override module for an instance declared in another module; set only `config`, `deps`, `aliases`, or `partsOverlays`.
- **`labelStyle` and `selectorLabels`**: Kubernetes forbids changing `spec.selector.matchLabels` on an existing Deployment or StatefulSet. When adopting a live workload that was installed with Helm (`app` and `release` labels), set `labelStyle = "helm"`. When the live workload uses custom selector keys, set `selectorLabels` to the exact label map from the cluster.
- **`extraDeps` and `platformIntents`**: Valid only on `kix.mkImport` instances. Setting `extraDeps` on a managed instance fails evaluation. Each entry in `extraDeps` is a Kix resource or `ref.<namespace>.<instance>`; when the import is active, `ref` entries must point to active instances (an `extraDeps` reference does not activate a dormant `optional` instance). `platformIntents` uses the same schema as [`networkPolicy.platformIntents`](/docs/reference/cluster-configuration/#network-policy) and attaches the generated policies as dependencies of the import marker.
- **`version`**: States the version the instance runs. Kix writes it onto the `PackageInstance` resource and checks it in the `meta.compatibleWith` constraints of the packages that depend on the instance. Without it, Kix uses the `out.version` the package builds, which most packages read from the image tag, and then the package's `meta.version`. Set it when the instance runs an image whose tag names no version, such as `latest` or a tag of your own build. See [The version an instance reports](/docs/reference/package-anatomy/#the-version-an-instance-reports).

### Stable and experimental packages

A package is stable or experimental. A stable package breaks only in a minor release. An experimental package may break in any release, including a patch release, and the break may be one that shows no error. `CHANGELOG.md` lists these breaks under the heading "Breaking in experimental packages and contracts".

The name you write in `package` shows the level:

```nix
instances.apps.cache.package = packages.valkey;
instances.apps.cache-2.package = packages.stable.valkey;
instances.apps.photos.package = packages.experimental.immich;
```

- **`packages.<name>`**: A stable package. `packages.stable.<name>` is the same package.
- **`packages.experimental.<name>`**: An experimental package. Writing `packages.<name>` for an experimental package fails with `[K0549]` and gives `packages.experimental.<name>`. `kix list packages` shows it as `experimental.<name>`.
- **Reserved names**: No package can be named `stable` or `experimental`.
- **A package that becomes stable**: `packages.experimental.<name>` then fails with the error "`packages.experimental.<name>` is stable now. Write `packages.<name>`."
- **A removed package**: `packages.experimental.<name>` and `packages.<name>` fail with an error that gives the change record's id and what to do instead.
- **A shared name**: An experimental package may have the same name as a stable package. It is then a rework of that package, and replaces it in a minor release.
- **Contracts**: A stable package reads only stable [dependency contracts](/docs/reference/dependency-contracts/#shared-contract-attributes-and-methods). An experimental package may read both stable and experimental contracts.
- **Modules**: All cluster modules are experimental (`kix/modules/experimental/`): `kix.modules.experimental.monitoring`, `kix.modules.experimental.irsa-webhook`, and `kix.modules.experimental.azure-workload-identity-webhook`. `kix.modules.monitoring` fails with `[K0549]`.
- **Automatic instances**: [`availablePackages = packages`](/docs/reference/cluster-configuration/#availablepackages) offers only the stable packages. Name each experimental package that Kix may add.

These packages are stable: `cnpg-cluster`, `cnpg-operator`, `echo-server`, `grafana`, `harbor`, `kube-state-metrics`, `node-exporter`, `persistent-volume-claim`, `priority-class`, `secret`, `secret-ref`, `storage-classes`, `valkey`, `victoria-metrics-agent`, `victoria-metrics-alert`, `victoria-metrics-cluster`, and `victoria-metrics-operator`. Every other package is experimental. A package becomes stable once it has run in production long enough to settle.

## config

`instances.<namespace>.<name>.config` sets values for the options declared in the package's `options` block.

```nix
instances.apps.web = {
  package = packages.web;
  config = {
    replicas = 3;
    ingress.host = "web.example.com";
  };
};
```

### Module merging and priorities

Because `config` has type `deferredModule`, multiple cluster modules can contribute configuration to the same instance. Kix evaluates four layers together using `lib.evalModules`:

| Priority (lower number wins) | Source | Notes |
| --- | --- | --- |
| `50` (`lib.mkForce`) | Any module using `lib.mkForce` | Overrides normal definitions and defaults. |
| `100` (normal definition) | Instance `config` and dependency config injections (`deps.<arg>.config`) | Conflicting plain definitions fail evaluation with file attribution. |
| `1000` (`lib.mkDefault`) | Instance `config` or dependency injection using `lib.mkDefault` | Wins over package-level defaults. |
| `1250` (`packageDefaultPriority`) | `lib.mkDefault` inside the package's own `config` block | Replaces option defaults (`1500`) while yielding to any instance or injected value. |
| `1500` (option default) | `default` in the package's `options` declarations | Base fallback value. |

An instance `config` block can also be written as a module function taking `{ config, clusterConfig, lib, ... }`:

```nix
instances.apps.web.config = { config, clusterConfig, lib, ... }: {
  ingress.host = lib.mkDefault "web.${clusterConfig.cluster.domain}";
};
```

### Locking fields against dependency injection (`kix.mkLocked`)

A package can inject configuration into one of its dependencies via `deps.<arg>.config` (for example, a database consumer injecting required PostgreSQL extensions into the database cluster). To prevent any consumer from injecting into a top-level option on an instance, wrap the value in `kix.mkLocked`:

```nix
instances.data.postgres.config.extensions = kix.mkLocked [ "pg_stat_statements" ];
```

If a consumer attempts to inject `extensions` into `data/postgres`, evaluation fails and names the consumer that tried to inject the locked field.

:::tip[Use it in a task]
See [Add typed package options](/docs/how-to/author-packages-and-clusters/add-typed-package-options/) for how packages declare options and defaults.
:::

## deps

`instances.<namespace>.<name>.deps` overrides automatic dependency resolution for specific build arguments of the package.

Every key in `deps` must match a dependency declared by the instance's package, even on inactive `optional = true` instances. If the package renamed that dependency (`deps.<arg>.renamedFrom`), evaluation fails with the rename's change ID and gives the new name. Any other unknown key fails with `[K3646]`. Because a `kix.mkImport` instance takes no dependencies, setting any `deps` key on an import also fails with `[K3646]`; use `extraDeps` to order an import after another instance.

```nix
{ packages, ref, ... }:
{
  instances.apps.web = {
    package = packages.web;
    deps = {
      database = ref.data.postgres-primary;
      cache = ref.apps.valkey;
    };
  };
}
```

### Wiring instances with `ref`

Every cluster module receives `ref` in its module arguments. Writing `ref.<namespace>.<instance>` points a dependency argument directly at that instance:

- **Single instance**: `deps.database = ref.data.postgres;` resolves `database` to the package view of `instances.data.postgres`.
- **List of instances**: `deps.registryLogins = [ ref.apps.operator-logins ref.apps.extra-logins ];` resolves the argument to a list of instance handles in the given order. Mixing `ref` pointers with non-`ref` values in the same list fails evaluation.
- **Full dependency checks**: A `ref`-wired dependency receives the same validation and wiring as an auto-resolved dependency: `meta.scope = "namespace"` boundaries are enforced, `meta.compatibleWith` version constraints are checked, `deps.<arg>.config` injections are forwarded to the target instance, and pointing `ref` at an `optional = true` instance activates it.
- **Namespace rule**: Kix fills a package argument from the consumer's own namespace. It uses an instance in another namespace only when the cluster definition names it with `ref`, or when the provider's package serves the whole cluster (by setting `meta.scope = "cluster"`, claiming a role in `meta.roles`, or declaring a `cluster:` entry in `meta.conflictsWith`). Stand-ins created with `kix.mkImport` also serve the whole cluster unless they set `scope = "namespace"`; when several imports match one name, select one with `ref`. An instance that Kix creates from `availablePackages` or enables via `optional = true` to satisfy a dependency also binds from any namespace, because the cluster definition chose where it lives. When the only match for a required argument is in another namespace and does not serve the whole cluster, evaluation fails and the error prints the `deps` line to add. When several instances in other namespaces answer the name, the error lists a `deps` line for each. An optional argument (`x ? null`) in that situation takes its default, and Kix prints a warning that names the instance and the `deps` line to add.

### Direct values and `null`

- Any value that is not a `ref` (or a list of `ref`s) is passed as-is to the build argument without package view wrapping, compatibility checks, or config injection. The package's `assertions` also receive it in `deps`.
- Setting `deps.<arg> = null;` behaves the same as leaving `deps.<arg>` unset: Kix falls back to automatic resolution or the build argument's default value.
- Explicitly wiring `deps.<arg>` suppresses `availablePackages` auto-instantiation for that argument.
- An instance cannot depend on itself. Automatic resolution skips the instance when its own name, aliases, or roles match `<arg>`, and referencing the instance itself with `ref` in `deps.<arg>` fails evaluation. Because managed instances take priority over imports, a managed instance that matches `<arg>` does not automatically fall back to a `kix.mkImport` of that name; point `deps.<arg>` to the import with `ref` to use it.

### Cloud identities

Packages that call AWS, Google Cloud, or Azure APIs (such as `external-dns`) can accept a cloud identity instead of a Secret instance on the same dependency:

```nix
instances.external-dns.route53 = {
  package = packages.experimental.external-dns;
  deps.providerCredentials = kix.cloudIdentity.aws {
    roleArn = "arn:aws:iam::111122223333:role/external-dns";
  };
  # Or pass a Secret instance on the same dependency:
  # deps.providerCredentials = ref.external-dns.aws-keys;
};
```

| Constructor | Fields | What Kix writes on the ServiceAccount and pods |
| --- | --- | --- |
| `kix.cloudIdentity.aws` | `roleArn` (IAM role ARN) | `<annotationPrefix>/role-arn` (`eks.amazonaws.com/role-arn` by default) on the ServiceAccount. With `cluster.flavor.eks.cloudIdentity = "pod-identity"`, Kix omits this annotation because EKS Pod Identity links the ServiceAccount through an AWS association. |
| `kix.cloudIdentity.gcp` | optional `serviceAccount` (Google service account email) | `iam.gke.io/gcp-service-account` on the ServiceAccount when `serviceAccount` is set. `kix.cloudIdentity.gcp { }` omits the Google annotation when IAM roles are granted directly to the Kubernetes ServiceAccount. |
| `kix.cloudIdentity.azure` | `clientId`, optional `tenantId` (GUIDs) | `azure.workload.identity/client-id` (and `azure.workload.identity/tenant-id` when set) on the ServiceAccount, plus label `azure.workload.identity/use: "true"` on the pods. |

The cluster's `cloudIdentity` role provider controls how Kix renders the identity. The `eks`, `gke`, `gke-autopilot`, and `aks` flavors declare this provider automatically ([Flavors and capabilities](/docs/reference/flavors-and-capabilities/#cloud-identity)). Kix also writes `kix.run/cloud-identity` (containing the identity and mechanism as JSON) on the ServiceAccount, orders the ServiceAccount after the `cloudIdentity` provider, and adds `checksum/cloud-identity` to every pod template referencing that ServiceAccount so changing the identity restarts the pods.

Kix does not create cloud IAM resources. Configure the AWS IAM role trust policy (or EKS Pod Identity association), Google Cloud IAM binding, or Azure federated credential outside Kix for `system:serviceaccount:<namespace>:<serviceaccount-name>`.

The identity goes on the instance whose pods call the cloud. When another instance chooses the cloud, that instance keeps any Secret and the software's own setting for pod credentials. For example, StackGres backups take the identity in `deps.backupIdentity` on each `stackgres-cluster` instance, and the `stackgres-object-storage` instance sets `useIAMRole` or `fetchCredentialsFromMetadataService` instead of a Secret ([Deploy StackGres](/docs/how-to/package-task-guides/deploy-stackgres/#back-up-with-a-cloud-identity)). An operator creates those pods, so Kix cannot restart them when the identity changes.

Evaluation fails when:
- an identity has an unknown, missing, or malformed field;
- the cluster has no `cloudIdentity` provider;
- the identity's cloud does not match the cluster's `cloudIdentity` provider or the cloud API the package calls; or
- the package does not accept that dependency (`[K3646]`).

If a package does not yet accept `kix.cloudIdentity`, add the cloud's annotation to its ServiceAccount with `partsOverlays`. The cloud flavors declare their annotation domains, so the scorecard allows the annotation without warning. Changing a ServiceAccount annotation in `partsOverlays` does not restart pods automatically:

```nix
partsOverlays = [
  (scope: self: base: {
    serviceAccount = scope.mkResource {
      apiVersion = "v1";
      kind = "ServiceAccount";
      name = base.serviceAccount.name;
      annotations."eks.amazonaws.com/role-arn" = "arn:aws:iam::111122223333:role/report-uploader";
    };
  })
];
```

On a self-managed cluster running a workload identity webhook, add the matching module alongside the cluster flavor:

```nix
modules = [
  kix.flavors.kubeadm
  kix.modules.experimental.irsa-webhook   # runs amazon-eks-pod-identity-webhook
  # Only when the webhook runs with another --annotation-prefix:
  { irsaWebhook.annotationPrefix = "irsa.example.com"; }
];
```

Use `kix.modules.experimental.azure-workload-identity-webhook` on self-managed clusters running the Azure Workload Identity webhook. Kix does not yet include a module for Google Cloud identities outside GKE.

To share a workload definition across clusters that use cloud identities and clusters that use Secrets, set `deps.providerCredentials` in each cluster file. See [Keep credentials in the cluster file](/docs/how-to/start-and-inspect/select-and-configure-a-cluster-flavor/#keep-credentials-in-the-cluster-file).

:::tip[Use it in a task]
See [Wire cross-namespace dependencies explicitly](/docs/how-to/debug-dependency-wiring/wire-cross-namespace-dependencies-explicitly/) and [Debug a missing dependency](/docs/how-to/debug-dependency-wiring/debug-a-missing-dependency/).

## aliases

`instances.<namespace>.<name>.aliases` sets the dependency-resolution aliases for an instance.

```nix
instances.apps.valkey-cache = {
  package = packages.valkey;
  aliases = [ "cache" "redis" ];
};
```

- The instance's own `<name>` (`valkey-cache` above) and any roles in the package's `meta.roles` are always registered as resolution keys.
- When `aliases` is unset (the default), Kix registers the package's `meta.defaultAliases`.
- When `aliases` is set, it **replaces** `meta.defaultAliases`. Include any default alias the instance should still answer. `aliases = [ ]` gives the instance no aliases, so it answers only its instance name and the package's `meta.roles`.

When multiple instances in a cluster provide the same service (such as two PostgreSQL clusters or two ingress controllers), prefer wiring `deps.<arg> = ref.<namespace>.<instance>` on the consumer rather than inventing per-instance aliases.

:::tip[Use it in a task]
See [Use aliases and default aliases](/docs/how-to/debug-dependency-wiring/use-aliases-and-default-aliases/) for resolution order and disambiguation patterns.
:::

## optional

Setting `optional = true` keeps a declared instance dormant unless an active instance transitively requires it.

```nix
instances.data.clickhouse = {
  package = packages.experimental.clickhouse-cluster;
  optional = true;
  config.shards = 2;
};
```

### When an optional instance activates

Kix starts from all non-optional instances (`optional = false`) and walks the dependency graph to find all transitively required instances. An optional instance becomes active when an active instance reaches it through:
1. a **required** build argument (one with no `? null` default) that matches the optional instance's name, `aliases`, `meta.defaultAliases`, or `meta.roles`; or
2. an explicit `deps.<arg> = ref.<namespace>.<instance>` (or an entry in a `deps` ref list).

An optional build argument (`{ prometheus ? null, ... }`) never activates a dormant optional instance, and a dormant optional instance or import never answers an optional build argument (the argument receives `null` unless an active instance matches). Note that `extraDeps` or a `ref` in `out` on a `kix.mkImport` instance also does not activate an optional instance.

When activated, the instance is stamped with `kix.run/optional-activated: "true"` on its `PackageInstance` record and deployed normally. When dormant, it emits no manifests, skips dependency resolution, and injects no `deps.<arg>.config` into other instances, so an unmet dependency on a dormant instance does not fail evaluation.

## availability

`instances.<namespace>.<name>.availability` overrides `cluster.availability.default` for a single instance.

```nix
instances.apps.preview = {
  package = packages.web;
  availability = "none";
};
```

| Property | Value |
| --- | --- |
| Type | `null \| "none" \| "pod" \| "node" \| "zone"` |
| Default | `null` (inherits `cluster.availability.default`) |
| Maximum allowed | `cluster.availability.substrate` |

An instance can request a higher or lower availability level than `cluster.availability.default`, as long as it does not exceed `cluster.availability.substrate`. If the package declares `meta.availability.max` (or a workload builder declares `availability.max`) below the requested level, Kix caps the effective level at that ceiling and emits a warning.

## partsOverlays

`instances.<namespace>.<name>.partsOverlays` transforms, adds, or removes resources in an instance's evaluated parts tree without modifying the package definition.

```nix
instances.apps.web = {
  package = packages.web;
  partsOverlays = [
    (scope: self: base: {
      # Modify an existing resource part:
      deployment = base.deployment // {
        spec = lib.recursiveUpdate base.deployment.spec {
          template.spec.priorityClassName = self.highPriority.out.name;
        };
      };

      # Add a new resource part:
      highPriority = scope.mkClusterResource {
        apiVersion = "scheduling.k8s.io/v1";
        kind = "PriorityClass";
        name = "web-high-priority";
        extra.value = 1000;
      };
    })
  ];
};
```

### Evaluation order and arguments

Kix evaluates an instance's parts inside a single `lib.fix` fixed point in this order:
1. All `build` entries in the package run and merge (duplicate part names across `build` entries are an error).
2. Cluster-wide `globalPartsOverlays` run in order.
3. The instance's `partsOverlays` run in order.

Each overlay function has signature `scope: self: base: attrset` and its return value is merged onto `base` with `//`:
- `scope`: the instance's [resource builder scope](/docs/reference/resources-and-out/).
- `self`: the final fixed point after all overlays have run. Read `self.<part>.out.*` when referencing another part so dependencies are tracked.
- `base`: the parts attribute set produced before the current overlay ran. Read `base.<part>` when wrapping or modifying an existing part so you do not create an infinite recursion on `self.<part>`.
- Setting a non-`root` part to `null` removes it from the emitted manifests (`root` itself must remain a valid resource).

:::tip[Use it in a task]
See [Patch package output with overlays](/docs/how-to/adopt-existing-resources/patch-package-output-with-overlays/) for common overlay recipes, including extending `root.out` on Helm packages.
:::

## Multi-environment stamping and fragments

### `kix.mkEnv`

`kix.mkEnv` stamps a reusable set of instances into environment-prefixed namespaces (`<envName>-<setName>`).

```nix
kix.mkEnv envName envConfig instanceSets
```

| Argument | Type | Meaning |
| --- | --- | --- |
| `envName` | `str` | Environment prefix prepended to each instance set key (`"${envName}-${setName}"`). |
| `envConfig.config` | `attrs` (optional, default `{ }`) | Environment-wide parameters passed to each set function as `env.config`. |
| `envConfig.overrides` | `attrs` (optional, default `{ }`) | Per-set, per-instance overrides (`overrides.<setName>.<instName>.{ config?, parts? }`). |
| `instanceSets` | `attrsOf ({ ref, env } -> attrsOf instanceDef)` | Functions returning instance definitions for each logical namespace suffix `<setName>`. |

```nix
let
  appSet = { env, ... }: {
    api = {
      package = packages.api;
      config = {
        replicas = env.config.replicas;
        ingress.host = "api.${env.name}.example.com";
      };
    };
  };
in
{
  instances =
    (kix.mkEnv "staging" {
      config.replicas = 1;
    } { app = appSet; })
    // (kix.mkEnv "prod" {
      config.replicas = 3;
      overrides.app.api.config.replicas = 5;
    } { app = appSet; });
}
```

Key behaviors of `kix.mkEnv`:
- The example above produces `instances."staging-app".api` and `instances."prod-app".api`.
- Because dependency resolution prefers instances in the same namespace, services stamped into `"staging-app"` resolve dependencies in `"staging-app"` first.
- `overrides.<setName>.<instName>.config` is shallow-merged (`//`) onto the instance's `config` attribute set. If you need deep module merging for nested options, define an additional module targeting `instances."<envName>-<setName>".<instName>.config` instead.
- All environments stamped into one cluster share a single `Activation` record and deploy together. For environments that must deploy independently, build separate cluster definitions that import a shared base module.

### `kix.mergeFragments`

`kix.mergeFragments` combines cluster fragments authored by different teams into a single `namespaces` and `instances` configuration while rejecting collisions.

```nix
kix.mergeFragments {
  fragments = [
    (import ./teams/checkout.nix)
    (import ./teams/search.nix)
  ];
  namespacePolicies = {
    checkout.podSecurity = "restricted";
    search.podSecurity = "restricted";
  };
}
```

| Field | Type | Default | Behavior |
| --- | --- | --- | --- |
| `fragments` | `listOf { namespaces?, instances? }` | required | Each fragment's `instances` may be an attribute set or a function `args: attrset`. Defining the same `instances.<namespace>.<name>` in more than one fragment throws an evaluation error. |
| `namespacePolicies` | `attrsOf attrs` | `{ }` | Deep-merged with the fragments' `namespaces` definitions. Any conflicting leaf attribute across fragments or `namespacePolicies` throws an evaluation error. |
