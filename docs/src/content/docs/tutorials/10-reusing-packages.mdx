Once a package uses `scope` for resource naming and `options` for configuration, you can instantiate it as many times as you need: multiple instances in the same namespace, or separate instances across `staging` and `production` namespaces.

In this tutorial, you will inspect `tutorials/10-reuse-packages/cluster.nix`, which runs two separate `echo-server` backends and two separate `reverse-proxy` gateways from the exact same package definitions.

## Prerequisites

- Finish the [typed package options tutorial](/docs/tutorials/09-typed-package-options/).
- Keep the same `kix-examples` checkout.

## Why `scope` Makes Packages Reusable

In `reverse-proxy-package.nix`, look at how the package names its ConfigMap, Deployment, and Service:

```nix title="tutorials/09-typed-options/reverse-proxy-package.nix"
let
  name = scope.instanceName;
in
{
  configmap = scope.mkResource {
    apiVersion = "v1";
    kind = "ConfigMap";
    inherit name;
    # ...
  };
```

Because the package derives `name` from `scope.instanceName` (instead of hardcoding `"reverse-proxy"` or `"gateway"`), every instance in a namespace gets its own distinct resource names and selector labels:

- An instance key `api-gateway` receives `scope.instanceName = "api-gateway"` and `scope.selectorLabels` with `app.kubernetes.io/instance = "api-gateway"`.
- An instance key `admin-gateway` receives `scope.instanceName = "admin-gateway"` and `scope.selectorLabels` with `app.kubernetes.io/instance = "admin-gateway"`.

Neither their resource names (`ConfigMap/api-gateway` vs. `ConfigMap/admin-gateway`) nor their pod label selectors collide, even when both instances run side by side in the same namespace.

:::note[Reference]
See [The `scope` helper](/docs/reference/package-anatomy/#root-function-and-return-shape) for all fields and constructors on `scope`.
:::

## Inspect `10-reuse-packages`

Open `tutorials/10-reuse-packages/cluster.nix`. It reuses both `packages.echo-server` and the local `reverseProxyPackage` to create two independent proxy chains:

```nix title="tutorials/10-reuse-packages/cluster.nix"
namespaces.tutorial-10.instances = {
  api-backend = {
    package = packages.echo-server;
    config.message = "Response from API backend";
  };

  admin-backend = {
    package = packages.echo-server;
    config.message = "Response from Admin backend";
  };

  api-gateway = {
    package = reverseProxyPackage;
    deps.backend = ref.tutorial-10.api-backend;
    config = {
      proxyPath = "/api/";
      maxBodySize = "10m";
    };
  };

  admin-gateway = {
    package = reverseProxyPackage;
    deps.backend = ref.tutorial-10.admin-backend;
    config = {
      proxyPath = "/admin/";
      maxBodySize = "50m";
    };
  };
};
```

Look at how `deps.backend` is wired on each gateway:

- Neither backend is named `backend`; they are named `api-backend` and `admin-backend`.
- `api-gateway` sets `deps.backend = ref.tutorial-10.api-backend;`.
- `admin-gateway` sets `deps.backend = ref.tutorial-10.admin-backend;`.

Inside `reverseProxyPackage`, the `build` function still just reads `backend.out.fqdn` and `backend.out.port`. For `api-gateway`, `backend` resolves to `api-backend`. For `admin-gateway`, `backend` resolves to `admin-backend`.

## Reusing Packages Across Environment Namespaces

The same pattern works when you instantiate a stack across multiple namespaces (such as `app-v1` and `app-v2`, or `staging` and `prod`). When two instances live in different namespaces, they can even keep the canonical instance names `backend` and `gateway` in each namespace, allowing same-namespace dependency resolution to wire each `gateway` to its own namespace's `backend` automatically:

```nix
namespaces.app-v1.instances = {
  backend = {
    package = packages.echo-server;
    config.message = "Response from app-v1";
  };
  gateway = {
    package = reverseProxyPackage;
    config = {
      proxyPath = "/v1/";
      maxBodySize = "10m";
    };
  };
};

namespaces.app-v2.instances = {
  backend = {
    package = packages.echo-server;
    config.message = "Response from app-v2";
  };
  gateway = {
    package = reverseProxyPackage;
    config = {
      proxyPath = "/v2/";
      maxBodySize = "10m";
    };
  };
};
```

You will see this two-namespace layout again in tutorial 12 when we run cluster-wide scorecard rules across `app-v1` and `app-v2`.

## What You Learned

You reused the same package definitions across multiple instances:

<Recap>
- deriving resource names from `scope.instanceName` (or `scope.prefixedName`) prevents collisions when a package is instantiated more than once in the same namespace;
- `scope.mkDeployment` includes `app.kubernetes.io/instance = scope.instanceName` in `scope.selectorLabels`, so each instance's Service selects only its own pods;
- `deps.<arg> = ref.<namespace>.<instance>` lets multiple instances of the same package bind to different providers in the same namespace;
- placing instances in separate namespaces isolates their names and lets each namespace resolve same-namespace dependencies independently.
</Recap>
