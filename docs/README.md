# Kix documentation

Astro Starlight site for Kix. Built as a true sibling Nix subflake.

Deployed at **<https://kix.run/docs/>**. Cloudflare Pages serves the merged
`web/` and `docs/` artifact. See `.github/workflows/pages.yml`.

Each Kix version has its own docs, built at that version's git revision:
`/docs` is the latest release, `/docs/main` is main, and `/docs/vX.Y` is
each older minor release. The flake builds the docs in each of those roles:
`site`, `site-main`, and `site-archived`. Pages link to each other as
`/docs/...`, and a build under another path rewrites those links to its
own (`src/lib/remark-docs-base.mjs`).

## Build

```bash
nix build ./docs#site
```

The static site is written to `result/`. Serve it with any static file server, e.g.:

```bash
python3 -m http.server -d result 8000
```

## Dev server (live reload)

One command, run from the repository root:

```bash
nix run ./docs#dev
```

This builds the snippet + reference pipelines, syncs their output into
`docs/src/`, installs npm deps if missing, and starts the Astro dev
server with HMR. Open the URL it prints (usually <http://localhost:4321>).
Startup also checks every static `/src/...` import in the MDX tree after the
generated files are synchronized, so missing snippets and command captures
fail before the server starts.

Captures sidecars (`docs/src/command-output/`) are committed to git and
not regenerated by this script; see [Captures](#captures) for the
regen apps.

> **Nix features.** This flake requires `nix-command` + `flakes` (standard on
> nix-darwin / NixOS) and declares `pipe-operators` via `nixConfig`. Accept the
> nix prompt on first use, or set `accept-flake-config = true` in your
> `~/.config/nix/nix.conf`.

Re-run after editing source `.nix` files (packages, kix-examples snippet
files) to re-sync the generated content. Pure prose edits inside `docs/`
hot-reload without restarting.

### Manual dev path (rarely needed)

If `nix run ./docs#dev` isn't an option, do it by hand:

```bash
nix build ./docs#snippets          --no-link --print-out-paths   # → /nix/store/...
nix build ./docs#reference         --no-link --print-out-paths   # → /nix/store/...
# Copy each output into the docs/src tree (see flake.nix preBuild for paths)
nix develop ./docs
cd docs && npm install && npm run dev
```

## Layout

- `src/content/docs/`: MDX content, organized by [Diátaxis](https://diataxis.fr/) quadrant:
  - `tutorials/`: learning-oriented walkthroughs
  - `how-to/`: task-oriented recipes
  - `reference/`: information-oriented API/option docs
  - `explanation/`: understanding-oriented background
- `astro.config.mjs`: site config, sidebar, and plugins
- `src/content.config.ts`: Starlight content collection schema

Pages under `reference/package-catalog/` are generated at build time and
ignored by git. Do not edit them directly; edit the package in `kix/packages/`
or `docs/how-to-coverage.json` instead. `docs/nix/reference.nix` reads the
`meta`, `options`, and `build` dependencies of every package in
`kix/packages/stable/` and `kix/packages/experimental/`, and
`docs/scripts/package-catalog.py` writes the catalog index and one MDX page
per package. To link a how-to guide on a package page, add the package ID
(such as `valkey` or `experimental/cilium`) to that guide's `packages` list in
`docs/how-to-coverage.json`.

`nix build ./docs#site` and `nix run ./docs#dev` build the catalog and copy it
into `src/content/docs/reference/package-catalog/`. To build only the catalog,
run `nix build ./docs#reference`.

## Snippets

The snippet pipeline auto-discovers `.nix`, `.sh`, and `.py` files containing
`# region:NAME` markers under `kix-examples/` and this repository, then drops
each region into `src/snippets/<relative-source-path>/<region>.<extension>` as
raw code (no frontmatter, no fence). No registration step.

**Add a new snippet:**

1. In any supported source file under `kix-examples/` or this repository, wrap
   the code you want to expose:

   ```nix
   # region:isProxy
   isProxy =
     inst:
     builtins.elem "reverse-proxy" (inst._meta.packageMeta.provides or [ ]);
   # endregion:isProxy
   ```

   Rules: markers on their own line; one region per name per file;
   region name matches `[a-zA-Z][a-zA-Z0-9-]*`; end markers must name
   the region they close. Nested regions are allowed.

2. Rebuild. The output path mirrors the source path. For example
   `examples/19-scorecards/scorecard.nix` with a `# region:isProxy`
   marker emits `src/snippets/examples/19-scorecards/scorecard/isProxy.nix`.

That's it: no edits to `docs/flake.nix`.

**Use a snippet in a docs page** (page must be `.mdx`, not `.md`):

```mdx
---
title: "Scorecards explained"
description: ...
---

import Snippet from '/src/components/Snippet.astro';
import isProxy from '/src/snippets/examples/19-scorecards/scorecard/isProxy.json';

Scorecard rules identify reverse-proxy packages with this helper:

<Snippet {...isProxy} />
```

`<Snippet>` (from `docs/src/components/Snippet.astro`) renders the code
through Starlight's `<Code>` component (syntax highlighting, copy-to-clipboard,
title showing the line range) and adds a "View source on GitHub" link
pointing at the exact line range. Links into `kix-examples` use its locked
revision from `flake.lock`; links into this repository use its `main` branch.
Both source URL bases are configured in `docs/flake.nix`.

Nested regions can be elided by the calling MDX page. This keeps the source
file free of docs-only presentation hints:

```mdx
<Snippet
  {...clusterFrame}
  elide={{ helloWorldInstance: '        # package instances go here' }}
/>
```

**Raw code only (no link, no component):** the pipeline also emits a
`.nix` sidecar with just the region body. Use this if you want to render
the snippet your own way:

```mdx
import { Code } from '@astrojs/starlight/components';
import isProxyCode from '/src/snippets/examples/19-scorecards/scorecard/isProxy.nix?raw';

<Code code={isProxyCode} lang="nix" />
```

## Captures

The captures pipeline produces the JSON sidecars under
`docs/src/command-output/` that the `<Command>` component renders as
captured CLI output (e.g. `kix list clusters`, `kix check`, `kix
deploy`). Sidecars are committed to git; the site build reads them
straight from the source tree.

Two regen apps, one per execution mode:

- **Offline** (`nix run ./docs#regen-captures-offline -- --apply`):
  invokes `kix` against a workspace (kix-examples + overlay + setup
  mutations) with no live cluster. Used for `check`, `build`,
  `graph`, `list`, and intentional-failure captures (e.g. the
  unresolved-dep demo in tutorial 06).
- **Live** (`nix run ./docs#regen-captures -- --apply`): spins up a
  dedicated `kind-kix-docs` kind cluster and runs every `live` step
  (deploy, diff, status, kubectl get) against it. Used for output
  whose shape only makes sense against a real Kubernetes API.

CI runs `regen-captures-offline -- --check` on pull requests, except
those that change only packages, change records, library tests or test
clusters. Regenerate and commit the offline sidecars before merging
a change that affects their output. Package version bumps skip this,
and the release regenerates every sidecar.

Both drivers share `docs/nix/captures-lib.nix` (workspace setup,
mutate / capture step shells, drift comparison) and consume the
declarative manifest at `docs/nix/captures.nix`. The workspace's
`kix` input is overridden via the Kix CLI's `--override-input`
flag to a known store path, so the eval never has to re-fetch the
repository from GitHub. A kix-examples flake that still names
the input `kixpkgs` has it renamed to `kix` in the workspace copy, since
Kix reads the library only from an input named `kix`. Kix treats the
overridden input as a development library and prints a note on each
command, which the `drop-development-library-note` display transform
removes from the captures.

## Plugins

- [`starlight-llms-txt`](https://github.com/delucis/starlight-llms-txt): emits `llms.txt` and per-page `.md` for LLM ingestion.
- [`starlight-sidebar-topics`](https://starlight-sidebar-topics.netlify.app/): splits the Diátaxis quadrants into top-level "topics", each with its own scoped sidebar.
- [`starlight-links-validator`](https://starlight-links-validator.vercel.app/): fails the build on broken internal links. Links must include the `/docs/` base prefix; see `docs/CLAUDE.md` for the convention.
- [`starlight-github-alerts`](https://starlight-github-alerts.netlify.app/): renders GitHub-style `> [!NOTE]` / `> [!WARNING]` blocks as Starlight asides.
- [`starlight-page-actions`](https://starlight-page-actions.dlcastillop.com/): "Copy as Markdown" + "Open in ChatGPT/Claude" + share menu in the page header.

## Agent-facing surface

Coding agents read the site far more cheaply as Markdown than as HTML: a
typical how-to page is about 80 KB of HTML against about 2 KB of Markdown.
`starlight-llms-txt` emits a `.md` twin for every route except `404`, and
three mechanisms point agents at them.

**Content negotiation.** `web/public/_worker.js` serves the `.md` twin when
the request carries `Accept: text/markdown`, and adds `Vary: Accept` so caches
keep the two representations apart. Cloudflare Pages runs that file as the
site Worker whenever it is present in the deployed directory, and does not
publish it as a static asset. Claude Code, Cursor, GitHub Copilot, and OpenCode
all send the header already.

**`<link rel="alternate">`.** `src/components/Head.astro` overrides Starlight's
`Head` to advertise the twin. Codex CLI ignores `Accept` and reads this tag
instead, so it is the only route by which Codex finds the Markdown.

**`llms.txt`.** `web/public/llms.txt` is the root index, which is where agents
look first. It links the whole-site `llms-small.txt` and `llms-full.txt` that
the plugin generates under `/docs/`, the sitemap, and each Diátaxis section.
Listing real page URLs matters: agents given no index invent paths and 404.

**Sitemap.** `@astrojs/sitemap` covers only the docs, and emits them under
`/docs/`. `web/public/sitemap-index.xml` is the whole-site index that
`robots.txt` points at: it lists `/sitemap-0.xml` (the landing page) and
`/docs/sitemap-0.xml` (all 558 documentation URLs). Adding a page outside
`docs/` means adding it to `web/public/sitemap-0.xml` by hand.

Check the whole surface against a deployed URL with:

```bash
curl -sI -H 'Accept: text/markdown' https://kix.run/docs/tutorials/ | grep -i 'content-type\|vary'
curl -s https://kix.run/docs/tutorials/ | grep 'rel="alternate"'
curl -s https://kix.run/llms.txt | head -3
```

Note that `llms.txt` is close to useless for AI *search* crawlers, which
overwhelmingly ignore it. It earns its place here as a map for coding agents,
which is a separate audience with separate behaviour.
