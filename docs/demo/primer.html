kix: a compiler for Kubernetes

The 60-second version. No code. Just what it does, why it exists, and where it fits into what you already run.

The problem kix solves

Kubernetes configuration is stringly typed. A Service finds its Deployment by matching a label string. RBAC rules reference resource names by string. ConfigMaps are wired to Pods by name. Nothing checks that these strings actually line up — not Helm, not Kustomize, not kubectl.

When one person manages a cluster, they keep the wiring straight in their head. When a team does, mistakes creep in. When you want to let developers deploy their own services, the risk multiplies: a typo in a selector means silent failure at runtime. A missing RBAC rule means a 3am page. A dangling ConfigMap reference means a Pod that never starts.

The usual response is to lock things down — fewer people with deploy access, more review gates, more tickets. That keeps things safe, but it also means developers can't ship without waiting on the platform team.

kix flips this. Instead of restricting who can make changes, it verifies that changes are correct. Developers move fast. The compiler catches their mistakes before anything reaches the cluster.

What kix is

kix is a build tool. You describe your Kubernetes resources in a structured language. kix compiles that description into standard Kubernetes manifests — the same YAML you'd write by hand or generate with Helm.

The difference: during compilation, kix checks that everything fits together. Selectors match. Names resolve. Dependencies exist. RBAC rules reference real resources. If something doesn't line up, you get an error at build time, not at deploy time.

Your config → kix build → Standard K8s manifests → kubectl / ArgoCD / your pipeline The output is plain Kubernetes YAML/JSON. It deploys to any cluster. Nothing changes about your runtime.
Think of it like a compiler for a programming language. You write in a higher-level language. The compiler catches type errors, missing references, and broken contracts. What comes out is the same machine code (Kubernetes manifests) you'd write by hand — just verified.

What kix is not

  • Not a runtime. kix produces manifests. It doesn't run on your cluster, doesn't install agents, doesn't require sidecars. Your cluster runs whatever it runs today.
  • Not an OS change. kix uses Nix as its build engine, but only on the machine that compiles manifests (your laptop, CI). Your nodes stay on whatever OS they're on — Ubuntu, CentOS, Bottlerocket. kix never touches them.
  • Not a replacement for your deployment pipeline. kix outputs manifests. You deploy them however you already do — kubectl, ArgoCD, Flux, a bash script. (kix deploy, currently in development, adds wave ordering and health monitoring on top.)
  • Not an AI product. kix doesn't use AI. It's a deterministic compiler. It does, however, create a verification layer that makes AI-generated configuration safe to deploy — because the compiler checks the output regardless of who or what wrote it.

What it catches

These are real categories of errors that kix prevents at compile time. In traditional YAML workflows, all of them are silent until something breaks in the cluster.

Without kix (runtime failures)

  • Service selector doesn't match any Pod
  • Deployment references a ConfigMap that doesn't exist
  • RBAC rule grants access to a misspelled resource
  • Ingress points to a Service in the wrong namespace
  • Pod mounts a Secret that was deleted last sprint
  • Two teams deploy conflicting NetworkPolicies

With kix (compile-time errors)

  • Selectors are derived from the Deployment — always match
  • ConfigMap is a tracked dependency — must exist
  • RBAC references are checked against the resource graph
  • Cross-namespace references are explicit and verified
  • Every reference is a live dependency — can't dangle
  • Module system merges policies and flags conflicts

The dependency graph

When you reference one resource from another in kix, the compiler tracks that connection. Over an entire cluster, these connections form a dependency graph — a complete map of what depends on what.

This graph enables things that are impossible with flat YAML files:

  • Targeted diffs. Change a ConfigMap → the graph shows you exactly which Deployments are affected. Nothing else.
  • Wave deployments. The graph tells you the correct order: create the ServiceAccount before the Deployment that uses it, the ConfigMap before the Pod that mounts it.
  • Safe rollback. The entire cluster state is a single content-addressed hash. Roll back to a previous hash and you restore every resource, every dependency, every version. Consistently.
  • Drift detection. Recompute hashes, compare with what's running. If they diverge, something changed outside of kix.
This isn't a diagram you draw. The graph is built automatically from your actual references. No annotations, no config files, no manual wiring. If your code references it, the graph tracks it.

How teams use it

kix is built around a simple division: the platform team provides infrastructure and policies, and app teams declare what they need. The compiler wires them together.

Platform team

Sets up shared infrastructure: ingress controllers, cert managers, storage classes, network policies, monitoring. Defines options and defaults that app teams inherit. When the platform team changes the TLS issuer or storage class, every app that depends on it updates automatically — no coordination needed.

App teams

Declare their services and what those services need: a database, a cache, a TLS certificate. They don't hardcode infrastructure names. The compiler resolves their dependencies from whatever the platform team provides. App teams can deploy independently — the compiler ensures their changes don't break anything.

The result

Developers get self-service. Platform teams keep control. Changes from any team are verified against the full cluster state before they're applied. No more "who changed what and did it break something" — the compiler answers that question before deploy.

The Nix question

kix uses Nix as its build engine. This is a deliberate choice: Nix gives kix deterministic evaluation, content-addressed hashing, and a powerful module system for free. But it raises a fair question: do I need to learn Nix?

The short answer: barely. Writing a kix package looks almost identical to writing the Kubernetes YAML you already know. The fields are the same. The structure is the same. The syntax is slightly different (curly braces, semicolons instead of indentation), but the concepts are 1:1 with Kubernetes — not with Nix.

You don't need to know Nix's package manager, NixOS, flakes, derivations, or any of the broader Nix ecosystem. kix uses Nix the language the way TypeScript uses JavaScript — as a foundation, not as a prerequisite.

Migration is gradual. kix can import existing YAML files and Helm charts directly. You can migrate one service at a time. The verification benefits apply to whatever you've moved into kix — everything else continues working as before.

Towards AI

AI can generate Kubernetes configuration faster than any human. But speed without verification is just faster mistakes. Today, there's no tool that checks whether AI-generated manifests are actually correct — whether selectors match, dependencies exist, RBAC rules make sense.

A compiler changes that. Whether a human writes the config or an AI generates it, the compiler catches the same classes of errors. This is what makes kix interesting for the AI future: not that it uses AI, but that it creates a verification layer that makes AI-generated infrastructure safe to review and deploy.

The workflow becomes: AI proposes changes. The compiler verifies them. You review a deterministic diff that shows exactly what will change. That's a trust model that scales — because the trust is in the compiler, not in the AI.

The workflow

1. Build Compile your cluster definition. Merge modules, resolve dependencies, type-check, validate. Output: verified Kubernetes manifests. 2. Diff Compare compiled manifests against the live cluster. See exactly what will change: created, modified, deleted, orphaned. Deterministic — same code always produces the same diff. 3. Deploy Apply verified changes to the cluster. Wave ordering based on the dependency graph. Health monitoring during rollout. Halt on failure. 4. Rollback Point to a previous root hash. The entire previous state is content-addressed — nothing lost. Consistent rollback across all affected resources.
Build works today. Diff is functional. Deploy and rollback are under active development. The compiled manifests can be deployed with any existing tool (kubectl, ArgoCD, Flux) in the meantime.

Common questions

Does kix replace Helm?
It can. kix can also import Helm charts and use them as dependencies alongside native kix packages. You don't have to migrate everything at once.
Does it work with ArgoCD / Flux / my existing GitOps pipeline?
Yes. kix outputs standard Kubernetes manifests. Anything that can apply YAML can deploy kix output.
Does it change anything about my cluster nodes or runtime?
No. kix runs on the build machine only (your laptop, CI). It produces manifests. Your cluster nodes, container runtime, and OS are unaffected.
How is this different from cdk8s / Pulumi / Crossplane?
cdk8s and Pulumi generate manifests from code but don't verify cross-resource correctness — they're code generators, not compilers. Crossplane manages infrastructure from inside the cluster. kix is a build-time compiler that verifies the entire cluster state before anything is applied.
Is this production-ready?
The compiler and manifest generation run in production today. The deployment pipeline (wave ordering, health monitoring, rollback) is under active development.
What's the migration path for a large existing cluster?
Gradual. Import existing YAML and Helm charts. Migrate services one at a time. kix verifies whatever you've migrated; everything else continues unchanged. You start getting value from the first service you move over.
