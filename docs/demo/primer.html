Your cluster is already in a repo.
What if you could compile it?

GitOps got one thing right: your cluster state belongs in git. History, review, rollback, audit trail. Everyone agreed. Everyone does it.

But GitOps put YAML in the repo and called it done. What if instead of syncing files, you could evaluate them — as one program, where the compiler catches what code review misses?

Today

Five tools. None of them talk to each other.

Count the tools between "code" and "running in the cluster." Each one solves one problem and knows nothing about the others.

Helm templates your YAML. It doesn't know what's in the next chart. Kustomize patches it. It doesn't know what the patch breaks. Argo / Flux syncs it. It doesn't know the Service selector is wrong. Kyverno / OPA polices it. It sees one resource at admission time, not the whole picture. You debug it. You are the integration layer.

The Service doesn't know the Deployment exists. The policy engine doesn't know what the app actually needs. Each tool processes its slice in isolation. Consistency across the system? That's your job. That's what breaks.

The result: A typo in a Kustomize overlay passes review, passes sync, passes admission — and surfaces as a runtime failure when someone notices the path to the namespace folder was wrong. You copy-paste a cluster setup to Tokyo and find out weeks later that a label was off. Every cluster should follow the same standards, but keeping three in sync is a manual, error-prone discipline.
The idea

Evaluate everything together.

Not concatenate. Not template-and-patch. Evaluate. As one program. Where every reference between resources is a real reference the compiler can follow.

GitOps said: "The repo is the source of truth." kix says: "Then compile the truth — and verify it's consistent before it ships."

kix puts every resource, every dependency, every team's config, and every policy into one evaluation. The compiler sees all of it at once. That single property is where everything else comes from.

This is the only thing you need to understand. Every feature on this page is a direct consequence of evaluating the entire cluster as one expression. Not a feature that was added — a property that falls out.
Because the compiler sees all resources

Every cross-reference is checked.

A Service references a Deployment's selector. A RoleBinding points to a Role. A Deployment mounts a ConfigMap. Today, nothing checks that these line up. In kix, they're real references inside one evaluation — so of course the compiler catches mismatches.

Today: copy-paste and hope
# deployment.yaml
labels:
  app: api-server
selector:
  matchLabels:
    app: api-server

# service.yaml (separate file)
selector:
  app: api-servr   # ← typo. Passes linting.
                    #   Passes apply. Fails at
                    #   runtime. Silently.
kix: reference, don't copy
deployment = scope.mkResource {
  kind = "Deployment";
  name = "api-server";
  spec.selector.matchLabels =
    { app = "api-server"; };
  # ...
};

service = scope.mkResource {
  kind = "Service";
  spec.selector =
    self.deployment.out.selector;
  # ^ real reference. Compiler
  #   tracks it. Can't mismatch.
};
Not a linter. Not a "best practice." It's a structural property: if the Deployment doesn't exist or the selector changes, the reference breaks and the build fails. Same for ConfigMap mounts, RBAC bindings, ServiceAccount names — every reference you'd normally copy-paste is instead a tracked dependency inside the evaluation.
Because the compiler sees all instances

Packages say what they need. The compiler wires it.

A package declares "I need postgres." The compiler knows every instance in the cluster. It finds one in the same namespace. It injects it. No hardcoded service names. No values.yaml. No wiring code. 

# The package signature declares dependencies — like function arguments
{ scope, lib, postgres, valkey }:

# Use them naturally:
configmap = scope.mkResource {
  kind = "ConfigMap";
  data = {
    DATABASE_HOST = postgres.out.fqdn;       # "postgres.myns.svc.cluster.local"
    CACHE_HOST    = valkey.out.fqdn;         # "valkey.myns.svc.cluster.local"
  };
};
↓
# In the cluster definition, just place them together:
instances.my-namespace = {
  my-app   = { package = packages.my-app;  };
  postgres = { package = packages.postgres; };
  valkey   = { package = packages.valkey;   };
};

# The compiler sees that my-app needs "postgres" and "valkey".
# It finds exactly one of each in the same namespace. Injects them.
# The dependency is tracked in the content-addressed graph.
Swap an implementation? Set an alias: aliases = [ "valkey" ]; on a redis instance. The compiler checks that redis actually provides every field the consumer accesses. If the app uses valkey.out.sentinelPort and redis doesn't have it — the build fails. Structural duck typing, not wishful thinking.
Because all configs enter one evaluation

Teams write independently. The compiler merges.

Each team owns a module. Platform team sets defaults and policy. App teams declare their services. The module system merges everything — list concatenation, conflict detection, priority hierarchy. No shared config file. No coordination tickets.

Platform team
# platform.nix
config = {
  cluster.domain = "prod.example.com";

  # Infrastructure for everyone:
  instances.infra = {
    ingress  = { ... };
    certs    = { ... };
    policies = {
      # reads from ALL team modules
      config.tenants =
        config.tenants;
    };
  };
};
App team
# shop.nix
config = {
  # Declare your tenant:
  tenants.acme.namespaces = [
    "shop-prod"
    "shop-stage"
  ];

  # Declare your services:
  instances.shop-prod = {
    app = {
      package = packages.shop;
      config.replicas = 16;
      # No issuer, no ingress class,
      # no storage class — DI wires it
    };
    postgres = { package = packages.postgres; };
  };
};
Add a namespace? One line in your team's module. Tenant network policies, RBAC, priority classes — all update automatically because they read from the same merged evaluation. Another team adds their namespaces to the same tenant? The module system concatenates the lists. No merge conflict. No PR to the platform team.
Because policy is part of the evaluation

Defaults, overrides, and enforced policy. One system.

No separate policy engine. No admission webhooks racing your deploy pipeline. Policy is a constraint in the build — evaluated alongside everything else. 

# Platform team: overridable default (priority 1000)
config.instances.*.*.config.resources.limits.memory = mkDefault "512Mi";

# App team: overrides it (normal priority — wins over mkDefault)
config.instances.shop-prod.app.config.resources.limits.memory = "1Gi";
# Result: "1Gi"

# Security team: enforced policy (priority 50 — wins over everything)
config.instances.*.*.config.securityContext.runAsNonRoot = mkForce true;

# App team tries to override:
config.instances.shop-prod.app.config.securityContext.runAsNonRoot = false;
# Result: true. mkForce wins. No escape.
Three layers: mkDefault (overridable default) < normal value (team config) < mkForce (enforced policy). Same mechanism NixOS uses to configure an entire Linux distribution. Any use of mkForce by a dev is an auditable signal — you can flag it in review or block it in CI.
Because one evaluation produces one deterministic output

Content-addressed. Diffable. Rollbackable.

The entire cluster compiles to one root hash. Every resource is a content hash. Every dependency is a hash reference. Same input, same output. Always. 

$ kix build prod                        # compile: merge, resolve, validate

$ kix diff prod                         # compare against live cluster

  identical: 187
  modified:    4      ← you review these
  kix-only:    2      ← will be created
  cluster-only: 1    ← orphan (not managed by kix)

  ~ Deployment/coredns
    image: coredns:1.12.3 → coredns:1.13.1
  ~ Service/ingress-public
    externalTrafficPolicy: Local → Cluster

$ kix deploy prod                       # apply in dependency order
Rollback? Point to the previous root hash. The entire previous state is reproducible — every resource, every dependency, every version. Drift? Recompute hashes and compare with what's running. Wave deploy? The dependency graph tells you the correct order. These aren't features. They're consequences of having one deterministic output.
Because the cluster is a program

Three clusters? One definition. Three parameters.

US, EU, Tokyo — each should follow the same standards. Today that's copy-paste. In kix, the cluster is a function. Same structure, different inputs. 

# Shared stack — used by every cluster
baseModules = [
  ./platform.nix         # nginx, metallb, cilium, cert-manager
  ./monitoring.nix       # prometheus, grafana
  ./apps.nix             # your services
];

# Each cluster: same modules, different config
cluster-us = kix.buildCluster {
  name = "prod-us";
  modules = baseModules ++ [{
    cluster.region = "us-east";
    cluster.domain = "us.example.com";
    instances.app-prod.app.config.replicas = 16;
  }];
};

cluster-eu = kix.buildCluster {
  name = "prod-eu";
  modules = baseModules ++ [{
    cluster.region = "eu-west";
    cluster.domain = "eu.example.com";
    instances.app-prod.app.config.replicas = 8;
  }];
};

cluster-tokyo = kix.buildCluster {
  name = "prod-tokyo";
  modules = baseModules ++ [{
    cluster.region = "ap-northeast";
    cluster.domain = "tokyo.example.com";
    instances.app-prod.app.config.replicas = 4;
  }];
};
Update nginx cluster-wide? Edit one line in platform.nix. All three clusters update. The compiler verifies each one independently. Add a service to Tokyo? Add it to the shared modules or to Tokyo's override — either way, the compiler checks that its dependencies exist in that cluster. No more "I copy-pasted the EU setup but forgot to change the label."
The stack replacement

One system instead of five.

kix doesn't add to your stack. It replaces the layers between "code" and "cluster."

You no longer need: Because kix: Helm (templating) Packages are programs, not templates Kustomize (patching) Module system merges with priorities Argo / Flux (sync) kix deploy applies in dependency order Kyverno / OPA (admission policy) Policy is part of the build, not a webhook Manual coordination (glue) One evaluation — the compiler is the glue
Incremental adoption. You don't have to replace everything on day one. kix wraps existing Helm charts — they become tracked resources with full dependency resolution. You can import services that already exist in the cluster without redeploying them. Start with one app. Adopt the next service when you're confident. The out contract is identical between imports, Helm wraps, and native packages — downstream code never changes.

One idea. Everything else follows.

The idea: The entire cluster is one evaluation. Therefore: The compiler sees all resources → cross-references are checked The compiler sees all instances → dependencies resolve automatically All team configs merge into one build → conflicts are caught, not discovered Policy enters the same evaluation → enforcement is structural, not bolted on One evaluation, one output → deterministic diff, rollback, wave deploy Dependencies are references → you get a graph for free

You already centralized the state in git. You already review in PRs. You already want a single source of truth. kix makes the repo actually understand what's in it — instead of being a folder of text files that your sync tool blindly applies.
