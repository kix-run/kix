# 2026-10-03 · `kix/packages/otel-collector` · The package has only been evaluated, never deployed, so its rendered collector configuration is unproven.

`nix build .#cluster-otel-collector` builds, and `otelcol-contrib validate` from the pinned 0.161.0 image accepts both rendered configurations. Run in docker (runc) as uid 10001 with a read-only root filesystem, the gateway configuration answers health on 13133, serves its metrics on 8888, accepts the `otlp_grpc` exporter on an `http://` endpoint with `tls.insecure`, and writes one OTLP JSON line per export to `/dev/stdout`, with its own logs on stderr. Two things are unproven on Kubernetes. The `file/events` exporter reopens `/dev/stdout` by path as uid 10001; that worked under docker, but kind's CRI containerd sets up the pipe itself. The `k8s_objects` receiver has not watched a real API server, so the one-line-per-notification output and `exclude_watch_type = [ "DELETED" ]` rest on reading upstream source. Deploy `clusters/test-otel-collector.nix` on kind with a log shipper, and check that one Event appears as one log line.
