# 2026-11-18 · `kix/lib/flavors/kind.nix` · The kind flavour waits for kind's own CoreDNS even when a managed coredns instance serves DNS.

The flavour declares the `platform-dns` import of `Deployment/coredns` as required. A managed instance that claims the `dns` role does not turn the import off. An upgrade test on 2026-11-13 saw this on a kind cluster created without kubeadm's CoreDNS addon: every deploy waited for `PackageInstance/platform-dns` until it timed out with "import target Deployment/coredns (apiVersion apps/v1) not found". `clusters/test-coredns.nix` sets `platform-dns.optional = true` to deploy at all. The flavour could drop the import when another instance provides `dns`, or mark it optional as the other flavours do, which loses the DNS ordering that 2026-10-02-optional-platform-dns-orders-no-workload.md describes.
- 2026-11-23: the kind flavour now waits for `Service/kube-dns` in `kube-system`, not `Deployment/coredns`. A managed coredns instance named `kube-dns` creates that Service, so the wait passes for it. An instance with another name still waits until the deploy times out. The `platform-dns.optional = true` override in `clusters/test-coredns.nix`, whose instance is `kube-system/kube-dns`, may no longer be needed. Test removing it on a kind cluster.
