# 2026-11-24 · `kix/lib`, `kix plan` · A package cannot mark an option change that destroys data, so check, plan, and deploy say nothing when a nats instance with streams is switched from one server to three.

On kind, `replicas = 3` on a single-server `nats` instance (an earlier version of the package, before the `clustered` option) with two one-replica streams passed `kix check`, and `kix plan` showed only `spec.replicas: 1 → 3` and the new cluster block in nats.conf. The deploy failed after 180 s because the two new servers cannot elect a metadata leader while nats-0 runs standalone, and its advice was to deploy again, which failed the same way. The next restart of nats-0 deleted both streams ("Detected orphaned stream '$G > DATA', will cleanup"). The package cannot see the live replica count, so an assertion cannot refuse the change, and Kix has no way for a package to say "this option moving from A to B loses data" for plan and deploy to compare with the live object and refuse without a confirmation. Other clustered stores with a standalone mode have the same kind of switch. The package now makes the mode its own option, `clustered`, and refuses an availability level that disagrees with it, so raising the level alone stops at `kix check`. Setting `clustered = true` on purpose still passes check and plan with no warning, and the same deploy failure and loss follow. The loss is documented in the nats package header (Limits) and the NATS how-to.
