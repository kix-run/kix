# 2026-11-27 · `cli/kix/src/cluster/activation/features.rs` · `kix deploy --operator-removed` cannot refuse while an older Kix operator still runs.

The flag states that no operator runs, and Kix acts on it: it marks the operator's records `Superseded` or `Failed` and removes `spec.source`, which is the only evidence an operator was involved. If an older operator is mid-deploy, it does not take the deploy lock, so it and the CLI write the same objects at once, and the operator writes the retired annotations back. Nothing detects it afterwards, because `[K9557]` needs a record with `spec.source`. Kix now prints a `kubectl` command that looks for pods named or built from `kix-operator` (`PlanEvent::TookBack` in `cli/kix-cli/src/plan/progress.rs`), which is a guess because Kix ships no operator package and nothing names or labels the operator's Deployment.

Decision required from Adam: ship an operator package with a fixed label and refuse the flag when a Deployment with that label exists in any namespace (one `list` call, needs `list` on Deployments, misses an operator installed another way), or keep the printed check. Refusing while a driven record is `Deploying` unless a second flag is given was rejected, because it is a flag whose meaning depends on state.
