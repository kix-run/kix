# 2026-11-27 · `cli/kix-cli/src/plan/render.rs` · The plan says "this deploy overwrites the field" for an object it will apply without force.

When the plan asks the API server what a forced apply would take and gets no answer (`planner::ask` returns `None`), the run applies the object without force and Kubernetes refuses the conflict. The drift section still prints "this deploy overwrites the field and takes ownership back from ...", because `takes_back` and `conflict_with` look only at the write reason `RevertsDrift`. The dry-run section of the same plan shows a field ownership conflict for that object, so the plan says two opposite things. The same happens when the answer names another Kix cluster. The plan document does not record whether an object has an answer. An optional field on each reverted write ("has an answer") would let the text print the conflict line instead.
