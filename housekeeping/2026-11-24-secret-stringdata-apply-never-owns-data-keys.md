# 2026-11-24 · `cli/kix/src/cluster/secrets.rs` · Kix applies Secret values as `stringData`, so under server-side apply it never owns the `data` keys.

The `kix` field manager owns only `f:stringData.<key>`, a write-only field. When another manager also owned `data.<key>` (Flux's kustomize-controller after a takeover) and that manager's fields are released with an empty apply, Kubernetes deletes `data` and the Secret is empty. Seen moving a Flux SOPS Secret: `kix status` still reported every resource ok, and only `kix plan --reconcile` showed `+ $.data`. The same cause keeps keys on the cluster after they leave the SOPS file, because no manager owns them, so nothing prunes them.

The cause is one decision made in two places. `merge_string_data` (`secrets.rs`) writes SOPS values, and the build writes literal values, into `stringData`. Ownership, pruning, conflicts, and the `kix.run/applied-hash` drift stamp all work on `data`, the field the server stores. `kix status` hashes only what Kix owns, so an emptied `data` leaves the hash unchanged. `owned_view.rs` (`redact_secret`) depends on this split: a SOPS Secret compares equal in `kix plan --read-only` because nothing Kix owns is visible.

Options:

1. Apply `data`. Convert `stringData` to base64 `data` in one place before every apply and dry run (`apply/ssa.rs`), with `stringData` winning a key in both, as the server does. Ownership, pruning of removed keys, conflicts, and status drift then all see the stored field. Costs: `redact_secret` needs a new rule for SOPS keys, whose values the build does not hold (compare presence only, or every SOPS key shows as changed in `kix plan --read-only` and `kix snapshot`). A `data` key another manager changed (`kubectl edit`, an operator, Flux with other values) now stops the deploy with a field ownership conflict where Kix used to overwrite it; that needs a change record. On upgrade, the first deploy applies every Secret again: ownership moves from `stringData.<key>` to `data.<key>` in one apply with equal values, so no key disappears and no pod restarts (the content hash comes from the build). Keys left unowned before the upgrade stay. An older Kix reading a Secret the new one applied would show its SOPS keys as changed in a read-only plan. Proving the ownership move needs a real API server: `FakeApi` does not model `managedFields`, so record fixtures with `cli/kix/tests/fixtures/record.sh` on kind.
2. Keep `stringData` and add a presence check: `kix status` reports a Secret whose live `data` lacks a key Kix applied. Smaller, and it would have flagged the test. It detects the loss after it happens and leaves pruning and conflicts wrong.
3. Send both `data` and `stringData`. Kix would own both, but every diff and drift view would then handle two copies of each value. No better than option 1 and harder to read.

Recommendation: option 1, in its own pull request with recorded fixtures for the upgrade. Until then, release another manager's Secret fields only after checking with `kubectl apply --server-side --dry-run=server` that `data` survives, then run `kix deploy --reconcile`.
