# 2026-11-18 · `kubevirt` `out.mkVirtualMachine` · After an upgrade to v1.9, every Kix apply of an older VM with `dataVolumeTemplates` fails on a field conflict.

When virt-controller v1.9.1 first ran, it rewrote the existing VirtualMachine `demo` with an Update. It added `metadata.creationTimestamp: null` inside each entry of `spec.dataVolumeTemplates`, and so took ownership of that list. Kix applies the list without the null, so the next server-side apply of the VM fails with "virt-controller owns .spec.dataVolumeTemplates" until a deploy runs with `--force-conflicts`. A VM created under v1.9.1 did not show this on kind. Rendering the null in `mkVirtualMachine` would hide it but special-cases one controller's serialization. `ownership.cede` on the field would leave the templates to virt-controller.
