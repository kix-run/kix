# 2026-11-24 · `kix/packages/experimental/external-secrets` · A SecretStore that references its own ServiceAccount cannot take a `kix.cloudIdentity`.

Upstream recommends that each SecretStore name a ServiceAccount of its own (`auth.jwt.serviceAccountRef` for AWS, `auth.workloadIdentity` for Google Cloud, `serviceAccountRef` with `authType: WorkloadIdentity` for Azure), so tenants do not share the controller's role. In this mode the controller reads the ServiceAccount's annotations and requests its token itself (`providers/v1/aws/auth/auth.go`, `providers/v1/gcp/secretmanager/workload_identity.go`, `providers/v1/azure/keyvault/keyvault_new_sdk.go` at v2.15.0). No pod runs as that ServiceAccount, so the cluster's webhook or node agent plays no part. `kix.cloudIdentity.use` and `bind` render the identity through the cluster's mechanism, which does not match this. On EKS Pod Identity the mechanism writes no `eks.amazonaws.com/role-arn`, and the controller then fails with "an IAM role must be associated with service account". With a self-managed IRSA webhook under another `annotationPrefix`, the controller still reads only `eks.amazonaws.com/role-arn`. On a cluster with no mechanism, Kix refuses the identity, though the controller would need none. On Azure the store also needs a tenant ID, from the `tenant-id` annotation or the store's `tenantId`, which `kix.cloudIdentity.azure` leaves optional. Today a user writes the annotations on the ServiceAccount by hand.

Decision required from the maintainer: whether a ServiceAccount that a client reads, rather than one a pod runs as, gets its own render path in `kix/lib/vocab/cloud-identity.nix`, and where a store-level identity would live (an `mkSecretStore` argument, or a package per store). See `v2_discussions/177_workload_cloud_identity.md`.
