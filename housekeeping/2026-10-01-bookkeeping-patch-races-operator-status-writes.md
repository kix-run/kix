# 2026-10-01 · `cli/kix/src/cluster/apply.rs` · The annotation patch kix deploy sends after each apply makes an operator that is already reconciling the object lose its status write.

`apply_resource` applies with server-side apply and then sends a second write, `update_bookkeeping_annotations_checked`, to set `kix.run/activations` and `kix.run/applied-hash`. An operator that read the object between the two writes and stores status with an update (not a patch) gets a conflict. The Infisical operator logs "Could not set condition for IsReady", filters metadata-only events (`GenerationChangedPredicate`), and does not retry soon: an InfisicalConnection retries after five minutes, which is the deploy's 300s readiness ceiling (`HARD_CEILING` in `readiness.rs`), and an InfisicalAuth that authenticated is not retried at all. A fresh kind deploy of `infisical-operator` failed this way until the package stopped making its connection wait for the Deployment. The race remains in three places: a deploy that changes `address` for a running operator, a connection built from `out.crds.InfisicalConnection`, and every InfisicalAuth built with `mkInfisicalAuth`, which is applied while the operator runs. An auth that loses its IsReady also blocks the InfisicalStaticSecret that names it, because the operator refuses to sync until the auth is ready (`infisicalstaticsecret/reconciler.go:255-258`). Restarting the operator recovers. Seen on kind with kix-0.1.0 from rework/w0, operator v0.11.10; the auth case is inferred from the operator source, since it needs an Infisical identity.
