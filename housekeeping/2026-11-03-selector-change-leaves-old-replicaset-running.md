# 2026-11-03 · `kix/packages/velero/workloads.nix` (and any Deployment whose selector changes) · A Deployment replaced for a selector change left its old ReplicaSet running, so two Velero servers ran side by side for a month.

On one cluster the velero package's Deployment gained `app.kubernetes.io/component` in `spec.selector.matchLabels`. A selector cannot change in place, so the Deployment was deleted and created again. Its old ReplicaSet had no owner afterwards and kept its pod: Velero 1.15.2, beside the package's 1.18.4. Both servers ran every scheduled backup, each made its own VolumeSnapshot and DataUpload for every volume, and every backup ended PartiallyFailed with `more than one DataUpload found operationID`.

It is not known whether `kix deploy` or a person deleted the Deployment, or with which propagation policy. Check what `kix deploy` does when a change needs a workload to be replaced. If it deletes the workload, it should let the deletion cascade to the ReplicaSets, or name what it leaves behind. Find leftovers with `kubectl get rs -A -o json | jq -r '.items[] | select(.metadata.ownerReferences == null) | .metadata.namespace + "/" + .metadata.name'`.
