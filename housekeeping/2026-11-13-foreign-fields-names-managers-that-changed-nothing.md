# 2026-11-13 · `cli/kix/src/cluster/drift.rs` · `kix status` still names a manager for a field Kix never applied, because nothing on the live object says which fields Kix applied.

`kix status` names a manager in its "changed since deploy" line, and adds `--force-conflicts` to its `Next:` line, from the `unshared_paths` of each manager: the fields it owns that Kix's `Apply` entry does not also own. That leaves out managers that share every field with Kix, because a shared field still holds Kix's value. It does not leave out a field that Kix never applied. For example, kubeadm may own a field of the coredns ConfigMap from before Kix took the object, and the build may not set that field. Status still names kubeadm, and still suggests `--force-conflicts`, although a deploy would not conflict on that field. Status reads no build, and the applied-hash stamp records a hash, not the fields Kix applied. `kix plan` and `kix diff` do not have this problem, because `plan::origin::live_drift` keeps only fields the new build sets. To fix it in status, a deploy would have to record which fields it applied, for example in the Activation record, which is a change to cluster state.
