# 2026-11-26 · `kix/packages/experimental/stackgres-operator` · Prune deletes the StackGres operator before its webhook configurations.

The package renders `validatingWebhook` and `mutatingWebhook` with metadata only, because the operator writes the entries. The operator Deployment `requires` both configurations, and the operator Service depends on the Deployment's selector. So prune deletes the Deployment and the Service first, then the configurations. For a moment the API server calls webhooks with no pods behind them, and any create or update of a StackGres kind fails (`failurePolicy: Fail`). The webhook Service edge in `graph::dependency_pairs` cannot help, because the manifest names no Service. Adding `requires = [ self.operatorService ]` to the configurations alone makes a cycle with the Deployment's `requires`.

Option A: drop the Deployment's `requires` on the configurations and make each configuration require `operatorService`. Upstream allows this. In StackGres 1.19.5 (tag commit `003e92b0`), `stackgres-k8s/src/operator/src/main/java/io/stackgres/operator/app/CrdWebhookInstaller.java` looks each configuration up with `findByName(operatorName)`, creates it when it is missing, and updates it when it exists. The upstream Helm chart also renders both configurations. The cost: the operator may then start before the configurations exist, so its ClusterRole needs `create` on ValidatingWebhookConfigurations and MutatingWebhookConfigurations. Kubernetes RBAC cannot limit `create` by name, so the operator gets the right to create any webhook configuration in the cluster. Branch `fix/stackgres-webhook-order` (commit `9a2b069c`) builds option A with a library test, untested live.

Option B: keep the current order and accept the window. It lasts only while the operator is being removed, when admission failures for its own kinds matter little. On 2026-11-26 the team lead chose option B. Widening the operator's rights is the maintainer's decision.
