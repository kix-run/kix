a kubernetes compiler · dependency injection at work

You declare intent. DI resolves the rest.

You never wire the cluster. Each package asks for roles ("a database", "a queue", "expose me", "scrape me") and dependency injection binds every one by rule, propagates each app's constraints down into whatever fills the role, and resolves concrete facts up. Nothing below the apps was declared: required-dep resolution auto-instantiated the shared Postgres, the gateway, the monitoring stack and the whole platform floor. Hundreds of these bindings and constraints settle the same way. Toggle apps, flip to resolution, or clash a constraint on the shared database.

Ask for a role, not an instance. A request resolves by a ladder: explicit › same-namespace › cross-namespace › auto-instantiate › else error.
Constraints flow along the bindings. Each consumer injects config into the role it asked for; the dep forwards it on.
Declare intent, derive mechanism. Deploy waves, HTTPRoutes, ServiceMonitors, network policy — all derived from the edges.
Told at compile time. An ambiguous bind, or a clash on a shared stateful resource, is an error before anything is applied.
the same resolution · why kix evaluates it twice

Two fixpoints: config settles first, then values.

A consumer doesn't just read its dependency, it pushes config into it — and that config is computed from the consumer's own config. But the consumer's value is computed from the dependency. Do both at once and you get a loop with no first move. So kix splits the solve in two: resolve all config to a fixed point as pure data, freeze it, then resolve all values to a fixed point against that frozen config. Watch the loop deadlock, then watch the split untie it.

Press run. Or hit "naive: one pass" to see why a single fixpoint can't work.

Why two and not one. A function-shaped dep config injection reads the consumer's evaluated config and projects it into the dependency (a database forwarding extensions to its postgres). To resolve it inside the build fixpoint you'd need the consumer's full view, which needs its build, which needs its dependencies, which for a database loops back to the postgres being injected into. Stack overflow. Phase ① computes config only — no build, no deps, just data flowing along injections — so the loop never forms. Phase ② then builds against config that is already frozen. (There is a third closure before either: required dependencies with no instance are auto-instantiated, which is how the whole platform floor above came to exist.)
