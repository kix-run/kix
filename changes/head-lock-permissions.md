Kix now installs and updates its own four CustomResourceDefinitions (`activations.kix.run`, `packageinstances.kix.run`, `activationheads.kix.run`, and `packageinstancerevisions.kix.run`) before it changes a cluster. Before upgrading, grant every Kubernetes account that runs `kix deploy`, `kix rollback`, `kix gc`, or `kix migrate domain`, and the Kix operator's account, `get` on those four CRDs. The account that runs the first upgraded Kix on a cluster also needs `create` on `customresourcedefinitions` to install the CRDs that are missing, and `update` on them when a later Kix brings a newer definition. Grant every such account `get`, `list`, `create`, and `update` on `activationheads.kix.run`, which holds the deploy lock, and `get`, `list`, `create`, `patch`, and `delete` on `packageinstancerevisions.kix.run`, plus `patch` on `packageinstancerevisions/status`, which list the objects each deploy applied. An account that only runs `kix plan` needs `list` on `activationheads.kix.run` and on `packageinstancerevisions.kix.run`. `kix plan` and `kix deploy` read each object of a kind the account may not list one at a time, and stop when the account may neither list nor get it, naming the kinds. If you use operator mode, upgrade the Kix operator before you run the upgraded Kix against its cluster, because an older operator writes the retired annotations `kix.run/activations` and `kix.run/applied-hash` back onto every object it applies. Commands stop before changing anything when these permissions are missing, reporting `[K9557]` when Kix cannot read, create, or update one of its CRDs. Every command that takes the deploy lock stops with `[K9557]` while the installed operator does not list `revisions` in `kix.run/operator-features` on `activations.kix.run`, and `--operator` commands also stop until it lists `requests` and `head-lock`. An operator from Kix 0.9 or earlier lists no features, so Kix cannot detect it and you must upgrade it first.
