Before upgrading, update RBAC for every Kubernetes account that runs Kix commands (and for the Kix operator, if you use operator mode), and upgrade the Kix operator before running Kix against its cluster. Kix now installs and updates its four internal CustomResourceDefinitions (`activations.kix.run`, `packageinstances.kix.run`, `activationheads.kix.run`, and `packageinstancerevisions.kix.run`) before modifying a cluster. Every account that runs `kix deploy`, `kix rollback`, `kix gc`, or `kix migrate domain`, as well as the Kix operator's ServiceAccount, needs `get` on those four CRDs, `get`, `list`, `create`, and `update` on `activationheads.kix.run`, and `get`, `list`, `create`, and `delete` on `packageinstancerevisions.kix.run` (plus `patch` on `packageinstancerevisions/status`); the account that first runs one of those commands or the operator on a cluster after upgrading also needs `create` on `customresourcedefinitions` to install missing CRDs, and whichever account runs a later version of Kix with newer CRD definitions needs `update` on `customresourcedefinitions`. Read-only `kix plan` accounts need `list` on `activationheads.kix.run` and `packageinstancerevisions.kix.run`, plus either cluster-wide `list` or namespaced `get` on every resource kind in the build. Commands stop with `[K9557]` before changing anything if these permissions are missing, if `--operator` is used before the operator reports `requests`, `head-lock`, and `revisions` in `kix.run/operator-features` on `activations.kix.run`, or, before planning, if that Kix cluster has a current, queued, or deploying deployment record submitted to the operator while `activations.kix.run` does not list `revisions` in `kix.run/operator-features` (which happens when an older operator is installed, including Kix 0.9 or earlier, or when the operator was uninstalled; if you uninstalled the operator, run `kix deploy <cluster> --operator-removed` once). Other Kix clusters on the same Kubernetes cluster are unaffected.
