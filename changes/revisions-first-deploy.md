The first deploy of each Kix cluster with this version moves it to the new bookkeeping. Before it writes any object, the deploy, or the Kix operator's next deploy or drift repair, gives each deployment record an earlier version wrote, and that a later deploy still needs, `PackageInstanceRevision` objects of what the record deployed: it creates the revisions and then writes one change to each record. The deploy then rewrites the metadata of each object of the Kix cluster once: it renames the object's field manager `kix` to `kix/<cluster>` and removes the annotations `kix.run/activations` and `kix.run/applied-hash`. The plan says how many objects it rewrites in a line that starts with `Upgrade:`, and `kix plan -o json` gives the number as `metadata_rewrites`. Controllers that copy an object's annotations into its Pods may restart those Pods once. The same deploy applies again each unchanged object that has no `kix.run/applied-hash` annotation, and an object that cedes fields with `ownership.cede` can show once as changed on the cluster, because Kix now leaves ceded fields out of the hash of what it applied. If the first deploy stops part way, the records it gave revisions stay readable, and the next deploy finishes rewriting the metadata. Do not run `kix gc` with an earlier version on a Kix cluster this version has deployed: an earlier `kix gc` reads the removed annotations and can delete objects that are still deployed. If an earlier version of Kix deploys the Kix cluster anyway, the next deploy with this version moves it again.
