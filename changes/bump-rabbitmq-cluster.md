`rabbitmq-cluster` runs RabbitMQ 4.4.1 instead of 4.3.6. The first deploy after you upgrade restarts the RabbitMQ pods one at a time, and queues, messages, users, and policies stay. You cannot go back: RabbitMQ does not support a downgrade, and 4.3.6 fails to start on data that 4.4.1 has written. To keep a way back, export the definitions and back up the volumes before you upgrade. RabbitMQ 4.4 changes some behavior. An OAuth 2 setup whose identity provider serves `http://` endpoints, or whose `issuer` does not match its discovery URL (such as Cloud Foundry UAA), fails to authenticate until you set `auth_oauth2.discovery.verify_issuer` or `auth_oauth2.discovery.verify_https_endpoints` to `false` in `settings`. The HTTP API replaces `GET /api/auth/hash_password/{password}` with `POST /api/auth/hash_password`. A passive declare of a queue or an exchange now needs one of the configure, write, or read permissions on it. The operator does not enable the new feature flag `rabbitmq_4.4.0`, so run `rabbitmqctl enable_feature_flag all` in a RabbitMQ pod before the next minor upgrade.
