Existing `external-secrets` instances need no changes. `packages.experimental.external-secrets` now accepts a cloud identity on `deps.controllerCredentials` (`kix.cloudIdentity.aws`, `kix.cloudIdentity.gcp`, or `kix.cloudIdentity.azure`) so the External Secrets controller can authenticate through its ServiceAccount. Kix writes the cloud's annotations and pod labels on the controller and restarts its pods when the identity changes. To use that identity in a `SecretStore` or `ClusterSecretStore`, leave `auth` unset on AWS (`aws`) and Google Cloud (`gcpsm`) stores, or set `authType = "WorkloadIdentity"` without `serviceAccountRef` on Azure (`azurekv`) stores. `out.mkSecretStore` and `out.mkClusterSecretStore` fail evaluation if a store using the controller's identity targets a different cloud. Because every store configured this way shares the controller's role, any namespace allowed to create a `SecretStore` can read whatever secrets that cloud role can access. `deps.controllerCredentials` rejects Secret instances; to use static keys, reference a Secret in the store's `spec` (`auth.secretRef` on AWS and Google Cloud, or `authSecretRef` on Azure). For a store that references its own ServiceAccount (`auth.jwt.serviceAccountRef` on AWS, `auth.workloadIdentity` on Google Cloud, or `serviceAccountRef` on Azure), set the cloud annotation (such as `eks.amazonaws.com/role-arn`) directly on that ServiceAccount rather than using `kix.cloudIdentity`. The package also publishes the controller identity's cloud (`"aws"`, `"gcp"`, `"azure"`, or `null`) as `out.identityCloud`.
