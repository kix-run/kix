Existing `external-secrets` instances need no changes. `packages.experimental.external-secrets` now accepts a cloud identity on `deps.controllerCredentials` (`kix.cloudIdentity.aws`, `kix.cloudIdentity.gcp`, or `kix.cloudIdentity.azure`) so the External Secrets controller can authenticate through its ServiceAccount. Kix writes the required ServiceAccount annotations and pod labels on the controller and restarts the controller pods when the identity changes. To use that identity in a `SecretStore` or `ClusterSecretStore`, leave `auth` unset on AWS (`aws`) and Google Cloud (`gcpsm`) stores, or set `authType: WorkloadIdentity` without `serviceAccountRef` on Azure (`azurekv`) stores. `out.mkSecretStore` and `out.mkClusterSecretStore` reject such a store when its cloud differs from the controller identity's cloud. Every store configured this way shares the controller's identity, so any namespace that can create a `SecretStore` can read whatever that cloud role can read. `deps.controllerCredentials` rejects Secret instances; for static keys, reference a Secret in the store's `spec` (such as `auth.secretRef` on AWS and Google Cloud, or `authSecretRef` on Azure). For a store that names its own ServiceAccount (`auth.jwt.serviceAccountRef` on AWS, `auth.workloadIdentity` on Google Cloud, or `serviceAccountRef` on Azure), set the annotations External Secrets expects (such as `eks.amazonaws.com/role-arn`) directly on that ServiceAccount instead of using `kix.cloudIdentity`. The package also exposes the controller identity's cloud (`"aws"`, `"gcp"`, `"azure"`, or `null`) as `out.identityCloud`.
