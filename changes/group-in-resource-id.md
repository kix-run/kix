No cluster configuration changes are needed, unless you deploy from a saved plan file (`kix deploy --plan`) created by an earlier version of Kix that deletes resources outside the core `v1` API group; regenerate those plan files with `kix plan <cluster> --out <file>` using the same flags. Kix now tracks each resource's API group alongside its kind, namespace, and name, fixing a bug where `kix deploy`, `kix plan`, `kix rollback`, `kix gc`, and the Kix operator looked up APIs by kind alone and could read, update, or delete an object in the wrong API group (such as `Job` in `batch` versus `batch.volcano.sh`). For resources outside the core `v1` API group, resource IDs in `kix deploy --log-format json`, `objects.writes` and `objects.deletes` in `kix plan`, and `PackageInstanceRevision` records now include a `group` field. For deployment records written by earlier versions without API groups, if a resource is missing or replaced and multiple API groups serve its kind, `kix status` marks it as not checked (`present: "ambiguous"` in JSON and YAML); run `kix deploy <cluster> --reconcile` or deploy a change to record the API groups. `kix plan`, `kix deploy`, and `kix rollback` stop and refuse a change that moves a resource to a different API group while keeping the same kind, namespace, and name, because plans do not yet include the API group in resource names; instead, first deploy a build that removes the resource, then deploy a build that adds it in the new API group.
