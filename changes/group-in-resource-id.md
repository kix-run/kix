No changes to cluster configurations are needed. If you saved a plan file with an earlier version of Kix and that plan deletes objects outside the core `v1` API group, `kix deploy --plan` no longer accepts it. Save a fresh plan with `kix plan <cluster> --out <file>` using the same flags as before, such as `--prune`. Other saved plans still work. Kix now includes the API group when identifying Kubernetes objects, so it distinguishes kinds that share a name across API groups, such as `Job` in `batch` and `Job` in `batch.volcano.sh`. Previously, `kix deploy`, `kix plan`, `kix rollback`, `kix gc`, and the in-cluster operator looked up Kubernetes APIs by kind alone and could read, update, or delete an object in the wrong API group. For objects outside the core `v1` API group, resource IDs in `kix deploy --log-format json` and entries in `objects.writes` and `objects.deletes` in `kix plan` output and saved plans now include a `group` field. The `PackageInstanceRevision` objects a deployment record names also store each object's API group. Older deployment records do not include API groups. If an object from an older record is missing or replaced and multiple API groups serve its kind, `kix status` marks it as not checked, with `present` set to `ambiguous` in `-o json` and `-o yaml`. Run `kix deploy <cluster> --reconcile` or deploy a change to record the API groups. `kix plan`, `kix deploy`, and `kix rollback` refuse a change that moves an object to another API group while keeping the same kind, namespace, and name, because plans do not yet include the API group in object names. First deploy a build that removes the object, then deploy a build that adds it in the new API group.
