If you saved a plan file with an earlier version of Kix and that plan deletes objects outside the core `v1` API group, `kix deploy --plan` no longer accepts it. Save a fresh plan with `kix plan <cluster> --out <file>` and the same flags as before, such as `--prune`. Other saved plans still work, and you do not need to change your cluster configuration. Kix now includes the API group when identifying Kubernetes objects, so it distinguishes resource kinds that share a name across API groups, such as `Job` in `batch` and `Job` in `batch.volcano.sh`. Before, `kix deploy`, `kix plan`, `kix rollback`, `kix gc`, and the in-cluster operator looked up APIs by kind alone and could read, update, or delete an object in the wrong API group. For objects outside the core `v1` API group, resource IDs in `kix deploy --log-format json` and entries in a plan's `objects.writes` and `objects.deletes` lists now include a `group` field. `status.packageIndex` on `Activation` records also adds a `groups` map for those objects. Deploy records written by earlier versions of Kix do not list API groups. If that deploy's version of an object is not on the cluster and multiple API groups serve its kind, `kix status` marks the object as not checked, with `present` set to `ambiguous` in `-o json` and `-o yaml`. Run `kix deploy <cluster> --reconcile` or deploy a change to record the API groups.
