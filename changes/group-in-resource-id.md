If you have a plan file saved by an earlier version of Kix and that plan deletes objects outside the core `v1` API group, `kix deploy --plan` no longer accepts it. Save a fresh plan with `kix plan <cluster> --out <file>`, with the flags you used before, such as `--prune`. You do not need to change your cluster configuration. Kix now includes the API group when identifying Kubernetes objects, so it distinguishes resource kinds that share a name across API groups, such as `Job` in `batch` and `Job` in `batch.volcano.sh`. Previously, `kix deploy`, `kix plan`, `kix rollback`, `kix gc`, and the in-cluster operator looked up an object's API by kind alone. When a cluster had two kinds with the same name, they could read, update, or delete the object in the wrong API group. Resource IDs in `kix deploy --log-format json` and entries in a plan's `objects.writes` and `objects.deletes` lists now include a `group` field, and `status.packageIndex` on `Activation` records adds a `groups` map. Both omit the core `v1` API group. When Kix reads records, logs, or plans from earlier versions, it treats objects without a recorded group as core `v1` objects.
