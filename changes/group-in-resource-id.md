If you saved a plan file with an earlier version of Kix and that plan deletes resources outside the core `v1` API group, `kix deploy --plan` rejects it. Save a fresh plan with `kix plan <cluster> --out <file>` using the same flags. Other saved plans and all cluster configurations work without changes. Kix now includes each resource's API group alongside its kind, namespace, and name. Previously, `kix deploy`, `kix plan`, `kix rollback`, `kix gc`, and the Kix operator looked up APIs by kind alone and could read, update, or delete an object in the wrong API group (such as `Job` in `batch` versus `batch.volcano.sh`). For resources outside the core `v1` API group, resource IDs in `kix deploy --log-format json`, entries in `objects.writes` and `objects.deletes` in `kix plan`, and `PackageInstanceRevision` objects now include a `group` field. On deployment records written by earlier versions without API groups, if a resource is missing or replaced and multiple API groups serve its kind, `kix status` marks it as not checked (`present: "ambiguous"` in JSON and YAML). Run `kix deploy <cluster> --reconcile` or deploy a change to record the API groups. `kix plan`, `kix deploy`, and `kix rollback` refuse a build that moves a resource to another API group while keeping the same kind, namespace, and name, because plans do not yet include the API group in resource names. First deploy a build that removes the resource, then deploy a build that adds it in the new API group.
