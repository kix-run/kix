Kix now keeps what each deploy did in `PackageInstanceRevision` objects (`packageinstancerevisions.kix.run`) instead of in annotations on every deployed object. A revision lists the objects one build makes for one package instance by build hash, API group, kind, namespace, and name, and records in `status.applied` the hash of what Kix last applied to each of them. Each Kix cluster also has a revision for the objects that belong to no package instance, such as Namespaces, and one for the objects that deploys without `--prune` left on the cluster. A revision's name is the Kix cluster's name and a hash of its list, and Kubernetes refuses a change to the list. A deployment record names its revisions in `status.revisions`, and a deploy that leaves a package instance unchanged names the revision the previous deploy created. Kix keeps only the revisions that the current record, a deploy in progress or queued, and a `Failed` or `Partial` record still need, and deletes the rest when a deploy finishes and in `kix gc`. Run `kubectl get packageinstancerevisions -l kix.run/cluster=<cluster>` to list a Kix cluster's revisions. A deploy no longer writes to objects it does not change. `kix plan` and `kix deploy` now decide from the live objects and the revisions what to write, and each entry in `objects.writes` of `kix plan -o json` says in `reason` why Kix writes an object whose build did not change. `kix status` names an object that is missing from the cluster on any machine, including one that does not have the build. If a Kix cluster's list of objects kept from earlier deploys is missing or cannot be read, `kix gc --full-scan` builds it again from the live objects this Kix cluster applied that no other deployment record names. A package instance with more objects than one revision can hold, about 6,500, is refused before anything is applied.
