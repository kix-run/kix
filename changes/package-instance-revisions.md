Kix now tracks deployed objects and their applied hashes in cluster-scoped `PackageInstanceRevision` resources (`packageinstancerevisions.kix.run`) instead of writing per-deploy annotations onto every object, so deploys no longer touch unchanged resources. Each `Activation` record references its revisions in `status.revisions` (one per package instance, one for cluster-level resources, and an optional one for kept orphans), reusing existing revisions for unchanged instances, and `kix deploy` and `kix gc` clean up revisions that no active, queued, deploying, `Failed`, or `Partial` record needs (inspect them with `kubectl get packageinstancerevisions -l kix.run/cluster=<cluster>`). In `kix plan -o json`, each entry in `objects.writes` for an unchanged build manifest now includes a `reason` field (`applied_by_record`, `left_by_degraded`, `applied_hash_missing`, `reverts_drift`, or `held_by_other_cluster`), conflicts with another Kix cluster appear under `admission` with reason `kix_cluster_conflict`, and Kix's custom resources appear under `not_checked` with reason `crd_installed_by_kix` when the Kubernetes cluster does not yet serve Kix's CRDs (which `kix deploy`, `kix rollback`, `kix gc`, `kix migrate domain`, and the Kix operator install before modifying the cluster). `kix status` now detects missing objects even on machines without the deployed build, and `kix gc --full-scan` rebuilds a missing or unreadable kept-orphans revision from the live objects this Kix cluster applied that no other deployment record of the cluster lists and that are not in the compared build. Package instances with more than roughly 6,500 objects (or pre-0.6 deployment records without a package index that exceed Kubernetes's 1.5 MiB object size limit) are refused before applying; if Kix applies resources but fails to save their applied hashes, the deploy stops before finalizing so the next deploy can record them and finish.
