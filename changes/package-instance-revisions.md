Kix now records deployed objects and their applied hashes in cluster-scoped `PackageInstanceRevision` resources (`packageinstancerevisions.kix.run`) instead of patching tracking annotations onto every object. As a result, deploys no longer modify unchanged resources, and `kix status` can name missing objects even on machines without the deployed build. Each `Activation` record links its revisions in `status.revisions` (one per package instance, one for cluster-level resources, and an optional one for kept orphans), reusing existing revisions for unchanged instances. `kix deploy` and `kix gc` delete revisions that no active, queued, deploying, `Failed`, or `Partial` record references. You can list a cluster's revisions with `kubectl get packageinstancerevisions -l kix.run/cluster=<cluster>`. If the kept-orphans revision is missing or unreadable, `kix gc --full-scan` rebuilds it from live objects applied by this Kix cluster that are absent from both the compared build and the cluster's other revisions.

In `kix plan -o json`, `objects.writes` entries for manifests that did not change in the build now include a `reason` field (`applied_by_record`, `left_by_degraded`, `applied_hash_missing`, `reverts_drift`, or `held_by_other_cluster`). Conflicts with another Kix cluster appear under `admission` with reason `kix_cluster_conflict`. On clusters where Kix has not yet installed its CustomResourceDefinitions, Kix's custom resources appear under `not_checked` with reason `crd_installed_by_kix`. Kix stops before applying if a single revision exceeds Kubernetes's 1.5 MiB object size limit (roughly 6,500 objects in one package instance, or across a pre-0.6 deployment record without a package index). If Kix applies resources but fails to save their applied hashes, the deploy stops before finalizing so the next deploy can record them and finish.
