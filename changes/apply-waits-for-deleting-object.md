`kix deploy`, `kix rollback`, and the Kix operator now wait for an object that is already being deleted on the cluster to finish deleting before recreating it from the build. Previously, Kix applied changes onto the deleting object (one with a `deletionTimestamp`, usually waiting on a finalizer) and reported success even though Kubernetes was about to remove it. Because the old object is deleted first, the replacement starts empty and keeps none of the old object's data (for example, a PersistentVolumeClaim starts with an empty volume). If the old object is still on the cluster when the wait times out, the run fails with `[K2794]` and does not create the replacement. `kix plan` warns about these objects in text and Markdown output and records them under `being_deleted` (`resource`, `since`, `finalizers`, `holds_data`) in the plan file, flagging any object that may hold data.
