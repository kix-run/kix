If `kix deploy`, `kix rollback`, or `kix gc` now fails with `[K2794]`, a deleted object is still on the cluster waiting on a finalizer or a slow shutdown. If cleanup is still running normally, run the command again later or pass a longer `--timeout` to `kix deploy` (up to `5m`). If a finalizer is stuck, check that its controller or operator is running, or run the `kubectl patch` command in the error message to remove the finalizer and skip its cleanup, then run the Kix command again. Previously, Kix counted an object as deleted as soon as Kubernetes accepted the delete request. Now Kix deletes independent objects in parallel and waits for each deleted object to be removed from the cluster. It fails with `[K2794]` and exit code 1 if an object goes `--timeout` without a finalizer being removed (3 minutes by default; 5 minutes in the Kix operator) or reaches 5 minutes in total. During pruning or `kix gc`, Kix keeps any orphaned resources that the build records as dependencies of the stuck object and retries them on the next run (most packages do not yet record that a custom resource depends on its operator). When `kix deploy` (for a changed object, or with `--reconcile`) or the Kix operator applies an object that is being deleted, it now waits for deletion to finish and creates the object again, and `kix status` reports any deleting object as not ready (exit code 2). When an Activation record is deleted in operator mode and a resource remains on the cluster, the Kix operator keeps its finalizer on the record and retries every 30 seconds. `kix gc` and the Kix operator also now delete resources with `Background` propagation like `kix deploy --prune`, so deleting a Job or ReplicationController deletes its pods too. In `--log-format line`, Kix now prints `will be deleted` instead of `still on the cluster` when listing objects to prune, and `deleted` instead of `ready` once each pruned object is gone.
