If `kix deploy`, `kix rollback`, or `kix gc` fails with `[K2794]`, a deleted object is still on the cluster waiting for a finalizer or a slow shutdown. If cleanup is still running normally, wait for it to finish and run the command again, or pass a longer `--timeout` to `kix deploy` (up to `5m`). If a controller's finalizer is stuck, check that the controller is running, or run the `kubectl patch` command in the error message to remove the finalizer and skip its external cleanup. When a built-in Kubernetes finalizer protects an object still in use (such as `kubernetes.io/pvc-protection`), the error explains what holds the object and omits the removal command. Previously, Kix counted an object as deleted as soon as Kubernetes accepted the delete request. Kix now waits for each deleted object to disappear from the cluster (during `--prune`, `kix gc`, and in-place recreates, or when applying an object that is already being deleted), and fails with `[K2794]` and exit code `1` if an object goes `--timeout` without losing a finalizer (3 minutes by default in `kix deploy`, `kix rollback`, and `kix gc`; 5 minutes in the Kix operator) or reaches 5 minutes in total. During pruning and `kix gc`, if an object stays on the cluster after a delete attempt, Kix keeps any orphaned resources that the build records as its dependencies and retries them on the next run (most packages do not yet record that a custom resource depends on its operator). `kix status` now reports any deleting object of the cluster, including ones not in the current deploy, and exits with code `2`. In operator mode, if a resource stays on the cluster when an Activation record is deleted, the Kix operator keeps its finalizer on the record, posts a `DeletionUnfinished` Warning Event, and retries.
