Existing `velero` instances using a Secret need no changes. `velero` now accepts a cloud identity in `deps.cloudCredentials` (`kix.cloudIdentity.aws`, `kix.cloudIdentity.gcp`, or `kix.cloudIdentity.azure`, matching `backupStorageLocation.provider`) so Velero authenticates through its `<instance>-server` ServiceAccount instead of a Secret. That ServiceAccount is shared by the server, the node agent, and the backup, restore, data-mover, and maintenance pods Velero launches. With a cloud identity, Kix omits the credentials file mount and leaves `credential` unset on the backup and snapshot locations, so Velero's plugins use default cloud SDK credentials. On AKS, Kix also adds the `azure.workload.identity/use: "true"` label to the server, the node agent, and `podLabels` in `nodeAgent.settings` and `repositoryMaintenance.settings`. With `kix.cloudIdentity.gcp`, set `backupStorageLocation.config.serviceAccount` to the Google service account email that signs download URLs. With `kix.cloudIdentity.azure`, set `backupStorageLocation.config.storageAccount` plus either `useAAD = "true"` or both `resourceGroup` and `subscriptionId`. Azure `volumeSnapshotLocation` is unsupported with a cloud identity because the Azure snapshot plugin requires a credentials file. Evaluation also fails when a cloud identity is combined with an in-cluster `objectStorage` dependency or with a `volumeSnapshotLocation` for another cloud.
