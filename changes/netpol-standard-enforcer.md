Existing GKE clusters need no configuration changes; the next deploy adds a `platform-network-policy` import record in `kube-system` (`gke-managed` on Autopilot). GKE clusters (`kix.flavors.gke` and `kix.flavors.gke-autopilot`) can now set `networkPolicy.enable = true` to generate standard Kubernetes `NetworkPolicy` objects for GKE Dataplane V2, and reject `cilium` instances because Dataplane V2 already enforces network policy. When you enable `networkPolicy.enable = true` on GKE, set `cluster.network.apiServer.cidrs` to the control plane endpoint `/32` addresses if any policy needs API server egress (such as for a workload bound to a `Role` or `ClusterRole`), and set `cluster.network.nodeCidrs` to your node IP ranges if any rule targets nodes (for example, Prometheus scraping `node-exporter`). `kix check` stops and names any required option that is missing. `cluster.network.apiServer.sources` defaults to the `konnectivity-agent` pods in `kube-system`. When a generated `NetworkPolicy` allows broader traffic than intended, Kix records the reason codes in `kix.run/network-policy-widened` and checks them with the new `security.networkPolicyWidened` scorecard rule: `kix check` warns when setting a `cluster.network` option would narrow a rule, and `kix check -v` lists platform limits as `info` findings. Selector validation (check 12) now skips Kix-generated `NetworkPolicy` objects (`kix.run/derived: "true"`), and the `hostNetwork` workload warning now refers to network policy in general instead of `CiliumNetworkPolicy`. Cluster-level scorecard rules now receive `derivedResources`, and setting `detail = true` on a finding reports it at `info` severity.
