Existing EKS clusters need no changes. EKS clusters (`kix.flavors.eks`) can now generate standard Kubernetes `NetworkPolicy` objects for the Amazon VPC CNI add-on. To turn this on, enable `enableNetworkPolicy` in the Amazon VPC CNI add-on configuration, then set `cluster.flavor.eks.networkPolicy = "vpc-cni"` and `networkPolicy.enable = true` (leaving `cluster.flavor.eks.networkPolicy` at `"none"` with `networkPolicy.enable = true` fails the build with setup instructions). Set `cluster.network.serviceCidr` so Kix derives the API server egress address automatically and excludes Service IPs from outbound external (`world`) rules; while `serviceCidr` is unset, `security.networkPolicyWidened` warns on policies with external egress rules, and API server egress requires `cluster.network.apiServer.cidrs`. When policies need them, also set `cluster.network.apiServer.sources` to the control plane subnets for admission webhooks and aggregated APIs, and `cluster.network.nodeCidrs` to the node subnets for rules targeting nodes. Because EKS pods and nodes share VPC subnets with VPC endpoints, load balancers, and databases, Kix keeps those subnets in external egress rules (`world-egress-pod-subnets` and `world-egress-node-subnets`) and does not require `cluster.network.podCidr`. Platform limits that no Kix setting can narrow, including CIDR rules matching pods and nodes in shared VPC subnets and the roughly one-second startup window before a new pod's egress rules take effect, are reported as `info` findings under `kix check -v`.
