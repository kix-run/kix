Existing EKS clusters need no changes. EKS clusters can now generate standard Kubernetes `NetworkPolicy` objects when network policy is enabled in the Amazon VPC CNI add-on. To turn this on, enable `enableNetworkPolicy` in the Amazon VPC CNI add-on configuration, then set `cluster.flavor.eks.networkPolicy = "vpc-cni"` and `networkPolicy.enable = true`. (`cluster.flavor.eks.networkPolicy` defaults to `"none"`, matching a default EKS cluster, and setting `networkPolicy.enable = true` while it is `"none"` stops the build with setup instructions.) When a workload or rule needs them, also set `cluster.network.serviceCidr` or `cluster.network.apiServer.cidrs` for API server egress, `cluster.network.apiServer.sources` for admission webhooks and aggregated APIs, and `cluster.network.nodeCidrs` for rules that target nodes. The `security.networkPolicyWidened` scorecard rule warns when VPC CNI `ipBlock` rules allow pod, node, or Service traffic that Cilium would block, and warns about the roughly one-second window after pod startup before egress policies apply. Because EKS nodes share VPC subnets with VPC endpoints, load balancers, and databases, Kix keeps those subnets in `world` egress rules and reports `world-egress-node-subnets` in the scorecard. Pods take addresses from the same subnets, so `world` egress rules do not exclude the pod range either, and the scorecard reports that as `world-egress-pod-subnets` without asking for `cluster.network.podCidr`.
