Existing EKS clusters need no changes. EKS clusters (`kix.flavors.eks`) can now generate standard Kubernetes `NetworkPolicy` objects for the Amazon VPC CNI add-on. To enable this, turn on `enableNetworkPolicy` in the Amazon VPC CNI add-on configuration, then set `cluster.flavor.eks.networkPolicy = "vpc-cni"` and `networkPolicy.enable = true`. Leaving `cluster.flavor.eks.networkPolicy` at its default `"none"` while `networkPolicy.enable = true` stops the build with setup instructions. When policies require them, also set `cluster.network.serviceCidr` or `cluster.network.apiServer.cidrs` for API server egress, `cluster.network.apiServer.sources` for admission webhooks and aggregated APIs, and `cluster.network.nodeCidrs` for rules targeting nodes. Because EKS nodes and pods share VPC subnets with VPC endpoints, load balancers, and databases, outbound `world` rules keep those subnets (`world-egress-node-subnets` and `world-egress-pod-subnets`, without requiring `cluster.network.podCidr`). The `security.networkPolicyWidened` scorecard rule warns while `cluster.network.serviceCidr` is unset, because setting it narrows `world` rules. The VPC CNI's limits, which no setting removes (`ipBlock` rules matching pods and nodes in the VPC subnets, and the roughly one-second window before a new pod's egress rules apply), are `info` findings that `kix check -v` lists.
