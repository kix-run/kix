Existing EKS clusters need no changes, and can now opt into generated standard Kubernetes `NetworkPolicy` objects when the Amazon VPC CNI add-on enforces network policy. `cluster.flavor.eks.networkPolicy` defaults to `"none"`, matching a default EKS cluster; setting `networkPolicy.enable = true` while it is `"none"` fails the build and explains how to turn enforcement on. To enable generated network policies on EKS, turn on `enableNetworkPolicy` in the Amazon VPC CNI add-on configuration, then set `cluster.flavor.eks.networkPolicy = "vpc-cni"` and `networkPolicy.enable = true`. Depending on what your workloads use, also set `cluster.network.serviceCidr` (or `cluster.network.apiServer.cidrs`) for API server egress, `cluster.network.apiServer.sources` for admission webhooks and aggregated APIs, and `cluster.network.nodeCidrs` for rules targeting nodes. Where VPC CNI `ipBlock` matching allows pod, node, or Service traffic that Cilium would block, or during the roughly one-second startup window before egress policies take effect on new pods, the `security.networkPolicyWidened` scorecard rule reports a warning. On EKS the node range is the VPC subnets, which also hold VPC endpoints, load balancers, and databases, so `world` egress rules do not exclude it, and the scorecard reports that as `world-egress-node-subnets`.
