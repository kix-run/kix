Update any external scripts, policies, or admission rules that inspect Kix's tracking metadata. Match the Server-Side Apply field manager `kix/<cluster>` instead of `kix`. Read deployed object lists from the `PackageInstanceRevision` resources linked in an `Activation` record's `status.revisions` (each entry has a hash of the manifest Kix sends for the object, its API group, kind, namespace, and name, and the objects it depends on) instead of from `kix.run/activations` or `status.packageIndex`. Read applied hashes from `status.applied` on those revisions (mapping each entry's hash to the hash of the Kix-owned live fields) instead of from `kix.run/applied-hash`. Kix no longer writes `kix.run/activations`, `kix.run/applied-hash`, `kix.run/identity-hash`, `kix.run/depends-on`, `kix.run/package`, `kix.run/package-namespace`, or `kix.run/lifecycle` on deployed objects (an `Activation` record keeps its own), and no longer writes `status.packageIndex` or `status.orphansKeptFrom` on `Activation` records. Find an object's package instance, and its lifecycle, in the `slot` of the revision that names it. To tell whether Kix wrote an object, read its `kix/<cluster>` field-manager entry instead of `kix.run/identity-hash`. Built manifests, such as the output of `kix export --with-kix-metadata`, still carry `kix.run/identity-hash`, `kix.run/depends-on`, `kix.run/package`, `kix.run/package-namespace`, and `kix.run/lifecycle`, and Kix removes them before it sends a manifest to the cluster. On the first deploy after upgrading, Kix renames each object's `kix` field-manager entry to `kix/<cluster>` and removes the retired annotations. If another Kix cluster on the same Kubernetes cluster still uses an earlier version of Kix, shared objects keep their `kix` field-manager entry and retired annotations until both Kix clusters deploy with this version. Until then, changing a shared field stops with a field ownership conflict naming `kix`.
