When two Kix clusters deployed the same object and both removed it from their builds, the object could stay on the Kubernetes cluster with no deployment record naming it. After that, `kix plan`, `kix gc`, and `kix deploy --prune` never found it again. This happened because a Kix cluster treated the other cluster's leftover field manager entry on the object as proof that the other cluster still deployed it, and stopped naming the object in its own records. Now a Kix cluster counts another cluster as still deploying an object only when that cluster's records name it, and its own record keeps naming a shared object until Kix sees its field manager entry gone. A `kix deploy` whose only remaining work is releasing a shared object now runs instead of printing "Nothing to apply". `kix gc --full-scan` now lists an object that no record names but that carries the cluster's own field manager entry (`kix/<cluster>`) as that cluster's object, so it can delete the object without `--include unattributed`. To clean up a cluster already in this state, find the Kix cluster whose field manager is on the object and run `kix gc <cluster> --full-scan --dry-run` to review the list, then run `kix gc <cluster> --full-scan`.
