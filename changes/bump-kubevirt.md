`kubevirt` installs KubeVirt v1.10.0 instead of v1.5.0. KubeVirt supports updates only from the latest patch of one minor to the latest patch of the next, so this jump skips its supported path. To follow that path, set the instance's `image.tag` to v1.5.3, v1.6.6, v1.7.4, v1.8.4, and v1.9.1 in turn, deploy once for each, and then remove the setting. If you enabled the alpha `MigrationStallDetection` feature gate, turn it off before you upgrade to v1.10, or the upgrade does not finish. Running virtual machines keep running on their old virt-launcher pods until they restart. A deploy now judges a running VirtualMachine by `status.desiredGeneration`, so it no longer waits for a restart after KubeVirt rewrites the VM. When a change needs a restart, the deploy reports the VM as ready with a restart pending and names `virtctl restart`. If the next deploy after the upgrade reports a field ownership conflict on `.spec.dataVolumeTemplates`, run it once with `--force-conflicts`. KubeVirt turns on every Beta feature gate by default, so virt-operator now also runs virt-template-apiserver and virt-template-controller (virt-template v0.3.0) in the `kubevirt` namespace. v1.10 also turns on the VSOCK and UtilityVolumes gates, and memory dumps now need UtilityVolumes. To turn off a gate, list it in `extraSpec.configuration.developerConfiguration.disabledFeatureGates`. virt-exportproxy now always runs, because VMExport is no longer behind a gate. Changes to a VirtualMachine's live-updatable fields now reach the running VM by default (rollout strategy `LiveUpdate`). Set `extraSpec.configuration.vmRolloutStrategy = "Stage"` to keep the old behaviour. Releases since v1.5 removed the `instancetype.kubevirt.io/v1alpha1` and `v1alpha2` APIs and the macvtap and SLIRP network bindings, and renamed several metrics and recording rules. Move objects and virtual machines off these before you upgrade. In v1.10, a Plugin's `spec.domainHooks` is now `spec.launcherHooks` and needs explicit hook points, VirtualMachineBackup reports its type per volume in `status.includedVolumes[].type` and its endpoints in `status.links`, and virtual machines in an Istio mesh need Istio 1.27 or later. Going back does not work: an older virt-operator cannot install its CRDs over what v1.10.0 stored, and KubeVirt stays Degraded until v1.10.0 is deployed again.
