- [ ] **Cluster-level instances**: first-class home for instances whose resources are cluster-scoped (StorageClass, VolumeSnapshotClass, CSIDriver, ClusterRole-only bundles, etc.). ### Open design questions
- [x] **A resource can cede fields to a controller** (2026-09-20, shipped 2026-09-20). Field ownership was all-or-nothing: an operator that rewrote a CRD Kix shipped (cdi drops a deprecated version from `.spec.versions`) or a webhook Kix applied (StackGres takes over `.webhooks[].rules`) made every later deploy a 409, and `--force-conflicts` took every field of every resource back. `ownership.cede = [ "spec.versions" ]` on the resource (also on `scope.mkCRD`) is stamped as `kix.run/cede-fields`; `apply.rs` retries a conflict confined to ceded paths without those fields, so the operator keeps them, and fails any other conflict as before. cdi ships upstream's full version list again and cedes `spec.versions`; stackgres-operator cedes `webhooks[*].rules`. The third entry in the group, Mayastor's runtime-installed DiskPool CRD, is a `scope.mkCRDRef` with `installedBy` (the marker deploy already waits on), not an ownership question.
- [x] **A workload can carry its own availability ceiling** (2026-09-20, shipped 2026-09-20). `meta.availability.max` capped a whole instance, so openebs's `max = "pod"` for three single-replica controllers also lowered etcd and NATS from `DoNotSchedule` to `ScheduleAnyway` on the zone key. `availability.max` on the builder call (`scope.mkDeployment { availability.max = "pod"; ... }`) seals that one workload at the lower level, warns once naming it, and stamps `_availability` on the sealed resource so the availability processors judge it there; the package's `availability` argument and every other workload keep the requested level. openebs dropped its instance ceiling for seven per-workload ones. Test a21.
- [x] **A `none` ceiling is one pod** (2026-10-01). `none` as a ceiling means a workload runs one pod at a time; `pod` keeps "survives a pod crash or rolling update". The availability plugin refuses a Deployment or StatefulSet above one replica under an effective ceiling of `none` (builder `availability.max` or `meta.availability.max`, the lower of the two), after overlays and for chart workloads too. Ceilings are validated where written (`checkCeiling`, builder `availability` keys, refused on DaemonSets), and a builder ceiling is recorded on the sealed workload even when it does not cap. `every-package-evaluates` runs each package at `none` and `zone`. Placement rule: package ceiling for program limits, builder ceiling for anything that depends on config or wiring. Tests `lib-availability-ceiling-*`. Under a package ceiling, `kix.availability.pick` refuses a table whose values above the ceiling differ and `atLeast` refuses a threshold above it (`underCeiling`, 2026-10-02); `meta.availability` takes only `max`. grafana moved its limit to a builder ceiling; kube-state-metrics and prometheus-operator are `none` with one replica, and their `replicas` options and `monitoring.grafana.replicas` are gone.
- [x] **`architecture.clusterDomainLiteral` and the package-eval source scan** (2026-10-01): a rendered `cluster.local` fails a build on another domain; package-eval builds every package with `clusterDomain = "eval.kix.test"`.
- [x] **Version grammar** (2026-10-01): `kix/lib/core/version.nix`; `v` prefixes and vendor build tags parse; constraints compare at their own precision and unknown versions warn. `compatibleWith` now reads a managed dependency's `meta.version`.
- [x] **`autoRoot` refuses to guess** (2026-10-01): a chart's root is the only Service, else the only workload; otherwise evaluation fails and `kix.helmChart { root }` names it.
- [x] **`kix.expose` with `paths` renders an HTTPRoute** (2026-09-18, shipped 2026-09-20). Multi-backend routing only rendered an Ingress, so harbor could not be exposed on a cluster that routes through a Gateway. `httpRoute.fromPaths` renders one HTTPRoute with a rule per path, each to its own backend, translating the Ingress `pathType` words. Ingress stays supported, but Gateway API is the direction every cluster is moving in and routing features are built for it first. Test t96. The network-policy edge from the Gateway's data plane is still open.
- [x] **A package asks for the Pod Security level its pods need** (2026-09-19, shipped 2026-09-20). `meta.podSecurity` on the package; the namespace carries `pod-security.kubernetes.io/enforce` at the most permissive level any of its instances needs, `namespaces.<ns>.podSecurity` sets it by hand, and a hand-set level stricter than an instance needs is an eval error naming the instance. kubevirt declares `privileged`, as upstream labels its namespace. Test t92.
- [x] **The `global` option is gone** (2026-09-19, removed 2026-09-20). Every key of `global` was fed into every package's option evaluation, so a key one package did not declare failed the whole build, and no cluster in the tree set it. Cluster-wide decisions already reach packages through typed channels: the availability level, network policy, the DI arguments. A future broadcast need gets its own typed channel rather than an untyped bag.
- [x] **Operator RBAC is vendored** (2026-09-19, shipped 2026-10-02). The `cdi` package had copied an upstream ClusterRole rule for rule and left out the namespace `Role` and its `RoleBinding`; the operator started, reported ready, and did nothing. kubevirt and cdi now keep upstream's operator roles under `<pkg>/rbac/*.json`, vendored from the release bundle by `scripts/vendor-crds.py` (`rbac/sources.txt`, `Kind/name` selectors) and checked in CI with the CRDs. The packages bind them through `scope.rbac` role sets. Deriving RBAC from declared CRDs (`v2_discussions/35_crd_derived_rbac_webhooks.md`) stays open.
- [x] **`kix.expose` opens the ingress controller's path to the backend** (2026-09-18, hit twice; shipped 2026-09-20). `ingress-nginx` publishes `out.podSelector` and `out.podNamespace`, and `kix.expose` emits one policy per backing Service opening that Service's pod port to the controller's pods. harbor's hand-written all-pods intent is gone. It went through the role registry first and came back out: `findRoleProvider` refuses two providers of a role, and two ingress controllers in one cluster is a shape this package already supports, so the edge is written from the `ingressNginx` dep the caller already holds. Verified on stage2 with cilium audit mode turned off for the backend endpoint: 200 through the Ingress, 504 with the derived policy deleted, 200 again when it is put back. Gateway API is not covered — see the note in HANDBOOK §16.5.
- [ ] Package root as common leaf dependency or root
- [ ] Direction of abstraction: deploying an app ON a surface (cloud-run-like) vs. wrapping/composing an app IN a surface (being cloud-run) — this is a concrete UX question that shapes the entire API
- [ ] How to model the derivation vs resource vs module tension — three competing goals in direct conflict: (1) perfectly verifiable traceability (security), (2) complete customization (maintenance), (3) ease of consumption. Modules can't support duplication (multiple SAs), derivations can't be post-modified, resources easily lose dependency tracking
- [ ] Content-addressing means updates launch side-by-side (different hash), not in-place replacement — native K8s rolling update semantics become incompatible. This is a fundamental design property that needs explicit handling
- [ ] Kubenix-style service definitions (`services.coredns."default".enable = true`) — allows multi-instance, attribute-set-keyed service declarations
- [ ] Move to manifest module system — explicit migration step for how manifests are composed
- [ ] a "kix managed only" mode
- [ ] multi-activation support => should they be mutually exclusive? (prepending all names with the cluster name) or should they share resources => same hash, same resource? (makes things like postgres probably tough (?)). Partly answered 2026-09-28 in favour of sharing: see the next item. Still open: see "Two Kix clusters that render one shared object differently" under Open design questions.
- [x] **Commands see one Kix cluster's objects** (2026-09-28, `v2_discussions/archive/150_scope_managed_sweep_to_one_cluster.md`). `fetch::sweep_managed` takes a `SweepScope` (`Cluster`, `Records`, `All`) and attributes each object through the Activation record hashes in its `kix.run/activations`, split by the records' `kix.run/cluster` label (`activation::Tenancy`, `fetch::attribute`). `kix diff`, `status`, `health`, `snapshot save`, `gc --hard` and the operator's reconcile read only the named cluster's objects and print how many they skipped per other cluster; `kix deploy`'s rebuild-from-live reads only the Active, Failed and kept-orphan records' closures; `kix drift` takes `--cluster` and otherwise names each object's clusters. With one Kix cluster the output is unchanged. When another cluster has records, an object naming no record is "unattributed": left out of read views and judged by `gc --hard` only with `--include-unattributed`. An orphan that another Kix cluster's current build still contains is kept by deploy, rollback, soft and hard gc, the operator's reconcile and its finalizer: plans list it as kept (`fetch::split_shared_orphans`), and every prune deletes through `prune_guard::PruneGuard`, which reads the object, then the records, and deletes with the read's uid and resourceVersion as preconditions. Every sweep lists the records after the objects, so a Kix cluster whose first deploy lands mid-sweep is never mistaken for this one. Breaking: `kix snapshot save <CLUSTER> <DIR>`. Still open: see "Two Kix clusters that render one shared object differently" under Open design questions.
- [ ] Eval-diagnostic severity levels (from the stage2 no-DNS incident, 2026-08-31): "no DNS instance found" is fatal-in-practice but prints as the same trace warning as advisory lints, and scrolled past while alertmanager/vmagent hung on resolution. Diagnostics want severity, and the deploy path should surface (or gate on) the fatal tier. Cluster-level scorecard findings now trace + gate builds (previously report-JSON only), which covers scorecard rules but not ad-hoc `builtins.trace` warnings like the DNS one.
- [ ] Uniform scheduling story: pinning a stack to a node set today means `config.nodeSelector` on some packages and `config.extraSpec.<component>.nodeSelector` on operator-CR packages (see monorepo shared/monitoring-stack.nix's `pinned` helper). A cluster- or instance-level scheduling constraint applied uniformly would remove the per-package divergence.
- [ ] DI capture-by-name hazard: an instance named `storage` is captured by grafana's optional `storage` PVC dep and mounted as one (lab1 + stage1 both dodged via `platform-storage`). Optional deps matching by bare instance name is too eager — consider requiring alias-based binding for optional deps, or warning when an unrelated-looking instance is captured.
- [ ] Per-resource identity labels (kixpkgs#46, from the red-team review 2026-08-31): `Service.out.selector` returns instance-common metadata labels, so any label-selecting consumer (ServiceMonitor via `self.service.out.selector`, and `kix.monitor` equally) over-matches in a multi-Service package — every pod scraped once per Service. Precise selection needs a per-part discriminator (e.g. a `kix.run/part: <partName>` label stamped on every resource and surfaced via out.*), which is churn on all rendered manifests and deserves its own design pass.
- [ ] Derive data-plane Service type from the `loadBalancer` role (2026-09-12, from the envoy-gateway `proxySpec` work): `kix.flavors.kind` already declares `cluster.roles.loadBalancer.binding = "absent"`, which is exactly the fact that makes a LoadBalancer-backed Gateway unprogrammable there. Today every kind scenario repeats the NodePort opt-in by hand. A package could read the binding and default the Service type from it — automation over brevity, and it generalizes past envoy-gateway (any package that would provision a LoadBalancer). Against: implicit, couples a package to a cluster-role vocabulary, and the failure it prevents is loud rather than silent.
- [x] Declared readiness (kix.run/readiness, 2026-08-31) covers path==value; the CLI still hardcodes SGCluster/Gateway condition vocabularies (readiness.rs). Extend the declaration to condition-based rules (`condition = { type; status; }`) and migrate those when their packages gain typed CRD builders. Done 2026-09-20: `readiness = { condition = { type; status; }; }` is accepted by mkCRD/mkCRDRef and evaluated by the CLI; stackgres-operator (Bootstrapped), envoy-gateway (Accepted/Programmed, via new Gateway API CRD refs) and cilium (Valid) declare theirs, and `check_readiness` keeps only Kubernetes-defined kinds. The `hasNetworkPolicy` rule reads the enforcer's `out.netpol.policyKinds` instead of naming Cilium.

## Security & compliance

> "Security teams have money — platform teams do not. But platform teams can get money from security."

- [x] Package ownership model — `meta.owner` field on packages, surfaced in `kix list packages` (text and JSON). OWNER column auto-hides when no packages declare owners. Foundation for IDP catalog, scorecards, and team-scoped views.
- [ ] Security defaults via mkDefault — e.g. all pods non-root by default, users must mkForce to override
  - mkForce as an auditable signal: any use of mkForce to override security defaults can be flagged, surfaced in review, or blocked by policy
  - The full nix module priority hierarchy (mkDefault → normal → mkOverride → mkForce) is what makes multi-team cluster configs maintainable at scale
- [ ] CVE tracking — integrate with NixOS security tracker (https://tracker.security.nixos.org/suggestions/) for awareness of vulnerabilities in dependencies
- [x] Scorecard rules — multi-level policy evaluation framework (manifest, package, namespace, cluster). Built-in rule library (`lib/rules/`) with 15 rules covering security, reliability, and governance. Configurable severity per scope (namespace, owner, rule). Findings feed into kix diagnostics: error-level block the build, warnings are traced. Cluster config via `scorecard` module option. See `lib/scorecard.nix`, `lib/rules/`, `clusters/nw1/scorecard.nix`.

## Open design questions (still-to-get-right)

Things that are either "shipped but the underlying question isn't actually settled" or "deferred but important enough that we need to not forget them". Pulled from archived v2 discussion docs during the April 2026 cleanup.

- [ ] **CRD upgrade guards and stub migrations** (from `v2_discussions/146_crd_vendoring_and_upgrades.md`, 2026-09-19): vendoring shipped; still open: `mkCRD` builders follow the first listed version rather than the storage version, prune has no CRD guard (deleting a CRD cascades to every CR), a deploy does not check the live `status.storedVersions` before applying a CRD that drops a version. prometheus-operator keeps stubs for upstream kinds.
- [ ] **`minDomains` on derived spread** (from `v2_discussions/archive/143_pod_spread_and_failure_zones.md`) — at the `zone` level with three declared zones, should the constraint carry `minDomains = 3` so a cluster that claims three zones but has nodes in two fails visibly rather than packing? - [ ] **A namespace rung on the availability ladder** (145) — `namespaces.<ns>.availability` between the cluster default and the instance override, for a shared cluster that runs two environments side by side (`kix.mkEnv` style). A third lookup in `core/availability.nix` `resolve`; not built until a cluster needs it.

## Key risks & design principles

- **Nix adoption barrier** — nix has clear advantages but hasn't taken over the world; we need to actively study *why* people who know about nix's benefits still choose not to use it — not just build features. The intro tutorial and DX must be approachable for a non-nix user. Positioning: nix scales; helm and friends do not.
- **Adoption is the #1 killer of platforms** — not features. The experience for a non-infra developer must be so easy a novice could use it. Datadog vs Prometheus is the cautionary tale (user acquisition beats technical correctness).
- **"Not simple, but intuitive"** — the goal isn't to reduce the interface, but to distill inherent complexity into intuitive form. If the tool is "too smart", the user has to think about the tool rather than their work (mental overhead as a design constraint).
- **Eval times** — content-addressing could lead to long eval times; unclear if path caching helps.
- **Abstraction balance** — narrow interface ≠ less cognitive load; making things simpler than they are creates a dangerous illusion. Don't abstract away physical properties (cost, latency, SLA) — they're leaky abstractions people care about.
- **"Composability and cohesion over capability and completeness"** — the platform will grow by itself, but composability and cohesion must be actively protected.
- **Show value in weeks** — don't over-engineer. Find immediate MVPs and GTM opportunities. The demo must be compelling quickly, not after all features are built.
- **IaC as readable, long-lived intent** — "express ideas in a language you can re-read a year ago". This is a core reason to use nix over YAML/templating: the configuration is human-readable code, not opaque generated output.
