Kubernetes doesn't need
a new abstraction.
It needs a compiler.

Every previous attempt to make Kubernetes "easier" tried to abstract away the resources. They collapsed on edge cases, because the resources aren't the problem. The wiring is.

What's actually hard about Kubernetes

Keeping dozens of resources in agreement.

Kubernetes is a remarkably general set of primitives. Every field on every resource exists because some real-world case needs it. You can't abstract them away without collapsing on that case.

Nobody struggles to write a Deployment. What they struggle with is keeping a Deployment, Service, Ingress, NetworkPolicy, ServiceAccount, Role, RoleBinding, PVC, volume, volumeMount, ConfigMap, Secret, and Certificate all agreeing about names, labels, ports, hosts, permissions, and paths. When any one of them drifts, something breaks at runtime.

This is not a template problem. Templates produce text. The text is fine. The problem is that the text must stay consistent across N files forever, through every refactor, every team handoff, every new dep. That's a compiler problem.

The wirings, concretely

IntentWhat you actually write
"Route to these pods"Copy matchLabels into Service.spec.selector. Hope they match.
"I talk to postgres"Hand-construct host:port from the service's naming convention.
"My app listens on 8080"Declare 8080 four times — container, Service, Ingress, NetworkPolicy.
"I can read Secrets"ServiceAccount + Role + RoleBinding. Three resources, name-matched.
"10Gi at /data"PVC + volumes entry + volumeMounts entry, all sharing a name string.
"A → B on 5432"NetworkPolicy allowing egress from A + ingress to B. Forget one, traffic drops silently.

Every one of these is information declared in one place, manually repeated in another. Every one of them is a class of bug.

The right historical analogy

Kubernetes is still in the assembly era.

Assembly's problem was the language — registers, opcodes, stack management. C replaced the language.

Kubernetes' problem is not the language. The resources are fine. You could stare at a Deployment for a year and not find a better model. The problem is the wiring between resources — name strings, label matchers, redundant port declarations, permission triples.

You don't replace the language. You compile the wiring. That's what kix is. The resources stay 1:1 with real K8s resources. What changes is that you stop writing the sync-them-by-hand layer.

Why the Nix store

The IR we needed was sitting there for twenty years.

A compiler needs a dependency graph. Not one you ask the user to declare — one that falls out of the computation. The Nix store already does this, through a mechanism called string context.

When a kix package interpolates postgres.out.fqdn into an environment variable, Nix embeds postgres's content hash into the consumer's store path. The dependency edge isn't declared. It's a byproduct of the resource being constructed.

consumer/deployment.nix what you write 
build = { self, config, postgres, scope, kix }: {
  root = scope.mkDeployment {
    spec.template.spec.containers = [{
      env = kix.mkEnv {
        // postgres.out.fqdn isn't just a string —
        // it carries a hash edge into postgres's store path.
        DATABASE_URL = "postgres://${postgres.out.fqdn}:${toString postgres.out.port}";
      };
    }];
  };
}

The consumer's hash cannot be computed without depending on postgres. You couldn't fake the edge if you tried. The dependency graph is always complete, always correct, and always cryptographically sound.

Everything else — blast radius, drift detection, fleet diff, parallel-safe deploys, rollback, compliance evidence — is surfacing what the Merkle DAG already knows, not building new analysis engines.

What you stop writing

What the compiler derives.

Each of these used to be a hand-written resource set in your Helm chart. Each is now a consequence of the dependency graph.

Selectors

One source, many consumers.

Workload selectors, Service selectors, HPA target references, PDB matchers — all derived from the same matchLabels. Mismatches can't happen — there's only one source.

NetworkPolicies

Derived from the connection graph.

The compiler sees that service A uses b.out.fqdn. It emits egress from A and ingress to B automatically. Add a consumer, get the policy. No hand-written deny lists.

RBAC

Intents, not triples.

rbac.watch, rbac.reconcile, rbac.own. The compiler lowers these to the ServiceAccount + Role + RoleBinding set. Rules merge and dedup.

Storage

One declaration, three resources.

A workload declares "10Gi at /data." PVC, volume entry, volumeMount entry — all emitted, all named consistently. The storage class comes from the cluster's hardware profile, not the package.

Deploy ordering

Waves from the DAG.

Resources with no deps deploy first. Dependents follow. You never annotate a wave. The dependency structure is the wave structure.

Blast radius

A DAG traversal, not a review.

Change an input, get a new hash. Every downstream node whose hash changes is in the blast radius. Every node whose hash doesn't change provably isn't. nix-store -q --tree is the audit trail.

Under the hood

The compiler passes, briefly.

Enough that you can see this isn't hand-waving. The full walkthrough lives in v2_discussions/29_compiler-design.md and kix/lib/architecture.md.

1. Resolution

Cluster modules merge. DI resolves dep arguments via DNS-like lookup. Optional deps auto-instantiate.

2. Compilation

Each package builds its resources through a per-instance scope. Labels, selectors, cross-resource wiring derive from the workload's single source of truth.

3. Wiring validation

Selector coherence, port agreement, cross-namespace reference validity, CRD schema conformance. Errors at eval time, not at apply time.

4. Derivation

NetworkPolicies from the connection graph. RBAC from access intents. Monitoring from declared capabilities. The cross-cutting resources that used to be hand-written.

5. Whole-cluster analysis

Scorecard rules (policy). Architecture rules (capability hygiene). Version compatibility. Reachability checks. Everything that requires seeing the whole cluster at once.

6. Emission

Content-addressed YAML. An Activation CR that roots the entire closure. A CLI that walks the DAG, computes waves, and applies via SSA with structured readiness verdicts.

What happens to Helm, Argo, Backstage

kix absorbs. It doesn't replace.

The lesson from rig.dev is expensive and instructive: if you ask platform engineers to throw away their Helm charts, they say no and you die. kix doesn't ask.

  • Helm charts are imported via importChart. The compiler reconstructs their internal dependency graph and treats them as first-class packages. You keep your charts; you get compiler benefits on top.
  • Argo stays where it is as a runtime reconciliation layer. kix replaces the decision of what to deploy, not the mechanism of making the cluster match.
  • Backstage / your IDP stays if you like it. The kix catalog is derived from the deployment and can be exposed to any IDP. The catalog is always consistent because it's the same source.
  • OPA / Kyverno continue to enforce at admission as defense-in-depth. kix prevents the violations at build; OPA catches anything that slips through, including things kix didn't build.

The operator experience

One CLI. No nix in your hand.

You don't run nix build. You run kix. The CLI evaluates, diffs, plans, and deploys wave-by-wave with SSA. It streams progress through a DAG-aware TUI. It rolls back by pointer swap. It exports SBOM, SLSA provenance, and SOC2 / ISO / DORA / NIS2 evidence bundles as one command.

What we'll tell you before you ask

The honest caveats.

  • Yes, you need Nix. We don't hide it. We chose it because string context is irreplaceable and we'd have to rebuild it anyway. The surface area of Nix you actually write is narrow — see the developer page.
  • The default demo runs on kind. It also runs on GKE, EKS, AKS, OpenShift, k3s, Talos, and bare metal via the flavor system. kind is how we smoke-test daily.
  • Some day-2 capabilities are roadmap. Storage migration orchestration, operator swaps as refactor, cross-cluster migration — the design is in v2_discussions/, the foundation is shipped, the full experience is landing over M2–M4.
  • We're pre-revenue. We are looking for design partners, not early customers. If you want to be the first production deployment, we want to talk. If you want an SLA-backed SaaS, we aren't there yet.
