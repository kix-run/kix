Moment 1 — Write

A package that talks to postgres.

An API service. It needs postgres. It exposes HTTPS. It needs to read its own namespace's secrets. Here's the whole package.

packages/api-server/default.nix the whole package 
{ scope, lib, kix, ... }: {

  options = {
    image = lib.mkOption { type = lib.types.str; default = "api-server:v1.5.0"; };
    host  = lib.mkOption { type = lib.types.str; default = "api.example.com"; };
  };

  build = { self, config, scope, kix, postgres }: {

    root = scope.mkDeployment {
      spec.replicas = 3;
      spec.template.spec.containers = [{
        name = "api";
        image = config.image;
        ports = [{ name = "http"; containerPort = 8080; }];
        env = kix.mkEnv {
          // This one string creates a hash-level edge
          // into postgres. No wiring to maintain.
          DATABASE_URL = "postgres://${postgres.out.fqdn}:${toString postgres.out.port}/api";
        };
      }];
    };

    service = self.root |> kix.service.fromWorkload {} |> scope.mkResource;

    ingress = self.service |> kix.ingress.fromService {
      host = config.host;
      tls = true;
    } |> scope.mkResource;

    rbac = scope.mkRoleSet (kix.rbac.watch [ "secrets" ]);
  };
}

What you don't write

  • A Service selector — derived from the Deployment's matchLabels.
  • An Ingress backend port — derived from the Service's port named http.
  • A Certificate, a ClusterIssuer reference, a TLS block — derived from tls = true + the cluster's exposure policy.
  • A NetworkPolicy allowing egress to postgres — derived because your env var references postgres.out.fqdn.
  • A ServiceAccount + Role + RoleBinding triple — derived from rbac.watch.
  • An apiVersion you had to look up — scope.mkDeployment knows the cluster's target version.

That's four resources written. Nine resources emitted. Zero hand-sync between them.

Moment 2 — Deploy

One command. Wave-by-wave. Readiness-aware.

You don't run nix build. You don't write a Helm release name. You run kix deploy. The CLI evaluates, diffs against the live cluster, shows the plan, and applies the waves via server-side apply with structured readiness verdicts.

Moment 3 — Change

Bump the image. The compiler knows what moves.

You change one field: the image tag. You run the same kix deploy command. This is what you see.

~/my-cluster 
$ kix diff .#cluster-dev --vs-live

change plan (vs live cluster)
  ~ Deployment/api
    spec.template.spec.containers[0].image:
      - api-server:v1.5.0
      + api-server:v1.6.0

blast radius
  1 resource changes.
  246 resources proven unchanged (same hash).

downstream hash changes
  Deployment/api                     hash changed
    (all other resources, including
     Service/api, NetworkPolicy/api,
     Certificate/api-tls, RBAC):      hash unchanged

One line of code moved. One line of hash moved. Everything else is provably unchanged. This is what "blast radius as a cryptographic proof" means in practice. No grep across N charts. No "I think this only affects the api." You know.

Moment 4 — The harder change

Swap the postgres operator. The compiler plans it.

You want to migrate from StackGres to CloudNativePG. In the incumbent stack this is a four-week runbook, two spreadsheets, and one very nervous engineer.

In kix it's a two-line edit in your cluster config — swapping which package provides the postgres dep-slot.

clusters/prod.nix the diff 
instances.postgres = {
  - package = kix.packages.stackgres-cluster;
  + package = kix.packages.cloudnative-pg;
  config = { size = "50Gi"; };
};
~/my-cluster 
$ kix deploy .#cluster-prod

! stateful operator swap detected
  postgres.out provides: { fqdn, port, superuser-secret, ca-cert }
  old operator: stackgres-cluster       (present)
  new operator: cloudnative-pg          (planned)
  consumers:    api-server, reports-svc (unchanged, compile-compatible)

migration plan
  1. deploy cloudnative-pg alongside stackgres-cluster
  2. pg_dump from stackgres primary (estimated 4m)
  3. pg_restore into cloudnative-pg primary (estimated 6m)
  4. switch postgres.out.fqdn service alias (atomic)
  5. drain stackgres connections (30s grace)
  6. remove stackgres-cluster

estimated downtime: ~30s during step 4
estimated total duration: ~11m

continue? [y/N]

This specific flow is on the M2–M3 roadmap (v2_discussions/67_stateful_migration_orchestration.md). The foundation — dep-slot identity, the connection graph, the compile-time proof that consumers are unaffected — is shipped today. Storage migration and operator swap are the planned apex.

The concern you haven't said out loud yet

How much Nix do you actually have to learn?

Honest answer: much less than you think, much more than a YAML engineer has to learn today. The kix package author writes:

  • Attribute sets ({ foo = ...; }) — like JSON, different punctuation.
  • Function arguments ({ scope, lib, kix, postgres }: { ... }).
  • Three kix constructors: scope.mkDeployment, scope.mkResource, kix.mkEnv.
  • The pipe operator (|>) — the same one you already know from Elixir, F#, shell.

You don't write derivations. You don't touch flakes beyond the top level. You don't deal with overlays. The surface area of Nix you actually touch is narrow, deliberately.

The reason the learning curve is worth paying: the compiler stops you from going wrong. Like onboarding onto a Rust codebase — you don't have to understand every module because the compiler enforces invariants you don't know about yet. Your first change being safe isn't optional. It's structural.

Getting started

Three commands to running kix.

# 1. install Nix (once, if you don't have it)
curl --proto '=https' --tlsv1.2 -sSf -L \
  https://install.determinate.systems/nix | sh -s -- install

# 2. clone the demo
git clone https://github.com/example-org/kixpkgs
cd kixpkgs

# 3. bring up a kind cluster with the full demo stack
nix develop
kix deploy .#cluster-ludo-kind

That builds the full demo stack — cilium, cert-manager, ingress-nginx, stackgres, a small app — on a local kind cluster. Start poking. Run kix diff after every change. Run kix rollback when you want to undo.

The honest part

What doesn't work yet.

The foundation is shipped. The full day-2 spectrum is not. Things that are still ahead of us on the milestone roadmap:

  • Stateful migration orchestration — the full operator-swap flow shown above is M2–M3.
  • Cross-cluster migration — compiler sees both clusters, plans the move. Design in v2_discussions/67, implementation to follow.
  • In-cluster evaluation mode — no-CI pull model where the operator evaluates from git. Design in interesting_thoughts/89.
  • SaaS control plane — today kix is a CLI and an optional in-cluster operator. A hosted control plane is not yet built.
  • IDE tooling beyond Nix LSP — language server for kix-specific diagnostics (structured warnings, cross-package references) is in design.

If one of these is the thing you need to move forward, let us know. Design partners shape the roadmap.
