# Kix CLI

The Rust CLI for kixpkgs evaluates Nix-defined Kubernetes clusters, diffs against live state, and deploys in dependency order with server-side apply. Users run `kix`, never raw `nix`.

## Workspace

```
kix/             library: eval, manifest handling, cluster operations, planning, plan files
kix-container/   library: the seekable zstd container bundles and plan files share
kix-bundle/      library: bundles, a build as one file, read without Nix
kix-cli/         binary: clap CLI, command dispatch, plan display
kix-operator/    binary: kube-rs controller watching Activation CRs
runtime/         bundled runtime assembly (programs.json, runtime.nix, assemble.py, legal.py, without-nix.sh, nix-builder.sh)
fuzz/            cargo-fuzz targets for the bundle and plan file readers (own workspace)
```

Both binaries depend on `kix`, and `kix-cli` on `kix-bundle`, which is
built on `kix` as any other user of the library would be. `kix` knows
nothing of bundles: a bundle reaches it as a `CarriedBuild`. Both `kix`
(for `plan::file`) and `kix-bundle` build on `kix-container`, which knows
frames, the seek table, caps, and hashing, and nothing of store paths or
plans. Kix Enterprise depends on `kix` and `kix-bundle` by git rev and
reads plan files through `kix::plan::file`.

### Bundle acceptance checks

- `kix bundle` reads back what it writes and refuses it unless the bundle's
  graph equals the result directory's graph (`result_dir` aside).
  `every_test_cluster_bundles` in `kix-cli/tests/commands_test.rs` bundles
  every cluster `kix list clusters` names; it is ignored by default (about
  10 minutes):
  `cargo test -p kix-cli --test commands_test -- --ignored every_test_cluster_bundles`.
- `kix-bundle/tests/plan_bound.rs` changes honest bundles
  (`kix-bundle/tests/fixtures/`) at random and checks that each is refused
  or deploys exactly the objects its plan document shows. It reaches the
  planner through `kix::plan::fixtures` (the `test-util` feature). It runs 256
  cases by default; pass `PROPTEST_CASES=20000 cargo test -p kix-bundle --release --test plan_bound`
  for a long run.
- `fuzz/` holds libFuzzer targets for `PathsChecked::read` (held to a bound
  on the bytes it allocates, `kix_fuzz::check_paths`), `Bundle::read`, and
  `PlanFile::verify` with every shown manifest read (`kixplan_read`, held to
  `kix_fuzz::PLAN_HOLD_BYTES`), each on files as uploaded and on frames the
  fuzzer changes decompressed (`*_frames`). Seed the plan file targets from
  `kix/tests/fixtures/plan.kixplan`. They build on stable rustc without a
  sanitizer: `cd fuzz && RUSTC_BOOTSTRAP=1 cargo fuzz build -s none -O`, seed
  with `./seed.py <bundle>... seeds` (`kix bundle` of the test clusters), and
  run with `cargo fuzz run -s none -O <target> seeds/raw` (or `seeds/frames`)
  `-- -fork=4 -max_total_time=300 -max_len=2500000 -rss_limit_mb=4096`.
- `.github/workflows/bundle-checks.yml` runs each fuzz target and
  `every_test_cluster_bundles` on pull requests that change the bundle code
  (20 seconds per target), and weekly (two minutes per target). Every
  release pull request runs them.

### Releases

Kix uses semantic versioning. `CHANGELOG.md` lists what each release
changed, and the `release` skill (`.claude/skills/release/SKILL.md`) cuts
one. `CLAUDE.md` § Versioning and breaking changes says what counts as
breaking.

The workspace version in `cli/Cargo.toml` decides when Kix is released. On
each push to main, the `version` job in `.github/workflows/cli-tests.yml`
looks for a `v<version>` tag in this repository. With none yet, the push is
a release, and merging a version change is what makes one. After the tests
pass:

1. The `runtime` matrix job builds `.#kix-runtime-spec` for `x86_64-linux`,
   `aarch64-linux`, and `aarch64-darwin`.
2. The `release` matrix job builds `kix` for each platform (`x86_64-linux` and
   `aarch64-linux` on Ubuntu with `cargo zigbuild` targeting `musl`, and
   `aarch64-darwin` natively on the self-hosted Mac Studio runner
   `kix-macos-nix`), each through `cargo auditable` so the binary carries its
   crate list, runs `cli/runtime/assemble.py` and
   `cli/runtime/legal.py`, and packages each self-contained tarball
   (`kix-<system>.tar.gz`, unpacking to `kix-<version>-<system>/`) containing
   `bin/kix` and `libexec/kix/` (`nix-2.35.4`, `helm-3.19.1`, `helm-4.3.1`,
   `kubectl-1.37.2`, `sops-3.12.1`, `manifest.json`, and
   `THIRD_PARTY_LICENSES`), alongside `kix-<version>-third-party-sources.tar.zst`
   for LGPL compliance. For each binary it writes the RustSec report that
   `cargo audit bin` reads from the binary's embedded crate list, ships it in
   the archive as `share/kix/cargo-audit.json` and beside it as
   `kix-<version>-<system>-cargo-audit.json`, and stops when a binary has no
   crate list or a known vulnerability. The `test` job runs `cargo audit` on
   `cli/Cargo.lock` for every change.
3. The `without-nix` matrix job unpacks each archive on a runner with `/nix`
   unreachable and runs `cli/runtime/without-nix.sh` (`kix doctor`,
   `kix build minimal`, and `kix build helm`). In parallel, the `nix-builder`
   matrix job runs `cli/runtime/nix-builder.sh` on a runner with Nix installed
   as an untrusted user, checking that `kix build helm` produces identical YAML
   under both builders, that an untracked `kix.toml` is refused with the
   `git add kix.toml` hint, and that `nix build .#cluster-helm-activation` works
   on a `builder = "nix"` project.
4. Once `without-nix` and `nix-builder` pass, `publish` uploads the three
   platform archives, the third-party sources archive, the three audit
   reports, and `SHA256SUMS` to the
   public [kix-run/kix-releases](https://github.com/kix-run/kix-releases) as
   `v<version>`, with that version's `CHANGELOG.md` section as the notes, and
   marks it `latest`. The job then tags the commit `v<version>` here, and
   starts the site deploy, which builds kix.run/docs from the new tag
   (`.github/workflows/pages.yml`). Other pushes to main build no binaries.

A workspace version lower than the latest `v*` tag, or a release with no
`CHANGELOG.md` section, fails the `version` job, before anything is built.
Running a failed release again is safe: the job skips a release that
already exists in kix-releases and creates the tag last. A manual run
(`gh workflow run cli-tests.yml --ref <branch>`) builds the binaries as a
workflow artifact, reporting `<version>+<run number>`, and publishes
nothing.

The version reaches the build as `KIX_VERSION`. `kix::VERSION` reads it at
compile time and falls back to the crate version, and everything that
reports a Kix version (`kix --version`, a plan's `kix.version`, compliance
receipts) uses `kix::VERSION`.

## Deploy pipeline

```
new Build (Build::of_flake, or --bundle → Build::carried; checked for a retired domain, then stamped) → Build::installable refuses a stale pin
  → kix::plan::Planner::run(build, OldSide) (kix/src/plan/planner.rs), which prints nothing and reports through PlanEvent:
    → connect, then `TargetChecks::run`: the binding check (`cluster::binding::check`, see "Cluster binding"), the name check (`binding::check_name`), and the Kubernetes version check. A build bound to another Kubernetes cluster, an unbound build where a bound one has deployed, or a key-named build over a cluster that Kix 0.6 deployed as `cluster` is refused before anything else is read
    → the baseline: Baseline::of_cluster (or --current-activation, OldSide::LocalCache: Baseline::of_cache)
      (store path GC'd? → reconstruct old manifests from the live objects naming the Active, Failed, or kept-orphan records: SweepScope::Records { cluster, hashes })
      → load the builds the Active record's status.orphansKeptFrom names
      → leave out the Failed records if another (non-operator) deploy of this cluster is Deploying
      → else load every Failed record and resolve each to its closure in the local store
    → the changes: Baseline::changes
      → detect_changes (identity-hash set diff, local only)
      → fold_failed_closures (re-apply what a failed deploy may have changed, orphan what it left)
      → fold_kept_closures (orphan what the builds in the Active record's status.orphansKeptFrom declared and this build does not)
    → Planner::plan: keep_shared, DeployPlan::from_graph_and_changes (no wave layer), the package diff
      → plan::objects::of: refuse unless every write and delete is one the package-grouped plan shows (see "Writes the plan shows")
  → when connected and there is something to write: the engine over the plan as a dry run (`kix plan`)
  → show package-grouped plan, refused writes, drift → stop if a write would be refused (`--on-error stop`) → confirm
  → CheckedPlan::run → scheduler::run_deploy (DAG-streaming, SSA + readiness per node)
    → record.begin: create the Activation CR and mark it Deploying
  → prune orphans (named in the plan and in `DeployEvent::PruneStart { resources, kept, delete }`, which carries the never-pruned Namespaces and CRDs in `kept` apart from `resources` under every policy, so each renderer lists them as kept; warn-only unless `--prune`) → finalize activation
    (stopped before finalize? → record.abort marks the record Failed)
    (finalize failed? → DeployError::FinalizeFailed: exit non-zero, build not cached as current)
```

## Cluster identity

The `<cluster>` argument is a flake attribute (`clusters.harbor =
./test-harbor.nix` makes it `harbor`). A cluster is identified by its
`buildCluster` `name`, which `mkFlake` defaults to the attribute and a
definition may set itself (`test-harbor`); the build writes it into
`kix-packages.json` (`StoreGraph::cluster_name`) and the Activation record's
`kix.run/cluster` label. Every lookup of cluster state
uses that name: the Activation records, the `SweepScope::Cluster` sweep, and
the local cache files `~/.cache/kix/activations/<name>.{path,root,kept-*}`.
`kix deploy` and `kix gc --hard` take the name from the build, and `kix status`
and `kix inspect` from the evaluated `ClusterOutput::cluster_name()` (the
build's record label; `ClusterOutput::name` is the attribute). Commands that
read state without building, or before building (health, rollback,
`status --operator`, soft gc, gc `--operator`, and compliance attest
`--from-cluster`), call `CommandContext::cluster_identity(arg, Lookup)`.
Evaluating `kixClusters.<attr>.name` forces the definition's `buildCluster`
call, nearly a whole cluster evaluation that needs the flake's inputs, so it
is the last step: with no flake (`--flake` names a directory without
`flake.nix`) the argument is the name; when an Activation record in the
current context carries the argument as its `kix.run/cluster` label
(`activation::records_exist`, one LIST with no discovery) the argument is the
name; otherwise `kix::eval::eval_cluster_name()` evaluates it, and a flake
that does not define the attribute or has no `kixClusters` leaves the
argument. The flake reference goes into the installable
(`<flake>#legacyPackages...`, `eval::cluster_name_command`), so `--flake
github:...` works. When the evaluation fails, `Lookup::Mutating` (rollback,
soft gc, and gc `--operator`) is an error naming the attribute and the failure;
`Lookup::ReadOnly` prints a warning and uses the argument. Soft gc refuses
when the build's `cluster_name` differs from the name it resolved before the
build, and passes the build's name to `keep_shared` and `delete_resources`.
`kix snapshot save` and `kix drift --cluster` need no flake and take the name
itself.

The cache file carries no kube context, so two contexts deploying clusters
of the same name share it. Soft gc takes the old build from the Active
record (`kix::plan::baseline::active_build_dir`, which uses the cache only when
`store::build_hash_of` matches the record's hash), and `kix deploy
--current-activation` refuses after connecting when the cached build is not
the context's Active build (`check_cached_baseline`).

## System resolution

Every flake lookup names the system the `kix` binary was built for
(`eval::nix::current_system`, chosen at compile time from the target
triple): `legacyPackages.<system>.kixClusters`,
`legacyPackages.<system>.kixPackages`, `kixClusters.<attr>.info`, and
`kixClusters.<attr>.activationIndex` (evaluated via `nix eval --raw` into
Kix's local store). There is no `--system` flag and no probing of other
systems; `kix.lib.mkFlake` emits all four systems by default, so a flake
usually has the one Kix asks for. When Nix says the flake "does not provide"
the attribute, the caller runs one `nix eval <flake>#legacyPackages` with
`builtins.attrNames`
(`eval::nix::system_not_provided`). When the current system is absent and
others exist, the lookup fails with `KixEvalError::SystemNotProvided`, which
names both and says how to add the system to `mkFlake`'s `systems`. When
the flake has no such output for any system, `kix list` reports
`NoKixOutputs`, the cluster lookups and the build keep `ClusterNotFound`,
and `eval_cluster_name` keeps `Ok(None)`. When the check itself fails, the
caller keeps that same original meaning. Exit codes do not change.

## Cluster binding

A definition may set `cluster.kubernetes.uid`, the UID of the target
cluster's `kube-system` Namespace, which never changes for the life of a
Kubernetes cluster and differs for every one. The build carries it in
`kix-packages.json` as `kubernetes.uid` (`KixPackageIndex::kubernetes`,
`StoreGraph::kubernetes_uid`; absent in builds from before the field, which
read as unbound), the Nix-rendered Activation record carries it as the
`kix.run/kubernetes-uid` label (`keys::KUBERNETES_UID`), and `Records::submit`
writes the same label on an operator-driven record.

`cluster::binding::check(client, connection, action, cluster, declared)`
runs in every command that applies a build of the definition, after it
connects and before it reads or writes anything else: `Planner::run` under
`OldSide::Cluster` (deploy, plan, `--plan`, `--bundle`, `--operator`),
`deploy::run_deploy_async` and `deploy::run_operator` when the plan did not
connect (`--current-activation`, through `CheckedPlan::target_checks`),
`gc::run_soft` and `gc::run_hard_async` right after connecting, and the
operator's Queued branch (`controller::check_binding`,
which reads only the build's `kix-packages.json`). It has two halves. A
declared UID (`check_declared`) is compared with a GET of
`/api/v1/namespaces/kube-system`; a 403 is its own refusal naming the
permission to grant, worded for the account or for the operator's service
account. An undeclared one (`check_unbound`) lists the Activation records
with the label (`activation::bound_record`, one LIST with no discovery, 404
when the CRD is absent) and refuses if one of them finished a deploy
(`Active` or `Degraded`, or carrying `kix.run/deployed-at`), whichever Kix
cluster wrote it. A Failed or Queued record that never deployed does not
lock the cluster; it then reads the live UID too, so a label that is not this
cluster's (records restored from another cluster, `UnboundRestored`) is
named as such and the advice gives the live UID. `rollback::plan_rollback`
runs only `check_declared`, once the target build is loaded: the target is a
build this Kix cluster deployed here before, so a target from before the
definition was bound is not a wrong-context mistake. The messages
(`BindingError`) lead with "Kix refused to deploy ... Nothing was applied.",
or for `gc` (`binding::Action::GarbageCollect`) "Kix refused to
garbage-collect ... Nothing was deleted.", and name the context and server URL from the kubeconfig
(`binding::Connection::of_context`, no network), or the operator's own API
server (`Connection::InCluster`); API refusals render through
`errors::api_error` as `HTTP <code> <reason>: <message>`. The operator marks
a refused Queued record Failed (`Records::fail_queued`) with the message and
publishes a Warning event (`K8sEventObserver::warn_now`); on a 403 it leaves
the record Queued, publishes the event, and returns an error so the record
is retried. Read-only commands do not check; `kix status` prints the live
UID in its header, and the operator view's JSON as `kubernetes_uid`; the flat
view's JSON stays the bare array (`status::KubernetesId`).
The lock is lifted by removing the label from the records, which the how-to
page documents.

`binding::check_name(client, connection, cluster, name_from_flake_key)` runs
beside the binding check in deploy and plan (`TargetChecks::run`). Kix 0.6
named a cluster `cluster` when its definition called `kix.buildCluster`
without `name`; `mkFlake` now names it after its `clusters` key and marks
that in `kix-packages.json` as `nameFromFlakeKey`
(`KixPackageIndex::name_from_flake_key`, `StoreGraph::name_from_flake_key`;
absent reads as `false`). When it is set, the check refuses
(`BindingError::RenamedByFlake`) if the cluster has no Activation records
for the new name and has some for `cluster` (`activation::records_exist`,
two LISTs with no discovery). Setting `name` in the definition turns it off.

## Kubernetes version check

A definition may set `k8sVersion`, which the build checks every package's
`meta.k8s.minVersion` and `maxVersion` against. The build carries it, as
written, in `kix-packages.json` as `kubernetes.version` beside `uid`
(`KubernetesBinding::version`, `StoreGraph::kubernetes_version`; absent or
`null` means unset, and nothing is compared).
`kubernetes.versionFrom` beside it names the platform whose interface file
supplied the value through `kix.interface`, which sets it with `mkDefault`;
`eval/cluster.nix` derives it from the option's priority and the loaded
interfaces (`KubernetesBinding::version_from`,
`StoreGraph::kubernetes_version_from`), and the refusal for such a build
(`VersionError::MismatchInherited`) names the platform and offers a new
interface file or an override in the definition.
`cluster::kubernetes_version::check(client, connection, cluster, declared,
platform)` runs right after `binding::check` at three of its sites:
`Planner::run` under `OldSide::Cluster`, `deploy::run_deploy_async` when the
plan did not connect (`CheckedPlan::target_checks`), and the operator's Queued branch
(`controller::check_version`, on the same `kix-packages.json` read as the
binding). `kix plan --current-activation` does not connect, so it does not
check; `kix deploy --current-activation` connects after its confirmation and
checks then. `gc` does not run it: the garbage set does not depend on the
version. It reads `/version` once (`kubernetes_version::live_version`,
`LiveVersion { git_version, version }`) and parses `gitVersion` with
`Version::parse`, which drops a leading `v` and anything from the first `-`
or `+` (`v1.31.4+k3s1`, `v1.31.4-eks-2d5f260`, `v1.31.2-gke.1209000`), and
falls back to `major` and `minor` (a trailing `+` on `minor` removed) when
`gitVersion` does not parse or is all zeros, as a development build's
`v0.0.0-master+$Format:%H$` is. `Version::accepts` compares over the parts the
definition writes: `"1.31"` matches any 1.31.x, `"1.31.4"` only 1.31.4; when
the live version is known less precisely than the declared one, the
comparison stops at the parts it knows. `VersionError::Mismatch` carries the
raw `gitVersion` and `Version::suggest`'s value, the live version written as
precisely as the declared one, and its message follows `BindingError`'s
shape ("Kix refused to deploy ... Nothing was applied.", cause, fix);
`VersionError::Read` wraps a failed or unparseable `/version`. `kix plan`
exits as it does on a binding refusal (`PlanError::KubernetesVersion`, exit
1). `rollback::plan_rollback` calls `kubernetes_version::note` instead, which
returns one line on a mismatch and `None` otherwise, including when the
version cannot be read, so the rollback always goes ahead. The operator marks
a refused Queued record Failed (`Records::fail_queued`) and publishes a
`KubernetesVersionRefused` Warning event; a failed read (`VersionError::Read`,
including an unparseable answer) publishes a `KubernetesVersionUnchecked`
Warning event and returns an error, so the record stays Queued and is
retried; an Active record is never checked. `kix status` prints
the live `gitVersion` under the cluster ID (`status::KubernetesId`, the
operator view's JSON `kubernetes_version`). `FakeApi::serve_version` makes
the test apiserver answer `/version`; until it is called, `/version` is 404,
so a test that expects no read fails loudly if one happens.

The DAG-streaming `scheduler` makes each node
eligible the moment its direct predecessors have emitted `Verdict::Ready`,
streams independent subtrees through in parallel, and drives the inline TUI
(`--tui`), which draws a live tree grouped by Kix package. `rollback`, `gc`,
and the operator all run on the same scheduler and `DeployObserver` stream.

## `kix plan`: the deploy pipeline as a dry run

`kix plan` is made by the code that deploys. `plan::prepare`
(`commands/plan.rs`) builds and runs `kix::plan::Planner`, which loads the
old side and computes the actions and the engine plan, as `kix
deploy` does; `plan::dry_run` runs `CheckedPlan::dry_run`, the engine
over that plan through `ops::DryRun`, so every SSA and DELETE goes with
`dryRun=All`, and the run has no Activation record, so its lifecycle writes
(begin, checkpoint, stamping, finalize) never happen; `plan::document` turns the result into the `Plan` document.
`kix deploy` runs the same three steps before it asks for confirmation, and
`kix deploy --dry-run` is `kix plan` with the deploy's flags.

- **What the apiserver said.** `ops::DryRun` keeps a `preview::Journal`: for each object the live object and the dry-run result
  (`apply::ApplyPreview`, returned by `apply_resource` only under dry run),
  a recreate, a prune answer, or a typed `preview::Refusal` (conflict with
  its owners and fields, webhook denial, ValidatingAdmissionPolicy denial,
  webhook without dry-run support, validation with `immutable`, forbidden,
  missing namespace, unknown kind, SOPS decryption).
  `CheckedPlan::dry_run` returns it with the result. Under dry run `apply` takes the
  kind from the discovery cache with no refresh and `rediscover` does
  nothing, since a dry run creates no CRD.
- **Every refusal shows.** The plan runs with `OnErrorPolicy::Continue`, and
  under `dry_run` the scheduler promotes the dependents of a failed node
  instead of cancelling them, because nothing a dry run writes persists.
- **Field changes.** `plan::server::Overlay` starts from the package diff
  the deploy prints and replaces each answered object's entry with the
  server's: `field_changes` compares the live object with the dry-run
  result after `comparable` drops server-maintained metadata, `status`, and
  `deprecated.daemonset.template.generation`, and hides Secret values
  (including `last-applied-configuration` on a Secret). A missing live
  object is an addition; an object with no change drops out; a package the
  build comparison called unchanged becomes changed when the server says so.
- **Fields Kubernetes would not keep.** `cluster::kept::not_kept(sent,
  stored)` runs inside `apply::apply_resource` on every apply, dry run or
  real, against the manifest actually sent (SOPS values hydrated, ceded
  fields stripped after a conflict) and the server's answer. It reports a
  field Kix sent that the answer lacks (`dropped`, a field the CRD's schema
  pruned) or holds at another value (`changed`, a mutating webhook), from
  `structural_diff` of the two after `comparable`. A field only the answer
  has is not a finding. Also kept: a zero value (`""`, `0`, `false`, empty
  map or list) on a kind of a known group (`types::is_known_api`), since Go
  types drop or default it; the same quantity or number in another
  spelling; a Secret's `stringData` stored as base64 `data` (and `data`
  compared by decoded bytes); a list item another stored item of the list
  keeps; a field at or under a path the object cedes (`kix.run/cede-fields`, `[*]` matching any item); `status`; and a namespace on a cluster-scoped object. Secret
  values read `(secret, not shown)`. The findings ride on `ApplyPreview` and
  `DryRunOutcome::Recreated`, and `plan::server::not_kept` collects them
  into the plan's `not_kept` for every create, update, and recreate the dry
  run answered, leaving out custom resources whose CRD this deploy changes
  (`changed_crds`), which were checked against the old schema. The text and
  Markdown print them as a warning after the stops; they neither stop the
  deploy nor count as a change.
- **Not checked.** `plan::document` files an unknown kind whose CRD the
  build brings (a CRD manifest of that group and kind, or a `crd-ref-*`
  import marker for a CRD in its API group), an unknown-kind, invalid, or
  other refusal of an object whose CRD the dry run would change
  (`changed_crds`: the object was checked against the CRD now served), a
  missing namespace the build creates, a webhook without dry-run support,
  and a node the engine never tried under `not_checked`, not as refusals. A
  first deploy is mostly this. An immutable-field refusal followed by a
  `Recreated` answer for the same object is dropped, since the deploy
  recreates it. A recreated object stays in `packages` as changed, with the
  build comparison's field changes when the create could not be dry-run.
- **Deploy stops first.** When the plan has a conflict, a refused write, or a
  refused prune delete and `--on-error stop` (the default), `kix deploy`
  exits 1 before applying anything. `--on-error continue` applies the rest.
- **Exit status.** `kix plan` exits 0 when nothing would change, 2 when
  something would (a prune `delete` fate counts, `Plan::has_changes`), and 3
  when the deploy would stop (a refusal, or a
  stateful migration without `--accept-migrations`).
- **Offline.** `--current-activation` connects to nothing: the plan
  compares the cached build with the new one, `made_by: builds`, and every
  write-path check, and drift, is `not_checked` with reason `builds_only`.
- **Progress.** With `-o markdown`, `main`'s `output_mode` sets
  `progress_on_stderr` for `plan` and `deploy --dry-run`, so the `crate::say!`
  progress lines of `prepare` go to stderr and stdout is the Markdown alone.
  `kix plan -o json|yaml` is refused, pointing at `--save`.
- **Saved.** `--save F` makes the document at `Detail::Manifests` and writes
  it with `crate::plan::save`: `kix::plan::file::write` to a temp file
  beside `F`, `PlanFile::verify` of it, then a rename, as `write_build`
  does for bundles. `kix diff --save` does the same, then cuts the printed
  document down to its `--detail` (`Packages::take_manifests`,
  `Packages::drop_field_changes`).

**Plan files** (`kix/src/plan/file.rs`; the module doc is the
specification). A `.kixplan` is a `kix-container` file: frame 0 the
`Header` (`format` `kixplan`, `version` 1, `plan` at `--detail fields`,
`graph`, a `GraphListing` from `file::graph_of`, which is `kix graph
--format json`'s shape, `shown`, by object id the package key that lists it
(`Packages::take_manifests`; `_cluster` for `cluster_level`, the package it
moves to for a moved object), the SHA-256 of its old and new manifest file,
and its `Rollout`, and `files` as `[sha256, size]` sorted),
then the manifests as compact JSON, each the `--detail manifests` side as
shown (secrets hidden, whole up to 3 MiB, the apiserver's request limit), named by its SHA-256. `write(plan,
graph, out)` takes the manifests out of the plan (`take_manifests`) and
computes `rollout` (a Deployment, StatefulSet, or DaemonSet with a
`$.spec.template.` field change is `restart`, or `on_delete` under that
update strategy; moved from Kix Enterprise's `pods()`). `PlanFile::open`
reads the seek table and the header, counts the header's JSON values
before parsing it (`MAX_HEADER_VALUES`), and checks the file list;
`PlanFile::verify` also reads every file once, checks each against its name
and that it is JSON, and gives the whole file's SHA-256; `old_manifest`,
`new_manifest`, and `file` read one manifest, checked. The caps are in the
module doc. `kix deploy --plan` loads with `verify` and uses `header.plan`;
`plan_sha256` is `sha256:` and that hash. The header's JSON Schema is
`kix-cli/schema/kixplan.schema.json` (same `schemas` test).
`kix/tests/fixtures/plan.kixplan` is the plan file of `file.rs`'s test
plan, and a test fails when Kix writes it differently
(`KIX_WRITE_FIXTURES=1 cargo test -p kix-lib plan::file` rewrites it).

The document (`kix/src/plan/document.rs`, `Plan`) is the one shape a plan
file holds and `kix diff` prints for `-o json` and `-o yaml`: `schema_version`, `made_by`
(`dry_run`, `live_read`, `builds`), `kix` (`KixBuild`: crate version and the
binary's store path), `cluster`, `build` (`Build::of`: result directory and the
Activation record's identity hash), `deployed` (`DeployedBuild`: `kix plan`
from `Planned::baseline`'s Active record, `kix diff` from the old side's record), `flags`
(`PlanFlags`, `kix plan` only), `packages` (typed), `objects_digest`, `objects` (see "Writes the
plan shows" below), and `migrations`, `conflicts`, `admission`,
`drift`, `prune`, and `readiness` as `Checked<T>`, serialized
`{"status":"checked","items":[...]}` or
`{"status":"not_checked","reason":"builds_only|read_only|deployed_build_unavailable|not_previewable"}`,
plus `not_checked` objects, `drift_unchecked` (left out when 0), and
`not_kept` (`[{resource, path, change: dropped|changed, sent, stored}]`,
`kix plan` only, left out when empty). `kix diff --detail plain|fields|manifests`
(default `plain`) sets how much `packages` says about each change (see
`plan/mod.rs` below); a plan file holds `fields`, with the manifests as
files. Its JSON Schema is committed at
`kix-cli/schema/plan.schema.json`, beside the CLI that prints the document;
`schemas` in `kix-cli` fails when the type and the file differ
(regenerate with `KIX_WRITE_SCHEMAS=1 cargo test -p kix-cli
schemas`, and set `SCHEMA_VERSION`, a `YYYY-MM-DD` date string, to the
day's date when a change is not backward compatible). `kix::plan::server`'s tests and the kind integration
test check that a plan and a diff against the same live state list the same
objects, and that a plan writes no record.

**Writes the plan shows** (`kix/src/plan/objects.rs`). People review the
package-grouped `PackageDiff`; the engine runs the flat `DeployPlan`.
`Planner::plan` joins them before the dry run, so `kix plan` and `kix
deploy` both refuse, naming the objects, a build whose plan leaves one out:

- *Writes* (W): every `ChangeAction::Apply` node of the engine plan, and
  every `Skip` node with a `rerun` manifest (a probe Job the engine may
  create again), as (`ResourceId`, store hash of its file). The file is the
  one `new_graph.resources` holds for that id; an id in no file or in two
  files is refused. Hashes come from store paths, not stamped annotations.
- *Shown* (P): `PackageDiff::shown`, filled by `diff_graphs` from the same
  package nodes it lists: every object of an added package, its
  PackageInstance included; the added, modified, and dep-affected
  resources of a changed package and of `cluster_level`; and the new
  Activation record. A package whose PackageInstance changed alone is
  changed. Each write must be in P, or be a *re-apply*: a file that the
  Active closure, a failed closure, or a kept closure already holds for the
  same id (`--reconcile`, the repair of a stopped deploy, a rerun Job).
  Re-applies add no object and no file the cluster's recorded builds lack.
- *Deletes* (D): the orphans the prune deletes under `--prune`
  (`deletes_of`: not `never_pruned`). Each must be removed in the diff
  (`Shown::deletes`, kept and shared ones aside) or, when the plan read the
  cluster, in its `prune` section.
- Outside the check, because Kix writes them and no build file describes
  them: the Activation record's lifecycle writes and the records it
  supersedes, the `kix.run/activations` stamp on unchanged objects,
  `--record-annotation` (never a key under Kix's domain, a subdomain of
  it, or a retired one: `Planned::annotate_record` refuses those, since
  Kix reads them off the record), the `kix.run/*` stamps, SOPS values decrypted into
  a Secret from the source file its store path names, and the delete before
  an immutable-field recreate of a write.
- Not written at all: on a consumer, a build whose record has
  `spec.interfaces`, Kix's own CRDs (`lifecycle::left_to_platform`). Its
  platform installs them, so the engine plan waits for them (a
  `TransitionKind::Wait` node, below) and `diff_graphs` leaves them out of
  the package diff.

The result is `CheckedPlan::objects`, which the document carries as
`objects` (`writes[]`: `kind`, `namespace`, `name`, `store_hash`,
`package`, and `change` = `added|modified|dep_affected|reapplied`; `deletes[]`:
`kind`, `namespace`, and `name`; each sorted) and `objects_digest`
(`plan::objects::digest`): `sha256:` and the hex SHA-256 of the compact JSON
`{"writes":[[kind,namespace,name,store_hash,package],...],"deletes":[[kind,namespace,name],...]}`,
each list sorted by its strings in byte order, `change` left out. The
dry-run overlay can drop a write the apiserver says changes nothing from
`packages`; `objects` still lists it. The text plan prints the counts, the
digest, and how many writes are re-applies. `kix diff` plans no deploy, so
both fields are `null` there.

**Three-way labels** (`kix/src/plan/origin.rs`). With the deployed build's manifests
each field change gets `labels`: `intended` where the deployed and new
builds differ (by path overlap with `structural_diff(deployed, new)`),
`reverts_drift` where the live object differs from the deployed build and
the deploy applies the object, `drift_kept` where it differs and the deploy
skips the object (unchanged identity hash; `--reconcile` applies it).
In a plan, drifted fields go to the `drift` section with the managers
(`drift::foreign_owners`) that own them live. A plan labels what it applies;
`kix diff` labels against the live view (`origin::label_live`), and only on
an object `drift::check_object` finds drifted, and `--from <build>` labels
everything `intended` (`label_builds`). Without the deployed build (its store
path is not on this machine) nothing is labelled. `kix diff`'s `drift` section
needs no build: `origin::live_drift` lists, for each live object
`drift::check_object` finds drifted and the new build contains, every field a
manager other than Kix changed or took over (`drift::foreign_fields`, leaving
out fields Kix's `Apply` entry still owns) that the new build sets, an
unrecorded `/scale` write, or one `$` entry when no field can be named. Its
paths use the diff engine's spelling (`containers[web]`, through
`ForeignField::diff_path`), like the field changes. `drift_unchecked` counts
the objects the check cannot judge (no applied-hash stamp, or no Kix
`managedFields` entry), and the text and Markdown print one line for them. A
drift entry another manager owns at a value other than the deployed one says
the deploy stops on an ownership conflict, unless the plan forces conflicts. A field another
manager took shows as an ownership conflict in a plan unless
`--force-conflicts`, under which it shows as `reverts_drift`.

## First contact: proving the cluster is there

`Client::try_from` never touches the network. Before `client::make_client` ran a
probe, that meant an unreachable cluster hung the *first request* instead of
erroring, and the `"failed to connect to cluster: {e}"` message at all sixteen
call sites was dead code: no error was ever produced for it to print, because
nothing had tried to connect.

There are two failure shapes and they have different owners.

1. **The connect never completes, or is refused.** The transport's
   `connect_timeout` bounds it and knows the cause ("tcp connect error:
   Connection refused", "deadline has elapsed"). The probe's only job is to add
   the endpoint on the way out, which kube alone never does
   (`FetchError::ConnectFailed`).
2. **The connect succeeds and the endpoint then says nothing.** No connect
   timeout can ever fire on this one. Over HTTPS the TLS handshake usually
   turns it into shape 1, but a load balancer that terminates TLS in front of a
   wedged apiserver does not. Only the probe's own deadline bounds it
   (`FetchError::Unreachable`).

The two deadlines are deliberately unequal (`connect_timeout + PROBE_GRACE`) so
they cannot race for the error message. An earlier draft made them equal and
`Unreachable` became unreachable: the transport's deadline always won.

The probe rides the real client with the `FirstContact` extension set, which
drops the retries for that one request. They exist to carry a deploy through an
apiserver restart, not to spend eighteen seconds proving a refused port is
still refused. Riding the real client also means the connection the probe opens
is pooled and reused by the discovery calls that follow, so the probe is a
pre-warm rather than a tax: measured against stage1 and stage2, the median cost is
0.3s and 0.0s. A separate probe client cost ~0.6s on both, all of it a second
TLS handshake thrown away.

Any HTTP response passes the probe, including 401, 403, and 404. That rule is
what stops the probe becoming a failure mode of its own on a cluster where the
account cannot read `/version`: an endpoint that answers at all is alive, and
the real call gets to report the real error. `KIX_PREFLIGHT=0` skips the probe
entirely and restores the previous behaviour.

| endpoint | before | after |
|---|---|---|
| refused port | ~18s, "connection refused" | **0.1s**, endpoint named |
| blackholed address (HTTPS) | 15s, `ServiceError: client error (Connect)` | 15s, endpoint named |
| accepts, then silent (TLS terminated) | **120s**, no endpoint | **20s**, endpoint named |
| stage1, reachable | 4.95s | 5.25s |
| stage2, reachable | 4.60s | 4.58s |


## Baseline: what a plan compares against

A deploy or rollback decides what to do by comparing compiler outputs: the
closure it is about to apply against the closure the cluster already runs.
Live cluster state is consulted to *execute* (SSA, delete) and to *observe*
(readiness), never to decide. Do not add a live read to the
decision path; if the from-side looks wrong, the from-side is what to fix.

The from-side has three parts:

1. The **Active** (or Degraded) record's closure, resolved from the new
   build's `deployed_build` (`--deployed-bundle`), then `built_via`, then
   `resolve_activation_by_hash` (`kix::plan::baseline::record_graph`). A
   build found by `built_via` or by hash is used only when it is the
   record's (its activation store hash is the record's identity hash), and
   a `built_via` path holding another build falls back to the lookup by
   hash before it is refused.
2. Every **Failed** record's closure, resolved the same way. A deploy that
   stops part way applies objects and never becomes Active, so without this
   its leftovers are described by neither side: its orphans are never pruned
   and the objects it changed never read as changed.

3. Every build the Active record lists under `status.orphansKeptFrom`
   (`activation::KeptOrphanSource { activation, identityHash, builtVia }`),
   resolved the same way. A deploy that keeps its orphans (warn-only, the
   default; `--prune-mode=no`; a failed delete) finalizes a record whose own
   closure no longer declares them, so without this the next
   `deploy --prune` says "Nothing to apply" and soft gc says "No garbage
   found", and only `gc --hard` can find them.

`apply::fold_failed_closures` folds the second into the plan. For any resource
a failed closure mentions we do not know which of two compiler outputs the
cluster holds, so a `Skip` whose identity appears there under a different hash
becomes an `Apply` (SSA is idempotent, so guessing wrong costs one unchanged
apply), and an identity only a failed closure has becomes an `Orphan`.
`apply::baseline_manifests` merges the two sets so `prune_order`
(`scheduler/node.rs`) can sort orphans that exist in no current closure; an
orphan with no manifest there is pruned last rather than left out. Both are
pure functions over manifests, unit-tested in `cluster/apply/`.

`apply::fold_kept_closures` folds the third in as orphans only: those builds
were applied in full and then replaced, so they never turn a `Skip` into an
`Apply`. `Baseline::orphans_kept_from` returns an `activation::KeptOrphans`:
`found` is every build the plan compared against (Active, folded Failed, and kept)
for which `apply::leaves_orphans` is true, and `unexamined` is every kept
source this machine could not resolve. It travels in
the checked plan to the run's `ops::ActivationRecord`; the engine passes `orphans_left` to
`DeployRecord::finalize` (true when the policy kept a prunable orphan or a prune
delete failed), and `KeptOrphans::recorded` makes the list `Records::finalize_deploy`
writes: `found` only when `orphans_left`, `unexamined` always (nothing in this
run could have deleted their orphans), and, with `carry_current`
(`--current-activation`, whose plan never read the record), the list on the
record current at finalize. An empty list removes the field. A run that never
finalizes (nothing changed) leaves the Active record's list as it was.
Finalize writes the list whole, so of two deploys planned against the same
Active record, the one that finalizes second drops the first one's kept builds. Users who
want the list to stay empty deploy with `--prune` every time
(`PrunePolicy::Delete` leaves `orphans_left` false unless a delete fails); no
config or env var sets that policy for the CLI, and the operator always runs
with it.

After finalize, deploy and rollback call `baseline::sync_kept_roots` (in
`kix::plan`) with the
list `CheckedPlan::run` returns. It keeps one Nix GC root
per listed build this machine can resolve
(`~/.cache/kix/activations/<cluster>.kept-<identity-hash>`) and removes roots
for builds no longer listed; `<cluster>.root` moves with every deploy, so
without these a listed build is collectable and every later plan reports it
as unreadable. A machine's roots are updated only when that machine finalizes
or gcs.

The package diff's old side is the Active build when this machine has it
(`Baseline::diff_side`). Otherwise it is synthesized from the baseline's
manifests, and each object goes to the package that the Active record's
`status.packageIndex` names for its identity hash, then a folded-in Failed
record's, and only then to where the new build puts that identity. The build
on disk wins over its record's index; when both are present and differ, the
plan logs a debug note and uses the build. A record without a readable index
(Kix 0.5 wrote none, and neither does the operator for an Activation applied by hand or from git) gives the new-build placement, so an object that moved
between packages and changed shows only under its new package.

`kix/src/plan/baseline.rs` does the resolution and owns two refusals: a
record whose closure is not in this machine's store is reported and
deliberately *not* consumed (it keeps asking until someone handles it), and
a non-operator `Deploying` record means another deploy may be in flight, so
the failed closures are left out of the plan and the `kubectl patch` escape
hatch is printed, rather than guessed at. It prints nothing itself: each
finding is a `PlanEvent`, and `kix-cli`'s `plan/progress.rs` prints it, the
unusable-build warnings even under `--quiet`.

One thing the record's new timing changes visibly: it is created before the
first wave, so the plan's last-wave apply of it reports `configured`, not
`created`, and a deploy summary's counts shift by one. Doc captures that show
a record line need regenerating.

- `commands/deploy/` (`mod.rs`, `observer.rs`, `saved_plan.rs`): deploy pipeline: plans through `plan::prepare` and `kix::plan::Planner`, which resolves the old activation (if its store path is gone, GC'd or built elsewhere, `Baseline::of_cluster` rebuilds the old manifest set from the live Kix-managed resources that name the Active record, a Failed record of this cluster, or a build under `orphansKeptFrom` (`inventory::SweepScope::Records`), so another Kix cluster's objects never become orphans, as their Kix-owned view against the new build (`owned_view::kix_owned_manifests_against`), excluding Activation CRs, so change detection and prune ordering still work; the same sweep, grouped by the other builds each object names (`baseline::LiveClosures`), resolves the Failed records and `orphansKeptFrom` sources this machine has no build for, so they are consumed and shortened like locally built ones instead of carried forward with a warning each (`PlanEvent::FailedUnresolved` and `KeptUnresolved` now carry every unresolved record or source at once, printed as one block); `StoreGraph::synthesize` then rebuilds a package-level StoreGraph from the stamped `kix.run/package` annotations + live PackageInstance versions so the plan shows changed/unchanged packages, not everything "added". Same two functions `kix diff` uses for its live and snapshot sides), displays plan (`prepare` is `kix plan`'s; when connected and there is something to write, the plan is the server-side dry run of `commands/plan.rs`, and a plan with refused writes stops the deploy before it applies anything under `--on-error stop`), confirms, and runs the engine through `CheckedPlan::run`. Observer selection: `--tui` (+ interactive stdout) uses `graph_stream::GraphStreamDriver` for the inline tree dashboard; otherwise a line-oriented `StreamCliObserver` (`observer.rs`) prints one line per terminal `Verdict`. `--reconcile` forces re-apply of all resources even when activation identity matches (heals drift). `--dry-run` runs `kix plan` with the same flags (`DeployArgs::plan` is the shared `PlanArgs`). **Exit status and local cache**: `RunEnd::of` reads the engine's result, which is `Ok` with `failed > 0` under `--on-error continue` and after a failed prune delete under either policy. `succeeded` (no failed and no cancelled node) decides the exit status, so any failure exits 1; `current` (no `Err`, no cancelled node, so the engine finalized rather than aborted) decides whether `save_activation_path` caches the build. Rollback uses the same `RunEnd`. The summary line reads `Deploy complete`, `Deploy failed` (some operation failed), or `Deploy stopped` (ended early with nothing failed). `--operator` delegates to `kix-operator` instead; `operator::watch_activation_progress` returns `Reconciled::{Active, Degraded}` and a Degraded record exits 1 after the cache is saved. `--force-conflicts` opts in to SSA force (default off: conflicts surface as `ApplyError::Conflict` with the conflicting field paths and current owner; use this when migrating a resource away from kubectl/helm for the first time). Import markers (PackageInstance with `kix.run/mode: import`) are applied like any other resource: their readiness check in `readiness::wait_for_import_target` polls the cluster for the described kind/name, so imports whose installer is in the same deploy are naturally wave-ordered after it. **Topology label preflight**: after the plan and before the confirmation, when a cluster connection already exists (not under `--current-activation`), `topology::topology_keys` reads every `topologyKey` the new manifests' spread constraints and (anti-)affinity name, `topology::list_nodes` lists the nodes once, and `topology::assess` prints one `warn:` line per label that a schedulable node lacks under a `DoNotSchedule` rule (the compiler derives spread on `cluster.topology.zoneKey` and cannot see a node; without this the first sign was a readiness stall naming the Deployment and nothing else). A 403 on nodes is a `note:`, not a failure. It warns only and never refuses.
- `commands/deploy_log.rs`: non-interactive deploy observers for `--log-format={line,json}`. `LineObserver` emits exactly two events per resource: one on `Verdict::Running + NodeDetail::Applied` ("created"/"configured") and one on terminal `Verdict::Ready` ("ready"). Intermediate `ReadinessProgress` events are suppressed unconditionally: the log is a resource-granular activity stream, not a live dashboard. What it does print for a long wait is the watchdog's `DeployEvent::Waiting` (one `waiting>` line per node at 10s, 30s, 60s, 120s, then every 60s, with the last readiness message and the readiness budget), so a wait on an absent import target is visible before its timeout; `StreamCliObserver` prints the same line dimmed. `JsonObserver` emits NDJSON with the same suppression rule, one `kix::cluster::deploy_log::Line` per event: every object carries `type`, `elapsed_ms`, and `schema_version`, a date set like the plan's. The JSON Schema of `Line` is committed at `kix-cli/schema/deploy-log.schema.json` and checked by the same `schemas` test as the plan's, and `tests/fixtures/deploy-log.ndjson` holds the exact lines of every kind of event. After the run `deploy` calls `JsonObserver::summary`, which prints a `summary` object (`dry_run`, `succeeded`, and the six counts) in place of the text summary line. Under `json` stdout holds only the log: `main` marks it as a document, so the plan and other text before the run go to stderr. `pretty` (the default) is the colored `StreamCliObserver` on TTY stdout and automatically downgrades to `line` on non-TTY. `-v` only expands Unchanged/Skip/Cancelled lines; it never turns on readiness-progress chatter.
- `commands/graph_stream.rs`: inline graph-streaming dashboard. `GraphStreamObserver` implements `DeployObserver` as a cheap mpsc sender; a dedicated OS thread owns a ratatui `Terminal` with an `Inline` viewport (default 3/4 of the screen, override with `--fold-height`), receives `DeployEvent`s + periodic ticks, updates `ViewState`, and redraws the tree. A dimmed `─` rule pinned to the top row of the inline viewport separates scrollback history (above) from the live dashboard (below). Nom-style viewport: every Ready resource is flushed to scrollback the tick it completes; the live viewport only ever contains Running / Failed / AwaitingInput / Drift rows plus a collapsed `N packages pending` summary for work that hasn't started. When all members of a package are flushed, a single package-summary line is emitted to scrollback so history reads as a progressive collapse. Failure frame pins a `⚠ failures` block at the top. Active-resource rows carry the latest readiness-progress message (`⏵ Deployment/foo  ⏱ 12s  2/3 ready`) from `NodeDetail::ReadinessProgress`. On spawn the driver redirects the tracing subscriber to `/tmp/kix-tui-<pid>.log` via `crate::trace_sink`; without that, `-v` under `--tui` would tear the ratatui backing buffer with stderr writes. `Ctrl-C` / `Esc` in the viewport cancels the underlying `CancelToken`.
- `trace_sink.rs`: runtime-switchable tracing writer. Default target is stderr; `GraphStreamDriver` flips it to a per-PID log file for the lifetime of the TUI session via `redirect_to_file()` / `restore_stderr()`. The single MakeWriter entry point `trace_sink::make_writer` is wired into `tracing_subscriber::fmt` in `main.rs`.
- `cluster/scheduler/` prune: an orphan whose kind is `Namespace` or `CustomResourceDefinition` is reported and never deleted (`lifecycle::never_pruned`, shared with `kix gc` in soft and hard mode and with the operator's teardown when an active Activation is deleted). Both take far more with them than the object named (a Namespace takes every object inside it, and a CRD takes every custom resource of that kind on the whole apiserver, including ones no Kix cluster ever touched), and neither is dangerous to leave behind, so removing one is a deliberate human act.
- `cluster/apply/` `ApplyError::CrdStoredVersion`: the apiserver refuses a CRD that drops an API version the cluster still has objects stored at, reporting it as a validation error on `status.storedVersions` that says nothing about what to do. `classify_apply_error` turns it into an error naming the fix: migrate the stored objects to a version the CRD still serves, or keep serving the old one. A deploy meets it whenever a vendored CRD is re-vendored after upstream retires a version.

- `commands/diff.rs`: one comparison of two `StoreGraph`s, rendered by the same `plan::*` producers the deploy plan uses (text, `json`, `yaml`, and `markdown` for PR comments) plus stateful migration pairs. `--detail plain|fields|manifests` (default `plain`) sets how much `json` and `yaml` say about each change; text and markdown ignore it. New side: the flake's build, or `--bundle <file>` read through `kix_bundle::read_build` (content and cluster name checked, as for `kix plan --bundle`). Old side: `--from-bundle <file>` is a bundled build, read the same way; `--from <dir>` is a build result when `kix-packages.json` is inside, otherwise a manifest directory (`kix snapshot save`, `kix export`) synthesized into a graph (`StoreGraph::synthesize`); `--bundle` with neither compares against an empty build, so everything is added and the cluster is not read; otherwise it is the live cluster's objects of the built Kix cluster (`SweepScope::Cluster`, less the objects the build drops that another Kix cluster's current build still contains, which deploy would keep), fetched as the **Kix-owned view** (`owned_view::kix_owned_manifests_against`) and synthesized the same way. A live object whose `kix.run/identity-hash` names a build manifest of the same kind, namespace, and name is replaced by that build manifest carrying the live `kix.run/*` annotations. This is the rule `kix deploy` uses to skip an object (`apply::detect_changes`): the identity hash is the hash of the manifest file, so the build does not change the object, and no server normalisation (an `omitempty` `""` dropped, a field another manager took, `creationTimestamp: null` in an atomic list, a webhook default, a CRD-pruned field) reaches the diff. Whether the object was edited since apply is drift, reported separately. A field the server refused or changed at apply (a field the CRD schema pruned, a value a mutating webhook overwrote) does not show here, because the object compares as its build manifest and the drift stamp is taken from the apply response. `kix plan` reports it in `not_kept` before the write, and `kix deploy` warns about it after the write (`cluster::kept`). Every object not swapped goes through `redact_secret` against the build manifest of the same name: each `data` key in a Secret's view becomes the build's `data` or `stringData` value when the decoded live value equals it, otherwise `HIDDEN_SECRET_VALUE`, and each `stringData` key the build declares and Kix's fieldset lists is restored the same way. No live Secret value reaches the comparison, whether Kix applied the Secret through `data`, through `stringData`, or not at all (no Kix `Apply` entry, so the view is the whole object). A SOPS Secret, whose build has no plaintext, compares on its other fields only, so a value changed out of band does not show. `kix_owned_view` itself (snapshot, deploy plan) runs `redact_secret` with no build, so every Secret value in it is `HIDDEN_SECRET_VALUE`. Only the current record (`activation::current_record`: Active or Degraded, newest `deployed-at`) is kept, so the summary's old activation is the one the cluster runs. A Job Kix built never deletes itself (the library refuses `ttlSecondsAfterFinished` on a Job and `helm.nix` strips it from chart Jobs), so a finished Job is on the cluster and compares like any other object until a later build drops it. `StoreGraph::synthesize_placed` places a live object first by the deployed record's package index (`status.packageIndex`, see `activation/`): when the index lists the object's `kix.run/identity-hash`, the object goes where the deployed build put it, so an object that moved between packages and changed shows removed from its old package and added to its new one, as with the deployed build on disk. `kix diff` reads the current record's index; a plan reads the Active record's, then the folded-in Failed records', newest first (`Baseline::synthesized`). Kept builds name no record, so their objects are not placed by an index. Without an index (a record written by Kix 0.5, one too large to store, an unknown `format`) or for an object the index does not list, `StoreGraph::synthesize` places a live object by its kind, namespace, and name in the new build, and a moved object shows only under its new package: under every build package that lists that identity (the index of a build made by Kix 0.6.0 or earlier can list an import marker such as `secret-ref-*` under several; a newer build lists every path under one package, so the first comparison against a 0.6.0 record shows such a marker as removed from the package that no longer lists it, although nothing is deleted), as a build package's own PackageInstance, or at cluster level. The `kix.run/package` stamp is read only for an identity the build does not have, because a build stamps every PackageInstance, import markers included, `_cluster`, and a marker several packages hold with the package that built it. So a marker whose identity hash moved after a failed deploy still sits under its declaring package as a changed resource, not as a removed package. For an unknown identity, an import marker stamped with a package joins it, and any other PackageInstance (a `kix.mkImport` platform import such as `platform-storage` is stamped `_cluster`) is a package of its own. `PackageDiff` carries `cluster_level` (resources outside any package: Namespaces, CRDs, and cluster-scoped bundles) and `activation` (old → new record name) so nothing the old flat comparison showed is lost. Exit 2 on any difference. It prints the `Plan` document for `-o json|yaml` (`made_by: builds` for `--from <build>`, `--from-bundle`, and `--bundle` alone, `live_read` otherwise; the write-path checks are `not_checked`). Against the live cluster it runs `drift::check_object` on every compared object and fills the `drift` section from the drifted ones (`origin::live_drift`), with or without the deployed build; the deployed value of a field comes from the build manifest when the identity hash is unchanged, else from the deployed build if loaded. When it can load the deployed build (`deployed_build`: the new build when the current record names it, else the record's `kix.run/built-via` directory) it also labels every field change three ways with `origin::label_live`, keeping each compared object's served form for the `managedFields` that name who made a drift; a drift on an object whose identity hash did not change is `drift_kept`. The text and Markdown output end with the drift section, printed after "No differences found." too, and a line saying what a read-only comparison cannot see. Drift alone does not make the exit status 2.
- `commands/plan.rs`: `kix plan`: `prepare` (the build, then `kix::plan::Planner` with the command line's flags or a saved plan's, against `OldSide::LocalCache` under `--current-activation` and the cluster otherwise), then `dry_run` (the engine under dry run with a `DryRunObserver` that counts writes on a stderr progress line and records failed and never-tried nodes), then `document` (the overlay, refusal classification, prune fates from the journal's prune answers, and `not_checked`). `print_text` is the plan text `kix deploy` also prints before confirming; `kix plan` passes `verbose` so every resource and field shows.
- `commands/gc/` (`mod.rs`, `plan.rs`, `render.rs`): soft (DAG diff old vs new) and hard (full cluster scan against a build made now) garbage collection. Both list a garbage Namespace or CRD under "Kept" and never delete it (`plan::split_never_pruned`, `lifecycle::never_pruned`); deploy's plan and offline dry run list never-pruned orphans the same way, apart from the orphans they count for deletion. Hard mode sweeps with `SweepScope::Cluster`, so other Kix clusters' objects never reach the plan (it prints a per-cluster skip count); an object that also names another cluster's current record is kept (`judge_hard`), and with other clusters present an object naming no record is listed as "Unattributed" and judged only with `--include-unattributed`. Hard mode deletes only stamped resources; label-only hits without `kix.run/identity-hash` are listed as "unstamped" and deleted only with `--include-unstamped` (Kix never applied them: inherited labels, kubectl-applied renders). Copies a controller made of Kix objects (`ManagedSweep::copies`) are listed as "Copies" and judged only with `--include-copies` (`judged_objects`); leaving them out does not block `clear_kept`, since they are not Kix's. `--operator` deletes retired (Superseded) Activation CRs; the operator's finalizer only lets them go, since it deletes resources only for an Active, Deploying, or Degraded record. `delete_resources` itself skips never-pruned kinds, so a caller that forgets `split_never_pruned` still cannot delete one. **Record retention** in every mode (`activation::RetentionPolicy`, `retire_plan`, pure and unit-tested): always keep the `--keep` newest Superseded Activation records (default 10) whatever their age, never more than `--keep-max` (default 50), and beyond the floor retire anything older than `--keep-for` (default 30d; `0` off). The floor counts only records that were ever current (rollback targets), so failed deploys cannot push the last rollback target out; a record superseded out of Failed is judged by the age rule, and `--keep-max` still caps everything kept, retiring the oldest such records first. Newest first by parsed `kix.run/deployed-at`, falling back to `status.failure.at` and then `creationTimestamp` for a record whose deploy never finished (the plan prints that time as `failed <t>` or `created <t>`); a record with none of them sorts oldest; ties break on name. Each retired record is deleted with `Preconditions { uid, resourceVersion }` (`Records::retire`), so a record that changed since the listing (a rollback made it Active again) is refused with 409 rather than deleted. The plan connects to the cluster before the Nix build (fail fast, one connection reused for the deletes). Soft mode never touches records otherwise; the deploy record is never soft garbage even though its store hash changes every build (`soft_garbage`). Why retention matters: `kix.run/activations` on every managed resource keeps one hash per deploy whose record still exists, and Kubernetes caps all annotations on an object at 256 KiB, so unbounded records would eventually make every SSA fail with 422; the next deploy after a gc drops the retired hashes (`merge_activation_set`). A listing failure is an error, never an empty plan. **Kept orphans**: `RecordRetirement` also carries the Active record, and soft mode adds `kept_garbage` (objects only a build in its `orphansKeptFrom` declares, resolved by `baseline::load_kept`) to what it deletes, listed under "Orphans kept by earlier deploys". After a run with no failed resource deletes, soft and hard mode call `clear_kept`, which removes the field from the Active record when `may_clear_kept` holds: the build gc compared against is that record's build, and gc examined everything (soft mode: every source resolved; hard mode: the sweep was forbidden no kind). It also drops this machine's kept roots. A 404 on delete is "already gone", not a failure, since a kept orphan may have been removed by hand
- `commands/migrate.rs`: `kix migrate domain <cluster>`, the one-off move of a cluster's Kix records off the retired `kix.dev` API group. Builds the cluster to get its two CRD manifests, always dry-runs first and prints the plan, then copies every Activation record to `kix.run` with spec, status, and history intact, verifies the count, clears the operator finalizer from the old records, and deletes the old CRDs. PackageInstance records are not copied: the next deploy re-creates them. Part of the compatibility layer in `kix/src/legacy_domain/` and goes when that goes.
- `commands/rollback.rs`: rollback to most recent Superseded activation. No Nix build: the target's build comes from `kix::plan::baseline::target_build` (`built_via`, else the cache by hash, refused unless it is the target record's build), and the plan from `kix::plan::Planner`'s `plan` over `Baseline::of_record`, so the plan, the folds of failed and kept closures, and the objects check are deploy's. Once confirmed it runs deploy's `refuse_before_writing` (a record name held by another build, objects without their namespace). `--operator` patches the Activation CR's source path and lets the operator reconcile. `--list` is a read-only history view: enumerates Superseded activations with name, identity-hash, timestamp, source store path (`built_via`), `previousActivation` link, and local-store availability, then exits without prompting, and supports `--output json|yaml` for scripting. Interactive selector and `--list` share `print_superseded_entries()` so both views show the same columns. Before applying, the confirmation modal renders the package-grouped diff via `plan::print_package_plan` against the current Active CR so the operator sees what flips. History is bounded by `kix gc` retention (at least 10 newest, at most 50, nothing older than 30d beyond the floor, by default), so `--list` is finite and a `previous:` link may name a retired record
- `commands/logs.rs`, `commands/pf.rs`: thin wrappers that build the cluster, resolve `<package>` to its primary workload (Deployment / StatefulSet / DaemonSet) via `commands/workload.rs::resolve_package_workload`, extract `spec.selector.matchLabels` as a `kubectl -l` selector, then `exec` into Kix's bundled `kubectl logs`/`kubectl port-forward` (`kix::runtime::Tool::Kubectl`). `--context` is forwarded; logs support `-f/--tail/--since/-c/-p`; pf accepts multiple port specs and `--address`.
- `commands/doctor.rs`: `kix doctor`: locates the bundled runtime directory, checks `manifest.json` against the program versions compiled into `kix`, and verifies the SHA-256 hash of every file and symlink target in `manifest.json`. It also reports the project's builder and where it was chosen (`kix.toml` under `--flake`, the default, or `KIX_TEST_BUILDER`), and fails when `kix.toml` is invalid or names a builder this Kix cannot use. Under the `nix` builder it also reports the machine's Nix (`system_nix::version_line`, failing for Nix older than 2.24, Lix, or no `nix` on `PATH`), and whether `allow-import-from-derivation` is on (`nix config show`, a warning when off). Each line starts with ✓, ! or ✗ and a short name for the check; the runtime's location appears only when `KIX_RUNTIME_DIR` set it, and a problem's detail and fix follow on indented lines.
- `commands/library.rs`: `kix lib update [--dry-run]`: updates the project's `kixpkgs` input in `flake.lock` to `github:kix-run/kixpkgs/v<version>` via `kix::library::update` without modifying `flake.nix`.
- `commands/workload.rs`: shared by logs/pf: builds the cluster (`commands::build_flake`), finds a package by instance name (exact match, ambiguity error with qualified suggestions, or `namespace/name` form), walks its `resource_paths`, and returns a `WorkloadTarget { kind, namespace, name, selector }` using the first Deployment → StatefulSet → DaemonSet it finds.
- `commands/export.rs`: dump built cluster manifests as plain Kubernetes YAML for exit-strategy handoff or audit bundles. Walks the freshly-built `StoreGraph` (same mechanic as `diff.rs` build-to-build mode) and writes each manifest as `<out>/<namespace>/<Kind>-<name>.yaml` via `manifest::serialize::manifests_to_yaml`. Two modes via `--for`: `exit` (default) strips `kix.run/*` annotations using `manifest::hash::strip_kix_annotations` and drops Kix-internal CRs (Activation, PackageInstance), producing neutral YAML a downstream consumer can `kubectl apply`. `audit` preserves stamped provenance annotations and Kix-internal CRs for compliance evidence
- `commands/operator.rs`: shared helpers for operator mode: `connect_and_verify()` (discovers, opens `Records`, which runs the domain gate, and lists one record to check access), then `apply_activation()`, `watch_activation_progress()`, and `wait_for_deletion()`, which take the `Records` it returns
- `commands/health.rs`: cluster integrity walk: indexes live resources by `kix.run/identity-hash`, checks every `kix.run/depends-on` edge resolves within the active activation's reachable set, and reports Healthy/External/Missing/AtRisk. **Graph-presence only: it does not compare field content**; that is `kix drift`'s job. Import-aware: resources with `kix.run/mode: import` annotation show as `external` status instead of healthy/degraded. An absent Job is missing like any other dependency: a Job Kix built never deletes itself, so a finished one is still on the cluster
- `commands/check.rs`: `kix check`, two steps. (1) `eval_cluster`, which is where every build-time check runs: constructor validators, error-level scorecard findings, and the cross-resource resolution checks (`kix/lib/eval/validate.nix`, run by `buildCluster`) all surface here as an eval failure; (2) the scorecard report, `--sarif` for SARIF 2.1.0. No schema or deprecated-API tool runs over the rendered manifests here, and nothing in it reads the flake `checks` output: schema validation is the `schema-cluster-<name>` flake check (`kixChecks.schemaCheck` in `kix/checks.nix`, kubeconform), exported by `mkFlake` for every cluster (for Helm clusters in a default `kix` project it fails under `nix flake check` at the first chart; CI runs `scripts/cluster-checks.sh` over `kix build` output)
- `commands/drift.rs`: `kix drift`, runtime content drift check via applied-hash stamps. Takes no flake; `--cluster` scopes it to one Kix cluster through the Activation records, otherwise it checks every Kix object and each report names its clusters (`DriftReport::clusters`, JSON `clusters`). It compares live objects against the `kix.run/applied-hash` annotations written at deploy time, so it runs from any kubeconfig-only context (no repo, no Nix build). Dispatched in `main.rs` BEFORE `CommandContext` is created (like `completions`) so no Nix backend is ever initialized. Per-resource verdict lines; drifted resources list attributed foreign owners ("spec.template…image taken by kubectl-patch at <ts>") and, when set, the unrecorded replicas change ("spec.replicas changed from 2 to 0 through /scale"); otherwise a drifted object with no other recorded manager prints that Kubernetes recorded no owner. `--output json` for scripting (`foreignOwners`, `unrecordedScale`). Exit 0 = all in-sync/unstamped, 1 = drift found. Tested against recorded managedFields fixtures in `kix/tests/fieldsv1_fixtures.rs`; no kind test covers `kix drift`
- `commands/images.rs`: list all container images in a cluster activation. Extracts image refs from pod specs across Deployments, StatefulSets, DaemonSets, Jobs, CronJobs, and Pods (including initContainers and ephemeralContainers). Default text output is one image per line (suitable for `xargs docker pull`). `--sources` adds per-image resource provenance. `--output json` emits structured `[{image, sources: [{kind, namespace, name, container}]}]` for scripting. Primary use case: airgap preloading (`kix images <cluster> | xargs -P4 -I{} docker pull {}`)
- `commands/pin.rs`: `kix pin`, the promotion verb. Four subcommands over a pin file, committed JSON recording what each image reference resolved to. `set <key> --tag <t>` asks the registry for the tag's manifest digest, refuses a tag that is not there, and rewrites the file; a key `<namespace>/<instance>` is an instance pin (`kix::pins::PinKey::Instance`) for `image` or the option `--option <path>` names, which needs `--repository` when new and no `--init`; `rm <key>` removes an entry from either map; `check --key` and `list` cover both maps; `--init` creates the file or adds a key, `--no-resolve` writes a pin with no digest and says so, `--digest` records a digest you already have, and `--force` overwrites a file that Kix did not write. `check` verifies every recorded digest is still present **by digest, not by tag**: a moved or deleted tag whose digest still runs is a warning, because there is nothing the author can do about it; a missing digest is a failure. `check --source-rev <rev>` is the freshness assertion, failing when a pin records a different source revision, which is the only way to catch a promotion step that did not run. Dispatched in `main.rs` BEFORE `CommandContext` (like `completions` and `drift`): it needs no flake and evaluates no cluster, because the state in which a pin most needs fixing is the state in which evaluation is unhappy about it
- `commands/pin/locate.rs`: finds the pin file when `--pins-file` is absent. It checks the working directory, then the directory named by `--flake` without evaluating the flake, then the git root. At the git root it accepts `pins.json`, or a single `*pins.json` file whose header declares `managedBy`. The marker prevents unrelated JSON files from becoming candidates. The scan does not follow symlinks or run outside a repository, and it refuses to choose when several candidates remain. A flake cannot declare the source path directly because a path literal evaluates to a Nix store path; recovering the original path would require evaluating the flake, which this command avoids
- `commands/compliance/`: compliance exports for auditors, CI, and compliance platforms. Three subcommands, all built on the same `shared::build_and_load` helper that runs `nix build` + loads the StoreGraph:
  - `sbom` emits a CycloneDX 1.6 SBOM to stdout. Walks the StoreGraph to produce a `platform` root component for the cluster, one `application` component per package (`pkg:kix/<ns>/<name>@<version>` purl), one `container` component per unique image (deduped, with optional SHA-256 digest from `@sha256:` refs, `pkg:docker/...?repository_url=<host>` purl), and one `library` component per flake input read from `flake.lock` (`pkg:nix/<name>@<rev>`). The dependency graph is derived from `StoreGraph::cross_deps` plus per-package image edges.
  - `attest` emits an unsigned in-toto Statement with a SLSA v1 provenance predicate. Subject is the activation identity hash (`nixStoreHash` digest type). `externalParameters` include the flake ref and a BLAKE3 digest of the on-disk `flake.lock`; `resolvedDependencies` carry the git HEAD, every flake input's rev/narHash, and every container image, with a `sha256` digest only when the reference actually carries one. `--builder-id` and `--invocation-id` override the `runDetails` block so CI can stamp its workflow URL. `--from-cluster` reads the deploy receipt off the cluster's active Activation instead of building, so the statement describes what **was** deployed rather than what would be, from a machine that has never built this cluster. Both routes go through `receipt::attestation_from_receipt`, so they cannot drift apart.
  - `receipt.rs` is not a subcommand. It assembles the provenance a deploy writes into the Activation's `status` subresource: flake ref, git commit **and whether the tree was dirty**, the `flake.lock` digest, every input, the Kix and Nix versions, and every image the build renders. It omits the manifests: built manifests carry secret values inline, so storing them would make every deploy record a readable credential archive. `shared::git_state` replaced `git_commit` to supply the dirty flag, and `deploy.rs` prints it above the confirmation.
  - `audit` bundles `scorecard-results.sarif`, `sbom.json`, `provenance.json`, `assessment-results.json`, and `audit-report.md` under `--out` (default `./compliance`). The OSCAL assessment maps findings to framework controls via static Rust tables (see `audit.rs`: SOC 2, ISO 27001, DORA, and NIS2). A control is marked `not-satisfied` only if an error-level scorecard finding exists whose rule ID starts with one of the control's declared `required_rules` prefixes. The markdown summary is a self-contained PR-comment-ready report. SARIF generation duplicates the shape used by `kix check --sarif`.

#### runtime (`kix/src/runtime.rs`, `cli/runtime/`)

- `runtime.rs`: locates and verifies Kix's bundled external tools (`Tool`: `Nix`, `NixStore`, `Helm`, `Kubectl`, `Sops`, requested with `Want::Shipped` or `Want::Exact(version)`). Looks up the runtime directory in order: `KIX_RUNTIME_DIR` (when set to a non-empty value; empty `KIX_RUNTIME_DIR=""` is ignored), `../libexec/kix` beside `current_exe()` (after resolving symlinks on the `kix` binary) when it contains `manifest.json`, or `KIX_BUILTIN_RUNTIME_DIR` when it contains `manifest.json`. Normal commands verify `<runtime>/manifest.json` (when present) against `cli/runtime/programs.json` (embedded via `include_str!`) once per process; `runtime::doctor()` also verifies the SHA-256 of every file and symlink target listed in `manifest.json`. `runtime::tool()` prepares a `std::process::Command`. Helm, kubectl, and sops always come from the runtime. For `Nix` and `NixStore` it follows the `NixRunner` this run uses: `Bundled { root }` (the `kix` and `remote` builders) takes the runtime's Nix, and `use_store()` writes `<root>/etc/nix/nix.conf` (`store = <root>`) and sets `NIX_CONF_DIR`, `NIX_STATE_DIR`, `NIX_USER_CONF_FILES=""`, and `NIX_SSL_CERT_FILE` (resolved from the host's system CA bundle locations), with `init_store()` creating the store database once under a lock; `System` (the `nix` builder) runs `nix`/`nix-store` from `PATH` with no Kix settings. `runtime::select_builder(builder, source)` sets the runner and records where the builder came from (`runtime::builder_source()`) once per process (a `OnceLock` beside `runtime()`), and `kix-cli`'s `commands::select_builder` calls it from `main` before any Nix runs. Under `System`, the first Nix command of a run checks the machine's Nix (`system_nix::check_once`: Nix 2.24 or later, not Lix, `nix` on `PATH`) and fails with `RuntimeError::SystemNix`. Kix writes no `nix.conf` then, so every `nix` call passes `--extra-experimental-features` itself. Without a call (unit tests, commands that read no project), `nix_runner()` returns `Bundled`. `KIX_STORE_ROOT` under the `nix` builder is an error (`RuntimeError::StoreRootWithSystemNix`).
- `cli/runtime/`: builds the self-contained runtime tree (`programs.json` pins `nix` `2.35.4`, `helm` `3.19.1` and `4.3.1`, `kubectl` `1.37.2`, and `sops` `3.12.1`; `flake.nix` exposes `.#kix-runtime-spec` from `cli/runtime/default.nix` and `.#kix-runtime` from `cli/runtime/in-store.nix`; `assemble.py` copies the binaries into `libexec/kix/<name>-<version>/`, relocates Mach-O `.dylib` load commands to `@loader_path` on macOS when not `--in-store` (Linux `nix` is a static `musl` binary), and writes `manifest.json`; `legal.py` writes `THIRD_PARTY_LICENSES` and the LGPL source archive; `without-nix.sh` tests the release archive with `/nix` unreachable; `nix-builder.sh` tests the release archive with the machine's Nix as an untrusted user).

#### project (`kix/src/project.rs`)

- `project.rs`: reads `kix.toml` beside `flake.nix` in the `--flake` directory (`ProjectConfig::load`). Its one key, `builder`, is `kix` (the default when the file or key is missing), `nix`, or `remote` (`BuilderKind`); `builder_source` records where the choice came from (`BuilderSource`). Unknown keys, unknown values, and invalid TOML are errors that name the file. `ProjectConfig::check_supported` is the one place that refuses `remote`. `check_agreement` compares the builder with `legacyPackages.<system>.kixConfig.builder`, which the library reads from the same file through Nix and so misses while git does not track `kix.toml`; `eval::nix::eval_activation_index` runs it once per run before it evaluates a cluster (skipped for `KIX_TEST_BUILDER`), and its `ProjectMismatch` names the fix (`git add kix.toml`, `kix lib update` or merging `mkFlake` for a flake without `kixConfig`, or both values). `KIX_TEST_BUILDER` overrides the file, for Kix's own tests only. A remote flake reference gets the default.

#### system_nix (`kix/src/system_nix.rs`)

- `system_nix.rs`: checks the machine's `nix` on `PATH` when `NixRunner::System` (`builder = "nix"`) is selected. `check_once()` runs `check_version()` once per process before the first `nix` or `nix-store` subprocess and caches the result in a `OnceLock`: requires upstream Nix (refusing Lix, which reports `(Lix, like Nix)` in `nix --version`) at version `2.24` (`MIN_VERSION`) or later (for `pipe-operators`), returning `SystemNixError` with the builder's `BuilderSource` and instructions to install Nix 2.24+ or set `builder = "kix"`. Also provides `version_line()`, and `import_from_derivation_allowed()` (reads `allow-import-from-derivation` from `nix config show`) for `kix doctor`.

#### library (`kix/src/library.rs`)

- `library.rs`: checks that the flake's `kixpkgs` library expects the same Helm 3 and Helm 4 versions as the running `kix` binary (`check_helm_versions`, reading `kix/lib/helm-versions.json` via `nix eval` before rendering a Helm chart and returning `HelmMismatch` with instructions to run `kix lib update` or upgrade `kix`), and implements `kix lib update` (`library::update`), which reads and parses `flake.lock` directly, walks the `nodes` graph from the root (skipping `follows` aliases so it finds the declaring input path), refuses pinned tags/commits, forks, or `path:` inputs in `flake.nix` with manual instructions, and updates `flake.lock` to `github:kix-run/kixpkgs/v<version>` via `nix flake lock --override-input`.

#### build_source (`kix/src/build_source.rs`)

- `Build` is the build plan and deploy work from, and a caller cannot hold one unchecked. It is the only way a command or the operator loads a build, new or one a record names. Its fields are private and it has two constructors, each doing every check once: `Build::local(build_path)` loads an activation index JSON file (`kix-activation-<cluster>.json`) or a legacy result directory in Kix's store via `eval::BuildFiles`, validating it (`Build::of_flake(flake, cluster, overrides, status)` runs `eval::nix::eval_activation_index` first, and its `FlakeBuildError` says whether the evaluation or the load failed, so each command keeps its own wording), and `Build::carried(bytes, cluster, read)` hashes the bytes itself, hands them to `read` for a `CarriedBuild` and its `StoreGraph`, and refuses a graph that is not valid or not of `cluster`. Either constructor then runs `legacy_domain::check_build` on the graph as loaded and stamps it (`eval::stamp`), in that order, so a graph is stamped once and the check sees it before stamping upgrades it. Everything else comes through accessors that give only checked results: `graph` (stamped) and `into_graph`, `installable` (consumes the `Build` and gives an `InstallableBuild`, or the check's `LegacyDomainError`; `kix plan`, `kix deploy` (with or without `--bundle`), and `kix migrate domain` take only an `InstallableBuild`, while a build a record names, which can predate the domain move, is never refused), `is_local` (the activation cache and GC root, the dirty-source wording), `carried_provenance` (the maker's `Provenance` and the core's SHA-256, for the receipt's `source.bundle.sha256`; `None` for a local build), `sops_sources(placeholders)` (`SopsSources::Local` for a local build; for a carried one, the carried files a Secret names, each refused unless its store path is made from its bytes, as `SopsSources::Carried`, placeholders for `kix plan`), and `deployed_build(identity_hash)` (a carried build's copy of the build a record names, stamped, refused unless the record has that identity hash and it is valid; `None` for a local build). `CarriedBuild` is the seam a build made elsewhere implements, inside or outside the crate: `sops_files`, `provenance`, and `deployed_build`, each a claim the `Build` checks. `Provenance` lives here; the bundle header re-exports it.

#### plan (`kix/src/plan/`)

- `planner.rs`: `Planner::new(PlanFlags, &dyn Fn(PlanEvent))`. `run(InstallableBuild, &OldSide) -> Planned` connects unless `OldSide::LocalCache`, loads the baseline, and runs `plan`. `plan(build graph, cluster, &Baseline, Option<&Client>) -> CheckedPlan` computes the changes (`Baseline::changes`, the kept-orphan list), keeps apart the orphans another Kix cluster deploys (`keep_shared`, under `cluster`, the name the records were found by), builds the `DeployPlan` and the `PackageDiff`, and runs the objects check, refused with `PlanError::Unshown`. `Planned` is plain data with public fields: the build, its manifests, the client, the baseline, the migration pairs, and the `CheckedPlan`. Its manifests stay private, so `Planned::annotate_record`, which refuses Kix's own keys, is the only way to change them. `CheckedPlan` is made only by the check: its fields are private and read through accessors, and the only changes after the check are `Planned::annotate_record` (`--record-annotation` on the record, refused under Kix's own domain), `Planned::overlay` (the dry run's answers in the package diff, returning the drift, or `None` without the deployed build), and `CheckedPlan::keep_shared` (a plan made without a client, once connected; it only removes orphans from the prune). `CheckedPlan` also keeps the record's manifest (created before the first node), the Failed records the baseline folded in (superseded on finalize), the Kix cluster the check found its records and shared orphans by, and the baseline's manifests (which order the prune); `annotate_record` writes the record copy too. `CheckedPlan::dry_run(Target, config, observer)` runs the engine over the plan through `ops::DryRun` and returns the apiserver's answers with the result (`kix plan`, `kix deploy`'s preview). `CheckedPlan::run(Target, receipt, config, observer)` is how deploy and rollback reach the engine, with the prune policy and conflict handling of the flags the check used. It builds the run's `ops::Cluster` itself, with the cluster, prune policy, conflict handling, old manifests, and the Activation record's name, identity hash, manifest, kept-orphans list, and consumed Failed records all from the checked plan, so the run finalizes and prunes under the cluster the check used and writes the record the check saw; it returns the `status.orphansKeptFrom` finalize wrote with the result. The caller supplies a `Target` and, for a deploy, the receipt. `Target::connect(client, sops)` is the only way to make a `Target`: it discovers through its own client, so the run's records are opened from what that cluster serves, and callers read `Target::discovery` for their own checks. Rollback refuses a target whose build names another Kix cluster than the one it found its records by. `scheduler::run_deploy` is private to the library: the only other way to it is the operator's `live::LivePlan`. So are the writes a run makes on its own: `apply::apply_resource`, `apply::record_activation_on_skipped`, and the record lifecycle writes `Records::begin_deploy`, `fail_deploy`, `record_waves`, and `finalize_deploy`. The one way in to a write outside the engine is `prune_guard::PruneGuard` (`new` and `delete` stay public), because `kix gc` and the operator's finalizer delete through it. `Baseline` has no public constructor but `of_record`. `PlanEvent` and `PlanError` are in `mod.rs`. `PlanFlags::prune_policy` (in `document.rs`) says what a run's prune deletes. Rollback runs `plan` over `Baseline::of_record`, which loads the current record's build through `record_graph`; when it cannot (not on this machine, will not load, or another build), the rollback says so, compares with no current build, and lists the current record as unexamined in the target's `orphansKeptFrom`, so a later prune that can read it removes its objects. A current record with no identity hash names no build to look for and cannot be listed, so the rollback says so (`PlanEvent::ActiveWithoutHash`) and points at `kix gc --hard`. The objects check's tests (`plan_bound_tests.rs`, `kix-bundle/tests/plan_bound.rs`) run `plan`
- `live.rs`: the operator's plan. `LivePlan::sweep(client, &activation, &desired)` takes the Activation record being reconciled, discovers, opens the records past the domain gate (`LivePlanError::Domain`; a failed discovery or sweep is `LivePlanError::Fetch`), sweeps the live objects of the record's Kix cluster (`live::cluster_of`: the `kix.run/cluster` label, else `spec.cluster`; `SweepScope::Cluster`), compares the build with them by identity hash (`detect_changes_live`) and keeps out the orphans another Kix cluster's current build contains, and builds the engine plan from the changes (failing on a graph error or a malformed import marker). The `LivePlan` it returns carries the counts, the shared orphans, and what the sweep left out for the operator's logs, and `LivePlan::run(manage_lifecycle, config, observer)` runs the engine with `PrunePolicy::Delete` and the operator's record settings: that record's identity hash stamped on every write, its lifecycle written only with `manage_lifecycle` (drift correction leaves it alone), no receipt, no record manifest, no conflict takeover, and never marked Failed on abort. `sweep` is the only way to make one, so the operator's plan is always one made from the live objects and its run writes the record it was made for. No check holds it to a package diff.
- `baseline.rs`: the from-side of a plan, shared by deploy, rollback, and soft gc: `Baseline` (the Active record, where its closure came from (`ActiveSource`), the failed and kept closures), made by `of_cluster`, `of_cache`, and `of_record`; `Baseline::changes` (detect, fold failed, fold kept, `--reconcile`), `orphans_kept_from` (the `KeptOrphans` the new record's list is made from), `manifests` (the merged set for display and prune ordering), `ran` (every closure the cluster ran, for the objects check), and `diff_side` (the old side of the package diff); `load_kept` (gc uses it too), `record_graph`, `active_build_dir`, and `sync_kept_roots`, which keeps the GC roots for the listed builds. See "Baseline" above.
- `mod.rs`, `diff.rs`, and `redact.rs`: `PackageDiff`/`PackageChangeDiff` types, `diff_graphs()` for package-level comparison (`diff_garbage()` for soft gc, in `diff.rs`), `split_never_pruned()`, and `document::Packages::of(&PackageDiff, Detail)` (the `packages` section of the `Plan` document). Every format the CLI prints, JSON, YAML, text, and Markdown, starts from the same `PackageDiff`, so they stay in sync. A removed resource whose kind `lifecycle::never_pruned` protects (Namespace, CRD) is never shown as a deletion in any format: `PackageChangeDiff::removed_and_kept()` splits it out, and JSON puts it in `kept_resources`. How much the JSON says is `document::Detail` (`--detail` on `kix diff` and `kix plan`): `Plain` gives each `modified_resources[]` entry `diff_count`; `Fields` adds `changes`, one `{path, change, old?, new?, labels?}` per field (`change` is `added`, `removed`, or `changed`; old to new); `Manifests` adds to that a `manifests` object on each package entry (`changed[]`, `cluster_level`, `added[]`, `removed[]`), `{"<display id>": {"old"?, "new"?}}` for every modified, added, and removed resource (kept ones left out), read through `ManifestIndex` (`redact.rs`): the two graphs for `kix diff`, and for `kix plan` the live object and the dry-run result of each object the apiserver answered for (`ManifestIndex::answered`). A Secret's `data` and `stringData` values, its `kix.run/content-hash` and `kix.run/applied-hash`, and every `checksum/*` annotation read `SECRET_NOT_SHOWN`, or `SECRET_CHANGED_NOT_SHOWN` on the new side when the old side holds a different value at the same path (so a line diff of the two manifests still shows it); a field value over `MAX_SHOWN_VALUE_BYTES` (16 KiB serialized) and a manifest over `MAX_SHOWN_MANIFEST_BYTES` (3 MiB, the apiserver's request body limit) read `(N bytes, not shown)`. Literal `env` values and ConfigMap data are shown as they are. A removed package lists its kept resources too (`PackageInfo::kept`), and every JSON package entry (`added[]`, `removed[]`, `changed[]`, `cluster_level`) carries a `kept_resources` list of display ids, empty where nothing is kept; `added[]`/`removed[]` `resources` is the package's total, kept included. `PackageDiff::resource_totals()` feeds the "real content" count of the text summary and markdown, which leaves kept resources out and counts them as kept. `without_secrets` (`redact.rs`) hides the same values for the text plan. `PackageDiff::labels` holds one label list per entry of a resource's `resource_diffs`. `fixtures` (tests and the `test-util` feature) builds the small graphs the library's and the CLI's diff tests compare
- `objects.rs`: `of` (the writes and deletes of a deploy, each matched to `PackageDiff::shown` or a re-apply, or `Unshown`), and `digest` (the document's `objects_digest`); see "Writes the plan shows"
- `document.rs`: the `Plan` document a plan file holds and `kix diff` prints (see "`kix plan`" above), `Checked<T>`, `NotCheckedReason` (its committed-schema test is in `kix-cli`), `Packages::take_manifests`, and `drop_field_changes`
- `file.rs`: plan files (`.kixplan`): `write`, `graph_of`, `PlanFile` (`open`, `verify`, `file`, `old_manifest`, `new_manifest`, `header`), `Header`, `ShownObject`, `Rollout`, `FileEntry`, `PlanFileError`, and the caps; see "Plan files" above
- `origin.rs`: three-way labels: `ThreeWay::label`, `label_live` (diff against live), `label_builds` (diff `--from <build>`), and `value_at`, which reads a diff-engine path (`$.spec.containers[web].image`) out of an object
- `server.rs`: `Overlay`, which replaces each answered object's package-diff entry with the dry-run field changes and labels them, and `field_changes`/`comparable`
- `saved.rs`: `kix deploy --plan`: `unusable` (schema version, no `objects` or `objects_digest` (a `kix diff` plan), an `objects_digest` its `objects` do not give (an edit), `made_by: builds`, and sections that do not match `made_by`: a `dry_run` plan with no `flags` or with conflicts, admission, or prune not checked, a `live_read` plan with `flags`, which only an edit produces; and a `live_read` plan whose drift is not checked: a diff of a snapshot, or one made without the deployed build), `flags_for` (the saved plan's planning flags; a command-line flag the plan was made without is an error, and a `kix diff` plan refuses `--prune`, `--force-conflicts`, `--reconcile`, and `--accept-migrations`), and `compare(reviewed, fresh) -> Comparison` (cluster; new `identity_hash`; `objects_digest`, refused when either is missing or they differ, with the writes and deletes that differ named (`Rule::Objects`); deployed `identity_hash`, or the record name when a record has none; flags; new conflicts by resource and admission refusals by resource and reason; new `reverted` drift by resource and path; new `delete` prune fates; and, for a `dry_run` plan, objects newly in `not_checked`, whose refusals and drift a dry run could not see). A rule the reviewed plan did not check is `skipped`; a different `kix` is `kix_differs`, never a mismatch: the objects digest already holds the deploy to the reviewed objects and files, and the binary is chosen by whoever deploys. `commands/deploy/` (`saved_plan.rs`) exits `EXIT_STALE` (4) on a mismatch, loads the plan file (`load_saved_plan`, `PlanFile::verify`; its SHA-256 is printed and in the JSON as `plan_sha256`) before any build, compares after `plan::document`, passes the merged planning flags to `run_deploy_async` (the apply never reads `args.plan`), and `check_saved_plan` is `--plan` with `--dry-run`, which exits 4 when stale, 3 when it matches but the deploy would stop (`doc.stops()` or migrations not accepted), and 0 otherwise

#### eval (`kix/src/eval/`)

- `store_graph.rs`: **central data structure.** `StoreGraph` holds the full in-memory DAG: `PackageNode` (instance_name, namespace, version, resource_paths, cross_deps) and `ResourceNode` (store_path, manifest). Built from a `BuildFiles` (an activation index JSON file `kix-activation-<cluster>.json` or a legacy result dir's `kix-packages.json`) + `nix-store -q --graph`, reading manifest bytes from Kix's store via `store::disk_path`. `assemble` (public, shared by every reader of a build) reads each manifest's bytes once, parses them with `manifest_json`, and fails on one it cannot read or parse, and on a package with no `spec.instanceName`. `validate()` runs on every build, whichever reader read it: each manifest's kind, `apiVersion` parts, name, and namespace one URL path segment each (not empty, `.`, or `..`, no `/`, `%`, `?`, `#`; kube-rs puts them in request paths unescaped); each object (kind, namespace, name) once; one Activation record, at `activation_path`, whose `kix.run/cluster` label is the index's `cluster`; each package's PackageInstance among the resources; one package per namespace and instance; and only import markers listed by more than one package. It does not run on `synthesize`'s graphs. `StoreGraph::synthesize(manifests, reference)` builds one from a flat set of stamped manifests instead (live objects' Kix-owned view, a snapshot, an export), and `synthesize_placed(manifests, reference, indexes)` places a manifest whose identity hash one of the `package_index::RecordPackageIndex`es lists where that index puts it before the rules below: a manifest whose kind, namespace, and name the reference holds goes where the reference puts that identity (under every package listing it, as a package's PackageInstance, or at cluster level), and only an unknown identity groups by its `kix.run/package[-namespace]` annotations, where every PackageInstance except an import marker stamped with another package makes a package (resources or not); a package sits at its PackageInstance's store path, `resource_owner` is filled, and a manifest reuses the reference's store path and manifest when its identity hash names a reference manifest of the same kind, namespace, and name (the deploy's skip rule); any other manifest keeps its own content-named synthetic path, so `plan::diff_graphs` sees the change. Used by `deploy` (previous state when the store path is gone) and `diff` (live and `--from <manifest dir>` sides)
- `build_files.rs`: `BuildFiles::read(location)` reads either an activation index JSON file (`kix-activation-<cluster>.json`, written by `builtins.toFile` with `version`, `activation`, `packages`, `scorecard`, `extraImages`, `imageSources`, and `interfaces`) or a legacy activation result directory of symlinks (`activation`, `kix-packages.json`, etc.), mapping logical `/nix/store/...` paths to their physical paths in Kix's store via `store::disk_path` and `store::real_path`.
- `derivation.rs`: minimal ATerm `.drv` parser (`Derivation::parse`) used by `helm.rs` to inspect `kix-helm` placeholder derivations (`outputs`, `input_drvs`, `input_srcs`, `builder`, `args`, `env`) when Nix evaluation needs a Helm chart fetched or rendered.
- `helm.rs` and `helm_yaml.rs`: rootless Helm chart fetching and template rendering without the Nix build sandbox. In `kix/lib/helm.nix`, `fetchHelmChart` and `importChart` emit `derivation { system = "kix-helm"; builder = "kix"; ... }` and read the output back with `builtins.readFile` (import-from-derivation). When `nix eval` hits an unbuilt `kix-helm` derivation, it fails with a message naming the `.drv` or output store path; `helm::pending` (called from `eval::nix::eval_with_helm`) inspects the `.drv` (walking `input_drvs` first so `fetch-chart` runs before `render-chart`), checks that the flake's `kix/lib/helm-versions.json` matches the CLI's bundled Helm versions, runs bundled `helm pull` / `helm template` (Helm 4 by default or Helm 3), converts the multi-document YAML stream to a JSON array in Rust (`helm_yaml::yaml_to_json`, matching `yq -o=json '.'`), registers the output in Kix's Nix store (`nix-store --add-fixed` for fetched tarballs, or `nix-store --dump` + `nix-store --load-db` to register the rendered output at the `.drv`'s input-addressed output store path with its real NAR hash), and `eval_with_helm` retries `nix eval`. Under the `nix` builder the library's nix route renders charts in ordinary derivations, so `eval_with_helm` runs `nix eval` once and never calls `helm::pending`. A `kix-helm` placeholder there is `KixEvalError::PlaceholderUnderNix` (a bug), and Nix's refusal to build during evaluation is `KixEvalError::ImportFromDerivationDisabled`.
- `manifest_json.rs`: the one parser for a build's manifests and `kix-packages.json` (`parse_manifest`, `parse_index`). Refuses a repeated key, serde_json's reserved `$serde_json::private::` key prefix, and nesting past 128. Every reader of a build uses it, so a build in the store and a bundle read the same bytes as the same value.
- `store_path.rs`: Nix store paths computed from content (text paths for `builtins.toFile`, source paths for `builtins.path` of a file, executable or not), so a bundle's paths can be checked without a Nix store. `name_of` accepts only names Nix's `checkName` accepts
- `store.rs`: manages Kix's chroot Nix store root (`bundled_store_root()`: `$KIX_STORE_ROOT`, or `$XDG_CACHE_HOME/kix/store`, or `~/.cache/kix/store` on both Linux and macOS; `store_root()` returns it as `Some` under the `Bundled` runner and `None` under `System`, where every helper leaves `/nix/store` paths unchanged) and translates between logical `/nix/store/...` paths and physical `<store_root>/nix/store/...` paths (`disk_path`, `real_path`, `canonicalize`). Also manages the activation cache at `<cache_dir>/kix/activations/`: `save/load_activation_path()`, `resolve_activation_by_hash()`, `save_activation_path` (registering `<cluster>.root` via `nix-store --add-root`), and `sync_kept_roots` (`<cluster>.kept-<identity-hash>` roots for builds listed under `status.orphansKeptFrom`).
- `evaluator.rs`: `KixEvaluator` wrapping a `Builder` trait with SQLite caching
- `cli_backend.rs`: **production builder.** `LocalBuilder` shells out to the `nix` commands `runtime::tool` gives (Kix's bundled Nix, or the machine's under the `nix` builder): `nix eval --json` of the flake's `kixClusters` (`kixClustersNix` under the `nix` builder, chosen by `eval::nix::clusters_attr`) and `kixPackages` for listing clusters, packages, and cluster info (via `eval::nix::eval_with_helm`, which calls `helm::pending` in a loop whenever evaluation hits an unbuilt `kix-helm` chart derivation), and `eval_activation_index` + a stamped `StoreGraph` for cluster evaluation. Benefits from Nix's built-in eval cache.
- `nix.rs`: every `nix`/`nix-store` command Kix runs (`Tool::Nix` / `Tool::NixStore`, using Kix's local store configured via `<store_root>/etc/nix/nix.conf` and `NIX_CONF_DIR` under `NixRunner::Bundled`, or the machine's `nix` on `PATH` under `NixRunner::System`): `eval_activation_index()` (runs `check_library_builder` once per process to verify `kix.toml` agrees with `legacyPackages.<system>.kixConfig.builder`, then runs `nix eval --raw <flake>#legacyPackages.<system>.<kixClusters|kixClustersNix>.<cluster>.activationIndex`, fulfilling any `kix-helm` derivations along the way via `eval_with_helm`), `flake_revision()` (`nix flake metadata --json`, reporting git `rev` or `dirtyRev`), `closure_graph()`, `path_info()`, `add_gc_root()`, and `version()`. `output()` runs a command and reports a failure with the command, exit status, and shortened stderr (`shorten_trace`)
- `stamp.rs`: `stamp_annotations()`, run by `Build` as it is made, by `Build::deployed_build` on the record's build it returns, and by `kix bundle` on the bundle it reads back to compare with the build (a `CarriedBuild` reader and `CarriedBuild::deployed_build` give unstamped graphs, which `Build` then stamps). It writes `kix.run/*` annotations onto StoreGraph manifests in-place; renames the Record to `<cluster>-<hash12>` so each deploy creates a distinct CR
- `cache.rs`: SQLite cache keyed by BLAKE3 of (flake path + lock + source fingerprint + attr + builder + store root, or a `system-nix` marker under the `System` runner)
- `mock.rs`: `MockBuilder` for tests without Nix

#### kix-bundle (`kix-bundle/src/`)

- `lib.rs`, `read.rs`, and `write.rs`: the format. The crate doc in `lib.rs` is the specification: format 3 (zstd's seekable format; frame 0 the `Header` with `format`, `version`, `kix_rev`, optional `receipt`, and `files` as `[path, size, references]`; data frames; seek table), the record, index, and cluster derived from the references (`Role`), every manifest and the index parsed with `manifest_json`, as a result directory's are, the caps and refusals each with what it protects, and the threat model. `PathsChecked::read` (`read.rs`, used by the Kix Enterprise server) checks the container, every store path, the roles and closure, and parses only the record; `Bundle::read` (agent and CLI) also parses every manifest and returns the `StoreGraph` (`assemble` + `validate`), with `result_dir` `bundle:sha256:<sha>`; `OpenBundle::open` reads the seek table and header only (what `--deployed-bundle` matches records with). `BundleError` messages show the uploader's text through `kix::text::printable`. `Contents::write` (`write.rs`) writes a bundle, and `from_result_dir` gathers one from a result directory with `nix path-info`. Its tests (`tests.rs`) run on `tests/fixtures/`, and check that `kix::plan::fixtures::kix_enterprise_test`, the JSON copy of one fixture that `kix-lib`'s own tests read, is still the build that bundle holds.
- `file.rs`: bundles on disk. `write_build` (`kix bundle`, whose command in `kix-cli/src/commands/bundle.rs` only builds and names the file) reads its output back with `Bundle::read` and refuses it unless the graph equals the result directory's (`result_dir` aside). `read_build` reads the `--bundle` file (at most `MAX_STORED_BYTES`), opens each `--deployed-bundle` header (a format 1 one is set aside with a warning, any other error fails), and makes the `Build::carried` whose reader is `Bundle::read`, for plan, deploy, and graph. `BundleSource` is the bundle's private `CarriedBuild`: `deployed_build` re-reads and re-verifies the file on each call; `sops_files` gives the bundle's `Role::Other` files, and `cluster::secrets` checks each carried SOPS source once per plan (age recipients only, no repeated key, at most 8 MiB of keys and values with YAML aliases expanded) and decrypts it once per deploy; `provenance` is the header's receipt plus `source.bundle.kixRev`.

#### manifest (`kix/src/manifest/`)

- `types.rs`: `ResourceId` (kind/namespace/name), `CLUSTER_SCOPED` constant. Used everywhere
- `workload.rs`: `pod_spec(&Value)`: the one table of where a kind keeps its pod template (`spec` for a Pod, `spec.template.spec` for Deployment/StatefulSet/DaemonSet/ReplicaSet/Job, one level deeper for a CronJob). `kix images`, the SBOM, and the topology preflight all read pod templates through it, so a kind added here is seen by all three
- `lifecycle.rs`: **the one classifier** for what a manifest is: `Lifecycle::{Desired, Marker, Record}` via `lifecycle_of(&Value)` / `lifecycle_of_live(&DynamicObject)`. Desired state is diffed, applied, and pruned; a Marker (PackageInstance with `kix.run/mode: import`) is applied and its target polled; a Record (the Activation) is applied once at the end of a deploy and only ever superseded, never pruned. `record_of()` finds the record in a set. Change detection (`apply.rs`) matches records like any other resource, so an unchanged build is still a `Skip` and the deploy short-circuits, but `Lifecycle::prunable()` keeps them out of the orphan set on both the store and live paths. Every former `kind == "Activation"` / `kix.run/mode == import` check (stamp, deploy, rollback, gc, export, health, readiness, graph, and the operator) reads this instead, and a unit test fails the build if a new comparison of the record kind appears anywhere else. Without this, the previous deploy's record, renamed by stamping on every deploy, reached change detection through the store-graph path and was reported as an orphan on every deploy (and `--prune` would have deleted it before finalize could supersede it)
- `diff/engine.rs`: `structural_diff(a, b)` → `Vec<Difference>` with JSON paths. Keyed-list-aware, and skips the spellings `diff/equivalence.rs` declares equal
- `diff/keyed_lists.rs`: defines which K8s arrays match by key (containers→name, ports→name, env→name, volumeMounts→mountPath, subjects→kind:name, volumeClaimTemplates→metadata.name); any other list whose items all have a unique non-empty `metadata.name`, or else `name`, matches by that name. Lists with no key (`engine.rs` `diff_content_arrays`) pair items with equal content wherever they sit, ignoring members equal to an absent field; if the leftovers sit at the same indexes on both sides, each pair of objects that shares a top-level scalar member with the same value (and each pair of scalars) is diffed in place; every other leftover is reported as removed at its old index and added at its new one
- `diff/equivalence.rs`: what the API server treats as the same: `null` and `[]` equal an absent field (`{}` does not, since `emptyDir: {}` and many CRD fields mean something), `SERVER_DEFAULTS` lists documented defaults that equal an absent or `null` field (`fieldRef.apiVersion: v1`; the `apiVersion`, `kind`, `spec.volumeMode`, and `status` the server adds to each `volumeClaimTemplates` entry; `volumeMounts[].readOnly: false`; probe `initialDelaySeconds`/`timeoutSeconds`/`periodSeconds`/`successThreshold`/`failureThreshold`), and members of `limits`, `requests`, `hard`, and `sizeLimit` compare as resource quantities by amount (`1` = `"1"`, `0.5` = `"500m"`). Matched against the path with list keys stripped. Applies to every comparison, build-to-build included
- `diff/display.rs`: `format_diffs()` renders differences as colored text
- `serialize.rs`: YAML/JSON output (`strip_nulls` removes nulls and ONLY nulls before YAML: an empty map is content, such as `emptyDir: {}` or a CRD's `subresources: {status: {}}`, and `kix build`/`kix export` used to drop them), `load_manifests_from_dir()` for snapshot/export loading (every `.yaml` in the tree, PackageInstances included: they are Kix-managed objects like any other; ids come from the manifest content)
- `hash.rs`: manifest normalization helpers (strip server metadata, Kix annotations, status, and nulls; Blake3 `content_hash`, `hash_value`, and `sort_keys`). The old build-vs-live machinery (`detect_drift`/`project_onto_shape`/`DriftStatus`) has been **deleted**, superseded by `fieldsv1.rs` + `drift.rs` (build-time hashes can't exact-match live objects: server zero-value omission, `stringData`→`data`, and quantity canonicalization). `strip_kix_annotations` stays in active use (export, applied-hash recipe)

#### pins (`kix/src/pins/`)

- `mod.rs`: reading and writing pin files. A pin file is JSON: an envelope `{version, managedBy, images, instances?}` (`deny_unknown_fields`). `images` maps a name to a pin; `instances` maps `<namespace>/<instance>` to option path to pin, and `PinKey` names an entry in either map (`PinFile::get`, `insert`, `remove`, `entries`; `PinFile::parse` reads text fetched from elsewhere, such as a forge). Version 1 has `images` only and version 2 adds `instances`; `render` writes version 1 whenever `instances` is empty, so a file without instance pins stays readable by a version 1 reader, and the reader refuses any other version, and version 1 with `instances`. Entries hold `{repository, tag, digest?, sourceRev?, promotedBy?, resolvedAt?, note?}`. JSON rather than Nix for a checkable reason: reading a Nix file means evaluating it, so reading a pin file would execute whatever it holds, and writing one requires escaping registry-supplied strings into a programming language. The eval cache fingerprints `.json` alongside `.nix`, `.yaml`, and `.yml` (`eval/cache.rs`), so nothing is lost by the choice. A bare map of pins is also accepted on read and is never treated as managed. Writing produces one canonical sorted form, which is why `PinFile::write` refuses a file that does not declare `managedBy` unless forced. `Pin` is `deny_unknown_fields`, matching the Nix reader, so a field Kix does not know is refused rather than silently dropped on the next write; `note` is the field for anything a person wants to say, carried through untouched and stripped by the Nix reader before it reaches the image option. Digests are validated as `sha256:` plus 64 hex characters on the way in

#### registry (`kix/src/registry/`)

- `reference.rs`: parsing `[registry/]repository[:tag][@digest]` with Docker's conventions: a leading segment is a registry only when it has a dot, a port, or is exactly `localhost`, and a bare Docker Hub name gains the `library/` prefix. `docker.io` maps to the `registry-1.docker.io` API host and to the historical `https://index.docker.io/v1/` credential key
- `credentials.rs`: the same places every container tool looks, in order: `KIX_REGISTRY_USERNAME`/`KIX_REGISTRY_PASSWORD`, a per-registry `credHelpers` entry, the general `credsStore` helper (`docker-credential-osxkeychain` and friends), then a literal `auths` entry. Anonymous is a valid outcome, not a failure
- `client.rs`: one question only: does this reference exist, and what is its manifest digest. Handles the bearer-token challenge, prefers index media types so a multi-architecture image resolves to its index digest (which is what a runtime resolves and what `crane digest` prints), and computes the digest from the response body rather than trusting the `Docker-Content-Digest` header, treating a disagreement between the two as an error. Reached only by `kix pin`: resolving a tag during a deploy is a non-goal

#### cluster (`kix/src/cluster/`)

- `apply/` (`mod.rs`, `ssa.rs`): ceded fields: a 409 on an object whose `kix.run/cede-fields` annotation covers every conflicting path (`without_ceded_conflicts`, paths parsed from the apiserver message, `[*]` matching any list element) is retried once without those fields, so an operator that rewrote them keeps them; any other conflict is still `ApplyError::Conflict`. `detect_changes()` (identity-hash set diff → `ChangeAction::Apply/Skip/Orphan`; an old or live object without `kix.run/identity-hash` is never an `Orphan`, since Kix only deletes what it stamped; a `Lifecycle::Record` on the old or live side is dropped before matching, so the previous deploy record can never be an orphan on any path, store-graph, live-reconstruction, or operator), `detect_changes_live()` (compare desired manifests against live cluster resources by identity-hash), `apply_resource()` (SSA via `kube`, field manager `kix`; private to the library, called by the engine's `ops`), `keys::RERUN` / `wants_rerun()` (the `kix.run/rerun: on-change` opt-in the scheduler's rerun rule reads). The SSA response echo is kept (not discarded): `apply_resource` computes the applied-content hash from it (`fieldsv1::applied_content_hash`) and writes `kix.run/applied-hash` in the same post-SSA bookkeeping merge patch as `kix.run/activations` (`update_bookkeeping_annotations`, no extra round trip). That patch also runs under field manager `kix`: leaving it unset records the write as manager `unknown` in managedFields and pollutes ownership-based drift attribution. `merge_activation_set()` is the pure set operation behind `kix.run/activations`: fold in the current activation, drop entries naming an Activation CR that no longer exists (`Records::live_hashes`), always keep the activation being deployed (its own CR lands in the last wave), and return a sorted set so the caller can skip the write when nothing changed. Passing `live = None` disables pruning: keeping a dead reference is recoverable, dropping a live one is not. `record_activation_on_skipped()` is the entry point for resources the deploy did *not* apply; it touches `kix.run/activations` only, never `kix.run/applied-hash`. `fold_failed_closures()` and `baseline_manifests()` are the from-side fold: see "Baseline" above. Both are pure over manifests, so nothing in the decision path reads the cluster
- `graph.rs`: `ResourceGraph` (petgraph DAG built from `kix.run/depends-on` annotations). Import-aware: nodes with `kix.run/mode: import` render as dashed/gray in dot output, `(import)` suffix in tree, and `isImport` field in JSON
- `migrate.rs`: `detect_migration_pairs(new, old)`, run by the planner and `kix diff`. A removed object and an added one in the same instance of a `kix.run/lifecycle: stateful` package pair when they share a kind, or when both may hold data (`may_hold_data`). That reads the library's `kix.run/holds-data` mark (`keys::HOLDS_DATA`) first. An object without one (chart output, or built by a Kix that wrote no mark) falls back to its storage fields (`volumeClaimTemplates`, `resources.requests.storage`, `capacity.storage`, `spec.storage`) and its API group, an unmarked custom resource counting as holding data. A pair stops the deploy until `--accept-migrations`.
- `stream.rs`: graph-streaming vocabulary: `Verdict`, `TransitionKind`, `NodeId`, `NodeDetail`, `NodeMeta`, `PlanNode`, `DeployEvent` (including `Stalled { idle, in_flight: Vec<InFlight { node, phase, since }>, aborting }` from the watchdog and `BestEffortFailed { what, message }` for checkpoint/stamp/finalize failures, and `FieldsNotKept { resource, fields }` when an apply succeeded but the server did not store some fields as sent), `Phase`, `InFlight`, `DeployObserver`, and `DeployResult`. The observer trait consumed by the CLI renderer, the non-interactive line/JSON observers, and the operator's tracing observer
- `scheduler/` (`mod.rs`, `plan.rs`, `node.rs`): **deploy engine**. `DeployPlan::from_graph_and_changes` (`plan.rs`) builds the plan from a `ResourceGraph` + `detect_changes` output, and fails with `readiness::MalformedMarker` on an import marker the library would not have written (see `readiness/`). On a consumer (a record with `spec.interfaces`) it makes Kix's own CRDs `TransitionKind::Wait` nodes: action `Skip`, and an `ImportTarget::left_to_platform` that names the platform and the versions the build's copy serves. The executor (`wait_for_platform`, in `node.rs`) never applies or stamps such a node. It waits through `ResourceIo::wait_ready` for the live CRD to be established and to serve those versions, and its failure messages tell the reader to deploy or upgrade Kix on the platform first. A dry run reads nothing for it. `run_deploy(cluster, plan, orphans, old_manifests, prune, config, observer)` is the ready-queue scheduler, private to the library (callers reach it through `plan::CheckedPlan::run`, `plan::CheckedPlan::dry_run`, or `plan::live::LivePlan::run`, so it only runs a plan the library made; `run_scripted` (test-util) runs any plan against `ScriptedOps`): every node becomes eligible the moment its direct predecessors have emitted `Verdict::Ready`, concurrency bounded by `SchedulerConfig::concurrency` (default `CONCURRENCY=64`). **The engine task never awaits foreign I/O while nodes are in flight**: every node, every discovery refresh, and every checkpoint is a task spawned into one `JoinSet`, and the supervisor's only awaits are that set, the cancel token, and the watchdog. The first shape held node futures in a `FuturesUnordered` and awaited rediscovery inline, which parked every apply and hung a deploy for 35 minutes. **CRD barrier**: a CRD-like node (kind `CustomResourceDefinition`, or an import marker for one) does not promote its dependents until one discovery refresh that started after it completes; several CRDs finishing together share one refresh; a refresh that fails stops the run with `DeployError::DiscoveryFailed { partial }` (a stale view is a partial view); `KubeResources::rediscover` first waits out listed group versions that answer 404 (see `discovery.rs`), so only a refresh that never settles or fails outright stops the run. Failure policy halt-dependents / continue-siblings (default) or halt-on-first-failure under `OnErrorPolicy::Stop`. Cascade-cancels transitive dependents on failure, except under dry run, where a failed node's dependents are still tried (nothing a dry run writes persists, so `kix plan` reports every refusal). A spawned task that panics is `DeployError::Internal`, never a lost node. Cancel (caller or watchdog) is observed through `CancelToken::cancelled()` in the supervisor's `select!`; the reason travels on the token, so a watchdog abort reads "no progress for 600s: waiting on ..." rather than "cancelled". On cancel the supervisor aborts every task and keeps draining the `JoinSet`: a node that finished just before the cancel is still counted, an aborted one becomes `Cancelled`, and only then does the run return; a cancel that lands as the last node finishes is re-checked after the loop so nothing is pruned or finalized. Whatever stops a run (cancel, `OnErrorPolicy::Stop`, a failed refresh), every node without a verdict gets `Cancelled { External }` and counts in `cancelled`, so renderers never leave a row Pending under a `Stopped` footer and the counts add up to the plan. Every post-loop write is bounded too (begin, stamping, each prune delete, final checkpoint, and finalize: 60s each), because the watchdog only watches nodes and the discovery refresh. Immutable-field conflicts recover via `ResourceIo::recreate_in_place` when the rid is pre-authorized in the orphan set (a resource that is in the plan is never in that set, so on a real deploy this branch only serves the unit test; the error text names the two recovery paths and tells the user to delete and deploy again otherwise). Both delete-and-recreate paths (this one and the rerun rule below, which `wants_rerun` limits to Jobs) go through `recreate()`, which refuses the kinds `lifecycle::never_pruned` protects (`recreate_refusal`): the node fails with an error naming the kind and what deleting it would take with it, and the user deletes it with kubectl if intended. **The rerun rule**: a manifest carrying `kix.run/rerun: on-change` (stamped by `kix.healthCheck` on probe Jobs) is never patched. The planner tags a changed one `TransitionKind::Recreate` and keeps the manifest on `PlanNodeEntry::rerun`; the executor calls `ResourceIo::get_live` first and applies plainly when nothing is live (first deploy, deleted by hand) or runs `recreate_in_place` when something is (foreground delete, wait, create), reporting `NodeDetail::Rerun { reason: "changed since the last run" }`. An unchanged one stays `Skip` but still runs a task: when its live object is in a terminal failure (`classify_workload_terminal`) it is recreated with reason "the last run failed", so a probe that failed against a degraded cluster runs again on the next deploy or rollback without a manual delete; a healthy one is counted unchanged and stamped like any Skip. That Skip-path retry is gated by `SchedulerConfig::rerun_failed`: the CLI sets it (a person asked for a run), the operator leaves it off (it diffs against live objects and requeues a failed run every 30 s, so on a degraded cluster it would delete and recreate the probe forever). With it off the Skip path still reads the live object and reports a failed one as `Verdict::Failed` without deleting it, so the gate stays red in the operator's status instead of reading as healthy; the operator still recreates a probe whose hash changed. A finished Job stays on the cluster (the library refuses `ttlSecondsAfterFinished` on a Job), so a live diff sees an unchanged one as present and does not run it again; a later build that drops the Job prunes it. `wants_rerun` honours the annotation on Jobs only: a Deployment stuck on its progress deadline is "failed" to the classifier too, and deleting it would be an outage. Under dry run `recreate_in_place` checks the delete with `dryRun=All` and reports `Created` without applying (the apply would hit the same 422 the real delete avoids). `failed_skipped_jobs(client, discovery, plan)` is what `kix deploy` and `kix rollback` ask before they take the "nothing to apply" exit on an unchanged plan: a failed probe kept the previous activation from switching, so a deploy that reverts to that activation's content sees no change, and without the pre-check the failed Job would never run again; when it names anything the command runs the engine and the Skip path does the rest. **Every skipped Job reads its live object** (`plan::skip_reads_live`), not only rerun ones: a finished Job stays on the cluster, so without the read a bootstrap Job that exhausted its backoff would count as unchanged and healthy on every later deploy and reconcile. A plain Job in a terminal failure is reported `Verdict::Failed` (the message says to change an input or delete it with kubectl and deploy again) and never deleted; one that succeeded or is gone is unchanged and stamped like any Skip. One still running is unchanged at once, unless something in the deploy depends on it (`SchedulerState::is_checked`, which also covers a rerun Job): then `check_unchanged` waits for the run, and a run that fails in that wait gets the same next step from `job_next_step` (`node.rs`). The identity hash covers the sealed manifest and everything upstream of it, so "changed" means the probe, the thing it checks, or something upstream of that moved. Opt-in by annotation, never by kind: applied to every Job it would re-run stackgres bootstrap SQL on any upstream change. Activation CR checkpointing batched every 16 terminal verdicts, one write in flight at most, running totals; the final checkpoint and finalize are awaited inline after the node phase under a 60s bound. Failures of best-effort writes (checkpoint, stamping unchanged resources, and finalize) are `DeployEvent::BestEffortFailed`, rendered by every observer, not `tracing::warn` lines. After a real apply or recreate, `execute_node` emits `DeployEvent::FieldsNotKept` when `ApplyResult::not_kept` (`cluster::kept::not_kept` of the manifest sent against the apply response) is not empty. It is a warning: the node goes on to readiness as usual. Every observer renders it (`warn:` in the interactive output, `warn>` in the line log, a `fields_not_kept` line in the JSON log, a `FieldsNotKept` Warning Event in the operator); a dry run leaves it to the plan's `not_kept`. A `Skip` node runs a task only when something in the deploy depends on it and `SchedulerConfig::check_unchanged` is set (the CLI always; the operator only for a new build, never during drift repair of a running one, which runs every requeue and would fail the record on every cycle for an unchanged object that never reports ready): `SchedulerState::new` walks from every node with a task (`Apply`, `Recreate`, `Wait`, and a `Skip` with a `rerun` manifest) to its predecessors and collects the `Skip` nodes it reaches, through other plain `Skip` nodes too (`checked_unchanged` in `plan.rs`). A skipped Job takes the Job path above, never the plain check below. For those, `check_unchanged` (`node.rs`) waits through `ResourceIo::wait_ready` with `applied_at = None` (a declared failure counts at once) under the normal timeout, so a Deployment that is restarting after a node reboot is waited for like after an apply and the watchdog prints its `waiting` line; a dry run and a kind `is_immediate_kind` lists read nothing, and an import marker waits on its target as usual. A failure is the readiness text plus a sentence saying this deploy did not change the object (`check_unchanged`), then the consequence, then the next step (`next_step_for_unchanged` in `mod.rs`: fix the object, or the import target of a marker, and deploy again; `--on-error continue` only under `SchedulerConfig::names_flags`, which the CLI sets and the operator does not), so a deploy over an object an earlier deploy left broken fails on that object instead of on a dependent or not at all. An unchanged CRD never enters the CRD barrier: its kinds were served before the run began. The event stream is the same as before (`Running`, then `Ready` with `Applied(Unchanged)`, or `Failed`), so observers need no new case. Every other `Skip` node, except a Job (see above), short-circuits without a task. Either way their rids are collected and stamped with the current activation in one concurrent pass once every node is terminal (an unchanged resource still belongs to this activation). A dry run (`ops::Cluster::dry_run`) is non-mutating: SSA and deletes go through `ops::DryRun` with `dryRun=All`, readiness short-circuits, and the run has no record, so begin, checkpoints, stamping, abort, and finalize never happen. The engine learns a run is dry from the `Cluster` alone. Also owns `OnErrorPolicy`, `PrunePolicy`. Tested without a cluster (`engine_tests`): the CRD barrier does not park running nodes, a failed refresh stops the run, a hung refresh is reported and aborted, a hung apply is reported then aborted on the 30/60/90/120 cadence, readiness heartbeats keep the watchdog quiet, cancel returns promptly with every task aborted and every node given a verdict, cancel during readiness never reaches prune or finalize, a hung checkpoint holds nothing, a hung stamp and a hung prune delete are bounded and reported, admission refills a freed slot at once, peak concurrency equals the cap, halt-on-first-failure finishes in-flight nodes and cancels the rest, a panicking task is fatal, gated applies complete only when released, an immutable conflict on a pre-authorized orphan recreates and is not pruned again, a rerun Job with a live object is recreated and without one is applied, a skipped rerun Job is recreated when its live object failed and left alone (and stamped) when it succeeded, a recreate that reports the object still present fails the node with that message, an unchanged predecessor is checked before its dependent runs and fails the deploy on itself when it is broken (naming it, with the dependents cancelled), a running unchanged Job holds back its dependents and is not waited for when nothing depends on it or it has finished, the check walks through unchanged nodes and skips immediate kinds, dry runs, unchanged CRDs (no rediscovery), and plans with nothing to apply, every failure says how many dependents it left undeployed, and a `proptest` over random DAGs with random per-node outcomes (ok, slow, fail, hang, readiness fails, and readiness hangs) checks every node reaches exactly one terminal verdict, in dependency order (by log position), with counts a pure function of the case that add up to the plan. All under `#[tokio::test(start_paused = true)]` wrapped in a one-hour virtual timeout, so a parked engine fails at once
- `ops/`: **the engine's seams to the cluster**. Three crate-private traits (`async_trait`): `ResourceIo` is the plan's objects: per node `apply`, `get_live` (the live object or `None`, a read even under dry run), `recreate_in_place`, and `wait_ready`; per run `rediscover` and `prune`. `DeployRecord` is the run's Activation record as the engine writes it: `begin`, `discovery_refreshed`, `checkpoint`, `stamp_unchanged`, `abort`, and `finalize`. `SecretHydrator` is `hydrate`. A run reaches them through one `ops::Cluster`, made only by `Cluster::new(KubeResources, RecordConfig, SopsSources)`, which builds the record on those same resources, or `Cluster::dry_run(DryRun)`, which has no record; which constructor made it is the one place a run is decided dry. Failures are typed (`RecordWriteError`, `ReadError`, `RecreateError`, `StampError`, and `DeleteError`, sharing `NotDiscovered`, each with a test-util `Scripted(String)` for the fake) and render the text the engine's events carry. When the domain gate refuses mid-run, a run with a record to write fails its begin, checkpoint, abort, and finalize with `RecordWriteError::Domain`, so it does not finalize as if it had no record. The engine never sees an `ApiResource`. `ops/resources.rs::KubeResources` is the real `ResourceIo`: holds the `Client`, the shared discovery cache (`DiscoveryCache = Arc<RwLock<Vec<(ApiResource, Scope)>>>`, refreshes MERGE via `discovery::merge_discovery` because the aggregated discovery doc churns after CRD writes and can transiently omit unrelated groups), kind resolution with refresh-on-miss (`refresh_until_found`: up to five refreshes with backoff, under 4 s of waiting; each a targeted `discovery::discover_group` for the manifest's group, falling back to a full walk when the group fetch fails; `get_live` has no group and always walks in full; the full walk here is `discovery::discover_resources_once`, one pass that leaves out a group version answering 404, so an unrelated group does not add `DISCOVERY_SETTLE` to each attempt), the run's identity hash and conflict handling, the live Activation set the record reads at `begin` (to prune `kix.run/activations`), and the prune guard. `recreate_in_place` treats a 404 on the delete as success (the object was already gone, which is what was wanted), polls up to 30 s for the object to vanish, and if it is still there afterwards returns "still exists 30s after delete (stuck finalizer?); not re-applied" instead of an apply that would fail with the same 422 and say nothing about why; `DryRun`'s sends the delete with `dryRun=All`, skips the poll, and still runs the dry-run apply so schema, admission, RBAC, and field conflicts are checked; only the immutable-field 422 that the real delete would have avoided is mapped to `Created`, which is what the real path produces. `get_live` refreshes discovery on a kind miss, as `apply` does. `prune` treats 404 as success, which matters once a failed closure is folded in: much of it was never created, and pruning something already gone must not count as a failure and land the new record Degraded. `ops/record.rs::ActivationRecord` is the real `DeployRecord`, on `activation::Records` opened from the discovery cache at each write (the record CRD can arrive mid-run), configured by `RecordConfig { name, manifest, receipt, consumed_failed, kept_orphans, mark_failed_on_abort }`. `begin` CREATES the Activation record and marks it Deploying rather than waiting for it to come round as the plan's last node, so a run that stops part way leaves a record of what it was attempting; on a cluster's first deploy that record's own CRD is not served yet, so the create is deferred to `discovery_refreshed`, which the engine calls after a successful refresh at the CRD barrier, the earliest point it can succeed. A run with a record to write whose `begin` meets the domain gate's refusal stops before its first node (`DeployError::BeginFailed`: "Nothing was applied: the deployment record could not be started." and the refusal, which ends with what to do). `abort(reason)` marks the record `Failed` and is called from every early return in `run_deploy` below `begin` (cancel, halt-on-error, discovery failure, and task panic); exactly one of `abort` and `finalize` happens per run, and `mark_failed_on_abort` is false for the operator, whose model is resume-on-requeue. A checkpoint that 404s is not a failure: the Activation CR is a node of the plan and lands in the last wave, so every checkpoint on a cluster's first deploy precedes it. Checkpoint, abort, and finalize are bounded at 30s; `orphans_kept_from` reports what finalize wrote. `ops/sops.rs::SopsHydrator` runs `sops` on `spawn_blocking`. `ops/dry_run.rs::DryRun` wraps `KubeResources` and `SopsHydrator`, which `DryRun::new` makes itself: a `KubeResources` fixes at construction whether its writes persist, and only `DryRun` makes a dry-run one, so no path through it persists a write; every SSA and DELETE goes with `dryRun=All`, `apply` resolves kinds from the cache without refreshing, `rediscover` does nothing, and each object's answer (and each hydration refusal) goes in a `preview::Journal` (see "`kix plan`" above). `ops/scripted.rs::ScriptedOps` (`cfg(test)` or feature `test-util`) is the fake: every call is a `Behaviour` (`Now`, `After(duration)`, `Gate(latch)`, `Hang`, and `Panic`), readiness can `Heartbeat` to model a slow healthy rollout, `NodeScript::live` scripts what `get_live` answers and `NodeScript::recreate` what `recreate_in_place` does, and it records a call log with virtual timestamps plus the peak number of concurrent applies. Nothing in it completes unless the script says so; a fake that answers on first poll cannot show a parked future. It implements all three traits, and `set_dry_run(true)` makes `Cluster::scripted` a dry run without a record.
- `preview.rs`: what a dry-run deploy's apiserver said per object: `DryRunAnswer`, `DryRunOutcome` (`Applied` with the `ApplyPreview`, `Recreated`, `Refused`, and `Pruned`), and `Refusal`, classified from the error status by `Refusal::of_status` (`conflict_owners` reads the managers and fields of a 409, keeping list keys with commas whole)
- `watchdog.rs`: **progress watchdog**. `Progress` is the shared record: last activity of any kind, and per in-flight node its `Phase` (hydrate, apply, readiness, plus `discovery` for the CRD barrier's refresh, tracked under the synthetic node `api-discovery` so a hung refresh is reported and aborted like a hung node) and when it began; readiness status callbacks count as activity, so a ten-minute StatefulSet rollout that reports every 2s is not a stall. `assess(policy, idle, in_flight, last_warned)` is the pure policy (quiet / warn / abort), unit-tested alone. `run` is the task: its own `interval` (`MissedTickBehavior::Delay`, so no catch-up ticks after the stall it is watching for), emits `DeployEvent::Stalled { idle, in_flight, aborting }` at `warn_after` (default 30s) and every `warn_after` after, and at `abort_after` (default 600s, `KIX_STALL_TIMEOUT` seconds, `0` never) cancels the run through the token with the reason. `describe()` renders the one line every observer prints: `no progress for 31s: waiting on Deployment/a@default (apply, 31s), ...`, longest-waiting first, capped at five. Separately from stalls, `Progress` keeps each in-flight node's last readiness message (`set_status`, from the scheduler's `on_status`) and the readiness budget (`set_readiness_budget`), and each tick `due_waits()` emits `DeployEvent::Waiting { node, phase, since, status, budget, holds, holds_total }` for every node whose wait is due a report (`wait_due`: at 10s, then 30s, 60s, 120s, then every 60s). `holds` and `holds_total` say what the wait holds up: the engine hands `Progress` the plan's edges and the nodes that run a task once (`set_plan`, in `Run::new`; a plain `Skip` node is left out even when the scheduler checks its live object, because the count means objects with something to deploy, while a `Skip` node carrying a rerun manifest is in), `emit` marks every node with a terminal verdict `finished`, and `holds()` names the slow node's direct dependents that are resources with work left (sorted by kind, namespace, and name) and counts every such resource behind it, walking through unchanged, finished, and synthetic nodes to reach them. The discovery refresh `set_stands_for` the CRDs it covers, so the `api-discovery` wait reports their dependents. `describe_wait()` renders it as `Service/web@app waiting: import target Service/web not found yet (30s of 180s); 6 objects wait for it: Deployment/foo-operator@foo, Foo/a@apps, Foo/b@apps, and 3 more` (singular `1 object waits for it`, no suffix when nothing waits). The TUI and the operator's Kubernetes events ignore it

- `readiness/` (`mod.rs`, `declared.rs`, `imports.rs`, `terminal.rs`): `expectations()` (`imports.rs`) reads `kix.run/expects` (`apiVersion|Kind|name` entries) and `wait_for_expectations()` polls each in the manifest's namespace (or at cluster scope) before `KubeResources::apply` patches; an object that never appears is `ApplyError::ExpectationUnmet`, naming the expectation and the reason. An import marker's target is looked up at the scope discovery reports for its kind (`kube::discovery::oneshot::pinned_kind`), so a cluster-scoped import (StorageClass, ClusterIssuer) is found; a kind discovery cannot see yet falls back to the marker's namespace. `wait_for_ready()` (`mod.rs`) polls per-kind conditions (Deployment replicas, CRD Established, Job succeeded, etc.). A DaemonSet whose node selector matches no node (`desiredNumberScheduled: 0` with the generation observed) is complete, as `kubectl rollout status` has it. An `OnDelete` DaemonSet is ready once its ready pods match the desired count; its updated count is not waited for, because the controller replaces a pod only when someone deletes it. `daemonset_pending_restart()` (`declared.rs`) returns how many pods still run the previous template, and `wait_for_ready()` then returns `ReadinessResult::ReadyPendingRestart { stale, message }`. The scheduler reports it as `Verdict::Ready` with `NodeDetail::PendingRestart { stale, message }` (a rerun or recreate outcome takes precedence). The message is generic: "the DaemonSet replaces a pod with the current template only when the pod is deleted". The pretty renderer prints `<label> ready, <n> pods pending manual restart (OnDelete): <message>`, the line log the same after `<label>>`, and the JSON log `{"pending_restart": {"stale": n, "message": ...}}`. The deploy's exit status is unchanged. How and when to delete the pods is the package's to document (mayastor's how-to restarts io-engine one node at a time after volume rebuilds finish). A terminal failure comes back as `ReadinessResult::Failed { message, output }`: on a Job-level hit (`backoffLimit` exceeded or a `Failed` condition) `scan_terminal` (`terminal.rs`) lists the Job's pods by the live object's `spec.selector` (the controller-uid selector) and `termination_output` collects each container's `state.terminated.message` (or `lastState`), which the kubelet fills from the log tail when the pod runs with `terminationMessagePolicy: FallbackToLogsOnError`. That is how a probe's `FAIL` lines reach the deploy output without a log API call: the last 20 lines (`TERMINATION_OUTPUT_LINES`), prefixed by container name only when several wrote something, with one leading line saying how many earlier lines were dropped. The scheduler carries them on `NodeDetail::ReadinessFailed { output, .. }`; the pretty renderer prints them dim under the failure line, the line log as `<label>>   | <line>`, the JSON log under `readiness_failed.output`, and the operator appends them to the Warning Event's note. `wait_for_import_target()` (`imports.rs`) handles PackageInstance import markers (`kix.run/mode: import`): parses `kix.run/import-kind/apiversion/name` annotations and polls the described resource. Scope is determined by kind: `CustomResourceDefinition` is cluster-scoped (and waits for `Established=True`), and everything else is namespaced and queried in the marker's own `metadata.namespace` (no `kix.run/import-namespace` annotation: imports always describe a resource in the marker's own namespace). A CRD ref marker (an import marker with `kix.run/crd-kind`, from `scope.mkCRDRef` or `kix.mkImport { crds }`) gives its target the versions it declares in `kix.run/crd-served-versions`; once the CRD is Established, a declared version missing from `spec.versions` or not `served` ends the wait with `ImportMismatch`. The library stamps that annotation on every CRD ref marker, so `import_target_from_manifest` returns `Err(MalformedMarker)` for one that lists no versions (it never falls back to `kix.run/crd-version`, which is only the default version), and `DeployPlan::from_graph_and_changes` passes the error up: `kix deploy`, `kix rollback`, and the operator refuse the build before applying anything. Libraries before 693d550d (2026-10-02) did not stamp it, so a rollback to such a build, or the operator on an Activation naming one, fails with a message to deploy a fresh build. A CRD import without `crd-kind` (`kix.mkImport { kind = "CustomResourceDefinition"; }`) is waited for with no version check. `Secret` imports with a `kix.run/import-secret-keys` annotation also verify every declared key is present in `data` before the marker is considered ready: missing keys produce `ReadinessResult::ImportMismatch { missing_keys, message }`, which `reconcile.rs` surfaces as `ReadinessFailed { missing_keys, .. }` so observers can render the exact missing keys as a structured line. Custom readiness conventions are DECLARED, not hardcoded: a CRD-owning package sets `readiness = { path; equals; }` or `readiness = { condition = { type; status; }; }` on its CRD builder, Kix stamps it on every CR built through the typed chain as the `kix.run/readiness` annotation (JSON `{"path": "/status/...", "equals": "..."}` or `{"condition": {"type": "...", "status": "..."}}`), and `declared_readiness`/`check_readiness` (`declared.rs`) evaluate it before any kind-based rule. The path form compares the value at the path with the string `equals`; a JSON boolean or number compares by its JSON text (`true` matches `"true"`, `3` matches `"3"`, and a float the operator writes as `1.0` matches only `"1.0"`), which is how CloudNativePG's Database and DatabaseRole gate on `status.applied`, and VictoriaMetrics operand CRs gate on `status.updateStatus == "operational"`; the `notEquals` path form is ready while the value is absent or anything else, which is how VictoriaMetrics configuration CRs (VMServiceScrape, VMRule, ...) settle when no VMAgent or VMAlert selects them and still fail on `failed`; the condition form is how StackGres clusters gate on `Bootstrapped=True`, Gateway API kinds on `Accepted`/`Programmed`, and Cilium policies on `Valid`. Neither form takes a status older than the spec: a path rule is unmet while `status.observedGeneration` is below `metadata.generation`, and a condition rule while the matched condition's own `observedGeneration` is, or `status.observedGeneration` when the condition carries none (`condition_observed_generation`, `generation_observed`); either value absent imposes no wait, so an operator that reports neither (CloudNativePG's Cluster) can read as ready from its previous status right after a spec change. The not-ready message then ends `, observed generation <n> of <m>`. The annotation may also carry a `"failed"` list (`DeclaredReadiness { ready: ReadyRule, failed: Vec<FailedRule> }`): `{"condition": {"type", "status", "reason"?}}` or `{"path", "equals", "rejected"?, "hint"?, "message"?}` entries naming the states the controller does not leave on its own (Cilium `Valid=False`, a Velero Backup's `Failed`). `declared_failure(obj, kind, applied_at)` returns the first match for the current spec as `DeclaredFailure { message, confirmed }`. `applied_at` is when this deploy changed the object (`node.rs` takes `Utc::now()` before the apply and passes it when the action was `Created` or `Configured`, `None` otherwise, through `ResourceIo::wait_ready`). `confirmed` is true when the condition's (or status's) `observedGeneration` has reached `metadata.generation`, or, with no generation, when the condition's `lastTransitionTime` (rounded up to the next second, since controllers write it with second precision) is not before `applied_at`; a match for an older generation, or one that transitioned before the apply, is not reported at all. `wait_for_ready` feeds the result to a `FailureWatch` after `scan_terminal` and before the ready check: a confirmed match ends the wait at once as `ReadinessResult::Failed`, and an unconfirmed one (neither field, as on a phase path) only after it has held for `DECLARED_FAILURE_GRACE` (10 s), since right after an apply the status may still be the verdict on the previous spec. A condition entry, or a path entry with `rejected`, is a verdict on the spec: `its controller rejected it with <Type>=<Status> (<reason>): <message>. This will not fix itself, so Kix stopped waiting. Change this <Kind> in the package or cluster definition that creates it, then deploy again.` (`rejected_message`; the path form reports `status.phase=<value>` and quotes the values at the entry's `message` pointers, a list joined by `; `). Any other path entry is a runtime outcome: `its controller set status.phase=<value> (<quoted>), a state it does not leave on its own, so Kix stopped waiting. <hint>`, falling back to `Find the cause in the object's status, fix it, then deploy again.` (`outcome_message`). A `failed` entry that does not parse is dropped on its own, and a library that predates the key writes none, so skew in either direction only makes the deploy wait as before. The `match` in `check_readiness` covers only kinds whose readiness Kubernetes itself defines; an operator's vocabulary never goes there. Malformed annotations fall through to kind rules (version skew ≠ unhealthy); note the un-annotated half of that skew: manifests built by a pre-declaration library have no annotation, and a status-less CR then hits `check_generic_ready`'s ready-on-empty, racing its operator instead of timing out, so rebuild such manifests rather than relying on the fallthrough. A generic-CR readiness timeout lists the condition vocabulary it observed and points at the declaration mechanism.
- `activation/` (`mod.rs`, `record.rs`, `retention.rs`): the deploy records (Activation CRs) and their lifecycle: phase-based model (Queued → Deploying → Active → Superseded). **`Records` is the one handle on them**, and a caller cannot hold one unchecked: `Records::open(client, discovery)` runs the domain gate (`legacy_domain::check_discovery`) and returns `OpenedRecords`, which only it makes from discovery: the records, or none when the cluster does not serve the Activation kind, so "no records" cannot be mistaken for a refused gate; `open_installed` makes a missing kind an `OpenError::NotInstalled`. Reads take the Kix cluster by its `kix.run/cluster` label: `active` (Active or Degraded), `failed`, `deploying`, `queued` (the operator's: phase-less or Queued with `spec.source`), `superseded` (every one, for retention), `rollback_targets` (`superseded` filtered by `Record::was_ever_current`), and `receipt`; plus `get(name)`, `identity_hash_of(name)`, and `live_hashes` (every record of every cluster, for pruning `kix.run/activations`). Writes: `begin_deploy`, `record_waves`, `fail_deploy`, `finalize_deploy`, `supersede`, `retire` (delete only if uid and resourceVersion are unchanged, as the apiserver's delete preconditions; a record built without a deploy has both empty, so the apiserver refuses it), `clear_orphans_kept_from`, and for operator mode `submit`, `write_receipt`, `set_finalizers`, and the operator's `watcher`. All status writes use `patch_status` (status subresource). Reads return `Record` (`record.rs`), one typed view (`Record::of(&DynamicObject)`: phase, identity hash, built-via, deployed-at, previous activation, failure reason and time, creation time, whether the operator drives it, `orphansKeptFrom`, wave progress, whether it is being deleted, and uid and resourceVersion, which are empty for a record built without a deploy). Every failure is a `RecordsError`, which names the operation and the record. `status.orphansKeptFrom` (`KeptOrphanSource`, `KeptOrphans`) names the builds whose orphans the finalizing deploy kept. `status.packageIndex` (`eval::package_index::RecordPackageIndex`, read into `Record::package_index`) is the build's package index, written by `begin_deploy` in a second status patch from `RecordConfig::package_index` (the CLI's `CheckedPlan` computes it from the new build, `CheckedPlan::package_index`). `kix deploy --operator` and `kix rollback --operator` write it through `Records::write_package_index` when they submit the record, because the operator holds no build graph: `{ "format": 1, "packages": { "<ns>/<instance>": { "instance": <PackageInstance identity hash>, "resources": [<identity hashes>] } }, "clusterLevel": [<identity hashes>] }`. About 35 bytes an object (some 13 KB for 25 packages and 331 objects). An index over `package_index::MAX_BYTES` (150 KiB, some 3,600 objects; every record listing reads up to 50 indexes) is not written, and a failed write only warns, because the index is a convenience for diffs and never the only source. A reader skips an index whose `format` it does not know. `status.previousActivation` links activations for rollback. `record_waves()` accepts accumulated wave records to avoid GET-before-PATCH round-trips. Full phase model is `Queued → Deploying → Active|Degraded|Failed → Superseded`. `PHASE_FAILED` is terminal and deliberately NOT matched by `active`: a half-applied closure is not the cluster's current state, and diffing against it would read every object only the Active closure has as an orphan, which `--prune` would then delete. `current_record()` (also `kix diff`'s, over live objects) makes `active` deterministic when a cluster holds two current records (newest `deployed-at`, ties on name) instead of taking whichever the apiserver listed first. `phase_on_begin()` leaves an Active record alone, so re-deploying the closure that is already current cannot demote it and then die leaving no current record at all; `phase_on_abort()` only fails a record this run marked Deploying. `fail_deploy()` writes the phase and `status.failure.{reason,at}`. `finalize_deploy()` takes `consumed_failed` and supersedes those records, skipping the one being finalized so a retry of a failed closure still lands Active. `Record::retention_time()` falls back to `status.failure.at` then `creationTimestamp`, so a record superseded out of `Failed` is retired by when it failed, not as `UnknownAge`. Retention itself (`RetentionPolicy`, `retire_plan`, in `retention.rs`) is pure; its floor counts only records that were ever current, a record that never finished a deploy is judged by age, and the cap holds for everything kept, retiring the oldest never-finished records first; its wording (`humanize`, the reasons) is `commands/gc/`'s (`render.rs`). `records_exist` (one LIST, no discovery) is outside `Records`: it only decides how a command-line argument is read
- `tenancy.rs`: which Kix cluster each record, and so each object, belongs to: `Tenancy` (from every record's `kix.run/cluster` label), `named_hashes` (the record hashes an object names), and `read(&OpenedRecords, cluster)`, one unfiltered LIST of the records through `Records`. - `client.rs`: **the apiserver transport policy**, applied once so every call site inherits it. `make_client(context, policy)` builds through `build_client`, then, unless `policy.preflight` is off, proves the endpoint answers before handing the client over (see "First contact" below). The library does not read the transport policy from the environment. Only the binaries call `ResiliencePolicy::from_env()`, in the operator's `main` and in `kix-cli`'s `client.rs`, whose `make_client(context)` every command connects through. `build_client(config, policy)` wraps kube's tower stack in `ResilienceLayer`: retries (429 for every method with `Retry-After` honoured; 5xx and connection loss for idempotent methods only, so a POST is retried only when the connection never opened), exponential backoff with equal jitter under a total budget, and a per-attempt deadline for non-watch requests. Watches bypass the deadline. It deliberately holds **no** in-flight cap: the first version did, and a permit held inside a future that the scheduler had parked (its `FuturesUnordered` is not polled while it awaits CRD rediscovery inline) deadlocked `kix deploy` with every thread idle, and no deadline can fire in a future nobody polls. Burst control lives in the sweep instead. When the budget is spent the last response or error is returned unchanged, so callers see the same `kube::Error` they always did. `decide()` is the pure policy, unit-tested against a scripted fake service. Knobs: `ResiliencePolicy` (defaults sized to outlast a webhook pod restart) with env overrides `KIX_RETRY_ATTEMPTS`, `KIX_REQUEST_TIMEOUT`, and `KIX_CONNECT_TIMEOUT`. A request carrying the `FirstContact` extension (`mark_first_contact`) gets one attempt and no deadline of its own: that is the probe in `client::make_client`. Persistence is what carries a deploy through an apiserver restart, but a cluster that is not there will not become there, and seven attempts over a 60s budget only delay the error (a refused port: ~18s with the retries, 0.1s without). It is an extension on the real client's request rather than a second client from a second policy, because a second client means a second connection pool: the probe would pay its own TLS handshake and throw the connection away, measured at ~0.6s against stage1 and stage2 on every cluster command. `decide()` is left untouched by this; `run()` short-circuits, so the pure policy does not grow a special case. The old per-patch retry loop in `apply.rs` is gone; it was one file's private copy of this

Verdicts: `InSync`, `Drifted { foreign }`, `Unstamped` (no stamp, NOT drift), and `NoFieldset` (managedFields stripped). Attribution: `foreign_owners` flattens every other manager's fieldsV1 into field paths with manager/operation/subresource/timestamp, excluding ONLY `subresource == "status"`. A `/scale` write appears there (subresource `scale`, `spec.replicas`, no timestamp) only when it sets a non-zero value and some manager owned `spec.replicas` before it. Any other `/scale` write (to 0, or after a scale to 0, as `kubectl scale --replicas=0` and back does) takes `spec.replicas` from Kix's `Apply` entry and records no owner (apiserver ScaleHandler plus skip-tracking for objects without managedFields). For Deployment, ReplicaSet, StatefulSet, and ReplicationController whose live `spec.replicas` no entry owns, `unrecorded_scale` hashes Kix's projection with `spec.replicas` set to each value 0..=1024; a match against the stamp yields `UnrecordedScale { deployed, live }` and proves replicas is the only Kix-owned field that changed. Not attributed: a custom resource's `/scale` (its replicas path lives in the CRD), an unrecorded replicas change combined with any other change to Kix's fields, and other changes that no entry records. PI `spec.driftIgnore` evaluation is a marked TODO hook
- `manifest/keys.rs`: the one place the Kix domain is spelled in Rust, and the annotations, labels, CRD names, API groups, and tool URIs built from it that the CLI and operator use. Keys only the Nix library writes live in `kix/lib/core/annotations.nix` alone. Reads of a Kix key go through `keys::get` / `get_meta` / `contains_meta`, never a direct map lookup: those are the one place a retired domain is tried as a fallback. A test fails if any other file in `kix/` or `cli/` spells a Kix domain in a string literal. The Nix half is `kix/lib/core/annotations.nix`.
- `legacy_domain/`: everything that exists only because clusters were deployed under a retired domain: the read fallback, the load-time manifest upgrade (keys, labels, and a record's own `apiVersion`), the bookkeeping null-outs, the gate that refuses an unmigrated cluster (`check_discovery`, run by `Records::open` and by `kix diff` and `kix plan`, which read objects but no records), and the migration itself. Four one-line hooks reach it. `DOMAINS` empty makes all of it inert.

## Key patterns

**Identity-hash** is the core primitive: the first 32 characters of a Nix store path. An identical hash means identical content and dependencies, so change detection is a hash-set comparison rather than a deep diff.

**StoreGraph** is the in-memory DAG built from `kix-packages.json` and Nix store references. Change detection, plan display, stamping, and GC all operate on `StoreGraph` pairs (old and new).

**Keyed-list diff.** The diff engine matches K8s arrays by natural keys (containers by `name`, ports by `name`, env by `name`, and volumeMounts by `mountPath`; other lists of objects by `metadata.name` or `name`), not by position. Without this, reordering items produces false diffs.

**Waves** are computed with Kahn's algorithm on the `kix.run/depends-on` DAG. Resources within a wave are independent and sorted lexicographically for determinism.

**Annotations** are stamped at build time: `kix.run/identity-hash`, `kix.run/package`, `kix.run/depends-on`, and `kix.run/activations`. Everything downstream reads these annotations rather than raw store paths.

**Builder abstraction.** The `Builder` trait (`eval/evaluator.rs`) is what a project's builder does: evaluate a cluster, list clusters, list packages, and list a cluster's packages. Its contract does not assume the work happens locally: a result names store paths the builder has made available in the local store. It has two implementations: `LocalBuilder` (production, which shells out to the `nix` CLI) and `MockBuilder` (tests, which runs without Nix).

**Operator mode** (`--operator` flag on `deploy`, `rollback`, and `gc`). Instead of calling the reconcile engine directly, the CLI creates or patches Activation CRs and watches their status while the operator applies the resources. Building and plan display still happen locally because they require Nix. It supports three flows:
- `deploy --operator`: build locally → show plan → apply Activation CR with source path → watch status.waves
- `rollback --operator`: find superseded activation → patch Activation CR source path to target → watch progress
- `gc --operator`: delete the Superseded Activation records the retention policy retires → the operator removes its finalizer and deletes no resources (it tears resources down only for an Active, Deploying, or Degraded record, and keeps Namespaces and CRDs even then, plus any object another Kix cluster's current build contains, through `PruneGuard`)

**Operator K8s Events**. The operator composes two `DeployObserver`s over the same `DeployEvent` stream: `OperatorObserver` emits structured tracing logs, and `K8sEventObserver` publishes K8s Events on the Activation CR via `kube::runtime::events::Recorder` so `kubectl describe activation` and downstream log aggregators surface the deploy timeline. Events are fire-and-forget (`tokio::spawn` per publish, failures logged at `debug` and dropped): they are telemetry, never part of deploy correctness. It suppresses Pending and most Running verdicts to stay under the cluster Event rate budget, and emits Normal/Warning Events for plan, terminal verdicts, prune, drift, recreate, hydration, and finalization. See `cli/kix-operator/src/k8s_events.rs`.

**Operator reconcile loop prevention.** The operator uses a stream-level generation filter to drop status-only updates. All status writes go through the status subresource (`patch_status`), which doesn't bump `metadata.generation`. The controller dispatches by phase: Queued CRs trigger activation switchover + deploy, Active CRs trigger drift detection, and Superseded CRs are no-ops.

**Unified reconcile.** Both new deployments and drift correction use the same path: load desired manifests, fetch the live Kix-managed resources of the record's Kix cluster (its `kix.run/cluster` label, else `spec.cluster`, else no cluster: an empty name that owns no record; `SweepScope::Cluster`), compare identity hashes and drop orphans another Kix cluster's current build still contains (`LivePlan::sweep` via `live_changes` in `plan/live.rs`), build the plan, and apply with `PrunePolicy::Delete`. The live cluster is the old state, scoped to one Kix cluster.

**Error boundary.** Libraries use `thiserror`, and binaries use `miette`.
