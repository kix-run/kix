# Kix CLI

Rust CLI for kixpkgs. Evaluates Nix-defined Kubernetes clusters, diffs against live state, and deploys wave-by-wave with SSA. Users run `kix`, never raw `nix`.

## Workspace

```
kix/             library — eval, manifest handling, cluster operations
kix-cli/         binary — clap CLI, command dispatch, plan display
kix-operator/    binary — kube-rs controller watching Activation CRs
```

Both binaries depend on `kix`. No other cross-deps.

## Deploy pipeline

```
nix build → StoreGraph → stamp annotations
  → fetch old activation from cluster (or --current-activation for local cache)
    (store path GC'd? → reconstruct old manifests from live kix-managed resources)
  → refuse if another (non-operator) deploy of this cluster is Deploying
  → load every Failed record and resolve each to its closure in the local store
  → detect_changes (identity-hash set diff, local only)
    → fold_failed_closures (re-apply what a failed deploy may have changed, orphan what it left)
  → DeployPlan::from_graph_and_changes (no wave layer)
  → show package-grouped plan → confirm
  → ops.begin: create the Activation CR and mark it Deploying
  → scheduler::run_deploy (DAG-streaming, SSA + readiness per node)
  → prune orphans (named in the plan and in `DeployEvent::PruneStart { resources, delete }`; warn-only unless `--prune`) → finalize activation
    (stopped before finalize? → ops.abort marks the record Failed)
```

Doc 99 ("graph streaming") replaced the wave-barrier executor with the
DAG-streaming `scheduler`. Each node becomes eligible the moment its direct
predecessors have emitted `Verdict::Ready`, independent subtrees stream
through in parallel, and the inline TUI (`--tui`) draws a live tree grouped
by kix package. `rollback`, `gc`, and the operator all run on the same
scheduler + `DeployObserver` stream; the old wave-barrier `reconcile.rs` and
`waves.rs` modules have been deleted.

`--dry-run` rides this same pipeline — there is no parallel render path.
`SchedulerConfig.dry_run` is plumbed down to `apply_resource` (SSA
`dryRun=All`) and every `DeleteParams`, so per-resource verbs
(`created`/`configured`) come from the apiserver's response and admission
webhook rejections, RBAC failures, and 409 conflicts surface up-front,
matching `kubectl --dry-run=server`. The offline combination
`--current-activation --dry-run` has no client to route through;
`render_offline_dry_run` synthesises the same labels locally from the
old-activation identity diff and prints through the same `apply_symbol`
mapping.

## Where things live

### kix-cli (`kix-cli/src/`)

- `cli.rs` — all clap command/flag definitions (`DeployArgs`, `GcArgs`, `DiffArgs`, `HealthArgs`, `RollbackArgs`, `GlobalArgs`, enums). `GlobalArgs` includes `--no-cache` to bypass the SQLite eval cache (forces fresh Nix evaluation every time) and `--override-input <NAME> <URL>` — a repeatable global flag mirroring `nix --override-input`. Each `(name, url)` pair is forwarded verbatim to every `nix` subprocess kix spawns (`flake show`, `eval`, `build`), so callers can repoint flake inputs without mutating `flake.nix`/`flake.lock`. The docs captures pipeline relies on this to pin kix-examples' `kixpkgs` input at a known store path during sandbox-free regeneration. Paired via `GlobalArgs::input_overrides()` into `Vec<(String, String)>` and applied through `CliNixBackend::apply_overrides(&mut Command)` plus an `input_overrides` slice on `build_cluster_activation_with_status`
- `plan.rs` — shared plan renderer for deploy + gc + diff. `PackageDiff`/`PackageChangeDiff` types, `diff_graphs()` for package-level comparison, `print_package_plan()` for namespace-grouped changes-only stdout display (deploy/gc/rollback modals), `render_package_diff_json()`/`render_package_diff_markdown()` as canonical structured producers consumed by both `kix diff --output {json,markdown}` and (future) the CI PR-comment GitHub Action. All formats share the same PackageDiff input so they stay in sync
- `output.rs` — color helpers (`green`/`red`/`yellow`/`dim`/`bold` → `Cow<str>`), `is_interactive()`, `CommandResponse` trait
## First contact: proving the cluster is there

`Client::try_from` never touches the network. Before `fetch::make_client` ran a
probe, that meant an unreachable cluster hung the *first request* instead of
erroring, and the `"failed to connect to cluster: {e}"` message at all sixteen
call sites was dead code: no error was ever produced for it to print, because
nothing had tried to connect (kixpkgs#36, diagnosed in kixpkgs#38).

There are two failure shapes and they have different owners.

1. **The connect never completes, or is refused.** The transport's
   `connect_timeout` bounds it and knows the cause ("tcp connect error:
   Connection refused", "deadline has elapsed"). The probe's only job is to add
   the endpoint on the way out, which kube alone never does
   (`FetchError::ConnectFailed`).
2. **The connect succeeds and the endpoint then says nothing.** No connect
   timeout can ever fire on this one. Over HTTPS the TLS handshake usually
   turns it into shape 1, but a load balancer that terminates TLS in front of a
   wedged apiserver does not. Only the probe's own deadline bounds it
   (`FetchError::Unreachable`).

The two deadlines are deliberately unequal (`connect_timeout + PROBE_GRACE`) so
they cannot race for the error message. An earlier draft made them equal and
`Unreachable` became unreachable: the transport's deadline always won.

The probe rides the real client with the `FirstContact` extension set, which
drops the retries for that one request. They exist to carry a deploy through an
apiserver restart, not to spend eighteen seconds proving a refused port is
still refused. Riding the real client also means the connection the probe opens
is pooled and reused by the discovery calls that follow, so the probe is a
pre-warm rather than a tax: measured against stage1 and stage2, the median cost is
0.3s and 0.0s. A separate probe client cost ~0.6s on both, all of it a second
TLS handshake thrown away.

Any HTTP response passes the probe, 401 and 403 and 404 included. That rule is
what stops the probe becoming a failure mode of its own on a cluster where the
account cannot read `/version`: an endpoint that answers at all is alive, and
the real call gets to report the real error. `KIX_PREFLIGHT=0` skips the probe
entirely and restores the previous behaviour.

| endpoint | before | after |
|---|---|---|
| refused port | ~18s, "connection refused" | **0.1s**, endpoint named |
| blackholed address (HTTPS) | 15s, `ServiceError: client error (Connect)` | 15s, endpoint named |
| accepts, then silent (TLS terminated) | **120s**, no endpoint | **20s**, endpoint named |
| stage1, reachable | 4.95s | 5.25s |
| stage2, reachable | 4.60s | 4.58s |


## Baseline: what a plan compares against

A deploy or rollback decides what to do by comparing compiler outputs: the
closure it is about to apply against the closure the cluster already runs.
Live cluster state is consulted to *execute* (SSA, delete) and to *observe*
(readiness), never to decide. That is the kix invariant, stated in
`v2_discussions/81_deploy_as_lifecycle_engine.md` ("Closure A to closure B")
and `v2_discussions/29_compiler-design.md`. Do not add a live read to the
decision path; if the from-side looks wrong, the from-side is what to fix.

The from-side has two parts:

1. The **Active** (or Degraded) record's closure, resolved by `built_via` then
   `resolve_activation_by_hash`.
2. Every **Failed** record's closure, resolved the same way. A deploy that
   stops part way applies objects and never becomes Active, so without this
   its leftovers are described by neither side: its orphans are never pruned
   and the objects it changed never read as changed (kixpkgs#82).

`apply::fold_failed_closures` folds the second into the plan. For any resource
a failed closure mentions we do not know which of two compiler outputs the
cluster holds, so a `Skip` whose identity appears there under a different hash
becomes an `Apply` (SSA is idempotent, so guessing wrong costs one unchanged
apply), and an identity only a failed closure has becomes an `Orphan`.
`apply::baseline_manifests` merges the two sets so `prune_order` can sort
orphans that exist in no current closure. Both are pure functions over
manifests, unit-tested in `cluster/apply.rs`.

`commands/baseline.rs` does the resolution and owns two refusals: a record
whose closure is not in this machine's store is reported and deliberately
*not* consumed (it keeps asking until someone handles it), and a non-operator
`Deploying` record means another deploy may be in flight, which is refused
with the `kubectl patch` escape hatch rather than guessed at.

One thing the record's new timing changes visibly: it is created before the
first wave, so the plan's last-wave apply of it reports `configured`, not
`created`, and a deploy summary's counts shift by one. Doc captures that show
a record line need regenerating.

- `commands/baseline.rs` — the from-side of a plan, shared by deploy and rollback: `load_failed` resolves every `Failed` record to its closure and reports the ones this machine cannot resolve; `refuse_if_deploy_in_flight` refuses while a non-operator `Deploying` record exists. See "Baseline" above.
- `commands/deploy.rs` — deploy pipeline: resolves old activation (if its store path is gone — GC'd or built elsewhere — `reconstruct_old_from_live` rebuilds the old manifest set from live kix-managed resources as their kix-owned view (`fetch::kix_owned_manifests`), excluding Activation CRs, so change detection and prune ordering still work; `StoreGraph::synthesize` then rebuilds a package-level StoreGraph from the stamped `kix.run/package` annotations + live PackageInstance versions so the plan shows changed/unchanged packages, not everything "added". Same two functions `kix diff` uses for its live and snapshot sides), displays plan, confirms, builds a `DeployPlan` and delegates to `kix::cluster::scheduler::run_deploy()` (doc 99). Observer selection: `--tui` (+ interactive stdout) uses `graph_stream::GraphStreamDriver` for the inline tree dashboard; otherwise a line-oriented `StreamCliObserver` prints one line per terminal `Verdict` (doc 99 §7 "nix-build-L" idiom). `--reconcile` forces re-apply of all resources even when activation identity matches (heals drift). `--dry-run` goes through the same `run_deploy()` with `SchedulerConfig.dry_run = true` — verbs come from the apiserver's SSA dry-run response, not a CLI guess; with `--current-activation` (no cluster connection) it instead takes `render_offline_dry_run`, which classifies Created/Configured locally via `classify_offline_apply` and renders through the same `apply_symbol` mapping and summary line. `--operator` delegates to the kix-operator instead. `--force-conflicts` opts in to SSA force (default off — conflicts surface as `ApplyError::Conflict` with the conflicting field paths and current owner; use this when migrating a resource away from kubectl/helm for the first time). Import markers (PackageInstance with `kix.run/mode: import`) are applied like any other resource — their readiness check in `readiness::wait_for_import_target` polls the cluster for the described kind/name, so imports whose installer is in the same deploy are naturally wave-ordered after it. **Topology label preflight**: after the plan and before the confirmation, when a cluster connection already exists (not under `--current-activation`), `topology::topology_keys` reads every `topologyKey` the new manifests' spread constraints and (anti-)affinity name, `topology::list_nodes` lists the nodes once, and `topology::assess` prints one `warn:` line per label that a schedulable node lacks under a `DoNotSchedule` rule (the compiler derives spread on `cluster.topology.zoneKey` and cannot see a node; without this the first sign was a readiness stall naming the Deployment and nothing else). A 403 on nodes is a `note:`, not a failure. Warn only, never a refusal
- `commands/deploy_log.rs` — non-interactive deploy observers for `--log-format={line,json}` (doc 99 §7, Stage D). `LineObserver` emits exactly two events per resource: one on `Verdict::Running + NodeDetail::Applied` ("created"/"configured") and one on terminal `Verdict::Ready` ("ready"). Intermediate `ReadinessProgress` events are suppressed unconditionally — the log is a resource-granular activity stream, not a live dashboard. `JsonObserver` emits NDJSON with the same suppression rule; every object carries `type` + `elapsed_ms`. `pretty` (the default) is the colored `StreamCliObserver` on TTY stdout and automatically downgrades to `line` on non-TTY. `-v` only expands Unchanged/Skip/Cancelled lines — it never turns on readiness-progress chatter
- `commands/graph_stream.rs` — inline graph-streaming dashboard (doc 99). `GraphStreamObserver` implements `DeployObserver` as a cheap mpsc sender; a dedicated OS thread owns a ratatui `Terminal` with an `Inline` viewport (default 3/4 of the screen, override with `--fold-height`), receives `DeployEvent`s + periodic ticks, updates `ViewState`, and redraws the tree. A dimmed `─` rule pinned to the top row of the inline viewport separates scrollback history (above) from the live dashboard (below). Nom-style viewport: every Ready resource is flushed to scrollback the tick it completes — the live viewport only ever contains Running / Failed / AwaitingInput / Drift rows plus a collapsed `N packages pending` summary for work that hasn't started. When all members of a package are flushed, a single package-summary line is emitted to scrollback so history reads as a progressive collapse. Failure frame pins a `⚠ failures` block at the top. Active-resource rows carry the latest readiness-progress message (`⏵ Deployment/foo  ⏱ 12s  2/3 ready`) from `NodeDetail::ReadinessProgress`. On spawn the driver redirects the tracing subscriber to `/tmp/kix-tui-<pid>.log` via `crate::trace_sink` — without that, `-v` under `--tui` would tear the ratatui backing buffer with stderr writes. `Ctrl-C` / `Esc` in the viewport cancels the underlying `CancelToken`
- `trace_sink.rs` — runtime-switchable tracing writer. Default target is stderr; `GraphStreamDriver` flips it to a per-PID log file for the lifetime of the TUI session via `redirect_to_file()` / `restore_stderr()`. The single MakeWriter entry point `trace_sink::make_writer` is wired into `tracing_subscriber::fmt` in `main.rs`
- `cluster/scheduler.rs` prune: an orphan whose kind is `Namespace` or `CustomResourceDefinition` is reported and never deleted (`never_pruned`). Both take far more with them than the object named — a Namespace every object inside it, a CRD every custom resource of that kind on the whole apiserver, including ones no Kix cluster ever touched — and neither is dangerous to leave behind, so removing one is a deliberate human act.
- `cluster/apply.rs` `ApplyError::CrdStoredVersion`: the apiserver refuses a CRD that drops an API version the cluster still has objects stored at, reporting it as a validation error on `status.storedVersions` that says nothing about what to do. `classify_apply_error` turns it into an error naming the fix: migrate the stored objects to a version the CRD still serves, or keep serving the old one. A deploy meets it whenever a vendored CRD is re-vendored after upstream retires a version.

- `commands/diff.rs` — one comparison of two `StoreGraph`s, rendered by the same `plan::*` producers the deploy plan uses (text, `json`, `yaml`, `markdown` for PR comments) plus stateful migration pairs. New side: the build. Old side: `--from <dir>` is a build result when `kix-packages.json` is inside, otherwise a manifest directory (`kix snapshot save`, `kix export`) synthesized into a graph (`StoreGraph::synthesize`); no flag means the live cluster, fetched as the **kix-owned view** (`fetch::kix_owned_manifests`) and synthesized the same way. `PackageDiff` carries `cluster_level` (resources outside any package: Namespaces, CRDs, cluster-scoped bundles) and `activation` (old → new record name) so nothing the old flat comparison showed is lost. Exit 2 on any difference
- `commands/gc.rs` — soft (DAG diff old vs new) and hard (full cluster scan) garbage collection. Hard mode deletes only stamped resources; label-only hits without `kix.run/identity-hash` are listed as "unstamped" and deleted only with `--include-unstamped` (kix never applied them: inherited labels, kubectl-applied renders). `--operator` deletes retired Activation CRs and lets the operator finalizer handle resource cleanup. **Record retention** in every mode (`activation::RetentionPolicy`, `retire_plan`, pure and unit-tested): always keep the `--keep` newest Superseded Activation records (default 10) whatever their age, never more than `--keep-max` (default 50), and beyond the floor retire anything older than `--keep-for` (default 30d; `0` off). Newest first by parsed `kix.run/deployed-at`; a record with no usable timestamp sorts oldest; ties break on name. Each retired record is deleted with `Preconditions { uid, resourceVersion }` (`delete_activation_if_unchanged`), so a record that changed since the listing (a rollback made it Active again) is refused with 409 rather than deleted. The plan connects to the cluster before the Nix build (fail fast, one connection reused for the deletes). Soft mode never touches records otherwise; the deploy record is never soft garbage even though its store hash changes every build (`soft_garbage`). Why retention matters: `kix.run/activations` on every managed resource keeps one hash per deploy whose record still exists, and Kubernetes caps all annotations on an object at 256 KiB, so unbounded records would eventually make every SSA fail with 422; the next deploy after a gc drops the retired hashes (`merge_activation_set`). A listing failure is an error, never an empty plan
- `commands/migrate.rs` — `kix migrate domain <cluster>`: the one-off move of a cluster's Kix records off the retired `kix.dev` API group. Builds the cluster to get its two CRD manifests, always dry-runs first and prints the plan, then copies every Activation record to `kix.run` with spec, status and history intact, verifies the count, clears the operator finalizer from the old records and deletes the old CRDs. PackageInstance records are not copied: the next deploy re-creates them. Part of the compatibility layer in `kix/src/legacy_domain/` and goes when that goes.
- `commands/rollback.rs` — rollback to most recent Superseded activation. No nix build — resolves old store path and re-applies via reconcile engine. `--operator` patches the Activation CR's source path and lets the operator reconcile. `--list` is a read-only history view: enumerates Superseded activations with name, identity-hash, timestamp, source store path (`built_via`), `previousActivation` link, and local-store availability, then exits without prompting — supports `--output json|yaml` for scripting. Interactive selector and `--list` share `print_superseded_entries()` so both views show the same columns. Before applying, the confirmation modal renders the package-grouped diff via `plan::print_package_plan` against the current Active CR so the operator sees exactly what flips. `v2_discussions/84_m0_m1_implementation_plan.md` §2. History is bounded by `kix gc` retention (at least 10 newest, at most 50, nothing older than 30d beyond the floor, by default), so `--list` is finite and a `previous:` link may name a retired record
- `commands/logs.rs`, `commands/pf.rs` — thin wrappers that build the cluster, resolve `<package>` to its primary workload (Deployment / StatefulSet / DaemonSet) via `commands/workload.rs::resolve_package_workload`, extract `spec.selector.matchLabels` as a `kubectl -l` selector, then `exec` into `kubectl logs`/`kubectl port-forward`. Deliberately shelling out — the point is "one tool" in the demo, not re-implementing log streaming or port proxying. Per `v2_discussions/84_m0_m1_implementation_plan.md` §4. `--context` is forwarded; logs support `-f/--tail/--since/-c/-p`; pf accepts multiple port specs and `--address`. Zero library changes.
- `commands/workload.rs` — shared helper for logs/pf: builds `StoreGraph`, finds a package by instance name (exact match, ambiguity error with qualified suggestions, or `namespace/name` form), walks its `resource_paths` and returns a `WorkloadTarget { kind, namespace, name, selector }` using the first Deployment → StatefulSet → DaemonSet it finds.
- `commands/export.rs` — dump built cluster manifests as plain Kubernetes YAML for exit-strategy handoff or audit bundles. Walks the freshly-built `StoreGraph` (same mechanic as `diff.rs` build-to-build mode), writes each manifest as `<out>/<namespace>/<Kind>-<name>.yaml` via `manifest::serialize::manifests_to_yaml`. Two modes via `--for`: `exit` (default) strips `kix.run/*` annotations using `cluster::normalize::strip_kix_annotations` and drops kix-internal CRs (Activation, PackageInstance) — the result is neutral YAML a downstream consumer can `kubectl apply`. `audit` preserves stamped provenance annotations and kix-internal CRs for compliance evidence (the M3 compliance-evidence precursor, per `v2_discussions/84_m0_m1_implementation_plan.md` §1)
- `commands/operator.rs` — shared helpers for operator mode: `connect_and_verify()`, `apply_activation()`, `watch_activation_progress()`, `wait_for_deletion()`
- `commands/health.rs` — cluster integrity walk: indexes live resources by `kix.run/identity-hash`, checks every `kix.run/depends-on` edge resolves within the active activation's reachable set, reports Healthy/External/Reaped/Missing/AtRisk. **Graph-presence only — it does not compare field content**; that is `kix drift`'s job. Import-aware: resources with `kix.run/mode: import` annotation show as `external` status instead of healthy/degraded. Reaped-aware: an absent dependency whose seal (read back from the local nix store by identity hash) declares its own deletion — `helm.sh/hook-delete-policy` containing `hook-succeeded` on a chart-rendered manifest, or a Job's `spec.ttlSecondsAfterFinished` — is a hook that ran and cleaned itself up, so it counts as satisfied and lands under `(completed hooks)` rather than dragging its whole downstream chain to `at risk`
- `commands/check.rs`: `kix check`, three steps. (1) `eval_cluster`, which is where every build-time check runs: constructor validators, error-level scorecard findings and the cross-resource resolution checks (`kix/lib/eval/validate.nix`, run by `buildCluster` since 2026-09) all surface here as an eval failure; (2) preflight tools over the rendered manifests (kubeconform, pluto, kyverno; a missing binary reports `skip`); (3) the scorecard report, `--sarif` for SARIF 2.1.0. Nothing in it reads the flake `checks` output
- `commands/drift.rs` — `kix drift`: runtime content drift check via applied-hash stamps (doc 122). Deliberately takes NO cluster/flake argument — it compares live objects against the `kix.run/applied-hash` annotations written at deploy time, so it runs from any kubeconfig-only context (no repo, no nix build). Dispatched in `main.rs` BEFORE `CommandContext` is created (like `completions`) so no Nix backend is ever initialized. Per-resource verdict lines; drifted resources list attributed foreign owners ("spec.template…image taken by kubectl-patch at <ts>"); `--output json` for scripting. Exit 0 = all in-sync/unstamped, 1 = drift found. Integration-tested in `tests/drift-integration.sh` (kind cluster, includes the `kubectl scale` /scale-subresource case)
- `commands/images.rs` — list all container images in a cluster activation. Extracts image refs from pod specs across Deployments, StatefulSets, DaemonSets, Jobs, CronJobs, and Pods (including initContainers and ephemeralContainers). Default text output is one image per line (suitable for `xargs docker pull`). `--sources` adds per-image resource provenance. `--output json` emits structured `[{image, sources: [{kind, namespace, name, container}]}]` for scripting. Primary use case: airgap preloading (`kix images <cluster> | xargs -P4 -I{} docker pull {}`)
- `commands/pin.rs` — `kix pin`, the promotion verb (`v2_discussions/archive/138_values_that_vary_per_deploy.md`). Three subcommands over a pin file, committed JSON recording what each image reference resolved to. `set <key> --tag <t>` asks the registry for the tag's manifest digest, refuses a tag that is not there, and rewrites the file; `--init` creates the file or adds a key, `--no-resolve` writes a pin with no digest and says so, `--digest` records a digest you already have, and `--force` overwrites a file that Kix did not write. `check` verifies every recorded digest is still present **by digest, not by tag**: a moved or deleted tag whose digest still runs is a warning, because there is nothing the author can do about it; a missing digest is a failure. `check --source-rev <rev>` is the freshness assertion, failing when a pin records a different source revision, which is the only way to catch a promotion step that silently did not run. Dispatched in `main.rs` BEFORE `CommandContext` (like `completions` and `drift`): it needs no flake and evaluates no cluster, because the state in which a pin most needs fixing is the state in which evaluation is unhappy about it
- `commands/pin/locate.rs`: finds the pin file when `--pins-file` is absent. It checks the working directory, then the directory named by `--flake` without evaluating the flake, then the git root. At the git root it accepts `pins.json`, or a single `*pins.json` file whose header declares `managedBy`. The marker prevents unrelated JSON files from becoming candidates. The scan does not follow symlinks or run outside a repository, and it refuses to choose when several candidates remain. A flake cannot declare the source path directly because a path literal evaluates to a Nix store path; recovering the original path would require evaluating the flake, which this command intentionally avoids
- `commands/compliance/` — compliance exports for auditors, CI, and compliance platforms (implements `v2_discussions/61_compliance_exports.md`). Three subcommands, all built on the same `shared::build_and_load` helper that runs `nix build` + loads the StoreGraph:
  - `sbom` emits a CycloneDX 1.6 SBOM to stdout. Walks the StoreGraph to produce a `platform` root component for the cluster, one `application` component per package (`pkg:kix/<ns>/<name>@<version>` purl), one `container` component per unique image (deduped, with optional SHA-256 digest from `@sha256:` refs, `pkg:docker/...?repository_url=<host>` purl), and one `library` component per flake input read from `flake.lock` (`pkg:nix/<name>@<rev>`). The dependency graph is derived from `StoreGraph::cross_deps` plus per-package image edges.
  - `attest` emits an unsigned in-toto Statement with a SLSA v1 provenance predicate. Subject is the activation identity hash (`nixStoreHash` digest type). `externalParameters` include the flake ref and a BLAKE3 digest of the on-disk `flake.lock`; `resolvedDependencies` carry the git HEAD, every flake input's rev/narHash, and every container image, with a `sha256` digest only when the reference actually carries one. `--builder-id` and `--invocation-id` override the `runDetails` block so CI can stamp its workflow URL. `--from-cluster` reads the deploy receipt off the cluster's active Activation instead of building, so the statement describes what **was** deployed rather than what would be, from a machine that has never built this cluster. Both routes go through `receipt::attestation_from_receipt`, so they cannot drift apart. Signing is deferred to doc 54 by design.
  - `receipt.rs` is not a subcommand. It assembles the provenance a deploy writes into the Activation's `status` subresource: flake ref, git commit **and whether the tree was dirty**, the `flake.lock` digest, every input, the kix and Nix versions, and every image the build renders. Deliberately not the manifests: built manifests carry secret values inline, so storing them would make every deploy record a readable credential archive, which is Helm's documented failure. `shared::git_state` replaced `git_commit` to supply the dirty flag, and `deploy.rs` prints it above the confirmation.
  - `audit` bundles `scorecard-results.sarif`, `sbom.json`, `provenance.json`, `assessment-results.json`, and `audit-report.md` under `--out` (default `./compliance`). The OSCAL assessment maps findings to framework controls via static Rust tables (see `audit.rs` — SOC 2, ISO 27001, DORA, NIS2). A control is marked `not-satisfied` only if an error-level scorecard finding exists whose rule ID starts with one of the control's declared `required_rules` prefixes. The markdown summary is a self-contained PR-comment-ready report. SARIF generation duplicates the shape used by `kix check --sarif`.

#### eval (`kix/src/eval/`)

- `store_graph.rs` — **central data structure.** `StoreGraph` holds the full in-memory DAG: `PackageNode` (instance_name, namespace, version, resource_paths, cross_deps), `ResourceNode` (store_path, manifest). Built from result dir's `kix-packages.json` + `nix-store -q --graph`. `StoreGraph::synthesize(manifests, reference)` builds one from a flat set of stamped manifests instead (live objects' kix-owned view, a snapshot, an export): resources group by their `kix.run/package[-namespace]` annotations, every PackageInstance makes a package (resources or not) and sits at its store path, `resource_owner` is filled, and a manifest reuses the reference's store path only when its identity hash AND content match — a live object drifted under its stamp keeps its own content-named synthetic path, so `plan::diff_graphs` sees the change. Used by `deploy` (previous state when the store path is gone) and `diff` (live and `--from <manifest dir>` sides)
- `store.rs` — activation cache at `~/.cache/kix/activations/`. `save/load_activation_path()` for local cache, `resolve_activation_by_hash()` to go from cluster identity-hash → local result dir. `save_activation_path` also registers a Nix GC root (`<cluster>.root` via `nix-store --add-root`) pinning the deployed activation — builds run `--no-link`, so without it `nix-collect-garbage` deletes the store path the next deploy diffs against
- `evaluator.rs` — `KixEvaluator` wrapping a `NixBackend` trait with SQLite caching
- `cli_backend.rs` — **production backend.** `CliNixBackend` shells out to `nix` CLI commands: `nix flake show --json` for listing clusters, `nix eval --json` for listing packages/cluster info, `nix build` + StoreGraph for evaluation. Benefits from Nix's built-in eval cache.
- `build.rs` — `build_cluster_activation_with_status()` shells out to `nix build .#cluster-{name}-activation`
- `cache.rs` — SQLite cache keyed by BLAKE3 of (flake path + lock + source fingerprint + attr)
- `ffi.rs` — experimental `FfiNixBackend` using `nix-bindings-*` FFI crates (gated behind `nix-ffi` feature, not currently used)
- `mock.rs` — `MockNixBackend` for tests without Nix

#### manifest (`kix/src/manifest/`)

- `types.rs` — `ResourceId` (kind/namespace/name), `CLUSTER_SCOPED` constant. Used everywhere
- `workload.rs` — `pod_spec(&Value)`: the one table of where a kind keeps its pod template (`spec` for a Pod, `spec.template.spec` for Deployment/StatefulSet/DaemonSet/ReplicaSet/Job, one level deeper for a CronJob). `kix images`, the SBOM and the topology preflight all read pod templates through it, so a kind added here is seen by all three
- `lifecycle.rs` — **the one classifier** for what a manifest is: `Lifecycle::{Desired, Marker, Record}` via `lifecycle_of(&Value)` / `lifecycle_of_live(&DynamicObject)`. Desired state is diffed, applied and pruned; a Marker (PackageInstance with `kix.run/mode: import`) is applied and its target polled; a Record (the Activation) is applied once at the end of a deploy and only ever superseded, never pruned. `record_of()` finds the record in a set. Change detection (`apply.rs`) matches records like any other resource, so an unchanged build is still a `Skip` and the deploy short-circuits, but `Lifecycle::prunable()` keeps them out of the orphan set on both the store and live paths. Every former `kind == "Activation"` / `kix.run/mode == import` check (stamp, deploy, rollback, gc, export, health, readiness, graph, the operator) reads this instead, and a unit test fails the build if a new comparison of the record kind appears anywhere else. Born from kixpkgs#59: the previous deploy's record, renamed by stamping on every deploy, reached change detection through the store-graph path and was reported as an orphan on every deploy (and `--prune` would have deleted it before finalize could supersede it)
- `stamp.rs` — `stamp_annotations()` writes `kix.run/*` annotations onto StoreGraph manifests in-place; renames the Record to `<cluster>-<hash12>` so each deploy creates a distinct CR
- `diff/engine.rs` — `structural_diff(a, b)` → `Vec<Difference>` with JSON paths. Keyed-list-aware
- `diff/keyed_lists.rs` — defines which K8s arrays match by key (containers→name, ports→name, env→name, volumeMounts→mountPath, subjects→kind:name)
- `diff/display.rs` — `format_diffs()` renders differences as colored text
- `serialize.rs` — YAML/JSON output (`strip_nulls` removes nulls and ONLY nulls before YAML: an empty map is content — `emptyDir: {}`, a CRD's `subresources: {status: {}}` — and `kix build`/`kix export` used to drop them), `load_manifests_from_dir()` for snapshot/export loading (every `.yaml` in the tree, PackageInstances included — they are kix-managed objects like any other; ids come from the manifest content)

#### pins (`kix/src/pins/`)

- `mod.rs` — reading and writing pin files. A pin file is JSON: an envelope `{version, managedBy, images}` whose entries hold `{repository, tag, digest?, sourceRev?, promotedBy?, resolvedAt?, note?}`. JSON rather than Nix for a checkable reason: reading a Nix file means evaluating it, so reading a pin file would execute whatever it holds, and writing one means hand-escaping registry-supplied strings into a programming language. The eval cache fingerprints `.json` alongside `.nix`, `.yaml` and `.yml` (`eval/cache.rs`), so nothing is lost by the choice. A bare map of pins is also accepted on read and is never treated as managed. Writing produces one canonical sorted form, which is why `PinFile::write` refuses a file that does not declare `managedBy` unless forced. `Pin` is `deny_unknown_fields`, matching the Nix reader, so a field Kix does not know is refused rather than silently dropped on the next write; `note` is the field for anything a person wants to say, carried through untouched and stripped by the Nix reader before it reaches the image option. Digests are validated as `sha256:` plus 64 hex characters on the way in

#### registry (`kix/src/registry/`)

- `reference.rs` — parsing `[registry/]repository[:tag][@digest]` with Docker's conventions: a leading segment is a registry only when it has a dot, a port, or is exactly `localhost`, and a bare Docker Hub name gains the `library/` prefix. `docker.io` maps to the `registry-1.docker.io` API host and to the historical `https://index.docker.io/v1/` credential key
- `credentials.rs` — the same places every container tool looks, in order: `KIX_REGISTRY_USERNAME`/`KIX_REGISTRY_PASSWORD`, a per-registry `credHelpers` entry, the general `credsStore` helper (`docker-credential-osxkeychain` and friends), then a literal `auths` entry. Anonymous is a valid outcome, not a failure
- `client.rs` — one question only: does this reference exist, and what is its manifest digest. Handles the bearer-token challenge, prefers index media types so a multi-architecture image resolves to its index digest (which is what a runtime resolves and what `crane digest` prints), and computes the digest from the response body rather than trusting the `Docker-Content-Digest` header, treating a disagreement between the two as an error. Reached only by `kix pin`: resolving a tag during a deploy is a non-goal per doc 120 §3.9

#### cluster (`kix/src/cluster/`)

- `apply.rs` — ceded fields: a 409 on an object whose `kix.run/cede-fields` annotation covers every conflicting path (`without_ceded_conflicts`, paths parsed from the apiserver message, `[*]` matching any list element) is retried once without those fields, so an operator that rewrote them keeps them; any other conflict is still `ApplyError::Conflict`. `detect_changes()` (identity-hash set diff → `ChangeAction::Apply/Skip/Orphan`; an old or live object without `kix.run/identity-hash` is never an `Orphan` — kix only deletes what it stamped; a `Lifecycle::Record` on the old or live side is dropped before matching, so the previous deploy record can never be an orphan on any path, store-graph, live-reconstruction or operator), `detect_changes_live()` (compare desired manifests against live cluster resources by identity-hash), `apply_wave()` (SSA via `kube`, field manager `kix`), `RERUN_ANNOTATION` / `wants_rerun()` (the `kix.run/rerun: on-change` opt-in the scheduler's rerun rule reads). The SSA response echo is kept (not discarded): `apply_resource` computes the applied-content hash from it (`fieldsv1::applied_content_hash`) and writes `kix.run/applied-hash` in the same post-SSA bookkeeping merge patch as `kix.run/activations` (`update_bookkeeping_annotations`, no extra round trip). That patch also runs under field manager `kix` — leaving it unset records the write as manager `unknown` in managedFields and pollutes ownership-based drift attribution (doc 122). `merge_activation_set()` is the pure set operation behind `kix.run/activations`: fold in the current activation, drop entries naming an Activation CR that no longer exists (`activation::live_activation_hashes`), always keep the activation being deployed (its own CR lands in the last wave), and return a sorted set so the caller can skip the write when nothing changed. Passing `live = None` disables pruning — keeping a dead reference is recoverable, dropping a live one is not. `record_activation_on_skipped()` is the entry point for resources the deploy did *not* apply; it touches `kix.run/activations` only, never `kix.run/applied-hash`. `fold_failed_closures()` and `baseline_manifests()` are the from-side fold that closes kixpkgs#82: see "Baseline" above. Both are pure over manifests, so nothing in the decision path reads the cluster
- `graph.rs` — `ResourceGraph` (petgraph DAG built from `kix.run/depends-on` annotations). Import-aware: nodes with `kix.run/mode: import` render as dashed/gray in dot output, `(import)` suffix in tree, `isImport` field in JSON
- `stream.rs` — graph-streaming vocabulary (doc 99): `Verdict`, `TransitionKind`, `NodeId`, `NodeDetail`, `NodeMeta`, `PlanNode`, `DeployEvent` (including `Stalled { idle, in_flight: Vec<InFlight { node, phase, since }>, aborting }` from the watchdog and `BestEffortFailed { what, message }` for checkpoint/stamp/finalize failures), `Phase`, `InFlight`, `DeployObserver`, `DeployResult`. The observer trait consumed by the CLI renderer, the non-interactive line/JSON observers, and the operator's tracing observer
- `scheduler.rs` — **deploy engine** (doc 99, reshaped by doc 134). `DeployPlan::from_graph_and_changes` builds the plan from a `ResourceGraph` + `detect_changes` output. `run_deploy(ops, plan, orphans, old_manifests, config, observer)` is the ready-queue scheduler: every node becomes eligible the moment its direct predecessors have emitted `Verdict::Ready`, concurrency bounded by `SchedulerConfig::concurrency` (default `CONCURRENCY=64`). **The engine task never awaits foreign I/O while nodes are in flight**: every node, every discovery refresh and every checkpoint is a task spawned into one `JoinSet`, and the supervisor's only awaits are that set, the cancel token and the watchdog. The first shape held node futures in a `FuturesUnordered` and awaited rediscovery inline, which parked every apply and hung a deploy for 35 minutes (kixpkgs#62). **CRD barrier**: a CRD-like node (kind `CustomResourceDefinition`, or an import marker for one) does not promote its dependents until one discovery refresh that started after it completes; several CRDs finishing together share one refresh; a refresh that fails stops the run with `DeployError::DiscoveryFailed { partial }` (a stale view is a partial view, the rule from #60). Failure policy halt-dependents / continue-siblings (default) or halt-on-first-failure under `OnErrorPolicy::Stop`. Cascade-cancels transitive dependents on failure. A spawned task that panics is `DeployError::Internal`, never a lost node. Cancel (caller or watchdog) is observed through `CancelToken::cancelled()` in the supervisor's `select!`; the reason travels on the token, so a watchdog abort reads "no progress for 600s: waiting on ..." rather than "cancelled". On cancel the supervisor aborts every task and keeps draining the `JoinSet`: a node that finished just before the cancel is still counted, an aborted one becomes `Cancelled`, and only then does the run return; a cancel that lands as the last node finishes is re-checked after the loop so nothing is pruned or finalized. Whatever stops a run (cancel, `OnErrorPolicy::Stop`, a failed refresh), every node without a verdict gets `Cancelled { External }` and counts in `cancelled`, so renderers never leave a row Pending under a `Stopped` footer and the counts add up to the plan. Every post-loop write is bounded too (begin, stamping, each prune delete, final checkpoint, finalize: 60s each), because the watchdog only watches nodes and the discovery refresh. `ops.dry_run()` must agree with `SchedulerConfig::dry_run` or the run stops before it starts. Immutable-field conflicts recover via `ClusterOps::recreate_in_place` when the rid is pre-authorized in the orphan set (a resource that is in the plan is never in that set, so on a real deploy this branch only serves the unit test; the error text names the two recovery paths and tells the user to delete and deploy again otherwise). **The rerun rule** (doc 136, kixpkgs#77): a manifest carrying `kix.run/rerun: on-change` (stamped by `kix.healthCheck` on probe Jobs) is never patched. The planner tags a changed one `TransitionKind::Recreate` and keeps the manifest on `PlanNodeEntry::rerun`; the executor calls `ClusterOps::get_live` first and applies plainly when nothing is live (first deploy, TTL-reaped, deleted by hand) or runs `recreate_in_place` when something is (foreground delete, wait, create), reporting `NodeDetail::Rerun { reason: "changed since the last run" }`. An unchanged one stays `Skip` but still runs a task: when its live object is in a terminal failure (`classify_workload_terminal`) it is recreated with reason "the last run failed", so a probe that failed against a degraded cluster runs again on the next deploy or rollback without a manual delete; a healthy one is counted unchanged and stamped like any Skip. That Skip-path retry is gated by `SchedulerConfig::rerun_failed`: the CLI sets it (a person asked for a run), the operator leaves it off (it diffs against live objects and requeues a failed run every 30 s, so on a degraded cluster it would delete and recreate the probe forever). With it off the Skip path still reads the live object and reports a failed one as `Verdict::Failed` without deleting it, so the gate stays red in the operator's status instead of reading as healthy; the operator still recreates a probe whose hash changed, and re-applies one its TTL reaped, since to a live diff that is a new resource. `wants_rerun` honours the annotation on Jobs only: a Deployment stuck on its progress deadline is "failed" to the classifier too, and deleting it would be an outage. Under dry run `recreate_in_place` checks the delete with `dryRun=All` and reports `Created` without applying (the apply would hit the same 422 the real delete avoids). `failed_rerun_nodes(client, discovery, plan)` is what `kix deploy` and `kix rollback` ask before they take the "nothing to apply" exit on an unchanged plan: a failed probe kept the previous activation from switching, so a deploy that reverts to that activation's content sees no change, and without the pre-check the failed Job would never run again; when it names anything the command runs the engine and the Skip path does the rest. The identity hash covers the sealed manifest and everything upstream of it, so "changed" means the probe, the thing it checks, or something upstream of that moved. Opt-in by annotation, never by kind: applied to every Job it would re-run stackgres bootstrap SQL on any upstream change. Activation CR checkpointing batched every 16 terminal verdicts, one write in flight at most, running totals; the final checkpoint and finalize are awaited inline after the node phase under a 60s bound. Failures of best-effort writes (checkpoint, stamping unchanged resources, finalize) are `DeployEvent::BestEffortFailed`, rendered by every observer, not `tracing::warn` lines. `Skip` nodes short-circuit without a task, but their rids are collected and stamped with the current activation in one concurrent pass once every node is terminal (an unchanged resource still belongs to this activation). `SchedulerConfig.dry_run` makes the whole run non-mutating: SSA and deletes hit the apiserver with `dryRun=All`, readiness short-circuits, and every real write is gated off in `KubeOps`. Also owns `OnErrorPolicy`, `PrunePolicy`, re-exports `delete_propagation_for`. Tested without a cluster (`engine_tests`): the CRD barrier does not park running nodes, a failed refresh stops the run, a hung refresh is reported and aborted, a hung apply is reported then aborted on the 30/60/90/120 cadence, readiness heartbeats keep the watchdog quiet, cancel returns promptly with every task aborted and every node given a verdict, cancel during readiness never reaches prune or finalize, a hung checkpoint holds nothing, a hung stamp and a hung prune delete are bounded and reported, admission refills a freed slot at once, peak concurrency equals the cap, halt-on-first-failure finishes in-flight nodes and cancels the rest, a panicking task is fatal, gated applies complete only when released, an immutable conflict on a pre-authorized orphan recreates and is not pruned again, a rerun Job with a live object is recreated and without one is applied, a skipped rerun Job is recreated when its live object failed and left alone (and stamped) when it succeeded, a recreate that reports the object still present fails the node with that message, and a `proptest` over random DAGs with random per-node outcomes (ok, slow, fail, hang, readiness fails, readiness hangs) checks every node reaches exactly one terminal verdict, in dependency order (by log position), with counts a pure function of the case that add up to the plan. All under `#[tokio::test(start_paused = true)]` wrapped in a one-hour virtual timeout, so a parked engine fails at once
- `ops/` — **the engine's one seam to the cluster** (doc 134 §2.5). `ClusterOps` (`async_trait`, `Arc<dyn ClusterOps>`) is every apiserver call and every other piece of I/O `run_deploy` performs: per node `hydrate`, `apply`, `get_live` (the live object or `None`, a read even under dry run), `recreate_in_place`, `wait_ready`; per run `begin`, `rediscover`, `checkpoint`, `record_activation_on_skipped`, `delete`, `finalize`. The engine never sees an `ApiResource`. `ops/kube.rs::KubeOps` is the real one: holds the `Client`, the shared discovery cache (`DiscoveryCache = Arc<RwLock<Vec<(ApiResource, Scope)>>>`, refreshes MERGE via `fetch::merge_discovery` because the aggregated discovery doc churns after CRD writes and can transiently omit unrelated groups), kind resolution with refresh-on-miss (targeted `fetch::discover_group` then full), the Activation identity (`KubeOpsConfig { cluster_name, activation_name, activation_identity_hash, force_conflicts, dry_run }`), the live Activation set read once in `begin`, `sops` on `spawn_blocking`, and 30s bounds on checkpoint and finalize. A checkpoint that 404s is not a failure: the Activation CR is a node of the plan and lands in the last wave, so every checkpoint on a cluster's first deploy precedes it. `recreate_in_place` treats a 404 on the delete as success (the object was already gone, which is what was wanted), polls up to 30 s for the object to vanish, and if it is still there afterwards returns "still exists 30s after delete (stuck finalizer?); not re-applied" instead of an apply that would fail with the same 422 and say nothing about why; under dry run it sends the delete with `dryRun=All`, skips the poll, and still runs the dry-run apply so schema, admission, RBAC and field conflicts are checked; only the immutable-field 422 that the real delete would have avoided is mapped to `Created`, which is what the real path produces. `get_live` refreshes discovery on a kind miss, as `apply` does. `ops/scripted.rs::ScriptedOps` (`cfg(test)` or feature `test-util`) is the fake: every call is a `Behaviour` (`Now`, `After(duration)`, `Gate(latch)`, `Hang`, `Panic`), readiness can `Heartbeat` to model a slow healthy rollout, `NodeScript::live` scripts what `get_live` answers and `NodeScript::recreate` what `recreate_in_place` does, and it records a call log with virtual timestamps plus the peak number of concurrent applies. Nothing in it completes unless the script says so; a fake that answers on first poll cannot show a parked future. `begin` now CREATES the Activation record and marks it Deploying rather than waiting for it to come round as the plan's last node, so a run that stops part way leaves a record of what it was attempting; on a cluster's first deploy that record's own CRD is not served yet, so the create is deferred to `rediscover` (the CRD barrier), the earliest point it can succeed. `abort(reason)` marks the record `Failed` and is called from every early return in `run_deploy` below `begin` (cancel, halt-on-error, discovery failure, task panic); exactly one of `abort` and `finalize` happens per run. `delete` treats 404 as success, which matters once a failed closure is folded in: much of it was never created, and pruning something already gone must not count as a failure and land the new record Degraded. `KubeOpsConfig` gained `activation_manifest`, `consumed_failed` and `mark_failed_on_abort` (false for the operator, whose model is resume-on-requeue)
- `watchdog.rs` — **progress watchdog** (kixpkgs#62, doc 134 §2.6). `Progress` is the shared record: last activity of any kind, and per in-flight node its `Phase` (hydrate, apply, readiness, plus `discovery` for the CRD barrier's refresh, tracked under the synthetic node `api-discovery` so a hung refresh is reported and aborted like a hung node) and when it began; readiness status callbacks count as activity, so a ten-minute StatefulSet rollout that reports every 2s is not a stall. `assess(policy, idle, in_flight, last_warned)` is the pure policy (quiet / warn / abort), unit-tested alone. `run` is the task: its own `interval` (`MissedTickBehavior::Delay`, so no catch-up ticks after the stall it is watching for), emits `DeployEvent::Stalled { idle, in_flight, aborting }` at `warn_after` (default 30s) and every `warn_after` after, and at `abort_after` (default 600s, `KIX_STALL_TIMEOUT` seconds, `0` never) cancels the run through the token with the reason. `describe()` renders the one line every observer prints: `no progress for 31s: waiting on Deployment/a@default (apply, 31s), ...`, longest-waiting first, capped at five
- `cancel.rs` — `CancelToken`: `cancel()`, `cancel_with_reason()`, `is_cancelled()`, `reason()`, and awaitable `cancelled()` (backed by `tokio_util::sync::CancellationToken`) so the engine's supervisor can select on it while every node is in flight
- `readiness.rs` — `expectations()` reads `kix.run/expects` (`apiVersion|Kind|name` entries) and `wait_for_expectations()` polls each in the manifest's namespace (or at cluster scope) before `KubeOps::apply` patches; an object that never appears is `ApplyError::ExpectationUnmet`, naming the expectation and the reason. An import marker's target is looked up at the scope discovery reports for its kind (`kube::discovery::oneshot::pinned_kind`), so a cluster-scoped import (StorageClass, ClusterIssuer) is found; a kind discovery cannot see yet falls back to the marker's namespace. `wait_for_ready()` polls per-kind conditions (Deployment replicas, CRD Established, Job succeeded, etc.). A DaemonSet whose node selector matches no node (`desiredNumberScheduled: 0` with the generation observed) is complete, as `kubectl rollout status` has it: mayastor's io-engine selects `openebs.io/engine=mayastor` nodes and a cluster labels those after the deploy, so the earlier `desired > 0` rule timed out every openebs deploy on an unlabelled cluster. A terminal failure comes back as `ReadinessResult::Failed { message, output }`: on a Job-level hit (`backoffLimit` exceeded or a `Failed` condition) `scan_terminal` lists the Job's pods by the live object's `spec.selector` (the controller-uid selector) and `termination_output` collects each container's `state.terminated.message` (or `lastState`), which the kubelet fills from the log tail when the pod runs with `terminationMessagePolicy: FallbackToLogsOnError`. That is how a probe's `FAIL` lines reach the deploy output without a log API call: the last 20 lines (`TERMINATION_OUTPUT_LINES`), prefixed by container name only when several wrote something, with one leading line saying how many earlier lines were dropped. The scheduler carries them on `NodeDetail::ReadinessFailed { output, .. }`; the pretty renderer prints them dim under the failure line, the line log as `<label>>   | <line>`, the JSON log under `readiness_failed.output`, and the operator appends them to the Warning Event's note. `wait_for_import_target()` handles PackageInstance import markers (`kix.run/mode: import`): parses `kix.run/import-kind/apiversion/name` annotations and polls the described resource. Scope is determined by kind — `CustomResourceDefinition` is cluster-scoped (and waits for `Established=True`), everything else is namespaced and queried in the marker's own `metadata.namespace` (no `kix.run/import-namespace` annotation: imports always describe a resource in the marker's own namespace). `Secret` imports with a `kix.run/import-secret-keys` annotation also verify every declared key is present in `data` before the marker is considered ready — missing keys produce `ReadinessResult::ImportMismatch { missing_keys, message }`, which `reconcile.rs` surfaces as `ReadinessFailed { missing_keys, .. }` so observers can render the exact missing keys as a structured line. Custom readiness conventions are DECLARED, not hardcoded: a CRD-owning package sets `readiness = { path; equals; }` or `readiness = { condition = { type; status; }; }` on its CRD builder, kix stamps it on every CR built through the typed chain as the `kix.run/readiness` annotation (JSON `{"path": "/status/...", "equals": "..."}` or `{"condition": {"type": "...", "status": "..."}}`), and `declared_readiness`/`check_readiness` evaluate it before any kind-based rule. The path form is how VictoriaMetrics CRs gate on `status.updateStatus == "operational"`; the condition form is how StackGres clusters gate on `Bootstrapped=True`, Gateway API kinds on `Accepted`/`Programmed` and Cilium policies on `Valid`. The `match` in `check_readiness` covers only kinds whose readiness Kubernetes itself defines; an operator's vocabulary never goes there. Malformed annotations fall through to kind rules (version skew ≠ unhealthy) — but note the un-annotated half of that skew: manifests built by a pre-declaration library have no annotation, and a status-less CR then hits check_generic_ready's ready-on-empty, racing its operator instead of timing out; rebuild such manifests rather than relying on the fallthrough. A generic-CR readiness timeout lists the condition vocabulary it observed and points at the declaration mechanism.
- `activation.rs` — Activation CR lifecycle: phase-based model (Queued → Deploying → Active → Superseded). `find_active()`, `find_queued()`, `list_superseded_activations()`, `begin_deploy()`, `record_waves()`, `finalize_deploy()`, `resume_point()`, `supersede_activation()`, `read_phase()`. All status writes use `patch_status` (status subresource). `status.previousActivation` links activations for rollback. `record_waves()` accepts accumulated wave records to avoid GET-before-PATCH round-trips. Full phase model is `Queued → Deploying → Active|Degraded|Failed → Superseded`. `PHASE_FAILED` is terminal and deliberately NOT matched by `find_active`: a half-applied closure is not the cluster's current state, and diffing against it would read every object only the Active closure has as an orphan, which `--prune` would then delete. `find_failed()` and `find_deploying()` read the other two phases. `pick_current()` makes `find_active` deterministic when a cluster holds two current records (newest `deployed-at`, ties on name) instead of taking whichever the apiserver listed first. `phase_on_begin()` leaves an Active record alone, so re-deploying the closure that is already current cannot demote it and then die leaving no current record at all; `phase_on_abort()` only fails a record this run marked Deploying. `fail_deploy()` writes the phase and `status.failure.{reason,at}`. `finalize_deploy()` takes `consumed_failed` and supersedes those records, skipping the one being finalized so a retry of a failed closure still lands Active. `deployed_at()` falls back to `status.failure.at` then `creationTimestamp`, so a record superseded out of `Failed` is not retired as `UnknownAge` on the first `kix gc`
- `client.rs` — **the apiserver transport policy**, applied once so every call site inherits it. `build_client(config, policy)` wraps kube's tower stack in `ResilienceLayer`: retries (429 for every method with `Retry-After` honoured; 5xx and connection loss for idempotent methods only, so a POST is retried only when the connection never opened), exponential backoff with equal jitter under a total budget, and a per-attempt deadline for non-watch requests. Watches bypass the deadline. It deliberately holds **no** in-flight cap: the first version did, and a permit held inside a future that the scheduler had parked (its `FuturesUnordered` is not polled while it awaits CRD rediscovery inline) deadlocked `kix deploy` with every thread idle, and no deadline can fire in a future nobody polls. Burst control lives in the sweep instead. When the budget is spent the last response or error is returned unchanged, so callers see the same `kube::Error` they always did. `decide()` is the pure policy, unit-tested against a scripted fake service. Knobs: `ResiliencePolicy` (defaults sized to outlast a webhook pod restart) with env overrides `KIX_RETRY_ATTEMPTS`, `KIX_REQUEST_TIMEOUT`, `KIX_CONNECT_TIMEOUT`. A request carrying the `FirstContact` extension (`mark_first_contact`) gets one attempt and no deadline of its own: that is the probe in `fetch::make_client`. Persistence is what carries a deploy through an apiserver restart, but a cluster that is not there will not become there, and seven attempts over a 60s budget only delay the error (a refused port: ~18s with the retries, 0.1s without). It is an extension on the real client's request rather than a second client from a second policy, because a second client means a second connection pool: the probe would pay its own TLS handshake and throw the connection away, measured at ~0.6s against stage1 and stage2 on every cluster command. `decide()` is left untouched by this; `run()` short-circuits, so the pure policy does not grow a special case. The old per-patch retry loop in `apply.rs` is gone; it was one file's private copy of this
- `errors.rs` — `FailureClass` + `classify(&kube::Error)` / `classify_status(code)`: the one table that says what an apiserver failure means (rate-limited, unavailable, server error, transport, timeout, unauthorized, forbidden, not found, conflict, invalid). Every site that used to compare `resp.code` by hand (apply conflicts, the sweep's 403, readiness 404) reads this instead, and the transport layer uses the same table to pick what to retry
- `topology.rs` — the topology label preflight behind `kix deploy` (see `commands/deploy.rs`): `topology_keys(manifests)` collects every `topologyKey` from `topologySpreadConstraints` and pod (anti-)affinity across every pod template `manifest::workload::pod_spec` knows, split into hard (`DoNotSchedule`, `requiredDuringScheduling`) and soft uses; `list_nodes(client)` is one LIST of Nodes reduced to name, labels and placeability (a cordoned node or one with a `NoSchedule`/`NoExecute` taint is not placeable, matching what `nodeTaintsPolicy: Honor` excludes, so kind's control plane lacking a zone label is not a finding), 403 is `NodesOutcome::Forbidden`; `assess(keys, nodes)` returns a `Finding` per hard key that any placeable node lacks and per soft key that no placeable node carries, and `Finding::describe()` is the one plain-language line. Pure apart from the LIST, unit-tested without a cluster
- `fetch.rs` — `make_client()` (builds through `client::build_client`, then proves the endpoint answers before handing the client over, see "First contact" below), `discover_resources()` (walks EVERY served version of each API group, preferred first, first ApiResource wins per kind — `recommended_resources()` alone hid all v1beta1 kinds of a group once a v1 kind joined it, e.g. operator.victoriametrics.com), `fetch_managed_resources()` (parallel LIST with the managed-by label selector, at most `DEFAULT_SWEEP_CONCURRENCY` = 16 in flight on spawned tasks (`KIX_SWEEP_CONCURRENCY`), then `partition_sweep()`: stamped objects (`kix.run/identity-hash`) are managed whatever owns them; unstamped + owned are controller children and dropped; unstamped + unowned are kept apart as `ManagedSweep::unstamped` for gc; an unstamped `Endpoints` named after a managed Service is that Service's mirror and dropped — controllers copy labels onto what they derive, so the label only finds candidates and the identity hash is the proof; `sweep_managed()` returns both lists plus `ManagedSweep::forbidden` (resource types that answered 403: a fact about the account, recorded so `diff` and `gc` can print "N not listable with this account" instead of passing off a narrower view as complete), `fetch_managed_resources()` only the managed one. Any other list failure that survives the transport's retries is an **error**, never an empty list: the old warn-and-skip made `kix diff` report every PackageInstance as "will be created" during an apiserver restart (429 "storage is (re)initializing", stage1 2026-09-07), and a plan built on a partial sweep is wrong in ways the user cannot see. Same rule in `deploy.rs`: a failed live reconstruction of the previous state is an error, not a first deploy. `merge_discovery()` / `discover_group()` (see scheduler.rs notes). There is no kind skip list any more: the old `SKIP_RESOURCES` fed both the sweep and apply-path discovery, which made every listed kind undeployable (helmchartconfigs.helm.cattle.io broke the first rke2 deploy that way; the lithus flavor's CSIDriver and StorageProfile were on it too) — kixpkgs#41. `normalize_for_diff()` strips server metadata **including managedFields** — never call it before drift hashing. `kix_owned_view()` is what `diff` and `snapshot save` compare against a build: the object projected onto kix's `Apply` fieldset (`fieldsv1::project`) with `apiVersion`/`kind`/name/namespace restored; objects with no kix `Apply` entry fall back to `normalize_for_diff()`
- `fieldsv1.rs` — pure fieldsV1 interpreter (doc 122, no cluster access): `kix_fieldset()` extracts kix's SSA managedFields entry (manager `kix`, operation `Apply`, no subresource) from TYPED metadata; `project()` implements fieldsV1 semantics (`f:` members with empty-subtree-as-atomic-leaf, `k:{...}` associative-list key matching, `v:` set values, `i:` positions, `.` node-itself; live array order preserved; entries missing from live are skipped = deletion detection); `applied_content_hash()` is the ONE shared stamp/check recipe: merge typed metadata → project onto kix fieldset → strip `kix.run/*` annotations → Blake3 over canonical JSON. Owns `APPLIED_HASH_ANNOTATION`. Fixture-tested against real recorded apiserver objects in `tests/fixtures/`
- `drift.rs` — runtime drift check (doc 122): `check_cluster()` fetches kix-managed resources (raw — no `normalize_for_diff`, which deletes managedFields) and compares each object's current applied-content hash against its `kix.run/applied-hash` stamp. Verdicts: `InSync`, `Drifted { foreign }`, `Unstamped` (no stamp — NOT drift), `NoFieldset` (managedFields stripped). Attribution flattens every other manager's fieldsV1 into field paths with manager/operation/subresource/timestamp, excluding ONLY `subresource == "status"` (autoscalers and `kubectl scale` write via `/scale` and must stay visible, doc 123). PI `spec.driftIgnore` evaluation is a marked TODO hook (doc 123)
- `manifest/keys.rs` — the one place the Kix domain is spelled in Rust, and every annotation, label, CRD name, API group and tool URI built from it. Reads of a Kix key go through `keys::get` / `get_meta` / `contains_meta`, never a direct map lookup: those are the one place a retired domain is tried as a fallback. A test fails if any other file in `kix/` or `cli/` spells a Kix domain in a string literal. The Nix half is `kix/lib/core/annotations.nix`.
- `legacy_domain/` — everything that exists only because clusters were deployed under a retired domain: the read fallback, the load-time manifest upgrade (keys, labels and a record's own `apiVersion`), the bookkeeping null-outs, the gate that refuses an unmigrated cluster, and the migration itself. Four one-line hooks reach it. `DOMAINS` empty makes all of it inert; the removal checklist is in `v2_discussions/archive/137_kix_run_domain_migration.md`.
- `normalize.rs` — manifest normalization helpers (strip server metadata, kix annotations, status, nulls; Blake3 `content_hash`, `hash_value`, `sort_keys`). The old build-vs-live machinery (`detect_drift`/`project_onto_shape`/`DriftStatus`) has been **deleted** — superseded by `fieldsv1.rs` + `drift.rs` (build-time hashes can't exact-match live objects: server zero-value omission, `stringData`→`data`, quantity canonicalization). `strip_kix_annotations` stays in active use (export, applied-hash recipe)

## Key patterns

**Identity-hash** is the core primitive. First 32 chars of a Nix store path. Same hash = identical content + deps. Change detection is a hash set comparison — no deep diff needed.

**StoreGraph** is the in-memory DAG built from `kix-packages.json` + Nix store references. Everything operates on StoreGraph pairs (old vs new): change detection, plan display, stamping, GC.

**Keyed-list diff.** The diff engine matches K8s arrays by natural keys (containers by `name`, ports by `name`, env by `name`, volumeMounts by `mountPath`) not by position. Without this, reordering items produces false diffs.

**Waves** via Kahn's algorithm on the `kix.run/depends-on` DAG. Within a wave, resources are independent. Lexicographic sort within waves for determinism.

**Annotations** stamped at build time: `kix.run/identity-hash`, `kix.run/package`, `kix.run/depends-on`, `kix.run/activations`. Everything downstream reads these, never raw store paths.

**Backend abstraction.** `NixBackend` trait — `CliNixBackend` (production, shells out to `nix` CLI) and `MockNixBackend` (tests, no Nix needed). An experimental `FfiNixBackend` using direct C FFI exists behind the `nix-ffi` feature but is not currently used.

**Operator mode** (`--operator` flag on deploy/rollback/gc). Instead of calling the reconcile engine directly, the CLI creates or patches Activation CRs and watches their status. The operator does the actual wave-by-wave apply. Build + plan display still happens locally (needs Nix). Three flows:
- `deploy --operator`: build locally → show plan → apply Activation CR with source path → watch status.waves
- `rollback --operator`: find superseded activation → patch Activation CR source path to target → watch progress
- `gc --operator`: delete the Activation records beyond `--keep` → operator finalizer cleans up resources

**Operator K8s Events** (doc 99 Stage H). The operator composes two `DeployObserver`s over the same `DeployEvent` stream: `OperatorObserver` emits structured tracing logs, and `K8sEventObserver` publishes K8s Events on the Activation CR via `kube::runtime::events::Recorder` so `kubectl describe activation` and downstream log aggregators surface the deploy timeline. Events are fire-and-forget (`tokio::spawn` per publish, failures logged at `debug` and dropped) — they are telemetry, never part of deploy correctness. Suppresses Pending and most Running verdicts to stay under the cluster Event rate budget; emits Normal/Warning Events for plan, terminal verdicts, prune, drift, recreate, hydration, and finalization. See `cli/kix-operator/src/k8s_events.rs`.

**Operator reconcile loop prevention.** The operator uses a stream-level generation filter to drop status-only updates. All status writes go through the status subresource (`patch_status`), which doesn't bump `metadata.generation`. The controller dispatches by phase: Queued CRs trigger activation switchover + deploy, Active CRs trigger drift detection, Superseded CRs are no-ops.

**Unified reconcile.** Both new deployments and drift correction use the same path: load desired manifests, fetch live kix-managed resources from the cluster, compare identity-hashes (`detect_changes_live`), wave-plan, and apply. No "old manifests" concept — the cluster IS the old state.

**Error boundary.** `thiserror` in libraries, `miette` in binary.
