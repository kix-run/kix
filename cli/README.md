# Kix CLI

Rust CLI for kixpkgs. Evaluates Nix-defined Kubernetes clusters, diffs against live state, and deploys wave-by-wave with SSA. Users run `kix`, never raw `nix`.

## Workspace

```
kix/             library — eval, manifest handling, cluster operations
kix-cli/         binary — clap CLI, command dispatch, plan display
kix-operator/    binary — kube-rs controller watching Activation CRs
fuzz/            cargo-fuzz targets for the bundle readers (own workspace)
```

Both binaries depend on `kix`. No other cross-deps.

### Bundle acceptance checks

- `kix bundle` reads back what it writes and refuses it unless the bundle's
  graph equals the result directory's graph (`result_dir` aside).
  `every_test_cluster_bundles` in `kix-cli/tests/commands_test.rs` bundles
  every cluster `kix list clusters` names; it is ignored by default (about
  10 minutes):
  `cargo test -p kix-cli --test commands_test -- --ignored every_test_cluster_bundles`.
- `commands/deploy/plan_bound_properties.rs` changes honest bundles
  (`kix/tests/fixtures/bundles/`) at random and checks that each is refused
  or deploys exactly the objects its plan document shows. 256 cases by
  default; `PROPTEST_CASES=20000 cargo test -p kix-cli --release --bin kix plan_bound_properties`
  for a long run.
- `fuzz/` holds libFuzzer targets for `PathsChecked::read` (held to a bound
  on the bytes it allocates, `kix_fuzz::check_paths`) and `Bundle::read`,
  each on bundle files as uploaded and on frames the fuzzer changes
  decompressed (`*_frames`). They build on stable rustc without a
  sanitizer: `cd fuzz && RUSTC_BOOTSTRAP=1 cargo fuzz build -s none -O`, seed
  with `./seed.py <bundle>... seeds` (`kix bundle` of the test clusters), and
  run with `cargo fuzz run -s none -O <target> seeds/raw` (or `seeds/frames`)
  `-- -fork=4 -max_total_time=300 -max_len=2500000 -rss_limit_mb=4096`.
- `.github/workflows/bundle-checks.yml` runs each fuzz target for two
  minutes and `every_test_cluster_bundles`, on changes to `cli/` and weekly.

## Deploy pipeline

```
new Build (Build::of_flake, or --bundle → Build::carried; checked for a retired domain, then stamped) → Build::installable refuses a stale pin
  → fetch old activation from cluster (or --current-activation for local cache)
    (store path GC'd? → reconstruct old manifests from the live objects naming the Active, Failed or kept-orphan records: SweepScope::Records { cluster, hashes })
  → refuse if another (non-operator) deploy of this cluster is Deploying
  → load every Failed record and resolve each to its closure in the local store
  → detect_changes (identity-hash set diff, local only)
    → fold_failed_closures (re-apply what a failed deploy may have changed, orphan what it left)
    → fold_kept_closures (orphan what the builds in the Active record's status.orphansKeptFrom declared and this build does not)
  → DeployPlan::from_graph_and_changes (no wave layer)
  → plan::objects::of: refuse unless every write and delete is one the package-grouped plan shows (see "Writes the plan shows")
  → when connected and there is something to write: the engine over the plan as a dry run (`kix plan`)
  → show package-grouped plan, refused writes, drift → stop if a write would be refused (`--on-error stop`) → confirm
  → ops.begin: create the Activation CR and mark it Deploying
  → scheduler::run_deploy (DAG-streaming, SSA + readiness per node)
  → prune orphans (named in the plan and in `DeployEvent::PruneStart { resources, kept, delete }`, which carries the never-pruned Namespaces and CRDs in `kept` apart from `resources` under every policy, so each renderer lists them as kept; warn-only unless `--prune`) → finalize activation
    (stopped before finalize? → ops.abort marks the record Failed)
    (finalize failed? → DeployError::FinalizeFailed: exit non-zero, build not cached as current)
```

## Cluster identity

The `<cluster>` argument is a flake attribute (`clusters.harbor =
./test-harbor.nix` makes it `harbor`). A cluster is identified by the `name`
its definition passes to `buildCluster` (`test-harbor`), which the build
writes into `kix-packages.json` (`StoreGraph::cluster_name`) and the
Activation record's `kix.run/cluster` label. Every lookup of cluster state
uses that name: the Activation records, the `SweepScope::Cluster` sweep, and
the local cache files `~/.cache/kix/activations/<name>.{path,root,kept-*}`.
`kix deploy` and `kix gc --hard` take the name from the build, and `kix status`
and `kix inspect` from the evaluated `ClusterOutput::cluster_name()` (the
build's record label; `ClusterOutput::name` is the attribute). Commands that
read state without building, or before building (health, rollback,
`status --operator`, soft gc, gc `--operator`, compliance attest
`--from-cluster`), call `CommandContext::cluster_identity(arg, Lookup)`.
Evaluating `kixClusters.<attr>.name` forces the definition's `buildCluster`
call, nearly a whole cluster evaluation that needs the flake's inputs, so it
is the last step: with no flake (`--flake` names a directory without
`flake.nix`) the argument is the name; when an Activation record in the
current context carries the argument as its `kix.run/cluster` label
(`activation::records_exist`, one LIST with no discovery) the argument is the
name; otherwise `kix::eval::eval_cluster_name()` evaluates it, and a flake
that does not define the attribute or has no `kixClusters` leaves the
argument. The flake reference goes into the installable
(`<flake>#legacyPackages...`, `eval::cluster_name_command`), so `--flake
github:...` works. When the evaluation fails, `Lookup::Mutating` (rollback,
soft gc, gc `--operator`) is an error naming the attribute and the failure;
`Lookup::ReadOnly` prints a warning and uses the argument. Soft gc refuses
when the build's `cluster_name` differs from the name it resolved before the
build, and passes the build's name to `keep_shared` and `delete_resources`.
`kix snapshot save` and `kix drift --cluster` need no flake and take the name
itself.

The cache file carries no kube context, so two contexts deploying clusters
of the same name share it. Soft gc takes the old build from the Active
record (`baseline::active_build_dir`, which uses the cache only when
`store::build_hash_of` matches the record's hash), and `kix deploy
--current-activation` refuses after connecting when the cached build is not
the context's Active build (`check_cached_baseline`).

Doc 99 ("graph streaming") replaced the wave-barrier executor with the
DAG-streaming `scheduler`. Each node becomes eligible the moment its direct
predecessors have emitted `Verdict::Ready`, independent subtrees stream
through in parallel, and the inline TUI (`--tui`) draws a live tree grouped
by kix package. `rollback`, `gc`, and the operator all run on the same
scheduler + `DeployObserver` stream; the old wave-barrier `reconcile.rs` and
`waves.rs` modules have been deleted.

## kix plan: the deploy pipeline as a dry run

`kix plan` (doc 157) is made by the code that deploys. `deploy::prepare`
builds, loads the old side, and computes the actions and the engine plan,
exactly as `kix deploy` does; `plan::dry_run` runs `scheduler::run_deploy`
over that plan with `SchedulerConfig.dry_run` and a `KubeOps` built with
`dry_run: true`, so every SSA and DELETE goes with `dryRun=All` and the
Activation record's lifecycle writes (begin, checkpoint, stamping, finalize)
are skipped; `plan::document` turns the result into the `Plan` document.
`kix deploy` runs the same three steps before it asks for confirmation, and
`kix deploy --dry-run` is `kix plan` with the deploy's flags.

- **What the apiserver said.** `KubeOps` keeps a `preview::Journal` under
  dry run: for each object the live object and the dry-run result
  (`apply::ApplyPreview`, returned by `apply_resource` only under dry run),
  a recreate, a prune answer, or a typed `preview::Refusal` (conflict with
  its owners and fields, webhook denial, ValidatingAdmissionPolicy denial,
  webhook without dry-run support, validation with `immutable`, forbidden,
  missing namespace, unknown kind, SOPS decryption).
  `KubeOps::take_dry_run_answers` drains it. Under dry run `apply` takes the
  kind from the discovery cache with no refresh and `rediscover` does
  nothing, since a dry run creates no CRD.
- **Every refusal shows.** The plan runs with `OnErrorPolicy::Continue`, and
  under `dry_run` the scheduler promotes the dependents of a failed node
  instead of cancelling them, because nothing a dry run writes persists.
- **Field changes.** `plan::server::Overlay` starts from the package diff
  the deploy prints and replaces each answered object's entry with the
  server's: `field_changes` compares the live object with the dry-run
  result after `comparable` drops server-maintained metadata, `status`, and
  `deprecated.daemonset.template.generation`, and hides Secret values
  (including `last-applied-configuration` on a Secret). A missing live
  object is an addition; an object with no change drops out; a package the
  build comparison called unchanged becomes changed when the server says so.
- **Not checked.** `plan::document` files an unknown kind whose CRD the
  build brings (a CRD manifest of that group and kind, or a `crd-ref-*`
  import marker for a CRD in its API group), an unknown-kind, invalid, or
  other refusal of an object whose CRD the dry run would change
  (`changed_crds`: the object was checked against the CRD now served), a
  missing namespace the build creates, a webhook without dry-run support,
  and a node the engine never tried under `not_checked`, not as refusals. A
  first deploy is mostly this. An immutable-field refusal followed by a
  `Recreated` answer for the same object is dropped, since the deploy
  recreates it. A recreated object stays in `packages` as changed, with the
  build comparison's field changes when the create could not be dry-run.
- **Deploy stops first.** When the plan has a conflict, a refused write, or a
  refused prune delete and `--on-error stop` (the default), `kix deploy`
  exits 1 before applying anything. `--on-error continue` applies the rest.
- **Exit status.** `kix plan` exits 0 when nothing would change, 2 when
  something would (a prune `delete` fate counts, `Plan::has_changes`), and 3
  when the deploy would stop (a refusal, or a
  stateful migration without `--accept-migrations`).
- **Offline.** `--current-activation` connects to nothing: the plan
  compares the cached build with the new one, `made_by: builds`, and every
  write-path check, and drift, is `not_checked` with reason `builds_only`.
- **Progress.** With `-o json|yaml|markdown`, `output::progress_to_stderr`
  sends the `crate::say!` progress lines of `prepare` to stderr so stdout is
  the document alone.

The document (`plan/document.rs`, `Plan`) is the one shape `kix plan` and
`kix diff` print for `-o json` and `-o yaml`: `schema_version`, `made_by`
(`dry_run`, `live_read`, `builds`), `kix` (`KixBuild`: crate version and the
binary's store path), `cluster`, `build` (`Build::of`: result directory and the
Activation record's identity hash), `deployed` (`DeployedBuild`: `kix plan`
from `Prepared::active`, `kix diff` from the old side's record), `flags`
(`PlanFlags`, `kix plan` only), `packages` (the old
`packages` object, typed), `objects_digest` and `objects` (see "Writes the
plan shows" below), and `migrations`, `conflicts`, `admission`,
`drift`, `prune`, `readiness` as `Checked<T>`, serialized
`{"status":"checked","items":[...]}` or
`{"status":"not_checked","reason":"builds_only|read_only|deployed_build_unavailable|not_previewable"}`,
plus `not_checked` objects. `--detail plain|fields|manifests` (default
`plain`) on both commands sets how much `packages` says about each change
(see `plan/mod.rs` below); `kix deploy --dry-run` uses `plain`. Its JSON Schema is committed at
`kix-cli/schema/plan.schema.json`; `plan::document::tests` fails when the
type and the file differ (regenerate with `KIX_WRITE_PLAN_SCHEMA=1 cargo
test -p kix-cli plan::document`, and set `SCHEMA_VERSION`, a `YYYY-MM-DD`
date string, to the day's date when a change is not backward compatible). `plan::server::tests` and the kind integration
test check that a plan and a diff against the same live state list the same
objects, and that a plan writes no record.

**Writes the plan shows** (`plan/objects.rs`). People review the
package-grouped `PackageDiff`; the engine runs the flat `DeployPlan`.
`deploy::prepare` joins them before the dry run, so `kix plan` and `kix
deploy` both refuse, naming the objects, a build whose plan leaves one out:

- *Writes* (W): every `ChangeAction::Apply` node of the engine plan, and
  every `Skip` node with a `rerun` manifest (a probe Job the engine may
  create again), as (`ResourceId`, store hash of its file). The file is the
  one `new_graph.resources` holds for that id; an id in no file or in two
  files is refused. Hashes come from store paths, not stamped annotations.
- *Shown* (P): `PackageDiff::shown`, filled by `diff_graphs` from the same
  package nodes it lists: every object of an added package, its
  PackageInstance included; the added, modified, and dep-affected
  resources of a changed package and of `cluster_level`; and the new
  Activation record. A package whose PackageInstance changed alone is
  changed. Each write must be in P, or be a *re-apply*: a file that the
  Active closure, a failed closure, or a kept closure already holds for the
  same id (`--reconcile`, the repair of a stopped deploy, a rerun Job).
  Re-applies add no object and no file the cluster's recorded builds lack.
- *Deletes* (D): the orphans the prune deletes under `--prune`
  (`deletes_of`: not `never_pruned`). Each must be removed in the diff
  (`Shown::deletes`, kept and shared ones aside) or, when the plan read the
  cluster, in its `prune` section.
- Outside the check, because Kix writes them and no build file describes
  them: the Activation record's lifecycle writes and the records it
  supersedes, the `kix.run/activations` stamp on unchanged objects,
  `--record-annotation`, the `kix.run/*` stamps, SOPS values decrypted into
  a Secret from the source file its store path names, and the delete before
  an immutable-field recreate of a write.

The result is `Prepared::objects`, which the document carries as
`objects` (`writes[]`: `kind`, `namespace`, `name`, `store_hash`,
`package`, `change` = `added|modified|dep_affected|reapplied`; `deletes[]`:
`kind`, `namespace`, `name`; each sorted) and `objects_digest`
(`plan::objects::digest`): `sha256:` and the hex SHA-256 of the compact JSON
`{"writes":[[kind,namespace,name,store_hash,package],...],"deletes":[[kind,namespace,name],...]}`,
each list sorted by its strings in byte order, `change` left out. The
dry-run overlay can drop a write the apiserver says changes nothing from
`packages`; `objects` still lists it. The text plan prints the counts, the
digest, and how many writes are re-applies. `kix diff` plans no deploy, so
both fields are `null` there.

**Three-way labels** (`plan/origin.rs`). With the deployed build's manifests
each field change gets `labels`: `intended` where the deployed and new
builds differ (by path overlap with `structural_diff(deployed, new)`),
`reverts_drift` where the live object differs from the deployed build and
the deploy applies the object, `drift_kept` where it differs and the deploy
skips the object (unchanged identity hash; `--reconcile` applies it).
Drifted fields go to the `drift` section with the managers
(`drift::foreign_owners`) that own them live. A plan labels what it applies;
`kix diff` labels against the live view (`origin::label_live`) and
`--from <build>` labels everything `intended` (`label_builds`). Without the
deployed build (its store path is not on this machine) nothing is labelled
and `drift` is `not_checked: deployed_build_unavailable`. A field another
manager took shows as an ownership conflict in a plan unless
`--force-conflicts`, under which it shows as `reverts_drift`.

## Where things live

### kix-cli (`kix-cli/src/`)

- `cli.rs` — all clap command/flag definitions (`DeployArgs`, `GcArgs`, `DiffArgs`, `HealthArgs`, `RollbackArgs`, `GlobalArgs`, enums). `GlobalArgs` includes `--no-cache` to bypass the SQLite eval cache (forces fresh Nix evaluation every time) and `--override-input <NAME> <URL>` — a repeatable global flag mirroring `nix --override-input`. Each `(name, url)` pair is forwarded verbatim to every `nix` subprocess kix spawns (`flake show`, `eval`, `build`), so callers can repoint flake inputs without mutating `flake.nix`/`flake.lock`. The docs captures pipeline relies on this to pin kix-examples' `kixpkgs` input at a known store path during sandbox-free regeneration. Paired via `GlobalArgs::input_overrides()` into `Vec<(String, String)>` and applied through `CliNixBackend::apply_overrides(&mut Command)` plus an `input_overrides` slice on `Build::of_flake`. `-o`, `--context`, `--flake`, `--no-cache` and `--override-input` are global, but `SCOPED_GLOBALS` lists which commands read each; `cli::command()` (used by `main.rs` and `completions`) gives every other command a hidden copy, so its `--help` omits the flag while parsing still accepts it anywhere on the line. A new command, or a command that starts reading one of these flags, needs an entry there; the `cli::tests` check that every entry names a real command and that every command still prints `--help`
- `plan/mod.rs` — shared plan renderer for deploy + gc + diff + plan. `PackageDiff`/`PackageChangeDiff` types, `diff_graphs()` for package-level comparison, `print_package_plan()` for namespace-grouped changes-only stdout display (deploy/gc/rollback modals), `split_never_pruned()`/`print_never_pruned()` for the "Kept:" list that gc and deploy's plan print under it, `render_package_diff_markdown()` and `document::Packages::of(&PackageDiff, Detail)` (the `packages` section of the `Plan` document) as canonical structured producers consumed by both `kix diff --output {json,markdown}` and (future) the CI PR-comment GitHub Action. All formats share the same PackageDiff input so they stay in sync. A removed resource whose kind `lifecycle::never_pruned` protects (Namespace, CRD) is never shown as a deletion in any format: `PackageChangeDiff::removed_and_kept()` splits it out, the text plan marks it `! ... (kept)`, markdown lists it under "Left the build, never deleted automatically", JSON puts it in `kept_resources`. How much the JSON says is `document::Detail` (`--detail` on `kix diff` and `kix plan`): `Plain` gives each `modified_resources[]` entry `diff_count`; `Fields` adds `changes`, one `{path, change, old?, new?, labels?}` per field (`change` is `added`, `removed`, or `changed`; old to new); `Manifests` adds to that a `manifests` object on each package entry (`changed[]`, `cluster_level`, `added[]`, `removed[]`), `{"<display id>": {"old"?, "new"?}}` for every modified, added, and removed resource (kept ones left out), read through `ManifestIndex`: the two graphs for `kix diff`, and for `kix plan` the live object and the dry-run result of each object the apiserver answered for (`ManifestIndex::answered`). A Secret's `data` and `stringData` values, its `kix.run/content-hash` and `kix.run/applied-hash`, and every `checksum/*` annotation read `SECRET_NOT_SHOWN`, or `SECRET_CHANGED_NOT_SHOWN` on the new side when the old side holds a different value at the same path (so a line diff of the two manifests still shows it); a field value over `MAX_SHOWN_VALUE_BYTES` (16 KiB serialized) and a manifest over `MAX_SHOWN_MANIFEST_BYTES` (256 KiB) read `(N bytes, not shown)`. Literal `env` values and ConfigMap data are shown as they are. A removed package lists its kept resources too (`PackageInfo::kept`; text and markdown show `(N removed, M kept)`), and every JSON package entry (`added[]`, `removed[]`, `changed[]`, `cluster_level`) carries a `kept_resources` list of display ids, empty where nothing is kept; `added[]`/`removed[]` `resources` is the package's total, kept included. `PackageDiff::resource_totals()` feeds the "real content" count of the text summary and markdown, which leaves kept resources out and counts them as kept. The text plan hides the same secret values as the JSON (`without_secrets`), and prints each field change's drift label (`render::label_tag`) when `PackageDiff::labelled`; `PackageDiff::labels` holds one label list per entry of a resource's `resource_diffs`.
- `plan/objects.rs` — `of` (the writes and deletes of a deploy, each matched to `PackageDiff::shown` or a re-apply, or `Unshown`), and `digest` (the document's `objects_digest`); see "Writes the plan shows"
- `plan/document.rs` — the `Plan` document `kix plan` and `kix diff` print (see "kix plan" above), `Checked<T>`, `NotCheckedReason`, and the committed-schema test
- `plan/origin.rs` — three-way labels: `ThreeWay::label`, `label_live` (diff against live), `label_builds` (diff `--from <build>`), and `value_at`, which reads a diff-engine path (`$.spec.containers[web].image`) out of an object
- `plan/server.rs` — `Overlay`, which replaces each answered object's package-diff entry with the dry-run field changes and labels them, and `field_changes`/`comparable`
- `plan/saved.rs` — `kix deploy --plan`: `unusable` (schema version, no `objects` or `objects_digest` (a `kix diff` plan), an `objects_digest` its `objects` do not give (an edit), `made_by: builds`, and sections that do not match `made_by`: a `dry_run` plan with no `flags` or with conflicts, admission, or prune not checked, a `live_read` plan with `flags`, which only an edit produces; and a `live_read` plan whose drift is not checked: a diff of a snapshot, or one made without the deployed build), `digest` (the file's SHA-256, printed and in the JSON as `plan_sha256`), `flags_for` (the saved plan's planning flags; a command-line flag the plan was made without is an error, and a `kix diff` plan refuses `--prune`, `--force-conflicts`, `--reconcile`, and `--accept-migrations`), and `compare(reviewed, fresh) -> Comparison`, the rules of doc 158 (cluster; new `identity_hash`; `objects_digest`, refused when either is missing or they differ, with the writes and deletes that differ named (`Rule::Objects`); deployed `identity_hash`, or the record name when a record has none; flags; new conflicts by resource and admission refusals by resource and reason; new `reverted` drift by resource and path; new `delete` prune fates; and, for a `dry_run` plan, objects newly in `not_checked`, whose refusals and drift a dry run could not see). A rule the reviewed plan did not check is `skipped`; a different `kix` is `kix_differs`, never a mismatch: the objects digest already holds the deploy to the reviewed objects and files, and the binary is chosen by whoever deploys. `EXIT_STALE` is 4. `commands/deploy.rs` loads the plan (`load_saved_plan`) before any build, compares after `plan::document`, passes the merged planning flags to `run_deploy_async` (the apply never reads `args.plan`), and `check_saved_plan` is `--plan` with `--dry-run`, which exits 4 when stale, 3 when it matches but the deploy would stop (`doc.stops()` or migrations not accepted), and 0 otherwise
- `plan/render.rs` — text and Markdown for the sections below the package list: refused writes, drift, prune fates the dry run found, objects not checked, and the footnote saying what the document did not check
- `output.rs` — color helpers (`green`/`red`/`yellow`/`dim`/`bold` → `Cow<str>`), `is_interactive()`, `CommandResponse` trait
## First contact: proving the cluster is there

`Client::try_from` never touches the network. Before `fetch::make_client` ran a
probe, that meant an unreachable cluster hung the *first request* instead of
erroring, and the `"failed to connect to cluster: {e}"` message at all sixteen
call sites was dead code: no error was ever produced for it to print, because
nothing had tried to connect (kixpkgs#36, diagnosed in kixpkgs#38).

There are two failure shapes and they have different owners.

1. **The connect never completes, or is refused.** The transport's
   `connect_timeout` bounds it and knows the cause ("tcp connect error:
   Connection refused", "deadline has elapsed"). The probe's only job is to add
   the endpoint on the way out, which kube alone never does
   (`FetchError::ConnectFailed`).
2. **The connect succeeds and the endpoint then says nothing.** No connect
   timeout can ever fire on this one. Over HTTPS the TLS handshake usually
   turns it into shape 1, but a load balancer that terminates TLS in front of a
   wedged apiserver does not. Only the probe's own deadline bounds it
   (`FetchError::Unreachable`).

The two deadlines are deliberately unequal (`connect_timeout + PROBE_GRACE`) so
they cannot race for the error message. An earlier draft made them equal and
`Unreachable` became unreachable: the transport's deadline always won.

The probe rides the real client with the `FirstContact` extension set, which
drops the retries for that one request. They exist to carry a deploy through an
apiserver restart, not to spend eighteen seconds proving a refused port is
still refused. Riding the real client also means the connection the probe opens
is pooled and reused by the discovery calls that follow, so the probe is a
pre-warm rather than a tax: measured against stage1 and stage2, the median cost is
0.3s and 0.0s. A separate probe client cost ~0.6s on both, all of it a second
TLS handshake thrown away.

Any HTTP response passes the probe, 401 and 403 and 404 included. That rule is
what stops the probe becoming a failure mode of its own on a cluster where the
account cannot read `/version`: an endpoint that answers at all is alive, and
the real call gets to report the real error. `KIX_PREFLIGHT=0` skips the probe
entirely and restores the previous behaviour.

| endpoint | before | after |
|---|---|---|
| refused port | ~18s, "connection refused" | **0.1s**, endpoint named |
| blackholed address (HTTPS) | 15s, `ServiceError: client error (Connect)` | 15s, endpoint named |
| accepts, then silent (TLS terminated) | **120s**, no endpoint | **20s**, endpoint named |
| stage1, reachable | 4.95s | 5.25s |
| stage2, reachable | 4.60s | 4.58s |


## Baseline: what a plan compares against

A deploy or rollback decides what to do by comparing compiler outputs: the
closure it is about to apply against the closure the cluster already runs.
Live cluster state is consulted to *execute* (SSA, delete) and to *observe*
(readiness), never to decide. That is the kix invariant, stated in
`v2_discussions/81_deploy_as_lifecycle_engine.md` ("Closure A to closure B")
and `v2_discussions/29_compiler-design.md`. Do not add a live read to the
decision path; if the from-side looks wrong, the from-side is what to fix.

The from-side has two parts:

1. The **Active** (or Degraded) record's closure, resolved by the build
   new build's `deployed_build` (`--deployed-bundle`), then `built_via`, then
   `resolve_activation_by_hash` (`baseline::record_graph`).
2. Every **Failed** record's closure, resolved the same way. A deploy that
   stops part way applies objects and never becomes Active, so without this
   its leftovers are described by neither side: its orphans are never pruned
   and the objects it changed never read as changed (kixpkgs#82).

3. Every build the Active record lists under `status.orphansKeptFrom`
   (`activation::KeptOrphanSource { activation, identityHash, builtVia }`),
   resolved the same way. A deploy that keeps its orphans (warn-only, the
   default; `--prune-mode=no`; a failed delete) finalizes a record whose own
   closure no longer declares them, so without this the next
   `deploy --prune` says "Nothing to apply" and soft gc says "No garbage
   found", and only `gc --hard` can find them.

`apply::fold_failed_closures` folds the second into the plan. For any resource
a failed closure mentions we do not know which of two compiler outputs the
cluster holds, so a `Skip` whose identity appears there under a different hash
becomes an `Apply` (SSA is idempotent, so guessing wrong costs one unchanged
apply), and an identity only a failed closure has becomes an `Orphan`.
`apply::baseline_manifests` merges the two sets so `prune_order` can sort
orphans that exist in no current closure. Both are pure functions over
manifests, unit-tested in `cluster/apply.rs`.

`apply::fold_kept_closures` folds the third in as orphans only: those builds
were applied in full and then replaced, so they never turn a `Skip` into an
`Apply`. `baseline::orphans_kept_from` returns an `activation::KeptOrphans`:
`found` is every build the plan compared against (Active, folded Failed, kept)
for which `apply::leaves_orphans` is true, and `unexamined` is every kept
source this machine could not resolve. It travels in
`KubeOpsConfig::kept_orphans`; the engine passes `orphans_left` to
`ClusterOps::finalize` (true when the policy kept a prunable orphan or a prune
delete failed), and `KeptOrphans::recorded` makes the list `finalize_deploy`
writes: `found` only when `orphans_left`, `unexamined` always (nothing in this
run could have deleted their orphans), and, with `carry_current`
(`--current-activation`, whose plan never read the record), the list on the
record current at finalize. An empty list removes the field. A run that never
finalizes (nothing changed) leaves the Active record's list as it was.
Finalize writes the list whole, so of two deploys planned against the same
Active record, the one that finalizes second drops the first one's kept builds
(`housekeeping/2026-09-28-kept-orphans-list-last-finalize-wins.md`). Users who
want the list to stay empty deploy with `--prune` every time
(`PrunePolicy::Delete` leaves `orphans_left` false unless a delete fails); no
config or env var sets that policy for the CLI, and the operator always runs
with it.

After finalize, deploy and rollback call `baseline::sync_kept_roots` with the
list `KubeOps::recorded_orphans_kept_from` reports. It keeps one Nix GC root
per listed build this machine can resolve
(`~/.cache/kix/activations/<cluster>.kept-<identity-hash>`) and removes roots
for builds no longer listed; `<cluster>.root` moves with every deploy, so
without these a listed build is collectable and every later plan reports it
as unreadable. A machine's roots are updated only when that machine finalizes
or gcs.

`commands/baseline.rs` does the resolution and owns two refusals: a record
whose closure is not in this machine's store is reported and deliberately
*not* consumed (it keeps asking until someone handles it), and a non-operator
`Deploying` record means another deploy may be in flight, which is refused
with the `kubectl patch` escape hatch rather than guessed at.

One thing the record's new timing changes visibly: it is created before the
first wave, so the plan's last-wave apply of it reports `configured`, not
`created`, and a deploy summary's counts shift by one. Doc captures that show
a record line need regenerating.

- `commands/baseline.rs` — the from-side of a plan, shared by deploy and rollback: `load_failed` resolves every `Failed` record to its closure and reports the ones this machine cannot resolve; `load_kept` resolves the Active record's `orphansKeptFrom` and warns about sources it cannot, pointing at `kix gc --hard`; `orphans_kept_from` computes the `KeptOrphans` the new record's list is made from; `sync_kept_roots` keeps the GC roots for the listed builds; `refuse_if_deploy_in_flight` refuses while a non-operator `Deploying` record exists. See "Baseline" above.
- `commands/deploy.rs` — deploy pipeline: resolves old activation (if its store path is gone — GC'd or built elsewhere — `reconstruct_old_from_live` rebuilds the old manifest set from the live kix-managed resources that name the Active record, a Failed record of this cluster, or a build under `orphansKeptFrom` (`fetch::SweepScope::Records`), so another Kix cluster's objects never become orphans, as their kix-owned view (`fetch::kix_owned_manifests`), excluding Activation CRs, so change detection and prune ordering still work; `StoreGraph::synthesize` then rebuilds a package-level StoreGraph from the stamped `kix.run/package` annotations + live PackageInstance versions so the plan shows changed/unchanged packages, not everything "added". Same two functions `kix diff` uses for its live and snapshot sides), displays plan (`prepare` is shared with `kix plan`; when connected and there is something to write, the plan is the server-side dry run of `commands/plan.rs`, and a plan with refused writes stops the deploy before it applies anything under `--on-error stop`), confirms, builds a `DeployPlan` and delegates to `kix::cluster::scheduler::run_deploy()` (doc 99). Observer selection: `--tui` (+ interactive stdout) uses `graph_stream::GraphStreamDriver` for the inline tree dashboard; otherwise a line-oriented `StreamCliObserver` prints one line per terminal `Verdict` (doc 99 §7 "nix-build-L" idiom). `--reconcile` forces re-apply of all resources even when activation identity matches (heals drift). `--dry-run` runs `kix plan` with the same flags (`DeployArgs::plan` is the shared `PlanArgs`). **Exit status and local cache**: `RunEnd::of` reads the engine's result, which is `Ok` with `failed > 0` under `--on-error continue` and after a failed prune delete under either policy. `succeeded` (no failed and no cancelled node) decides the exit status, so any failure exits 1; `current` (no `Err`, no cancelled node, so the engine finalized rather than aborted) decides whether `save_activation_path` caches the build. Rollback uses the same `RunEnd`. The summary line reads `Deploy complete`, `Deploy failed` (some operation failed), or `Deploy stopped` (ended early with nothing failed). `--operator` delegates to the kix-operator instead; `operator::watch_activation_progress` returns `Reconciled::{Active, Degraded}` and a Degraded record exits 1 after the cache is saved. `--force-conflicts` opts in to SSA force (default off — conflicts surface as `ApplyError::Conflict` with the conflicting field paths and current owner; use this when migrating a resource away from kubectl/helm for the first time). Import markers (PackageInstance with `kix.run/mode: import`) are applied like any other resource — their readiness check in `readiness::wait_for_import_target` polls the cluster for the described kind/name, so imports whose installer is in the same deploy are naturally wave-ordered after it. **Topology label preflight**: after the plan and before the confirmation, when a cluster connection already exists (not under `--current-activation`), `topology::topology_keys` reads every `topologyKey` the new manifests' spread constraints and (anti-)affinity name, `topology::list_nodes` lists the nodes once, and `topology::assess` prints one `warn:` line per label that a schedulable node lacks under a `DoNotSchedule` rule (the compiler derives spread on `cluster.topology.zoneKey` and cannot see a node; without this the first sign was a readiness stall naming the Deployment and nothing else). A 403 on nodes is a `note:`, not a failure. Warn only, never a refusal
- `commands/deploy_log.rs` — non-interactive deploy observers for `--log-format={line,json}` (doc 99 §7, Stage D). `LineObserver` emits exactly two events per resource: one on `Verdict::Running + NodeDetail::Applied` ("created"/"configured") and one on terminal `Verdict::Ready` ("ready"). Intermediate `ReadinessProgress` events are suppressed unconditionally — the log is a resource-granular activity stream, not a live dashboard. `JsonObserver` emits NDJSON with the same suppression rule; every object carries `type` + `elapsed_ms`. After the run `deploy.rs` calls `JsonObserver::summary`, which prints a `summary` object (`dry_run`, `succeeded`, and the six counts) in place of the text summary line; the plan before it is still text. `pretty` (the default) is the colored `StreamCliObserver` on TTY stdout and automatically downgrades to `line` on non-TTY. `-v` only expands Unchanged/Skip/Cancelled lines — it never turns on readiness-progress chatter

Nom-style viewport: every Ready resource is flushed to scrollback the tick it completes — the live viewport only ever contains Running / Failed / AwaitingInput / Drift rows plus a collapsed `N packages pending` summary for work that hasn't started. When all members of a package are flushed, a single package-summary line is emitted to scrollback so history reads as a progressive collapse. Failure frame pins a `⚠ failures` block at the top. Active-resource rows carry the latest readiness-progress message (`⏵ Deployment/foo  ⏱ 12s  2/3 ready`) from `NodeDetail::ReadinessProgress`. On spawn the driver redirects the tracing subscriber to `/tmp/kix-tui-<pid>.log` via `crate::trace_sink` — without that, `-v` under `--tui` would tear the ratatui backing buffer with stderr writes. `Ctrl-C` / `Esc` in the viewport cancels the underlying `CancelToken`

- `cluster/scheduler.rs` prune: an orphan whose kind is `Namespace` or `CustomResourceDefinition` is reported and never deleted (`lifecycle::never_pruned`, shared with `kix gc` in soft and hard mode and with the operator's teardown when an active Activation is deleted). Both take far more with them than the object named — a Namespace every object inside it, a CRD every custom resource of that kind on the whole apiserver, including ones no Kix cluster ever touched — and neither is dangerous to leave behind, so removing one is a deliberate human act.
- `cluster/apply.rs` `ApplyError::CrdStoredVersion`: the apiserver refuses a CRD that drops an API version the cluster still has objects stored at, reporting it as a validation error on `status.storedVersions` that says nothing about what to do. `classify_apply_error` turns it into an error naming the fix: migrate the stored objects to a version the CRD still serves, or keep serving the old one. A deploy meets it whenever a vendored CRD is re-vendored after upstream retires a version.

- `commands/diff.rs` — one comparison of two `StoreGraph`s, rendered by the same `plan::*` producers the deploy plan uses (text, `json`, `yaml`, `markdown` for PR comments) plus stateful migration pairs. `--detail plain|fields|manifests` (default `plain`) sets how much `json` and `yaml` say about each change; text and markdown ignore it. New side: the build. Old side: `--from <dir>` is a build result when `kix-packages.json` is inside, otherwise a manifest directory (`kix snapshot save`, `kix export`) synthesized into a graph (`StoreGraph::synthesize`); no flag means the live cluster's objects of the built Kix cluster (`SweepScope::Cluster`, less the objects the build drops that another Kix cluster's current build still contains, which deploy would keep), fetched as the **kix-owned view** (`fetch::kix_owned_manifests_against`) and synthesized the same way. A live object whose `kix.run/identity-hash` names a manifest in the build, that `drift::check_object` finds `InSync`, and in whose view every field that manifest sets holds an equal value (`build_holds_in`, with the diff engine's equivalences) is replaced by that build manifest carrying the live `kix.run/*` annotations; this keeps fields a server or mutating webhook added on that apply out of the diff. In sync alone only says the live fields match the apply response, so a field the CRD schema pruned or a value a webhook overwrote still shows, and the live stamps keep a package move visible, since both hashes leave `kix.run/*` out. A Secret whose fieldset lists `stringData` never passes that check, since the server never stores `stringData`. Every object not swapped goes through `redact_secret` against the build manifest of the same name: each `data` key in a Secret's view becomes the build's `data` or `stringData` value when the decoded live value equals it, otherwise `HIDDEN_SECRET_VALUE`, and each `stringData` key the build declares and kix's fieldset lists is restored the same way. No live Secret value reaches the comparison, whether kix applied the Secret through `data`, through `stringData`, or not at all (no kix Apply entry, so the view is the whole object). A SOPS Secret, whose build has no plaintext, compares on its other fields only, so a value changed out of band does not show. `kix_owned_view` itself (snapshot, deploy plan) runs `redact_secret` with no build, so every Secret value in it is `HIDDEN_SECRET_VALUE`. Only the current record (`activation::current_record`: Active or Degraded, newest `deployed-at`) is kept, so the summary's old activation is the one the cluster runs. A build resource that declares its own deletion (`lifecycle::declares_own_deletion`: a Job's `ttlSecondsAfterFinished`, or a `hook-succeeded` Helm delete policy), is absent live, and has the identity hash it had in the deployed build (the build itself when the current record names it, else the `kix-packages.json` under the record's `kix.run/built-via`) is added to the old side as built, with a stderr note, because `kix deploy` would leave it alone. `StoreGraph::synthesize` groups an import marker (`crd-ref-*`, `secret-ref-*`, `service-ref-*`) under its stamped package, as a build lists it, rather than as a package of its own; a marker stamped `_cluster` (a `kix.mkImport` platform import such as `platform-storage`, which the build indexes as a package) stays a package. A live object that matches a build path joins every build package listing that path, since one `secret-ref-*` marker can be listed by several packages but carries one `kix.run/package` stamp. `PackageDiff` carries `cluster_level` (resources outside any package: Namespaces, CRDs, cluster-scoped bundles) and `activation` (old → new record name) so nothing the old flat comparison showed is lost. Exit 2 on any difference. It prints the `Plan` document for `-o json|yaml` (`made_by: builds` for `--from <build>`, `live_read` otherwise; the write-path checks are `not_checked`). Against the live cluster it loads the deployed build (`deployed_build`: the new build when the current record names it, else the record's `kix.run/built-via` directory) and labels every field change three ways with `origin::label_live`, keeping each compared object's served form for the `managedFields` that name who made a drift; a drift on an object whose identity hash did not change is `drift_kept`. The text output ends with the drift section and a line saying what a read-only comparison cannot see.
- `commands/plan.rs` — `kix plan`: `deploy::prepare`, then `dry_run` (the engine under dry run with a `PlanObserver` that counts writes on a stderr progress line and records failed and never-tried nodes), then `document` (the overlay, refusal classification, prune fates from the journal's prune answers, `not_checked`). `print_text` is the plan text `kix deploy` also prints before confirming; `kix plan` passes `verbose` so every resource and field shows.
- `commands/gc.rs` — soft (DAG diff old vs new) and hard (full cluster scan against a build made now) garbage collection. Both list a garbage Namespace or CRD under "Kept" and never delete it (`plan::split_never_pruned`, `lifecycle::never_pruned`); deploy's plan and offline dry run list never-pruned orphans the same way, apart from the orphans they count for deletion. Hard mode sweeps with `SweepScope::Cluster`, so other Kix clusters' objects never reach the plan (it prints a per-cluster skip count); an object that also names another cluster's current record is kept (`judge_hard`), and with other clusters present an object naming no record is listed as "Unattributed" and judged only with `--include-unattributed`. Hard mode deletes only stamped resources; label-only hits without `kix.run/identity-hash` are listed as "unstamped" and deleted only with `--include-unstamped` (kix never applied them: inherited labels, kubectl-applied renders). `--operator` deletes retired (Superseded) Activation CRs; the operator's finalizer only lets them go, since it deletes resources only for an Active, Deploying or Degraded record. `delete_resources` itself skips never-pruned kinds, so a caller that forgets `split_never_pruned` still cannot delete one. **Record retention** in every mode (`activation::RetentionPolicy`, `retire_plan`, pure and unit-tested): always keep the `--keep` newest Superseded Activation records (default 10) whatever their age, never more than `--keep-max` (default 50), and beyond the floor retire anything older than `--keep-for` (default 30d; `0` off). Newest first by parsed `kix.run/deployed-at`; a record with no usable timestamp sorts oldest; ties break on name. Each retired record is deleted with `Preconditions { uid, resourceVersion }` (`delete_activation_if_unchanged`), so a record that changed since the listing (a rollback made it Active again) is refused with 409 rather than deleted. The plan connects to the cluster before the Nix build (fail fast, one connection reused for the deletes). Soft mode never touches records otherwise; the deploy record is never soft garbage even though its store hash changes every build (`soft_garbage`). Why retention matters: `kix.run/activations` on every managed resource keeps one hash per deploy whose record still exists, and Kubernetes caps all annotations on an object at 256 KiB, so unbounded records would eventually make every SSA fail with 422; the next deploy after a gc drops the retired hashes (`merge_activation_set`). A listing failure is an error, never an empty plan. **Kept orphans**: `RecordRetirement` also carries the Active record, and soft mode adds `kept_garbage` (objects only a build in its `orphansKeptFrom` declares, resolved by `baseline::load_kept`) to what it deletes, listed under "Orphans kept by earlier deploys". After a run with no failed resource deletes, soft and hard mode call `clear_kept`, which removes the field from the Active record when `may_clear_kept` holds: the build gc compared against is that record's build, and gc examined everything (soft mode: every source resolved; hard mode: the sweep was forbidden no kind). It also drops this machine's kept roots. A 404 on delete is "already gone", not a failure, since a kept orphan may have been removed by hand
- `commands/migrate.rs` — `kix migrate domain <cluster>`: the one-off move of a cluster's Kix records off the retired `kix.dev` API group. Builds the cluster to get its two CRD manifests, always dry-runs first and prints the plan, then copies every Activation record to `kix.run` with spec, status and history intact, verifies the count, clears the operator finalizer from the old records and deletes the old CRDs. PackageInstance records are not copied: the next deploy re-creates them. Part of the compatibility layer in `kix/src/legacy_domain/` and goes when that goes.
- `commands/rollback.rs` — rollback to most recent Superseded activation. No nix build — resolves old store path and re-applies via reconcile engine. `--operator` patches the Activation CR's source path and lets the operator reconcile. `--list` is a read-only history view: enumerates Superseded activations with name, identity-hash, timestamp, source store path (`built_via`), `previousActivation` link, and local-store availability, then exits without prompting — supports `--output json|yaml` for scripting. Interactive selector and `--list` share `print_superseded_entries()` so both views show the same columns. Before applying, the confirmation modal renders the package-grouped diff via `plan::print_package_plan` against the current Active CR so the operator sees exactly what flips. `v2_discussions/84_m0_m1_implementation_plan.md` §2. History is bounded by `kix gc` retention (at least 10 newest, at most 50, nothing older than 30d beyond the floor, by default), so `--list` is finite and a `previous:` link may name a retired record
- `commands/logs.rs`, `commands/pf.rs` — thin wrappers that build the cluster, resolve `<package>` to its primary workload (Deployment / StatefulSet / DaemonSet) via `commands/workload.rs::resolve_package_workload`, extract `spec.selector.matchLabels` as a `kubectl -l` selector, then `exec` into `kubectl logs`/`kubectl port-forward`. Deliberately shelling out — the point is "one tool" in the demo, not re-implementing log streaming or port proxying. Per `v2_discussions/84_m0_m1_implementation_plan.md` §4. `--context` is forwarded; logs support `-f/--tail/--since/-c/-p`; pf accepts multiple port specs and `--address`. Zero library changes.
- `commands/workload.rs` — shared by logs/pf: builds the cluster (`commands::build_flake`), finds a package by instance name (exact match, ambiguity error with qualified suggestions, or `namespace/name` form), walks its `resource_paths` and returns a `WorkloadTarget { kind, namespace, name, selector }` using the first Deployment → StatefulSet → DaemonSet it finds.
- `commands/export.rs` — dump built cluster manifests as plain Kubernetes YAML for exit-strategy handoff or audit bundles. Walks the freshly-built `StoreGraph` (same mechanic as `diff.rs` build-to-build mode), writes each manifest as `<out>/<namespace>/<Kind>-<name>.yaml` via `manifest::serialize::manifests_to_yaml`. Two modes via `--for`: `exit` (default) strips `kix.run/*` annotations using `cluster::normalize::strip_kix_annotations` and drops kix-internal CRs (Activation, PackageInstance) — the result is neutral YAML a downstream consumer can `kubectl apply`. `audit` preserves stamped provenance annotations and kix-internal CRs for compliance evidence (the M3 compliance-evidence precursor, per `v2_discussions/84_m0_m1_implementation_plan.md` §1)
- `commands/operator.rs` — shared helpers for operator mode: `connect_and_verify()`, `apply_activation()`, `watch_activation_progress()`, `wait_for_deletion()`
- `commands/health.rs` — cluster integrity walk: indexes live resources by `kix.run/identity-hash`, checks every `kix.run/depends-on` edge resolves within the active activation's reachable set, reports Healthy/External/Reaped/Missing/AtRisk. **Graph-presence only — it does not compare field content**; that is `kix drift`'s job. Import-aware: resources with `kix.run/mode: import` annotation show as `external` status instead of healthy/degraded. Reaped-aware: an absent dependency whose seal (read back from the local nix store by identity hash) declares its own deletion — `helm.sh/hook-delete-policy` containing `hook-succeeded` on a chart-rendered manifest, or a Job's `spec.ttlSecondsAfterFinished` — is a hook that ran and cleaned itself up, so it counts as satisfied and lands under `(completed hooks)` rather than dragging its whole downstream chain to `at risk`
- `commands/check.rs`: `kix check`, two steps. (1) `eval_cluster`, which is where every build-time check runs: constructor validators, error-level scorecard findings and the cross-resource resolution checks (`kix/lib/eval/validate.nix`, run by `buildCluster`) all surface here as an eval failure; (2) the scorecard report, `--sarif` for SARIF 2.1.0. No schema or deprecated-API tool runs over the rendered manifests here, and nothing in it reads the flake `checks` output: schema validation is the `schema-cluster-<name>` flake check (`kixChecks.schemaCheck` in `kix/checks.nix`, kubeconform), run by `nix flake check`
- `commands/drift.rs` — `kix drift`: runtime content drift check via applied-hash stamps (doc 122). Takes no flake; `--cluster` scopes it to one Kix cluster through the Activation records, otherwise it checks every Kix object and each report names its clusters (`DriftReport::clusters`, JSON `clusters`). It compares live objects against the `kix.run/applied-hash` annotations written at deploy time, so it runs from any kubeconfig-only context (no repo, no nix build). Dispatched in `main.rs` BEFORE `CommandContext` is created (like `completions`) so no Nix backend is ever initialized. Per-resource verdict lines; drifted resources list attributed foreign owners ("spec.template…image taken by kubectl-patch at <ts>") and, when set, the unrecorded replicas change ("spec.replicas changed from 2 to 0 through /scale"); otherwise a drifted object with no other recorded manager prints that Kubernetes recorded no owner. `--output json` for scripting (`foreignOwners`, `unrecordedScale`). Exit 0 = all in-sync/unstamped, 1 = drift found. Tested against recorded managedFields fixtures in `kix/tests/fieldsv1_fixtures.rs`; no kind test covers `kix drift`
- `commands/images.rs` — list all container images in a cluster activation. Extracts image refs from pod specs across Deployments, StatefulSets, DaemonSets, Jobs, CronJobs, and Pods (including initContainers and ephemeralContainers). Default text output is one image per line (suitable for `xargs docker pull`). `--sources` adds per-image resource provenance. `--output json` emits structured `[{image, sources: [{kind, namespace, name, container}]}]` for scripting. Primary use case: airgap preloading (`kix images <cluster> | xargs -P4 -I{} docker pull {}`)
- `commands/pin.rs` — `kix pin`, the promotion verb (`v2_discussions/archive/138_values_that_vary_per_deploy.md`). Three subcommands over a pin file, committed JSON recording what each image reference resolved to. `set <key> --tag <t>` asks the registry for the tag's manifest digest, refuses a tag that is not there, and rewrites the file; `--init` creates the file or adds a key, `--no-resolve` writes a pin with no digest and says so, `--digest` records a digest you already have, and `--force` overwrites a file that Kix did not write. `check` verifies every recorded digest is still present **by digest, not by tag**: a moved or deleted tag whose digest still runs is a warning, because there is nothing the author can do about it; a missing digest is a failure. `check --source-rev <rev>` is the freshness assertion, failing when a pin records a different source revision, which is the only way to catch a promotion step that silently did not run. Dispatched in `main.rs` BEFORE `CommandContext` (like `completions` and `drift`): it needs no flake and evaluates no cluster, because the state in which a pin most needs fixing is the state in which evaluation is unhappy about it
- `commands/pin/locate.rs`: finds the pin file when `--pins-file` is absent. It checks the working directory, then the directory named by `--flake` without evaluating the flake, then the git root. At the git root it accepts `pins.json`, or a single `*pins.json` file whose header declares `managedBy`. The marker prevents unrelated JSON files from becoming candidates. The scan does not follow symlinks or run outside a repository, and it refuses to choose when several candidates remain. A flake cannot declare the source path directly because a path literal evaluates to a Nix store path; recovering the original path would require evaluating the flake, which this command intentionally avoids
- `commands/compliance/` — compliance exports for auditors, CI, and compliance platforms (implements `v2_discussions/61_compliance_exports.md`). Three subcommands, all built on the same `shared::build_and_load` helper that runs `nix build` + loads the StoreGraph:
  - `sbom` emits a CycloneDX 1.6 SBOM to stdout. Walks the StoreGraph to produce a `platform` root component for the cluster, one `application` component per package (`pkg:kix/<ns>/<name>@<version>` purl), one `container` component per unique image (deduped, with optional SHA-256 digest from `@sha256:` refs, `pkg:docker/...?repository_url=<host>` purl), and one `library` component per flake input read from `flake.lock` (`pkg:nix/<name>@<rev>`). The dependency graph is derived from `StoreGraph::cross_deps` plus per-package image edges.
  - `attest` emits an unsigned in-toto Statement with a SLSA v1 provenance predicate. Subject is the activation identity hash (`nixStoreHash` digest type). `externalParameters` include the flake ref and a BLAKE3 digest of the on-disk `flake.lock`; `resolvedDependencies` carry the git HEAD, every flake input's rev/narHash, and every container image, with a `sha256` digest only when the reference actually carries one. `--builder-id` and `--invocation-id` override the `runDetails` block so CI can stamp its workflow URL. `--from-cluster` reads the deploy receipt off the cluster's active Activation instead of building, so the statement describes what **was** deployed rather than what would be, from a machine that has never built this cluster. Both routes go through `receipt::attestation_from_receipt`, so they cannot drift apart. Signing is deferred to doc 54 by design.
  - `receipt.rs` is not a subcommand. It assembles the provenance a deploy writes into the Activation's `status` subresource: flake ref, git commit **and whether the tree was dirty**, the `flake.lock` digest, every input, the kix and Nix versions, and every image the build renders. Deliberately not the manifests: built manifests carry secret values inline, so storing them would make every deploy record a readable credential archive, which is Helm's documented failure. `shared::git_state` replaced `git_commit` to supply the dirty flag, and `deploy.rs` prints it above the confirmation.
  - `audit` bundles `scorecard-results.sarif`, `sbom.json`, `provenance.json`, `assessment-results.json`, and `audit-report.md` under `--out` (default `./compliance`). The OSCAL assessment maps findings to framework controls via static Rust tables (see `audit.rs` — SOC 2, ISO 27001, DORA, NIS2). A control is marked `not-satisfied` only if an error-level scorecard finding exists whose rule ID starts with one of the control's declared `required_rules` prefixes. The markdown summary is a self-contained PR-comment-ready report. SARIF generation duplicates the shape used by `kix check --sarif`.

#### build_source (`kix/src/build_source.rs`)

- `Build` is the build plan and deploy work from, and a caller cannot hold one unchecked. It is the only way a command or the operator loads a build, new or one a record names. Its fields are private and it has two constructors, each doing every check once: `Build::local(result_dir)` loads a result directory in this machine's Nix store, validating it (`Build::of_flake(flake, cluster, overrides, status)` runs `nix build` first, and its `FlakeBuildError` says whether the build or the load failed, so each command keeps its own wording), and `Build::carried(bytes, cluster, read)` hashes the bytes itself, hands them to `read` for a `CarriedBuild` and its `StoreGraph`, and refuses a graph that is not valid or not of `cluster`. Either constructor then runs `legacy_domain::check_build` on the graph as loaded and stamps it (`eval::stamp`), in that order, so a graph is stamped once and the check sees it before stamping upgrades it. Everything else comes through accessors that give only checked results: `graph` (stamped) and `into_graph`, `installable` (consumes the `Build` and gives an `InstallableBuild`, or the check's `LegacyDomainError`; `kix plan`, `kix deploy` (with or without `--bundle`) and `kix migrate domain` take only an `InstallableBuild`, while a build a record names, which can predate the domain move, is never refused), `is_local` (the activation cache and GC root, the dirty-source wording), `carried_provenance` (the maker's `Provenance` and the core's SHA-256, for the receipt's `source.bundle.sha256`; `None` for a local build), `sops_sources(placeholders)` (`SopsSources::Local` for a local build; for a carried one, the carried files a Secret names, each refused unless its store path is made from its bytes, as `SopsSources::Carried`, placeholders for `kix plan`), and `deployed_build(identity_hash)` (a carried build's copy of the build a record names, stamped, refused unless the record has that identity hash and it is valid; `None` for a local build). `CarriedBuild` is the seam a build made elsewhere implements, inside or outside the crate: `sops_files`, `provenance` and `deployed_build`, each a claim the `Build` checks. `Provenance` lives here; the bundle header re-exports it.

#### eval (`kix/src/eval/`)

- `store_graph.rs` — **central data structure.** `StoreGraph` holds the full in-memory DAG: `PackageNode` (instance_name, namespace, version, resource_paths, cross_deps), `ResourceNode` (store_path, manifest). Built from result dir's `kix-packages.json` + `nix-store -q --graph`. `assemble` (public, shared by every reader of a build) reads each manifest's bytes once, parses them with `manifest_json`, and fails on one it cannot read or parse, and on a package with no `spec.instanceName`. `validate()` runs on every build, whichever reader read it: each manifest's kind, `apiVersion` parts, name and namespace one URL path segment each (not empty, `.` or `..`, no `/`, `%`, `?`, `#`; kube-rs puts them in request paths unescaped); each object (kind, namespace, name) once; one Activation record, at `activation_path`, whose `kix.run/cluster` label is the index's `cluster`; each package's PackageInstance among the resources; one package per namespace and instance; and only import markers listed by more than one package. It does not run on `synthesize`'s graphs. `StoreGraph::synthesize(manifests, reference)` builds one from a flat set of stamped manifests instead (live objects' kix-owned view, a snapshot, an export): resources group by their `kix.run/package[-namespace]` annotations (a manifest matching a reference path instead joins every reference package that lists the path), every PackageInstance except an import marker stamped with another package makes a package (resources or not) and sits at its store path, `resource_owner` is filled, and a manifest reuses the reference's store path only when its identity hash AND content match — a live object drifted under its stamp keeps its own content-named synthetic path, so `plan::diff_graphs` sees the change. Used by `deploy` (previous state when the store path is gone) and `diff` (live and `--from <manifest dir>` sides)
- `bundle.rs`: bundles (`kix bundle`, `--bundle`, `--deployed-bundle`). The module doc is the specification: format 3 (zstd's seekable format; frame 0 the `Header` with `format`, `version`, `kix_rev`, optional `receipt`, and `files` as `[path, size, references]`; data frames; seek table), the record, index and cluster derived from the references (`Role`), every manifest and the index parsed with `manifest_json`, as a result directory's are, the caps and refusals each with what it protects, and the threat model. `PathsChecked::read` (the Kix Enterprise server) checks the container, every store path, the roles and closure, and parses only the record; `Bundle::read` (agent and CLI) also parses every manifest and returns the `StoreGraph` (`assemble` + `validate`), with `result_dir` `bundle:sha256:<sha>`; `OpenBundle::open` reads the seek table and header only (what `--deployed-bundle` matches records with). `BundleError` messages show the uploader's text through `kix::text::printable`. `Contents::write` writes a bundle, `from_result_dir` gathers one from a result directory with `nix path-info`. `commands/bundle.rs`: `kix bundle` reads its output back with `Bundle::read` and refuses it unless the graph equals the result directory's (`result_dir` aside). `bundle::read` reads the `--bundle` file (at most `MAX_STORED_BYTES`), opens each `--deployed-bundle` header (a format 1 one is set aside with a warning, any other error fails), and makes the `Build::carried` whose reader is `Bundle::read`, for plan, deploy and graph. `BundleSource` is the bundle's private `CarriedBuild`: `deployed_build` re-reads and re-verifies the file on each call; `sops_files` gives the bundle's `Role::Other` files, and `cluster::secrets` checks each carried SOPS source once per plan (age recipients only, no repeated key, at most 8 MiB of keys and values with YAML aliases expanded) and decrypts it once per deploy; `provenance` is the header's receipt plus `source.bundle.kixRev`.
- `manifest_json.rs`: the one parser for a build's manifests and `kix-packages.json` (`parse_manifest`, `parse_index`). Refuses a repeated key, serde_json's reserved `$serde_json::private::` key prefix, and nesting past 128. Every reader of a build uses it, so a result directory and a bundle read the same bytes as the same value.
- `store_path.rs`: Nix store paths computed from content (text paths for `builtins.toFile`, source paths for `builtins.path` of a file, executable or not), so a bundle's paths can be checked without a Nix store. `name_of` accepts only names Nix's `checkName` accepts
- `store.rs` — activation cache at `~/.cache/kix/activations/`. `save/load_activation_path()` for local cache, `resolve_activation_by_hash()` to go from cluster identity-hash → local result dir. `save_activation_path` also registers a Nix GC root (`<cluster>.root` via `nix-store --add-root`) pinning the deployed activation — builds run `--no-link`, so without it `nix-collect-garbage` deletes the store path the next deploy diffs against. `sync_kept_roots` keeps `<cluster>.kept-<identity-hash>` roots for the builds an Activation lists under `status.orphansKeptFrom`
- `evaluator.rs` — `KixEvaluator` wrapping a `NixBackend` trait with SQLite caching
- `cli_backend.rs` — **production backend.** `CliNixBackend` shells out to `nix` CLI commands: `nix flake show --json` for listing clusters, `nix eval --json` for listing packages/cluster info, `nix build` + a stamped StoreGraph for evaluation (not through `Build`, so `eval` does not depend on `build_source`). Benefits from Nix's built-in eval cache.
- `build.rs` — `build_cluster_activation()` shells out to `nix build .#cluster-{name}-activation`; crate-private, reached through `Build::of_flake`
- `stamp.rs` — `stamp_annotations()`, run by `Build` as it is made, by `Build::deployed_build` on the record's build it returns, and by `kix bundle` on the bundle it reads back to compare with the build (a `CarriedBuild` reader and `CarriedBuild::deployed_build` give unstamped graphs, which `Build` then stamps). It writes `kix.run/*` annotations onto StoreGraph manifests in-place; renames the Record to `<cluster>-<hash12>` so each deploy creates a distinct CR
- `cache.rs` — SQLite cache keyed by BLAKE3 of (flake path + lock + source fingerprint + attr)
- `ffi.rs` — experimental `FfiNixBackend` using `nix-bindings-*` FFI crates (gated behind `nix-ffi` feature, not currently used)
- `mock.rs` — `MockNixBackend` for tests without Nix

#### manifest (`kix/src/manifest/`)

- `types.rs` — `ResourceId` (kind/namespace/name), `CLUSTER_SCOPED` constant. Used everywhere
- `workload.rs` — `pod_spec(&Value)`: the one table of where a kind keeps its pod template (`spec` for a Pod, `spec.template.spec` for Deployment/StatefulSet/DaemonSet/ReplicaSet/Job, one level deeper for a CronJob). `kix images`, the SBOM and the topology preflight all read pod templates through it, so a kind added here is seen by all three
- `lifecycle.rs` — **the one classifier** for what a manifest is: `Lifecycle::{Desired, Marker, Record}` via `lifecycle_of(&Value)` / `lifecycle_of_live(&DynamicObject)`. Desired state is diffed, applied and pruned; a Marker (PackageInstance with `kix.run/mode: import`) is applied and its target polled; a Record (the Activation) is applied once at the end of a deploy and only ever superseded, never pruned. `record_of()` finds the record in a set. Change detection (`apply.rs`) matches records like any other resource, so an unchanged build is still a `Skip` and the deploy short-circuits, but `Lifecycle::prunable()` keeps them out of the orphan set on both the store and live paths. Every former `kind == "Activation"` / `kix.run/mode == import` check (stamp, deploy, rollback, gc, export, health, readiness, graph, the operator) reads this instead, and a unit test fails the build if a new comparison of the record kind appears anywhere else. Born from kixpkgs#59: the previous deploy's record, renamed by stamping on every deploy, reached change detection through the store-graph path and was reported as an orphan on every deploy (and `--prune` would have deleted it before finalize could supersede it)
- `diff/engine.rs` — `structural_diff(a, b)` → `Vec<Difference>` with JSON paths. Keyed-list-aware, and skips the spellings `diff/equivalence.rs` declares equal
- `diff/equivalence.rs` — what the API server treats as the same: `null` and `[]` equal an absent field (`{}` does not, since `emptyDir: {}` and many CRD fields mean something), `SERVER_DEFAULTS` lists documented defaults that equal an absent or `null` field (`fieldRef.apiVersion: v1`; the `apiVersion`, `kind`, `spec.volumeMode`, and `status` the server adds to each `volumeClaimTemplates` entry; `volumeMounts[].readOnly: false`; probe `initialDelaySeconds`/`timeoutSeconds`/`periodSeconds`/`successThreshold`/`failureThreshold`), and members of `limits`, `requests`, `hard`, and `sizeLimit` compare as resource quantities by amount (`1` = `"1"`, `0.5` = `"500m"`). Matched against the path with list keys stripped. Applies to every comparison, build-to-build included, and to `StoreGraph::synthesize`'s content match
- `diff/keyed_lists.rs` — defines which K8s arrays match by key (containers→name, ports→name, env→name, volumeMounts→mountPath, subjects→kind:name, volumeClaimTemplates→metadata.name); any other list whose items are all objects with a unique non-empty `name` matches by `name`
- `diff/display.rs` — `format_diffs()` renders differences as colored text
- `serialize.rs` — YAML/JSON output (`strip_nulls` removes nulls and ONLY nulls before YAML: an empty map is content — `emptyDir: {}`, a CRD's `subresources: {status: {}}` — and `kix build`/`kix export` used to drop them), `load_manifests_from_dir()` for snapshot/export loading (every `.yaml` in the tree, PackageInstances included — they are kix-managed objects like any other; ids come from the manifest content)

#### pins (`kix/src/pins/`)

- `mod.rs` — reading and writing pin files. A pin file is JSON: an envelope `{version, managedBy, images}` whose entries hold `{repository, tag, digest?, sourceRev?, promotedBy?, resolvedAt?, note?}`. JSON rather than Nix for a checkable reason: reading a Nix file means evaluating it, so reading a pin file would execute whatever it holds, and writing one means hand-escaping registry-supplied strings into a programming language. The eval cache fingerprints `.json` alongside `.nix`, `.yaml` and `.yml` (`eval/cache.rs`), so nothing is lost by the choice. A bare map of pins is also accepted on read and is never treated as managed. Writing produces one canonical sorted form, which is why `PinFile::write` refuses a file that does not declare `managedBy` unless forced. `Pin` is `deny_unknown_fields`, matching the Nix reader, so a field Kix does not know is refused rather than silently dropped on the next write; `note` is the field for anything a person wants to say, carried through untouched and stripped by the Nix reader before it reaches the image option. Digests are validated as `sha256:` plus 64 hex characters on the way in

#### registry (`kix/src/registry/`)

- `reference.rs` — parsing `[registry/]repository[:tag][@digest]` with Docker's conventions: a leading segment is a registry only when it has a dot, a port, or is exactly `localhost`, and a bare Docker Hub name gains the `library/` prefix. `docker.io` maps to the `registry-1.docker.io` API host and to the historical `https://index.docker.io/v1/` credential key
- `credentials.rs` — the same places every container tool looks, in order: `KIX_REGISTRY_USERNAME`/`KIX_REGISTRY_PASSWORD`, a per-registry `credHelpers` entry, the general `credsStore` helper (`docker-credential-osxkeychain` and friends), then a literal `auths` entry. Anonymous is a valid outcome, not a failure
- `client.rs` — one question only: does this reference exist, and what is its manifest digest. Handles the bearer-token challenge, prefers index media types so a multi-architecture image resolves to its index digest (which is what a runtime resolves and what `crane digest` prints), and computes the digest from the response body rather than trusting the `Docker-Content-Digest` header, treating a disagreement between the two as an error. Reached only by `kix pin`: resolving a tag during a deploy is a non-goal per doc 120 §3.9

#### cluster (`kix/src/cluster/`)

- `apply.rs` — ceded fields: a 409 on an object whose `kix.run/cede-fields` annotation covers every conflicting path (`without_ceded_conflicts`, paths parsed from the apiserver message, `[*]` matching any list element) is retried once without those fields, so an operator that rewrote them keeps them; any other conflict is still `ApplyError::Conflict`. `detect_changes()` (identity-hash set diff → `ChangeAction::Apply/Skip/Orphan`; an old or live object without `kix.run/identity-hash` is never an `Orphan` — kix only deletes what it stamped; a `Lifecycle::Record` on the old or live side is dropped before matching, so the previous deploy record can never be an orphan on any path, store-graph, live-reconstruction or operator), `detect_changes_live()` (compare desired manifests against live cluster resources by identity-hash), `apply_wave()` (SSA via `kube`, field manager `kix`), `RERUN_ANNOTATION` / `wants_rerun()` (the `kix.run/rerun: on-change` opt-in the scheduler's rerun rule reads). The SSA response echo is kept (not discarded): `apply_resource` computes the applied-content hash from it (`fieldsv1::applied_content_hash`) and writes `kix.run/applied-hash` in the same post-SSA bookkeeping merge patch as `kix.run/activations` (`update_bookkeeping_annotations`, no extra round trip). That patch also runs under field manager `kix` — leaving it unset records the write as manager `unknown` in managedFields and pollutes ownership-based drift attribution (doc 122). `merge_activation_set()` is the pure set operation behind `kix.run/activations`: fold in the current activation, drop entries naming an Activation CR that no longer exists (`activation::live_activation_hashes`), always keep the activation being deployed (its own CR lands in the last wave), and return a sorted set so the caller can skip the write when nothing changed. Passing `live = None` disables pruning — keeping a dead reference is recoverable, dropping a live one is not. `record_activation_on_skipped()` is the entry point for resources the deploy did *not* apply; it touches `kix.run/activations` only, never `kix.run/applied-hash`. `fold_failed_closures()` and `baseline_manifests()` are the from-side fold that closes kixpkgs#82: see "Baseline" above. Both are pure over manifests, so nothing in the decision path reads the cluster
- `graph.rs` — `ResourceGraph` (petgraph DAG built from `kix.run/depends-on` annotations). Import-aware: nodes with `kix.run/mode: import` render as dashed/gray in dot output, `(import)` suffix in tree, `isImport` field in JSON
- `stream.rs` — graph-streaming vocabulary (doc 99): `Verdict`, `TransitionKind`, `NodeId`, `NodeDetail`, `NodeMeta`, `PlanNode`, `DeployEvent` (including `Stalled { idle, in_flight: Vec<InFlight { node, phase, since }>, aborting }` from the watchdog and `BestEffortFailed { what, message }` for checkpoint/stamp/finalize failures), `Phase`, `InFlight`, `DeployObserver`, `DeployResult`. The observer trait consumed by the CLI renderer, the non-interactive line/JSON observers, and the operator's tracing observer
- `scheduler.rs` — **deploy engine** (doc 99, reshaped by doc 134). `DeployPlan::from_graph_and_changes` builds the plan from a `ResourceGraph` + `detect_changes` output, and fails with `readiness::MalformedMarker` on an import marker the library would not have written (see `readiness.rs`). `run_deploy(ops, plan, orphans, old_manifests, config, observer)` is the ready-queue scheduler: every node becomes eligible the moment its direct predecessors have emitted `Verdict::Ready`, concurrency bounded by `SchedulerConfig::concurrency` (default `CONCURRENCY=64`). **The engine task never awaits foreign I/O while nodes are in flight**: every node, every discovery refresh and every checkpoint is a task spawned into one `JoinSet`, and the supervisor's only awaits are that set, the cancel token and the watchdog. The first shape held node futures in a `FuturesUnordered` and awaited rediscovery inline, which parked every apply and hung a deploy for 35 minutes (kixpkgs#62). **CRD barrier**: a CRD-like node (kind `CustomResourceDefinition`, or an import marker for one) does not promote its dependents until one discovery refresh that started after it completes; several CRDs finishing together share one refresh; a refresh that fails stops the run with `DeployError::DiscoveryFailed { partial }` (a stale view is a partial view, the rule from #60); `KubeOps::rediscover` first waits out listed group versions that answer 404 (see `fetch.rs`), so only a refresh that never settles or fails outright stops the run. Failure policy halt-dependents / continue-siblings (default) or halt-on-first-failure under `OnErrorPolicy::Stop`. Cascade-cancels transitive dependents on failure, except under dry run, where a failed node's dependents are still tried (nothing a dry run writes persists, so `kix plan` reports every refusal). A spawned task that panics is `DeployError::Internal`, never a lost node. Cancel (caller or watchdog) is observed through `CancelToken::cancelled()` in the supervisor's `select!`; the reason travels on the token, so a watchdog abort reads "no progress for 600s: waiting on ..." rather than "cancelled". On cancel the supervisor aborts every task and keeps draining the `JoinSet`: a node that finished just before the cancel is still counted, an aborted one becomes `Cancelled`, and only then does the run return; a cancel that lands as the last node finishes is re-checked after the loop so nothing is pruned or finalized. Whatever stops a run (cancel, `OnErrorPolicy::Stop`, a failed refresh), every node without a verdict gets `Cancelled { External }` and counts in `cancelled`, so renderers never leave a row Pending under a `Stopped` footer and the counts add up to the plan. Every post-loop write is bounded too (begin, stamping, each prune delete, final checkpoint, finalize: 60s each), because the watchdog only watches nodes and the discovery refresh. `ops.dry_run()` must agree with `SchedulerConfig::dry_run` or the run stops before it starts. Immutable-field conflicts recover via `ClusterOps::recreate_in_place` when the rid is pre-authorized in the orphan set (a resource that is in the plan is never in that set, so on a real deploy this branch only serves the unit test; the error text names the two recovery paths and tells the user to delete and deploy again otherwise). Both delete-and-recreate paths (this one and the rerun rule below, which `wants_rerun` limits to Jobs) go through `recreate()`, which refuses the kinds `lifecycle::never_pruned` protects (`recreate_refusal`): the node fails with an error naming the kind and what deleting it would take with it, and the user deletes it with kubectl if intended. **The rerun rule** (doc 136, kixpkgs#77): a manifest carrying `kix.run/rerun: on-change` (stamped by `kix.healthCheck` on probe Jobs) is never patched. The planner tags a changed one `TransitionKind::Recreate` and keeps the manifest on `PlanNodeEntry::rerun`; the executor calls `ClusterOps::get_live` first and applies plainly when nothing is live (first deploy, TTL-reaped, deleted by hand) or runs `recreate_in_place` when something is (foreground delete, wait, create), reporting `NodeDetail::Rerun { reason: "changed since the last run" }`. An unchanged one stays `Skip` but still runs a task: when its live object is in a terminal failure (`classify_workload_terminal`) it is recreated with reason "the last run failed", so a probe that failed against a degraded cluster runs again on the next deploy or rollback without a manual delete; a healthy one is counted unchanged and stamped like any Skip. That Skip-path retry is gated by `SchedulerConfig::rerun_failed`: the CLI sets it (a person asked for a run), the operator leaves it off (it diffs against live objects and requeues a failed run every 30 s, so on a degraded cluster it would delete and recreate the probe forever). With it off the Skip path still reads the live object and reports a failed one as `Verdict::Failed` without deleting it, so the gate stays red in the operator's status instead of reading as healthy; the operator still recreates a probe whose hash changed, and re-applies one its TTL reaped, since to a live diff that is a new resource. `wants_rerun` honours the annotation on Jobs only: a Deployment stuck on its progress deadline is "failed" to the classifier too, and deleting it would be an outage. Under dry run `recreate_in_place` checks the delete with `dryRun=All` and reports `Created` without applying (the apply would hit the same 422 the real delete avoids). `failed_rerun_nodes(client, discovery, plan)` is what `kix deploy` and `kix rollback` ask before they take the "nothing to apply" exit on an unchanged plan: a failed probe kept the previous activation from switching, so a deploy that reverts to that activation's content sees no change, and without the pre-check the failed Job would never run again; when it names anything the command runs the engine and the Skip path does the rest. The identity hash covers the sealed manifest and everything upstream of it, so "changed" means the probe, the thing it checks, or something upstream of that moved. Opt-in by annotation, never by kind: applied to every Job it would re-run stackgres bootstrap SQL on any upstream change. Activation CR checkpointing batched every 16 terminal verdicts, one write in flight at most, running totals; the final checkpoint and finalize are awaited inline after the node phase under a 60s bound. Failures of best-effort writes (checkpoint, stamping unchanged resources, finalize) are `DeployEvent::BestEffortFailed`, rendered by every observer, not `tracing::warn` lines. `Skip` nodes short-circuit without a task, but their rids are collected and stamped with the current activation in one concurrent pass once every node is terminal (an unchanged resource still belongs to this activation). `SchedulerConfig.dry_run` makes the whole run non-mutating: SSA and deletes hit the apiserver with `dryRun=All`, readiness short-circuits, and every real write is gated off in `KubeOps`. Also owns `OnErrorPolicy`, `PrunePolicy`, re-exports `delete_propagation_for`. Tested without a cluster (`engine_tests`): the CRD barrier does not park running nodes, a failed refresh stops the run, a hung refresh is reported and aborted, a hung apply is reported then aborted on the 30/60/90/120 cadence, readiness heartbeats keep the watchdog quiet, cancel returns promptly with every task aborted and every node given a verdict, cancel during readiness never reaches prune or finalize, a hung checkpoint holds nothing, a hung stamp and a hung prune delete are bounded and reported, admission refills a freed slot at once, peak concurrency equals the cap, halt-on-first-failure finishes in-flight nodes and cancels the rest, a panicking task is fatal, gated applies complete only when released, an immutable conflict on a pre-authorized orphan recreates and is not pruned again, a rerun Job with a live object is recreated and without one is applied, a skipped rerun Job is recreated when its live object failed and left alone (and stamped) when it succeeded, a recreate that reports the object still present fails the node with that message, and a `proptest` over random DAGs with random per-node outcomes (ok, slow, fail, hang, readiness fails, readiness hangs) checks every node reaches exactly one terminal verdict, in dependency order (by log position), with counts a pure function of the case that add up to the plan. All under `#[tokio::test(start_paused = true)]` wrapped in a one-hour virtual timeout, so a parked engine fails at once
- `ops/` — **the engine's one seam to the cluster** (doc 134 §2.5). `ClusterOps` (`async_trait`, `Arc<dyn ClusterOps>`) is every apiserver call and every other piece of I/O `run_deploy` performs: per node `hydrate`, `apply`, `get_live` (the live object or `None`, a read even under dry run), `recreate_in_place`, `wait_ready`; per run `begin`, `rediscover`, `checkpoint`, `record_activation_on_skipped`, `delete`, `finalize`. The engine never sees an `ApiResource`. `ops/kube.rs::KubeOps` is the real one: holds the `Client`, the shared discovery cache (`DiscoveryCache = Arc<RwLock<Vec<(ApiResource, Scope)>>>`, refreshes MERGE via `fetch::merge_discovery` because the aggregated discovery doc churns after CRD writes and can transiently omit unrelated groups), kind resolution with refresh-on-miss (`refresh_until_found`: up to five refreshes with backoff, under 4 s of waiting; each a targeted `fetch::discover_group` for the manifest's group, falling back to a full walk when the group fetch fails; `get_live` has no group and always walks in full; the full walk here is `fetch::discover_resources_once`, one pass that leaves out a group version answering 404, so an unrelated group does not add `DISCOVERY_SETTLE` to each attempt), the Activation identity (`KubeOpsConfig { cluster_name, activation_name, activation_identity_hash, force_conflicts, dry_run }`), the live Activation set read once in `begin`, `sops` on `spawn_blocking`, and 30s bounds on checkpoint and finalize. A checkpoint that 404s is not a failure: the Activation CR is a node of the plan and lands in the last wave, so every checkpoint on a cluster's first deploy precedes it. `recreate_in_place` treats a 404 on the delete as success (the object was already gone, which is what was wanted), polls up to 30 s for the object to vanish, and if it is still there afterwards returns "still exists 30s after delete (stuck finalizer?); not re-applied" instead of an apply that would fail with the same 422 and say nothing about why; under dry run it sends the delete with `dryRun=All`, skips the poll, and still runs the dry-run apply so schema, admission, RBAC and field conflicts are checked; only the immutable-field 422 that the real delete would have avoided is mapped to `Created`, which is what the real path produces. `get_live` refreshes discovery on a kind miss, as `apply` does. `ops/scripted.rs::ScriptedOps` (`cfg(test)` or feature `test-util`) is the fake: every call is a `Behaviour` (`Now`, `After(duration)`, `Gate(latch)`, `Hang`, `Panic`), readiness can `Heartbeat` to model a slow healthy rollout, `NodeScript::live` scripts what `get_live` answers and `NodeScript::recreate` what `recreate_in_place` does, and it records a call log with virtual timestamps plus the peak number of concurrent applies. Nothing in it completes unless the script says so; a fake that answers on first poll cannot show a parked future. `begin` now CREATES the Activation record and marks it Deploying rather than waiting for it to come round as the plan's last node, so a run that stops part way leaves a record of what it was attempting; on a cluster's first deploy that record's own CRD is not served yet, so the create is deferred to `rediscover` (the CRD barrier), the earliest point it can succeed. `abort(reason)` marks the record `Failed` and is called from every early return in `run_deploy` below `begin` (cancel, halt-on-error, discovery failure, task panic); exactly one of `abort` and `finalize` happens per run. `delete` treats 404 as success, which matters once a failed closure is folded in: much of it was never created, and pruning something already gone must not count as a failure and land the new record Degraded. `KubeOpsConfig` gained `activation_manifest`, `consumed_failed` and `mark_failed_on_abort` (false for the operator, whose model is resume-on-requeue) Under dry run `KubeOps` records each object's answer in a `preview::Journal` (see "kix plan" above): `apply` resolves kinds from the cache without refreshing and `rediscover` is a no-op.
- `preview.rs` — what a dry-run deploy's apiserver said per object: `DryRunAnswer`, `DryRunOutcome` (`Applied` with the `ApplyPreview`, `Recreated`, `Refused`, `Pruned`), and `Refusal`, classified from the error status by `Refusal::of_status` (`conflict_owners` reads the managers and fields of a 409, keeping list keys with commas whole)
- `watchdog.rs` — **progress watchdog** (kixpkgs#62, doc 134 §2.6). `Progress` is the shared record: last activity of any kind, and per in-flight node its `Phase` (hydrate, apply, readiness, plus `discovery` for the CRD barrier's refresh, tracked under the synthetic node `api-discovery` so a hung refresh is reported and aborted like a hung node) and when it began; readiness status callbacks count as activity, so a ten-minute StatefulSet rollout that reports every 2s is not a stall. `assess(policy, idle, in_flight, last_warned)` is the pure policy (quiet / warn / abort), unit-tested alone. `run` is the task: its own `interval` (`MissedTickBehavior::Delay`, so no catch-up ticks after the stall it is watching for), emits `DeployEvent::Stalled { idle, in_flight, aborting }` at `warn_after` (default 30s) and every `warn_after` after, and at `abort_after` (default 600s, `KIX_STALL_TIMEOUT` seconds, `0` never) cancels the run through the token with the reason. `describe()` renders the one line every observer prints: `no progress for 31s: waiting on Deployment/a@default (apply, 31s), ...`, longest-waiting first, capped at five
- `cancel.rs` — `CancelToken`: `cancel()`, `cancel_with_reason()`, `is_cancelled()`, `reason()`, and awaitable `cancelled()` (backed by `tokio_util::sync::CancellationToken`) so the engine's supervisor can select on it while every node is in flight
- `readiness.rs` — `expectations()` reads `kix.run/expects` (`apiVersion|Kind|name` entries) and `wait_for_expectations()` polls each in the manifest's namespace (or at cluster scope) before `KubeOps::apply` patches; an object that never appears is `ApplyError::ExpectationUnmet`, naming the expectation and the reason. An import marker's target is looked up at the scope discovery reports for its kind (`kube::discovery::oneshot::pinned_kind`), so a cluster-scoped import (StorageClass, ClusterIssuer) is found; a kind discovery cannot see yet falls back to the marker's namespace. `wait_for_ready()` polls per-kind conditions (Deployment replicas, CRD Established, Job succeeded, etc.). A DaemonSet whose node selector matches no node (`desiredNumberScheduled: 0` with the generation observed) is complete, as `kubectl rollout status` has it. An `OnDelete` DaemonSet is ready once its ready pods match the desired count; its updated count is not waited for, because the controller replaces a pod only when someone deletes it. `daemonset_pending_restart()` returns how many pods still run the previous template, and `wait_for_ready()` then returns `ReadinessResult::ReadyPendingRestart { stale, message }`. The scheduler reports it as `Verdict::Ready` with `NodeDetail::PendingRestart { stale, message }` (a rerun or recreate outcome takes precedence). The message is generic: "the DaemonSet replaces a pod with the current template only when the pod is deleted". The pretty renderer prints `<label> ready, <n> pods pending manual restart (OnDelete): <message>`, the line log the same after `<label>>`, and the JSON log `{"pending_restart": {"stale": n, "message": ...}}`. The deploy's exit status is unchanged. How and when to delete the pods is the package's to document (mayastor's how-to restarts io-engine one node at a time after volume rebuilds finish). A terminal failure comes back as `ReadinessResult::Failed { message, output }`: on a Job-level hit (`backoffLimit` exceeded or a `Failed` condition) `scan_terminal` lists the Job's pods by the live object's `spec.selector` (the controller-uid selector) and `termination_output` collects each container's `state.terminated.message` (or `lastState`), which the kubelet fills from the log tail when the pod runs with `terminationMessagePolicy: FallbackToLogsOnError`. That is how a probe's `FAIL` lines reach the deploy output without a log API call: the last 20 lines (`TERMINATION_OUTPUT_LINES`), prefixed by container name only when several wrote something, with one leading line saying how many earlier lines were dropped. The scheduler carries them on `NodeDetail::ReadinessFailed { output, .. }`; the pretty renderer prints them dim under the failure line, the line log as `<label>>   | <line>`, the JSON log under `readiness_failed.output`, and the operator appends them to the Warning Event's note. `wait_for_import_target()` handles PackageInstance import markers (`kix.run/mode: import`): parses `kix.run/import-kind/apiversion/name` annotations and polls the described resource. Scope is determined by kind — `CustomResourceDefinition` is cluster-scoped (and waits for `Established=True`), everything else is namespaced and queried in the marker's own `metadata.namespace` (no `kix.run/import-namespace` annotation: imports always describe a resource in the marker's own namespace). A CRD ref marker (an import marker with `kix.run/crd-kind`, from `scope.mkCRDRef` or `kix.mkImport { crds }`) gives its target the versions it declares in `kix.run/crd-served-versions`; once the CRD is Established, a declared version missing from `spec.versions` or not `served` ends the wait with `ImportMismatch`. The library stamps that annotation on every CRD ref marker, so `import_target_from_manifest` returns `Err(MalformedMarker)` for one that lists no versions (it never falls back to `kix.run/crd-version`, which is only the default version), and `DeployPlan::from_graph_and_changes` passes the error up: `kix deploy`, `kix rollback` and the operator refuse the build before applying anything. Libraries before 693d550d (2026-10-02) did not stamp it, so a rollback to such a build, or the operator on an Activation naming one, fails with a message to deploy a fresh build. A CRD import without `crd-kind` (`kix.mkImport { kind = "CustomResourceDefinition"; }`) is waited for with no version check. `Secret` imports with a `kix.run/import-secret-keys` annotation also verify every declared key is present in `data` before the marker is considered ready — missing keys produce `ReadinessResult::ImportMismatch { missing_keys, message }`, which `reconcile.rs` surfaces as `ReadinessFailed { missing_keys, .. }` so observers can render the exact missing keys as a structured line. Custom readiness conventions are DECLARED, not hardcoded: a CRD-owning package sets `readiness = { path; equals; }` or `readiness = { condition = { type; status; }; }` on its CRD builder, kix stamps it on every CR built through the typed chain as the `kix.run/readiness` annotation (JSON `{"path": "/status/...", "equals": "..."}` or `{"condition": {"type": "...", "status": "..."}}`), and `declared_readiness`/`check_readiness` evaluate it before any kind-based rule. The path form compares the value at the path with the string `equals`; a JSON boolean or number compares by its JSON text (`true` matches `"true"`, `3` matches `"3"`, and a float the operator writes as `1.0` matches only `"1.0"`), which is how CloudNativePG's Database and DatabaseRole gate on `status.applied`, and VictoriaMetrics operand CRs gate on `status.updateStatus == "operational"`; the `notEquals` path form is ready while the value is absent or anything else, which is how VictoriaMetrics configuration CRs (VMServiceScrape, VMRule, ...) settle when no VMAgent or VMAlert selects them and still fail on `failed`; the condition form is how StackGres clusters gate on `Bootstrapped=True`, Gateway API kinds on `Accepted`/`Programmed` and Cilium policies on `Valid`. Neither form takes a status older than the spec: a path rule is unmet while `status.observedGeneration` is below `metadata.generation`, and a condition rule while the matched condition's own `observedGeneration` is, or `status.observedGeneration` when the condition carries none (`condition_observed_generation`, `generation_observed`); either value absent imposes no wait, so an operator that reports neither (CloudNativePG's Cluster) can read as ready from its previous status right after a spec change. The not-ready message then ends `, observed generation <n> of <m>`. The `match` in `check_readiness` covers only kinds whose readiness Kubernetes itself defines; an operator's vocabulary never goes there. Malformed annotations fall through to kind rules (version skew ≠ unhealthy) — but note the un-annotated half of that skew: manifests built by a pre-declaration library have no annotation, and a status-less CR then hits check_generic_ready's ready-on-empty, racing its operator instead of timing out; rebuild such manifests rather than relying on the fallthrough. A generic-CR readiness timeout lists the condition vocabulary it observed and points at the declaration mechanism.
- `activation.rs` — Activation CR lifecycle: phase-based model (Queued → Deploying → Active → Superseded). `find_active()`, `find_queued()`, `list_superseded_activations()`, `begin_deploy()`, `record_waves()`, `finalize_deploy()`, `resume_point()`, `supersede_activation()`, `read_phase()`. Full phase model is `Queued → Deploying → Active|Degraded|Failed → Superseded`. `PHASE_FAILED` is terminal and deliberately NOT matched by `find_active`: a half-applied closure is not the cluster's current state, and diffing against it would read every object only the Active closure has as an orphan, which `--prune` would then delete. `find_failed()` and `find_deploying()` read the other two phases. `pick_current()` makes `find_active` deterministic when a cluster holds two current records (newest `deployed-at`, ties on name) instead of taking whichever the apiserver listed first. `phase_on_begin()` leaves an Active record alone, so re-deploying the closure that is already current cannot demote it and then die leaving no current record at all; `phase_on_abort()` only fails a record this run marked Deploying. `fail_deploy()` writes the phase and `status.failure.{reason,at}`. `finalize_deploy()` takes `consumed_failed` and supersedes those records, skipping the one being finalized so a retry of a failed closure still lands Active. `deployed_at()` falls back to `status.failure.at` then `creationTimestamp`, so a record superseded out of `Failed` is not retired as `UnknownAge` on the first `kix gc`
- `client.rs` — **the apiserver transport policy**, applied once so every call site inherits it. `build_client(config, policy)` wraps kube's tower stack in `ResilienceLayer`: retries (429 for every method with `Retry-After` honoured; 5xx and connection loss for idempotent methods only, so a POST is retried only when the connection never opened), exponential backoff with equal jitter under a total budget, and a per-attempt deadline for non-watch requests. Watches bypass the deadline. It deliberately holds **no** in-flight cap: the first version did, and a permit held inside a future that the scheduler had parked (its `FuturesUnordered` is not polled while it awaits CRD rediscovery inline) deadlocked `kix deploy` with every thread idle, and no deadline can fire in a future nobody polls. Burst control lives in the sweep instead. When the budget is spent the last response or error is returned unchanged, so callers see the same `kube::Error` they always did. `decide()` is the pure policy, unit-tested against a scripted fake service. Knobs: `ResiliencePolicy` (defaults sized to outlast a webhook pod restart) with env overrides `KIX_RETRY_ATTEMPTS`, `KIX_REQUEST_TIMEOUT`, `KIX_CONNECT_TIMEOUT`. A request carrying the `FirstContact` extension (`mark_first_contact`) gets one attempt and no deadline of its own: that is the probe in `fetch::make_client`. Persistence is what carries a deploy through an apiserver restart, but a cluster that is not there will not become there, and seven attempts over a 60s budget only delay the error (a refused port: ~18s with the retries, 0.1s without). It is an extension on the real client's request rather than a second client from a second policy, because a second client means a second connection pool: the probe would pay its own TLS handshake and throw the connection away, measured at ~0.6s against stage1 and stage2 on every cluster command. `decide()` is left untouched by this; `run()` short-circuits, so the pure policy does not grow a special case. The old per-patch retry loop in `apply.rs` is gone; it was one file's private copy of this
- `errors.rs` — `FailureClass` + `classify(&kube::Error)` / `classify_status(code)`: the one table that says what an apiserver failure means (rate-limited, unavailable, server error, transport, timeout, unauthorized, forbidden, not found, conflict, invalid). Every site that used to compare `resp.code` by hand (apply conflicts, the sweep's 403, readiness 404) reads this instead, and the transport layer uses the same table to pick what to retry

## Key patterns

**Identity-hash** is the core primitive. First 32 chars of a Nix store path. Same hash = identical content + deps. Change detection is a hash set comparison — no deep diff needed.

**StoreGraph** is the in-memory DAG built from `kix-packages.json` + Nix store references. Everything operates on StoreGraph pairs (old vs new): change detection, plan display, stamping, GC.

**Keyed-list diff.** The diff engine matches K8s arrays by natural keys (containers by `name`, ports by `name`, env by `name`, volumeMounts by `mountPath`) not by position. Without this, reordering items produces false diffs.

**Waves** via Kahn's algorithm on the `kix.run/depends-on` DAG. Within a wave, resources are independent. Lexicographic sort within waves for determinism.

**Annotations** stamped at build time: `kix.run/identity-hash`, `kix.run/package`, `kix.run/depends-on`, `kix.run/activations`. Everything downstream reads these, never raw store paths.

**Backend abstraction.** `NixBackend` trait — `CliNixBackend` (production, shells out to `nix` CLI) and `MockNixBackend` (tests, no Nix needed). An experimental `FfiNixBackend` using direct C FFI exists behind the `nix-ffi` feature but is not currently used.

**Operator mode** (`--operator` flag on deploy/rollback/gc). Instead of calling the reconcile engine directly, the CLI creates or patches Activation CRs and watches their status. The operator does the actual wave-by-wave apply. Build + plan display still happens locally (needs Nix). Three flows:
- `deploy --operator`: build locally → show plan → apply Activation CR with source path → watch status.waves
- `rollback --operator`: find superseded activation → patch Activation CR source path to target → watch progress
- `gc --operator`: delete the Superseded Activation records the retention policy retires → the operator removes its finalizer and deletes no resources (it tears resources down only for an Active, Deploying or Degraded record, and keeps Namespaces and CRDs even then, plus any object another Kix cluster's current build contains, through `PruneGuard`)

**Operator K8s Events** (doc 99 Stage H). The operator composes two `DeployObserver`s over the same `DeployEvent` stream: `OperatorObserver` emits structured tracing logs, and `K8sEventObserver` publishes K8s Events on the Activation CR via `kube::runtime::events::Recorder` so `kubectl describe activation` and downstream log aggregators surface the deploy timeline. Events are fire-and-forget (`tokio::spawn` per publish, failures logged at `debug` and dropped) — they are telemetry, never part of deploy correctness. Suppresses Pending and most Running verdicts to stay under the cluster Event rate budget; emits Normal/Warning Events for plan, terminal verdicts, prune, drift, recreate, hydration, and finalization. See `cli/kix-operator/src/k8s_events.rs`.

**Operator reconcile loop prevention.** The operator uses a stream-level generation filter to drop status-only updates. All status writes go through the status subresource (`patch_status`), which doesn't bump `metadata.generation`. The controller dispatches by phase: Queued CRs trigger activation switchover + deploy, Active CRs trigger drift detection, Superseded CRs are no-ops.

**Unified reconcile.** Both new deployments and drift correction use the same path: load desired manifests, fetch the live kix-managed resources of the record's Kix cluster (its `kix.run/cluster` label, else `spec.cluster`, else no cluster: an empty name that owns no record; `SweepScope::Cluster`), compare identity-hashes and drop orphans another Kix cluster's current build still contains (`controller::live_changes`), wave-plan, and apply with `PrunePolicy::Delete`. No "old manifests" concept — the cluster IS the old state, scoped to one Kix cluster.

**Error boundary.** `thiserror` in libraries, `miette` in binary.
