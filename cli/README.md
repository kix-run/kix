# Kix CLI

Rust CLI for kixpkgs. Evaluates Nix-defined Kubernetes clusters, diffs against live state, and deploys wave-by-wave with SSA. Users run `kix`, never raw `nix`.

## Workspace

```
kix/             library — eval, manifest handling, cluster operations
kix-cli/         binary — clap CLI, command dispatch, plan display
kix-operator/    binary — kube-rs controller watching Activation CRs
```

Both binaries depend on `kix`. No other cross-deps.

## Deploy pipeline

```
nix build → StoreGraph → stamp annotations
  → fetch old activation from cluster (or --current-activation for local cache)
    (store path GC'd? → reconstruct old manifests from live kix-managed resources)
  → detect_changes (identity-hash set diff, local only)
  → DeployPlan::from_graph_and_changes (no wave layer)
  → show package-grouped plan → confirm
  → scheduler::run_deploy (DAG-streaming, SSA + readiness per node)
  → prune orphans (named in the plan and in `DeployEvent::PruneStart { resources, delete }`; warn-only unless `--prune`) → finalize activation
```

Doc 99 ("graph streaming") replaced the wave-barrier executor with the
DAG-streaming `scheduler`. Each node becomes eligible the moment its direct
predecessors have emitted `Verdict::Ready`, independent subtrees stream
through in parallel, and the inline TUI (`--tui`) draws a live tree grouped
by kix package. `rollback`, `gc`, and the operator all run on the same
scheduler + `DeployObserver` stream; the old wave-barrier `reconcile.rs` and
`waves.rs` modules have been deleted.

`--dry-run` rides this same pipeline — there is no parallel render path.
`SchedulerConfig.dry_run` is plumbed down to `apply_resource` (SSA
`dryRun=All`) and every `DeleteParams`, so per-resource verbs
(`created`/`configured`) come from the apiserver's response and admission
webhook rejections, RBAC failures, and 409 conflicts surface up-front,
matching `kubectl --dry-run=server`. The offline combination
`--current-activation --dry-run` has no client to route through;
`render_offline_dry_run` synthesises the same labels locally from the
old-activation identity diff and prints through the same `apply_symbol`
mapping.

## Where things live

### kix-cli (`kix-cli/src/`)

- `cli.rs` — all clap command/flag definitions (`DeployArgs`, `GcArgs`, `DiffArgs`, `HealthArgs`, `RollbackArgs`, `GlobalArgs`, enums). `GlobalArgs` includes `--no-cache` to bypass the SQLite eval cache (forces fresh Nix evaluation every time) and `--override-input <NAME> <URL>` — a repeatable global flag mirroring `nix --override-input`. Each `(name, url)` pair is forwarded verbatim to every `nix` subprocess kix spawns (`flake show`, `eval`, `build`), so callers can repoint flake inputs without mutating `flake.nix`/`flake.lock`. The docs captures pipeline relies on this to pin kix-examples' `kixpkgs` input at a known store path during sandbox-free regeneration. Paired via `GlobalArgs::input_overrides()` into `Vec<(String, String)>` and applied through `CliNixBackend::apply_overrides(&mut Command)` plus an `input_overrides` slice on `build_cluster_activation_with_status`
- `plan.rs` — shared plan renderer for deploy + gc + diff. `PackageDiff`/`PackageChangeDiff` types, `diff_graphs()` for package-level comparison, `print_package_plan()` for namespace-grouped changes-only stdout display (deploy/gc/rollback modals), `render_package_diff_json()`/`render_package_diff_markdown()` as canonical structured producers consumed by both `kix diff --output {json,markdown}` and (future) the CI PR-comment GitHub Action. All formats share the same PackageDiff input so they stay in sync
- `output.rs` — color helpers (`green`/`red`/`yellow`/`dim`/`bold` → `Cow<str>`), `is_interactive()`, `CommandResponse` trait
- `commands/deploy.rs` — deploy pipeline: resolves old activation (if its store path is gone — GC'd or built elsewhere — `reconstruct_old_from_live` rebuilds the old manifest set from live kix-managed resources via `fieldsv1::merge_typed_metadata`, excluding Activation CRs, so change detection and prune ordering still work; `synthesize_old_graph` then rebuilds a package-level StoreGraph from the stamped `kix.dev/package` annotations + live PackageInstance versions so the plan shows changed/unchanged packages, not everything "added"), displays plan, confirms, builds a `DeployPlan` and delegates to `kix::cluster::scheduler::run_deploy()` (doc 99). Observer selection: `--tui` (+ interactive stdout) uses `graph_stream::GraphStreamDriver` for the inline tree dashboard; otherwise a line-oriented `StreamCliObserver` prints one line per terminal `Verdict` (doc 99 §7 "nix-build-L" idiom). `--reconcile` forces re-apply of all resources even when activation identity matches (heals drift). `--dry-run` goes through the same `run_deploy()` with `SchedulerConfig.dry_run = true` — verbs come from the apiserver's SSA dry-run response, not a CLI guess; with `--current-activation` (no cluster connection) it instead takes `render_offline_dry_run`, which classifies Created/Configured locally via `classify_offline_apply` and renders through the same `apply_symbol` mapping and summary line. `--operator` delegates to the kix-operator instead. `--force-conflicts` opts in to SSA force (default off — conflicts surface as `ApplyError::Conflict` with the conflicting field paths and current owner; use this when migrating a resource away from kubectl/helm for the first time). Import markers (PackageInstance with `kix.dev/mode: import`) are applied like any other resource — their readiness check in `readiness::wait_for_import_target` polls the cluster for the described kind/name, so imports whose installer is in the same deploy are naturally wave-ordered after it
- `commands/deploy_log.rs` — non-interactive deploy observers for `--log-format={line,json}` (doc 99 §7, Stage D). `LineObserver` emits exactly two events per resource: one on `Verdict::Running + NodeDetail::Applied` ("created"/"configured") and one on terminal `Verdict::Ready` ("ready"). Intermediate `ReadinessProgress` events are suppressed unconditionally — the log is a resource-granular activity stream, not a live dashboard. `JsonObserver` emits NDJSON with the same suppression rule; every object carries `type` + `elapsed_ms`. `pretty` (the default) is the colored `StreamCliObserver` on TTY stdout and automatically downgrades to `line` on non-TTY. `-v` only expands Unchanged/Skip/Cancelled lines — it never turns on readiness-progress chatter
- `commands/graph_stream.rs` — inline graph-streaming dashboard (doc 99). `GraphStreamObserver` implements `DeployObserver` as a cheap mpsc sender; a dedicated OS thread owns a ratatui `Terminal` with an `Inline` viewport (default 3/4 of the screen, override with `--fold-height`), receives `DeployEvent`s + periodic ticks, updates `ViewState`, and redraws the tree. A dimmed `─` rule pinned to the top row of the inline viewport separates scrollback history (above) from the live dashboard (below). Nom-style viewport: every Ready resource is flushed to scrollback the tick it completes — the live viewport only ever contains Running / Failed / AwaitingInput / Drift rows plus a collapsed `N packages pending` summary for work that hasn't started. When all members of a package are flushed, a single package-summary line is emitted to scrollback so history reads as a progressive collapse. Failure frame pins a `⚠ failures` block at the top. Active-resource rows carry the latest readiness-progress message (`⏵ Deployment/foo  ⏱ 12s  2/3 ready`) from `NodeDetail::ReadinessProgress`. On spawn the driver redirects the tracing subscriber to `/tmp/kix-tui-<pid>.log` via `crate::trace_sink` — without that, `-v` under `--tui` would tear the ratatui backing buffer with stderr writes. `Ctrl-C` / `Esc` in the viewport cancels the underlying `CancelToken`
- `trace_sink.rs` — runtime-switchable tracing writer. Default target is stderr; `GraphStreamDriver` flips it to a per-PID log file for the lifetime of the TUI session via `redirect_to_file()` / `restore_stderr()`. The single MakeWriter entry point `trace_sink::make_writer` is wired into `tracing_subscriber::fmt` in `main.rs`
- `commands/diff.rs` — three modes: build-to-build (two StoreGraphs), vs live cluster, vs snapshot directory. Output formats: `text` (default), `json`, `yaml`, `markdown` (GitHub PR-comment format, consumed by CI). JSON/markdown emit via the shared `plan::render_package_diff_*` producers with diff-specific extras (legacy resource listing, stateful migration pairs) appended
- `commands/gc.rs` — soft (DAG diff old vs new) and hard (full cluster scan) garbage collection. Hard mode deletes only stamped resources; label-only hits without `kix.dev/identity-hash` are listed as "unstamped" and deleted only with `--include-unstamped` (kix never applied them: inherited labels, kubectl-applied renders). `--operator` deletes retired Activation CRs and lets the operator finalizer handle resource cleanup. **Record retention** in every mode (`activation::RetentionPolicy`, `retire_plan`, pure and unit-tested): always keep the `--keep` newest Superseded Activation records (default 10) whatever their age, never more than `--keep-max` (default 50), and beyond the floor retire anything older than `--keep-for` (default 30d; `0` off). Newest first by parsed `kix.dev/deployed-at`; a record with no usable timestamp sorts oldest; ties break on name. Each retired record is deleted with `Preconditions { uid, resourceVersion }` (`delete_activation_if_unchanged`), so a record that changed since the listing (a rollback made it Active again) is refused with 409 rather than deleted. The plan connects to the cluster before the Nix build (fail fast, one connection reused for the deletes). Soft mode never touches records otherwise; the deploy record is never soft garbage even though its store hash changes every build (`soft_garbage`). Why retention matters: `kix.dev/activations` on every managed resource keeps one hash per deploy whose record still exists, and Kubernetes caps all annotations on an object at 256 KiB, so unbounded records would eventually make every SSA fail with 422; the next deploy after a gc drops the retired hashes (`merge_activation_set`). A listing failure is an error, never an empty plan
- `commands/rollback.rs` — rollback to most recent Superseded activation. No nix build — resolves old store path and re-applies via reconcile engine. `--operator` patches the Activation CR's source path and lets the operator reconcile. `--list` is a read-only history view: enumerates Superseded activations with name, identity-hash, timestamp, source store path (`built_via`), `previousActivation` link, and local-store availability, then exits without prompting — supports `--output json|yaml` for scripting. Interactive selector and `--list` share `print_superseded_entries()` so both views show the same columns. Before applying, the confirmation modal renders the package-grouped diff via `plan::print_package_plan` against the current Active CR so the operator sees exactly what flips. `v2_discussions/84_m0_m1_implementation_plan.md` §2. History is bounded by `kix gc` retention (at least 10 newest, at most 50, nothing older than 30d beyond the floor, by default), so `--list` is finite and a `previous:` link may name a retired record
- `commands/logs.rs`, `commands/pf.rs` — thin wrappers that build the cluster, resolve `<package>` to its primary workload (Deployment / StatefulSet / DaemonSet) via `commands/workload.rs::resolve_package_workload`, extract `spec.selector.matchLabels` as a `kubectl -l` selector, then `exec` into `kubectl logs`/`kubectl port-forward`. Deliberately shelling out — the point is "one tool" in the demo, not re-implementing log streaming or port proxying. Per `v2_discussions/84_m0_m1_implementation_plan.md` §4. `--context` is forwarded; logs support `-f/--tail/--since/-c/-p`; pf accepts multiple port specs and `--address`. Zero library changes.
- `commands/workload.rs` — shared helper for logs/pf: builds `StoreGraph`, finds a package by instance name (exact match, ambiguity error with qualified suggestions, or `namespace/name` form), walks its `resource_paths` and returns a `WorkloadTarget { kind, namespace, name, selector }` using the first Deployment → StatefulSet → DaemonSet it finds.
- `commands/export.rs` — dump built cluster manifests as plain Kubernetes YAML for exit-strategy handoff or audit bundles. Walks the freshly-built `StoreGraph` (same mechanic as `diff.rs` build-to-build mode), writes each manifest as `<out>/<namespace>/<Kind>-<name>.yaml` via `manifest::serialize::manifests_to_yaml`. Two modes via `--for`: `exit` (default) strips `kix.dev/*` annotations using `cluster::normalize::strip_kix_annotations` and drops kix-internal CRs (Activation, PackageInstance) — the result is neutral YAML a downstream consumer can `kubectl apply`. `audit` preserves stamped provenance annotations and kix-internal CRs for compliance evidence (the M3 compliance-evidence precursor, per `v2_discussions/84_m0_m1_implementation_plan.md` §1)
- `commands/operator.rs` — shared helpers for operator mode: `connect_and_verify()`, `apply_activation()`, `watch_activation_progress()`, `wait_for_deletion()`
- `commands/health.rs` — cluster integrity walk: indexes live resources by `kix.dev/identity-hash`, checks every `kix.dev/depends-on` edge resolves within the active activation's reachable set, reports Healthy/External/Reaped/Missing/AtRisk. **Graph-presence only — it does not compare field content**; that is `kix drift`'s job. Import-aware: resources with `kix.dev/mode: import` annotation show as `external` status instead of healthy/degraded. Reaped-aware: an absent dependency whose seal (read back from the local nix store by identity hash) declares its own deletion — `kix.dev/hook-delete-policy`/`helm.sh/hook-delete-policy` containing `hook-succeeded`, or a Job's `spec.ttlSecondsAfterFinished` — is a hook that ran and cleaned itself up, so it counts as satisfied and lands under `(completed hooks)` rather than dragging its whole downstream chain to `at risk`
- `commands/drift.rs` — `kix drift`: runtime content drift check via applied-hash stamps (doc 122). Deliberately takes NO cluster/flake argument — it compares live objects against the `kix.dev/applied-hash` annotations written at deploy time, so it runs from any kubeconfig-only context (no repo, no nix build). Dispatched in `main.rs` BEFORE `CommandContext` is created (like `completions`) so no Nix backend is ever initialized. Per-resource verdict lines; drifted resources list attributed foreign owners ("spec.template…image taken by kubectl-patch at <ts>"); `--output json` for scripting. Exit 0 = all in-sync/unstamped, 1 = drift found. Integration-tested in `tests/drift-integration.sh` (kind cluster, includes the `kubectl scale` /scale-subresource case)
- `commands/images.rs` — list all container images in a cluster activation. Extracts image refs from pod specs across Deployments, StatefulSets, DaemonSets, Jobs, CronJobs, and Pods (including initContainers and ephemeralContainers). Default text output is one image per line (suitable for `xargs docker pull`). `--sources` adds per-image resource provenance. `--output json` emits structured `[{image, sources: [{kind, namespace, name, container}]}]` for scripting. Primary use case: airgap preloading (`kix images <cluster> | xargs -P4 -I{} docker pull {}`)
- `commands/compliance/` — compliance exports for auditors, CI, and compliance platforms (implements `v2_discussions/61_compliance_exports.md`). Three subcommands, all built on the same `shared::build_and_load` helper that runs `nix build` + loads the StoreGraph:
  - `sbom` emits a CycloneDX 1.6 SBOM to stdout. Walks the StoreGraph to produce a `platform` root component for the cluster, one `application` component per package (`pkg:kix/<ns>/<name>@<version>` purl), one `container` component per unique image (deduped, with optional SHA-256 digest from `@sha256:` refs, `pkg:docker/...?repository_url=<host>` purl), and one `library` component per flake input read from `flake.lock` (`pkg:nix/<name>@<rev>`). The dependency graph is derived from `StoreGraph::cross_deps` plus per-package image edges.
  - `attest` emits an unsigned in-toto Statement with a SLSA v1 provenance predicate. Subject is the activation identity hash (`nixStoreHash` digest type). `externalParameters` include the flake ref and a BLAKE3 digest of the on-disk `flake.lock`; `resolvedDependencies` carry the git HEAD and every flake input's rev/narHash. `--builder-id` and `--invocation-id` override the `runDetails` block so CI can stamp its workflow URL. Signing is deferred to doc 54 by design.
  - `audit` bundles `scorecard-results.sarif`, `sbom.json`, `provenance.json`, `assessment-results.json`, and `audit-report.md` under `--out` (default `./compliance`). The OSCAL assessment maps findings to framework controls via static Rust tables (see `audit.rs` — SOC 2, ISO 27001, DORA, NIS2). A control is marked `not-satisfied` only if an error-level scorecard finding exists whose rule ID starts with one of the control's declared `required_rules` prefixes. The markdown summary is a self-contained PR-comment-ready report. SARIF generation duplicates the shape used by `kix check --sarif`.

#### eval (`kix/src/eval/`)

- `store_graph.rs` — **central data structure.** `StoreGraph` holds the full in-memory DAG: `PackageNode` (instance_name, namespace, version, resource_paths, cross_deps), `ResourceNode` (store_path, manifest). Built from result dir's `kix-packages.json` + `nix-store -q --graph`
- `store.rs` — activation cache at `~/.cache/kix/activations/`. `save/load_activation_path()` for local cache, `resolve_activation_by_hash()` to go from cluster identity-hash → local result dir. `save_activation_path` also registers a Nix GC root (`<cluster>.root` via `nix-store --add-root`) pinning the deployed activation — builds run `--no-link`, so without it `nix-collect-garbage` deletes the store path the next deploy diffs against
- `evaluator.rs` — `KixEvaluator` wrapping a `NixBackend` trait with SQLite caching
- `cli_backend.rs` — **production backend.** `CliNixBackend` shells out to `nix` CLI commands: `nix flake show --json` for listing clusters, `nix eval --json` for listing packages/cluster info, `nix build` + StoreGraph for evaluation. Benefits from Nix's built-in eval cache.
- `build.rs` — `build_cluster_activation_with_status()` shells out to `nix build .#cluster-{name}-activation`
- `cache.rs` — SQLite cache keyed by BLAKE3 of (flake path + lock + source fingerprint + attr)
- `ffi.rs` — experimental `FfiNixBackend` using `nix-bindings-*` FFI crates (gated behind `nix-ffi` feature, not currently used)
- `mock.rs` — `MockNixBackend` for tests without Nix

#### manifest (`kix/src/manifest/`)

- `types.rs` — `ResourceId` (kind/namespace/name), `CLUSTER_SCOPED` constant. Used everywhere
- `lifecycle.rs` — **the one classifier** for what a manifest is: `Lifecycle::{Desired, Marker, Record}` via `lifecycle_of(&Value)` / `lifecycle_of_live(&DynamicObject)`. Desired state is diffed, applied and pruned; a Marker (PackageInstance with `kix.dev/mode: import`) is applied and its target polled; a Record (the Activation) is applied once at the end of a deploy and only ever superseded, never pruned. `record_of()` finds the record in a set. Change detection (`apply.rs`) matches records like any other resource, so an unchanged build is still a `Skip` and the deploy short-circuits, but `Lifecycle::prunable()` keeps them out of the orphan set on both the store and live paths. Every former `kind == "Activation"` / `kix.dev/mode == import` check (stamp, deploy, rollback, gc, export, health, readiness, graph, the operator) reads this instead, and a unit test fails the build if a new comparison of the record kind appears anywhere else. Born from kixpkgs#59: the previous deploy's record, renamed by stamping on every deploy, reached change detection through the store-graph path and was reported as an orphan on every deploy (and `--prune` would have deleted it before finalize could supersede it)
- `stamp.rs` — `stamp_annotations()` writes `kix.dev/*` annotations onto StoreGraph manifests in-place; renames the Record to `<cluster>-<hash12>` so each deploy creates a distinct CR
- `diff/engine.rs` — `structural_diff(a, b)` → `Vec<Difference>` with JSON paths. Keyed-list-aware
- `diff/keyed_lists.rs` — defines which K8s arrays match by key (containers→name, ports→name, env→name, volumeMounts→mountPath, subjects→kind:name)
- `diff/display.rs` — `format_diffs()` renders differences as colored text
- `serialize.rs` — YAML/JSON output, `load_manifests_from_dir()` for snapshot loading

#### cluster (`kix/src/cluster/`)

- `apply.rs` — `detect_changes()` (identity-hash set diff → `ChangeAction::Apply/Skip/Orphan`; an old or live object without `kix.dev/identity-hash` is never an `Orphan` — kix only deletes what it stamped; a `Lifecycle::Record` on the old or live side is dropped before matching, so the previous deploy record can never be an orphan on any path, store-graph, live-reconstruction or operator), `detect_changes_live()` (compare desired manifests against live cluster resources by identity-hash), `apply_wave()` (SSA via `kube`, field manager `kix`). The SSA response echo is kept (not discarded): `apply_resource` computes the applied-content hash from it (`fieldsv1::applied_content_hash`) and writes `kix.dev/applied-hash` in the same post-SSA bookkeeping merge patch as `kix.dev/activations` (`update_bookkeeping_annotations`, no extra round trip). That patch also runs under field manager `kix` — leaving it unset records the write as manager `unknown` in managedFields and pollutes ownership-based drift attribution (doc 122). `merge_activation_set()` is the pure set operation behind `kix.dev/activations`: fold in the current activation, drop entries naming an Activation CR that no longer exists (`activation::live_activation_hashes`), always keep the activation being deployed (its own CR lands in the last wave), and return a sorted set so the caller can skip the write when nothing changed. Passing `live = None` disables pruning — keeping a dead reference is recoverable, dropping a live one is not. `record_activation_on_skipped()` is the entry point for resources the deploy did *not* apply; it touches `kix.dev/activations` only, never `kix.dev/applied-hash`
- `graph.rs` — `ResourceGraph` (petgraph DAG built from `kix.dev/depends-on` annotations). Import-aware: nodes with `kix.dev/mode: import` render as dashed/gray in dot output, `(import)` suffix in tree, `isImport` field in JSON
- `stream.rs` — graph-streaming vocabulary (doc 99): `Verdict`, `TransitionKind`, `NodeId`, `NodeDetail`, `NodeMeta`, `PlanNode`, `DeployEvent` (including `Stalled { idle, in_flight: Vec<InFlight { node, phase, since }>, aborting }` from the watchdog and `BestEffortFailed { what, message }` for checkpoint/stamp/finalize failures), `Phase`, `InFlight`, `DeployObserver`, `DeployResult`. The observer trait consumed by the CLI renderer, the non-interactive line/JSON observers, and the operator's tracing observer
- `scheduler.rs` — **deploy engine** (doc 99, reshaped by doc 134). `DeployPlan::from_graph_and_changes` builds the plan from a `ResourceGraph` + `detect_changes` output. `run_deploy(ops, plan, orphans, old_manifests, config, observer)` is the ready-queue scheduler: every node becomes eligible the moment its direct predecessors have emitted `Verdict::Ready`, concurrency bounded by `SchedulerConfig::concurrency` (default `CONCURRENCY=64`). **The engine task never awaits foreign I/O while nodes are in flight**: every node, every discovery refresh and every checkpoint is a task spawned into one `JoinSet`, and the supervisor's only awaits are that set, the cancel token and the watchdog. The first shape held node futures in a `FuturesUnordered` and awaited rediscovery inline, which parked every apply and hung a deploy for 35 minutes (kixpkgs#62). **CRD barrier**: a CRD-like node (kind `CustomResourceDefinition`, or an import marker for one) does not promote its dependents until one discovery refresh that started after it completes; several CRDs finishing together share one refresh; a refresh that fails stops the run with `DeployError::DiscoveryFailed { partial }` (a stale view is a partial view, the rule from #60). Failure policy halt-dependents / continue-siblings (default) or halt-on-first-failure under `OnErrorPolicy::Stop`. Cascade-cancels transitive dependents on failure. A spawned task that panics is `DeployError::Internal`, never a lost node. Cancel (caller or watchdog) is observed through `CancelToken::cancelled()` in the supervisor's `select!`; the reason travels on the token, so a watchdog abort reads "no progress for 600s: waiting on ..." rather than "cancelled". On cancel the supervisor aborts every task and keeps draining the `JoinSet`: a node that finished just before the cancel is still counted, an aborted one becomes `Cancelled`, and only then does the run return; a cancel that lands as the last node finishes is re-checked after the loop so nothing is pruned or finalized. Whatever stops a run (cancel, `OnErrorPolicy::Stop`, a failed refresh), every node without a verdict gets `Cancelled { External }` and counts in `cancelled`, so renderers never leave a row Pending under a `Stopped` footer and the counts add up to the plan. Every post-loop write is bounded too (begin, stamping, each prune delete, final checkpoint, finalize: 60s each), because the watchdog only watches nodes and the discovery refresh. `ops.dry_run()` must agree with `SchedulerConfig::dry_run` or the run stops before it starts. Immutable-field conflicts recover via `ClusterOps::recreate_in_place` when the rid is pre-authorized in the orphan set. Activation CR checkpointing batched every 16 terminal verdicts, one write in flight at most, running totals; the final checkpoint and finalize are awaited inline after the node phase under a 60s bound. Failures of best-effort writes (checkpoint, stamping unchanged resources, finalize) are `DeployEvent::BestEffortFailed`, rendered by every observer, not `tracing::warn` lines. `Skip` nodes short-circuit without a task, but their rids are collected and stamped with the current activation in one concurrent pass once every node is terminal (an unchanged resource still belongs to this activation). `SchedulerConfig.dry_run` makes the whole run non-mutating: SSA and deletes hit the apiserver with `dryRun=All`, readiness short-circuits, and every real write is gated off in `KubeOps`. Also owns `OnErrorPolicy`, `PrunePolicy`, re-exports `delete_propagation_for`. Tested without a cluster (`engine_tests`): the CRD barrier does not park running nodes, a failed refresh stops the run, a hung refresh is reported and aborted, a hung apply is reported then aborted on the 30/60/90/120 cadence, readiness heartbeats keep the watchdog quiet, cancel returns promptly with every task aborted and every node given a verdict, cancel during readiness never reaches prune or finalize, a hung checkpoint holds nothing, a hung stamp and a hung prune delete are bounded and reported, admission refills a freed slot at once, peak concurrency equals the cap, halt-on-first-failure finishes in-flight nodes and cancels the rest, a panicking task is fatal, gated applies complete only when released, an immutable conflict on a pre-authorized orphan recreates and is not pruned again, and a `proptest` over random DAGs with random per-node outcomes (ok, slow, fail, hang, readiness fails, readiness hangs) checks every node reaches exactly one terminal verdict, in dependency order (by log position), with counts a pure function of the case that add up to the plan. All under `#[tokio::test(start_paused = true)]` wrapped in a one-hour virtual timeout, so a parked engine fails at once
- `ops/` — **the engine's one seam to the cluster** (doc 134 §2.5). `ClusterOps` (`async_trait`, `Arc<dyn ClusterOps>`) is every apiserver call and every other piece of I/O `run_deploy` performs: per node `hydrate`, `apply`, `recreate_in_place`, `wait_ready`; per run `begin`, `rediscover`, `checkpoint`, `record_activation_on_skipped`, `delete`, `finalize`. The engine never sees an `ApiResource`. `ops/kube.rs::KubeOps` is the real one: holds the `Client`, the shared discovery cache (`DiscoveryCache = Arc<RwLock<Vec<(ApiResource, Scope)>>>`, refreshes MERGE via `fetch::merge_discovery` because the aggregated discovery doc churns after CRD writes and can transiently omit unrelated groups), kind resolution with refresh-on-miss (targeted `fetch::discover_group` then full), the Activation identity (`KubeOpsConfig { cluster_name, activation_name, activation_identity_hash, force_conflicts, dry_run }`), the live Activation set read once in `begin`, `sops` on `spawn_blocking`, and 30s bounds on checkpoint and finalize. A checkpoint that 404s is not a failure: the Activation CR is a node of the plan and lands in the last wave, so every checkpoint on a cluster's first deploy precedes it. `ops/scripted.rs::ScriptedOps` (`cfg(test)` or feature `test-util`) is the fake: every call is a `Behaviour` (`Now`, `After(duration)`, `Gate(latch)`, `Hang`, `Panic`), readiness can `Heartbeat` to model a slow healthy rollout, and it records a call log with virtual timestamps plus the peak number of concurrent applies. Nothing in it completes unless the script says so; a fake that answers on first poll cannot show a parked future
- `watchdog.rs` — **progress watchdog** (kixpkgs#62, doc 134 §2.6). `Progress` is the shared record: last activity of any kind, and per in-flight node its `Phase` (hydrate, apply, readiness, plus `discovery` for the CRD barrier's refresh, tracked under the synthetic node `api-discovery` so a hung refresh is reported and aborted like a hung node) and when it began; readiness status callbacks count as activity, so a ten-minute StatefulSet rollout that reports every 2s is not a stall. `assess(policy, idle, in_flight, last_warned)` is the pure policy (quiet / warn / abort), unit-tested alone. `run` is the task: its own `interval` (`MissedTickBehavior::Delay`, so no catch-up ticks after the stall it is watching for), emits `DeployEvent::Stalled { idle, in_flight, aborting }` at `warn_after` (default 30s) and every `warn_after` after, and at `abort_after` (default 600s, `KIX_STALL_TIMEOUT` seconds, `0` never) cancels the run through the token with the reason. `describe()` renders the one line every observer prints: `no progress for 31s: waiting on Deployment/a@default (apply, 31s), ...`, longest-waiting first, capped at five
- `cancel.rs` — `CancelToken`: `cancel()`, `cancel_with_reason()`, `is_cancelled()`, `reason()`, and awaitable `cancelled()` (backed by `tokio_util::sync::CancellationToken`) so the engine's supervisor can select on it while every node is in flight
- `readiness.rs` — `wait_for_ready()` polls per-kind conditions (Deployment replicas, CRD Established, Job succeeded, etc.). `wait_for_import_target()` handles PackageInstance import markers (`kix.dev/mode: import`): parses `kix.dev/import-kind/apiversion/name` annotations and polls the described resource. Scope is determined by kind — `CustomResourceDefinition` is cluster-scoped (and waits for `Established=True`), everything else is namespaced and queried in the marker's own `metadata.namespace` (no `kix.dev/import-namespace` annotation: imports always describe a resource in the marker's own namespace). `Secret` imports with a `kix.dev/import-secret-keys` annotation also verify every declared key is present in `data` before the marker is considered ready — missing keys produce `ReadinessResult::ImportMismatch { missing_keys, message }`, which `reconcile.rs` surfaces as `ReadinessFailed { missing_keys, .. }` so observers can render the exact missing keys as a structured line. Custom readiness conventions are DECLARED, not hardcoded: a CRD-owning package sets `readiness = { path; equals; }` on its CRD builder, kix stamps it on every CR built through the typed chain as the `kix.dev/readiness` annotation (JSON `{"path": "/status/...", "equals": "..."}`), and `declared_readiness`/`check_readiness` evaluate it before any kind-based rule — this is how VictoriaMetrics CRs gate on `status.updateStatus == "operational"` (their conditions are consumer-prefixed, never Ready/Available) with no VM kind list in the CLI. Malformed annotations fall through to kind rules (version skew ≠ unhealthy) — but note the un-annotated half of that skew: manifests built by a pre-declaration library have no annotation, and a status-less CR then hits check_generic_ready's ready-on-empty, racing its operator instead of timing out; rebuild such manifests rather than relying on the fallthrough. SGCluster/Gateway condition rules remain hardcoded until their packages gain typed CRD builders. A generic-CR readiness timeout lists the condition vocabulary it observed and points at the declaration mechanism.
- `activation.rs` — Activation CR lifecycle: phase-based model (Queued → Deploying → Active → Superseded). `find_active()`, `find_queued()`, `list_superseded_activations()`, `begin_deploy()`, `record_waves()`, `finalize_deploy()`, `resume_point()`, `supersede_activation()`, `read_phase()`. All status writes use `patch_status` (status subresource). `status.previousActivation` links activations for rollback. `record_waves()` accepts accumulated wave records to avoid GET-before-PATCH round-trips
- `client.rs` — **the apiserver transport policy**, applied once so every call site inherits it. `build_client(config, policy)` wraps kube's tower stack in `ResilienceLayer`: retries (429 for every method with `Retry-After` honoured; 5xx and connection loss for idempotent methods only, so a POST is retried only when the connection never opened), exponential backoff with equal jitter under a total budget, and a per-attempt deadline for non-watch requests. Watches bypass the deadline. It deliberately holds **no** in-flight cap: the first version did, and a permit held inside a future that the scheduler had parked (its `FuturesUnordered` is not polled while it awaits CRD rediscovery inline) deadlocked `kix deploy` with every thread idle, and no deadline can fire in a future nobody polls. Burst control lives in the sweep instead. When the budget is spent the last response or error is returned unchanged, so callers see the same `kube::Error` they always did. `decide()` is the pure policy, unit-tested against a scripted fake service. Knobs: `ResiliencePolicy` (defaults sized to outlast a webhook pod restart) with env overrides `KIX_RETRY_ATTEMPTS`, `KIX_REQUEST_TIMEOUT`, `KIX_CONNECT_TIMEOUT`. The old per-patch retry loop in `apply.rs` is gone; it was one file's private copy of this
- `errors.rs` — `FailureClass` + `classify(&kube::Error)` / `classify_status(code)`: the one table that says what an apiserver failure means (rate-limited, unavailable, server error, transport, timeout, unauthorized, forbidden, not found, conflict, invalid). Every site that used to compare `resp.code` by hand (apply conflicts, the sweep's 403, readiness 404) reads this instead, and the transport layer uses the same table to pick what to retry
- `fetch.rs` — `make_client()` (builds through `client::build_client`), `discover_resources()` (walks EVERY served version of each API group, preferred first, first ApiResource wins per kind — `recommended_resources()` alone hid all v1beta1 kinds of a group once a v1 kind joined it, e.g. operator.victoriametrics.com), `fetch_managed_resources()` (parallel LIST with the managed-by label selector, at most `DEFAULT_SWEEP_CONCURRENCY` = 16 in flight on spawned tasks (`KIX_SWEEP_CONCURRENCY`), then `partition_sweep()`: stamped objects (`kix.dev/identity-hash`) are managed whatever owns them; unstamped + owned are controller children and dropped; unstamped + unowned are kept apart as `ManagedSweep::unstamped` for gc; an unstamped `Endpoints` named after a managed Service is that Service's mirror and dropped — controllers copy labels onto what they derive, so the label only finds candidates and the identity hash is the proof; `sweep_managed()` returns both lists plus `ManagedSweep::forbidden` (resource types that answered 403: a fact about the account, recorded so `diff` and `gc` can print "N not listable with this account" instead of passing off a narrower view as complete), `fetch_managed_resources()` only the managed one. Any other list failure that survives the transport's retries is an **error**, never an empty list: the old warn-and-skip made `kix diff` report every PackageInstance as "will be created" during an apiserver restart (429 "storage is (re)initializing", stage1 2026-09-07), and a plan built on a partial sweep is wrong in ways the user cannot see. Same rule in `deploy.rs`: a failed live reconstruction of the previous state is an error, not a first deploy. `merge_discovery()` / `discover_group()` (see scheduler.rs notes). There is no kind skip list any more: the old `SKIP_RESOURCES` fed both the sweep and apply-path discovery, which made every listed kind undeployable (helmchartconfigs.helm.cattle.io broke the first rke2 deploy that way; the lithus flavor's CSIDriver and StorageProfile were on it too) — kixpkgs#41. `normalize_for_diff()` strips server metadata **including managedFields** — never call it before drift hashing
- `fieldsv1.rs` — pure fieldsV1 interpreter (doc 122, no cluster access): `kix_fieldset()` extracts kix's SSA managedFields entry (manager `kix`, operation `Apply`, no subresource) from TYPED metadata; `project()` implements fieldsV1 semantics (`f:` members with empty-subtree-as-atomic-leaf, `k:{...}` associative-list key matching, `v:` set values, `i:` positions, `.` node-itself; live array order preserved; entries missing from live are skipped = deletion detection); `applied_content_hash()` is the ONE shared stamp/check recipe: merge typed metadata → project onto kix fieldset → strip `kix.dev/*` annotations → Blake3 over canonical JSON. Owns `APPLIED_HASH_ANNOTATION`. Fixture-tested against real recorded apiserver objects in `tests/fixtures/`
- `drift.rs` — runtime drift check (doc 122): `check_cluster()` fetches kix-managed resources (raw — no `normalize_for_diff`, which deletes managedFields) and compares each object's current applied-content hash against its `kix.dev/applied-hash` stamp. Verdicts: `InSync`, `Drifted { foreign }`, `Unstamped` (no stamp — NOT drift), `NoFieldset` (managedFields stripped). Attribution flattens every other manager's fieldsV1 into field paths with manager/operation/subresource/timestamp, excluding ONLY `subresource == "status"` (autoscalers and `kubectl scale` write via `/scale` and must stay visible, doc 123). PI `spec.driftIgnore` evaluation is a marked TODO hook (doc 123)
- `normalize.rs` — manifest normalization helpers (strip server metadata, kix annotations, status, nulls; Blake3 `content_hash`, `hash_value`, `sort_keys`). The old build-vs-live machinery (`detect_drift`/`project_onto_shape`/`DriftStatus`) has been **deleted** — superseded by `fieldsv1.rs` + `drift.rs` (build-time hashes can't exact-match live objects: server zero-value omission, `stringData`→`data`, quantity canonicalization). `strip_kix_annotations` stays in active use (export, applied-hash recipe)

## Key patterns

**Identity-hash** is the core primitive. First 32 chars of a Nix store path. Same hash = identical content + deps. Change detection is a hash set comparison — no deep diff needed.

**StoreGraph** is the in-memory DAG built from `kix-packages.json` + Nix store references. Everything operates on StoreGraph pairs (old vs new): change detection, plan display, stamping, GC.

**Keyed-list diff.** The diff engine matches K8s arrays by natural keys (containers by `name`, ports by `name`, env by `name`, volumeMounts by `mountPath`) not by position. Without this, reordering items produces false diffs.

**Waves** via Kahn's algorithm on the `kix.dev/depends-on` DAG. Within a wave, resources are independent. Lexicographic sort within waves for determinism.

**Annotations** stamped at build time: `kix.dev/identity-hash`, `kix.dev/package`, `kix.dev/depends-on`, `kix.dev/activations`. Everything downstream reads these, never raw store paths.

**Backend abstraction.** `NixBackend` trait — `CliNixBackend` (production, shells out to `nix` CLI) and `MockNixBackend` (tests, no Nix needed). An experimental `FfiNixBackend` using direct C FFI exists behind the `nix-ffi` feature but is not currently used.

**Operator mode** (`--operator` flag on deploy/rollback/gc). Instead of calling the reconcile engine directly, the CLI creates or patches Activation CRs and watches their status. The operator does the actual wave-by-wave apply. Build + plan display still happens locally (needs Nix). Three flows:
- `deploy --operator`: build locally → show plan → apply Activation CR with source path → watch status.waves
- `rollback --operator`: find superseded activation → patch Activation CR source path to target → watch progress
- `gc --operator`: delete the Activation records beyond `--keep` → operator finalizer cleans up resources

**Operator K8s Events** (doc 99 Stage H). The operator composes two `DeployObserver`s over the same `DeployEvent` stream: `OperatorObserver` emits structured tracing logs, and `K8sEventObserver` publishes K8s Events on the Activation CR via `kube::runtime::events::Recorder` so `kubectl describe activation` and downstream log aggregators surface the deploy timeline. Events are fire-and-forget (`tokio::spawn` per publish, failures logged at `debug` and dropped) — they are telemetry, never part of deploy correctness. Suppresses Pending and most Running verdicts to stay under the cluster Event rate budget; emits Normal/Warning Events for plan, terminal verdicts, prune, drift, recreate, hydration, and finalization. See `cli/kix-operator/src/k8s_events.rs`.

**Operator reconcile loop prevention.** The operator uses a stream-level generation filter to drop status-only updates. All status writes go through the status subresource (`patch_status`), which doesn't bump `metadata.generation`. The controller dispatches by phase: Queued CRs trigger activation switchover + deploy, Active CRs trigger drift detection, Superseded CRs are no-ops.

**Unified reconcile.** Both new deployments and drift correction use the same path: load desired manifests, fetch live kix-managed resources from the cluster, compare identity-hashes (`detect_changes_live`), wave-plan, and apply. No "old manifests" concept — the cluster IS the old state.

**Error boundary.** `thiserror` in libraries, `miette` in binary.
