# Changelog

What changed in each Kix release. Kix uses semantic versioning and is still
below 1.0: a minor release (0.5 to 0.6) may break things, and a patch release
(0.5.0 to 0.5.1) does not. Each breaking entry says what to change when you
upgrade.

A release lists its changes under these headings:

- **Breaking (shows an error):** Kix stops with an error that says what to
  change.
- **Breaking (no error):** nothing fails, but the result is different. Read
  these first.
- **Upgrade notes:** nothing to change, but worth knowing before you upgrade.
- **Added**, **Changed**, and **Fixed**.

Every pull request that changes something a Kix user sees adds a line under
`## Unreleased`. `CLAUDE.md` § Versioning and breaking changes says what
counts as breaking.

## Unreleased

**Before you upgrade**, check each of these in your cluster definitions and packages. The entries below say more.

- A cluster listed in `kix.lib.mkFlake` that calls `kix.buildCluster` without `name`, and that Kix 0.6 deployed: add `name = "cluster";` to keep its deploy history.
- A `kix.buildCluster` call outside `kix.lib.mkFlake` without `name`: add one.
- `ttlSecondsAfterFinished` on a Job that a package builds, or passed to `kix.healthCheck`: remove it.
- A dependency served by an instance in another namespace: add `deps.<arg> = ref.<namespace>.<instance>` to the consumer, or `meta.scope = "cluster"` to the provider's package.
- `k8sVersion`: make it match the Kubernetes version the cluster runs.
- An object that an earlier deploy left broken: fix it, because a deploy that depends on it now fails.
- VictoriaMetrics `extraArgs`: remove the flags that the packages now set, and use the options the error names.
- `kix.withMountsOn`: check that each container name exists in the workload.
- Scripts that look for `completed` in `kix health` output: look for `healthy`.
- Scripts or CI jobs that run `nix build .#cluster-<name>-activation`, or a plain `nix build` or `nix flake check` of a cluster that uses Helm: switch to `kix build`, `kix bundle`, or `kix diff --from-bundle`, or set `builder = "nix"` in `kix.toml`.
- Machines that run `kix` from `PATH` without its `libexec/kix` folder: install the whole release archive, or set `KIX_RUNTIME_DIR`.
- Helm `extraFlags` that hold a flag and its value in one string, such as `"--set a=b"`: split them into separate list items.
- Helm charts that need Helm 3: set `helmVersion = "3"`. The default is now Helm 4.

### Breaking (shows an error)

- If a cluster definition sets `k8sVersion`, `kix deploy`, `kix plan`, and the operator now stop when the cluster runs a different Kubernetes version. Set `k8sVersion` to the value the error names, build again, and deploy. `"1.31"` matches any 1.31.x, and `"1.31.4"` matches only 1.31.4. `kix rollback` prints a note and goes ahead. A definition that leaves `k8sVersion` unset is not checked. See [`k8sVersion`](https://kix.run/docs/reference/cluster-configuration/#clusterprovider-k8sversion-and-clusterkubernetesuid).
- `kix deploy` now fails on an unchanged object that is not ready when something in the deploy depends on it, and the error says that nothing in this deploy changed that object. Fix the object and deploy again, or deploy with `--on-error continue` to deploy the objects that do not depend on it. See [Set the readiness timeout](https://kix.run/docs/how-to/operate-a-cluster/deploy-with-dry-run-timeouts-pruning-and-log-tui-output-modes/#set-the-readiness-timeout).
- `kix.buildCluster` no longer names a cluster `cluster` when it is called without `name`. Pass `name`, or list the cluster in `kix.lib.mkFlake`, which names it after its key. A cluster listed in `mkFlake` that already sets `name` keeps it.
- `kix deploy` and `kix plan` stop when a cluster listed in `kix.lib.mkFlake` calls `kix.buildCluster` without `name` and Kix 0.6 deployed it as `cluster`. Kix 0.7 names such a cluster after its `clusters` key, and a deploy under the new name would not find the old deploy records, so the operator would keep repairing the old build and Kix would never delete the objects only the old build has. Add `name = "cluster";` to keep the old name and its deploy history, or `name = "<key>";` to start a new deploy history under the new name and remove the old records yourself. Setting `name` turns the check off.
- A Job that a package builds may no longer set `ttlSecondsAfterFinished`, and `kix.healthCheck` no longer takes that argument. Kubernetes would delete the finished Job, and Kix would then see it as missing and run it again. Remove the field. A finished Job now stays on the cluster until a later build no longer contains it, and Kix deletes it then. A CronJob's `jobTemplate` may keep the field, because Kubernetes creates those Jobs. Kix removes the field from Jobs that a Helm chart renders.
- `victoria-metrics-agent` no longer accepts `remoteWrite.url` or `promscrape.config` in `extraArgs`, and `victoria-metrics-operator` no longer accepts `--zap-log-level`, `--leader-elect`, or `--health-probe-bind-address` (in either the one-dash or two-dash spelling). The build stops with an error that names the option to use instead: the `vmCluster` dependency sets the remote-write target, the operator writes the scrape configuration, and `logLevel` sets the log level. Remove the other flags.
- `victoria-metrics-cluster` no longer accepts `retentionPeriod` or `replicationFactor` in `vmstorage.extraArgs`, `vmselect.extraArgs`, or `vminsert.extraArgs`, nor `httpListenAddr` in `vmselect.extraArgs` or `vminsert.extraArgs`. Set the `retentionPeriod` and `replicationFactor` options instead, and remove `httpListenAddr`: the cluster's `out.serviceUrl` and `out.remoteWriteUrl` name ports 8481 and 8480. Release 0.6 already refused `dedup.minScrapeInterval` in `vmstorage.extraArgs` and `vmselect.extraArgs`.
- `kix.withMountsOn` now fails the build when no container in the workload has the given name. Before, it added the volume to the pod and mounted it nowhere. The error lists the workload's containers and init containers; fix the name in the `kix.withMountsOn` call.
- `kix.lib.mkFlake` no longer exports the `cluster-<name>-activation` flake package output (`packages.<system>.cluster-<name>-activation`) under the default `kix` builder. By default, Kix evaluates `legacyPackages.<system>.kixClusters.<name>.activationIndex` directly in its local store, and refuses an older Kix library (0.6.0 and earlier) that has no `activationIndex` with instructions to run `kix lib update`. If a CI job or script ran `nix build .#cluster-<name>-activation` to save a baseline for `kix diff`, use `kix bundle <cluster> before.kixbundle` and `kix diff <cluster> --bundle after.kixbundle --from-bundle before.kixbundle` (or `kix export <cluster> --out ./manifests` for plain YAML), or set `builder = "nix"` in `kix.toml` (and run `git add kix.toml`), which keeps `packages.<system>.cluster-<name>-activation`.
- Under the default `kix` builder, clusters that use Helm charts (`kix.helmChart`, `scope.helm.importChart`, or `scope.helm.importChartCrds`) can no longer be built with plain `nix build .#cluster-<name>`, and the `schema-cluster-<name>` and `rules-cluster-<name>` checks that `kix.lib.mkFlake` exports fail under `nix flake check` on clusters that use Helm charts. By default, Kix fetches and renders Helm charts itself, so evaluation needs no Nix build sandbox. Evaluate and check those clusters with `kix check <cluster>`, `kix build <cluster>`, `kix diff <cluster>`, or `kix deploy <cluster>` (or `scripts/kix-manifests.sh` and `scripts/cluster-checks.sh` in this repository), or set `builder = "nix"` in `kix.toml` (and run `git add kix.toml`) so Nix fetches and renders Helm charts as derivations during `nix build` and `nix flake check`.
- `extraFlags` on `kix.helmChart`, `scope.helm.importChart`, and `scope.helm.importChartCrds` now passes each list element as a single CLI argument to `helm template` instead of splitting elements on spaces in a shell. Split combined flag strings such as `[ "--set a=b" ]` into separate elements (`[ "--set" "a=b" ]`) or use `"--set=a=b"`.
- When a cluster uses a Helm chart, Kix checks that the Kix library in your `flake.lock` expects the same Helm 3 and Helm 4 versions as your installed Kix (`kix/lib/helm-versions.json`). If they differ, evaluation stops with an error telling you to run `kix lib update` (when Kix is newer than `flake.lock`) or upgrade Kix (when `flake.lock` is newer than Kix).
- Kix no longer runs `helm`, `kubectl`, or `sops` from `PATH`, and runs `nix` from `PATH` only when the project sets `builder = "nix"` in `kix.toml`. Otherwise every external tool comes from `libexec/kix/` beside `bin/kix` (or the directory named by `KIX_RUNTIME_DIR`). A bare `kix` binary copied out of `target/release/` without `libexec/kix/` stops with an error naming the directories it searched; unpack the release archive as a whole or set `KIX_RUNTIME_DIR`.
- A required dependency that Kix finds only in another namespace now stops the build, and the error prints the `deps` line to add. Add `deps.<arg> = ref.<namespace>.<instance>` to the consumer, or `meta.scope = "cluster"` to the provider's package. Before 0.7, a package that left `meta.scope` unset served every namespace. Packages that claim a role or declare a `cluster:` conflict, `kix.mkImport` stand-ins, and instances that Kix creates from `availablePackages` or enables via `optional = true` still bind from every namespace. The packages in this repository that other namespaces use by name now set `meta.scope = "cluster"`. A package with `meta.scope = "cluster"` gets at most one instance from `availablePackages`, and `meta.scope` accepts only `"cluster"` and `"namespace"`. See [Instances and composition](https://kix.run/docs/reference/instances-and-composition/).

### Breaking (no error)

- `kix health` no longer reports a `completed` status. A Job that is gone is reported as missing. A finished Job now stays on the cluster and reads as `healthy`, so a script that looks for `completed` should look for `healthy`.
- An optional dependency (`x ? null`) whose only match is in another namespace now takes its default, and Kix prints a warning that names the instance and the `deps` line to add.
- Helm charts now render with Helm 4 (`4.3.1`) by default instead of Helm 3 (`3.19.1`). Set `helmVersion = "3";` on `kix.helmChart`, `scope.helm.importChart`, or `scope.helm.importChartCrds` if an upstream chart relies on Helm 3 template behavior.
- Deploy receipts and SLSA provenance statements (`source.dirty`) now determine whether the Git working tree is dirty from Nix flake evaluation (`nix flake metadata`), which checks tracked files only. Untracked files no longer mark a build dirty.

### Upgrade notes

- The Activation records of a cluster definition that sets `cluster.kubernetes.uid` carry a new label, `kix.run/kubernetes-uid`. Older Kix ignores it.
- The first `kix diff` or `kix plan` after the upgrade may show a `secret-ref-*` or `service-ref-*` PackageInstance as removed from one package. Nothing is deleted, and the first deploy corrects it.
- The first deploy after the upgrade applies the Cilium network policies again, and every object that depends on them, because the `kix.run/readiness` annotation on each policy now lists the state that means Cilium rejected it. The same goes for Velero Backups, Restores, and Schedules, CDI DataVolumes, and the objects that depend on them. Only annotations change, so most pods do not restart. A pod whose template carries a checksum of a ConfigMap or Secret that depends on a network policy restarts once, for example `grafana`, `loki-logs`, and `immich-server`.
- The controller Deployments of cert-manager (controller and cainjector), kubevirt, cdi, prometheus-operator, victoria-metrics-operator, and clickhouse-operator are applied once more on the next deploy, because their `kix.run/depends-on` annotation now names their CRDs. Objects that depend on those Deployments, such as their PackageInstance records, are applied again too. The annotation sits on each object, not on a pod template, so no Deployment's pods restart. cert-manager's `startupapicheck` Job depends on the cainjector, so it runs once more.
- The setup Jobs of `reflector` and `ingress-nginx`, and every `kix.healthCheck` probe, run once more on the first deploy after the upgrade, because their manifests changed and they keep their names. They are safe to run again. The bootstrap Jobs of `stackgres-database` and `clickhouse-database` run again only when Kubernetes has already deleted them; a Job still on the cluster is patched to drop `ttlSecondsAfterFinished` and does not run again. From then on every Job stays on the cluster until a later build replaces it.
- The in-cluster operator reconciles the build named in the cluster's Active Activation record. A cluster that still runs a build from Kix 0.6 keeps running its self-deleting Jobs again on every reconcile until you deploy a build from this release.
- By default (`builder = "kix"`), Kix now evaluates flakes in its local store, a user-owned store (`$XDG_CACHE_HOME/kix/store` or `~/.cache/kix/store`), separate from `/nix/store`. The first build after upgrading downloads the project's locked flake inputs (`nixpkgs`, about 400 MB unpacked) and any Helm charts into Kix's local store, even on machines that already have Nix installed (unless the project sets `builder = "nix"` in `kix.toml`, which uses `/nix/store`).
- Under the default `kix` builder, result directories created by `nix build` before this release (`./result`) point into `/nix/store`, which Kix's local store cannot read when passed to `kix diff --from ./result`. Save comparison baselines with `kix bundle <cluster> before.kixbundle` and compare with `kix diff <cluster> --from-bundle before.kixbundle`, or set `builder = "nix"` in `kix.toml`.
- The evaluation cache key in `<cache dir>/kix/eval-cache.db` now includes the project's builder (`kix` or `nix`) and the store location (`KIX_STORE_ROOT` or `/nix/store`). After upgrading, the first cached command (`kix build`, `kix check`, `kix list`, `kix graph`, `kix inspect`, `kix images`, `kix status`, or `kix compliance audit`) evaluates the flake again.
- Moving the default Helm version from Helm 3 to Helm 4 changes the `cilium` package's ConfigMap by dropping three empty keys (`debug-verbose`, `nodeport-addresses`, and `policy-cidr-match-mode`). On clusters that deploy `cilium`, the first deploy after upgrading restarts the Cilium agent and operator, along with any workloads whose checksum annotations depend on them.
- On macOS, Kix now stores its evaluation cache, activation roots, and local store under `$XDG_CACHE_HOME/kix` or `~/.cache/kix` instead of `~/Library/Caches/kix`. After upgrading on macOS, the first evaluation populates `~/.cache/kix`; you can delete `~/Library/Caches/kix` to reclaim disk space.
- The first deploy after the upgrade applies the PackageInstance record again for each package that has no version, such as `persistent-volume-claim` and `storage-classes`, and for `stackgres-cluster` and `cnpg-cluster`, whose records gain a version.
- The first deploy after the upgrade reads the live state of almost every object, because most objects are applied again and Kix now checks the unchanged objects they depend on. An object that an earlier deploy left broken now fails that deploy, with a message that names it.

### Added

- `kix status` prints the cluster's Kubernetes version under its ID, and `kix status --operator -o json` adds `kubernetes_version`.
- A cluster listed in `kix.lib.mkFlake`'s `clusters` is named after its key unless it sets `name`, so the name no longer has to be written in both `flake.nix` and the cluster file.
- A CRD declaration can list the states that mean a custom resource will not become ready until its spec changes: `readiness.failed`, a list of `{ condition = { type; status; reason ? }; }` or `{ path; equals; }` entries beside the ready rule. When the controller reports one of them for the current spec, `kix deploy` stops waiting at once and shows the controller's condition, reason, and message, instead of failing at the readiness timeout. A package author can give an entry a `hint` that says what to do next. Packages in this repository declare it where the controller's verdict stands until the spec changes, for example Cilium, Velero, and CDI.
- A scorecard rule, `architecture.controllerRequiresCrds`, warns when a package defines CustomResourceDefinitions and runs a Deployment, StatefulSet, or DaemonSet, but no workload depends on the definitions. Listing them in `root.requires` orders the package's consumers after them, not the controller.
- `kix.withMountsOn` takes a list of container names as well as one name, mounts into init containers, and works on CronJobs. The same volume can now be mounted into several containers, or at several paths, from separate calls: a volume that is already declared with the same name and the same source is not added twice, and only a different source with the same name fails the build. `kix.mount.emptyDir` and `kix.mount.secret` take `readOnly`.
- `cluster.kubernetes.uid` binds a cluster definition to one Kubernetes cluster, named by the UID of its `kube-system` Namespace. `kix deploy`, `kix plan`, `kix gc`, and the operator refuse to run the build against another Kubernetes cluster, and once a bound definition has deployed, that Kubernetes cluster refuses definitions that do not name it. `kix rollback` refuses a target that names another Kubernetes cluster. `kix status` shows the ID in its header, and `kix status --operator -o json` as `kubernetes_uid`. See [Bind a cluster definition to its Kubernetes cluster](https://kix.run/docs/how-to/operate-a-cluster/bind-a-cluster-definition-to-its-kubernetes-cluster/).
- Kix now runs without a system Nix installation, `/nix` directory, Nix daemon, root access, or Linux user namespaces. Pre-built release archives (`x86_64-linux`, `aarch64-linux`, and `aarch64-darwin`) bundle `bin/kix` together with the Kix runtime in `libexec/kix/`, which contains `nix` (`2.35.4`, statically linked against `musl` on Linux and bundled with its `.dylib` libraries on macOS), `helm` (`4.3.1` and `3.19.1`), `kubectl` (`1.37.2`), `sops` (`3.12.1`), `manifest.json`, `THIRD_PARTY_LICENSES`, and a companion `kix-<version>-third-party-sources.tar.zst` release archive. Kix evaluates flakes into Kix's local store, a user-owned directory at `$XDG_CACHE_HOME/kix/store` or `~/.cache/kix/store` (overridden by `KIX_STORE_ROOT`, runtime directory overridden by `KIX_RUNTIME_DIR`). See [Install and run Kix](https://kix.run/docs/how-to/start-and-inspect/install-and-run-the-kix-cli/).
- `kix.toml` beside `flake.nix` selects the project's builder (`builder = "kix"` by default, or `builder = "nix"`). Setting `builder = "nix"` (and staging `kix.toml` with `git add kix.toml`) makes `kix` evaluate with the machine's `nix` on `PATH` (Nix 2.24 or later, not Lix) and `/nix/store`, inheriting the machine's `nix.conf` binary caches and remote builders without requiring `trusted-users`, renders Helm charts as ordinary Nix derivations so `nix build` and `nix flake check` work on clusters with Helm charts, and exports `packages.<system>.cluster-<name>-activation`. `builder = "remote"` is reserved for a future build service and refused in this version. See [`kix.toml`](https://kix.run/docs/reference/kix-toml/).
- `kix.lib.mkFlake` publishes `legacyPackages.<system>.kixLib`, the library and package set for the project's builder. A flake that also builds other things can merge `mkFlake`'s outputs into its own and build its own checks from `kixLib`. See [Use `mkFlake` inside a larger flake](https://kix.run/docs/how-to/start-and-inspect/use-mkflake-in-a-consuming-repo/#use-mkflake-inside-a-larger-flake). `kixpkgs.lib.forPkgs` supports only the default `kix` builder.
- `kix doctor` checks the Kix runtime (the program versions, and that no file changed since install) and the project's builder setting in `kix.toml` (under `--flake`). When `builder = "nix"`, it also checks that `nix` on `PATH` is upstream Nix 2.24 or later, and warns when `allow-import-from-derivation` is off. Each line starts with ✓, ! or ✗, and a problem's fix follows on the next line. See [`kix doctor`](https://kix.run/docs/reference/cli/doctor/).
- `kix lib update [--dry-run]` updates the project's `kixpkgs` input in `flake.lock` to the `v<version>` tag matching the installed Kix without modifying `flake.nix`. See [`kix lib`](https://kix.run/docs/reference/cli/lib/).
- `helmVersion` (`"3"` or `"4"`, default `"4"`) on `kix.helmChart`, `scope.helm.importChart`, and `scope.helm.importChartCrds` selects between the Helm 4 in the Kix runtime (`4.3.1`) and Helm 3 (`3.19.1`).

### Changed

- When `kix` writes an error to a log file or a pipe, it no longer breaks long lines. In a terminal it still wraps them to the window width. This keeps paths and commands in error messages whole, so you can search for them and copy them.
- When several instances in other namespaces answer a dependency name, the error lists each one with a ready-to-paste `deps` line.
- A Job that stays on the cluster after a failed run is now reported as failed on every later deploy and reconcile until it is replaced or deleted. Change an input so the Job gets a new name, or delete it with `kubectl` and deploy again. Kix does not delete a failed Job to retry it.
- When an object fails to deploy, the error now says how many objects Kix did not deploy because they depend on it.
- When a namespace is over its ResourceQuota, the error now lists every object Kix could not count, grouped by kind, so you can see that the real usage may be higher. Before, it left out custom resources whose kind declares no `usesAtLeast`. A kind whose `usesAtLeast` returns `{ }` runs nothing and is left out of the list; the packages in this repository now declare that for their kinds that only hold configuration, such as PrometheusRule, ServiceMonitor, Certificate, and CiliumNetworkPolicy. Each limit that is over now gets its own error.
- `kix.guardArgs` also checks flags given as an attrset, the form a VictoriaMetrics CR's `extraArgs` takes (a key matches with or without leading dashes), and its error now reads `which this package does not accept:` followed by the reason and the option to set instead. `victoria-metrics-cluster` and `reloader` use it for the flags they refused before, so only the wording of those errors changes.
- The PackageInstance record of a package that has no version, such as `persistent-volume-claim` and `storage-classes`, now leaves `spec.version` out instead of writing `<undefined>`, and building no longer prints `warning: package <name> has no version set`.
- `stackgres-cluster` and `cnpg-cluster` report the PostgreSQL version they run as their version, and the PackageInstance record shows it. A `meta.compatibleWith` bound on one of these packages now checks that version; before, it checked nothing.
- The JSON schemas of the `kix diff -o json` document and the `kix deploy --log-format json` log now say that later versions of Kix may add fields and new types of line. A program that reads them should skip the ones it does not know.
- When a deploy waits more than 10 seconds on one object, the `waiting` line now also says how many objects wait on it and names up to three of the objects that depend on it directly. The `--log-format json` `waiting` line gains `holds` and `holds_total`.
- `kix list` and commands that take a cluster name now say when the flake has no outputs for your system, and how to add it, instead of reporting the cluster as missing.
- `kix logs` and `kix pf` now run the `kubectl` in the Kix runtime, and `kix deploy` decrypts SOPS secrets with the `sops` in the Kix runtime, so neither tool needs to be installed on `PATH`.
- Nix evaluation errors now keep only the first three stack frames from the user's code, followed by `(stack trace truncated; run kix with -v to show the full trace)` and the error message. Pass `-v` (`--verbose`) to see the full trace.
- `valkey`'s metrics exporter sidecar now has a CPU limit of `1` instead of `250m`, because at `250m` it was throttled during scrapes and raised `CPUThrottlingHigh`. Its pods restart once. Set `metrics.resources.limits.cpu` to keep the old limit.

### Fixed

- A Deployment whose rollout is stuck is no longer counted as ready. Before, Kix counted it as ready when a pod from the old version was still running next to a new pod that never started, for example because its image does not exist. Kix now waits until no pod from the old version is left, and fails on the new pod's error. The waiting message says how many old pods are left.
- An object that two package instances list, such as a provider's Secret reference that a consumer holds as a part, now belongs to the instance that built it. Before, its owner could switch between the two on any unrelated change to either package.
- A network policy that Cilium rejects (`Valid=False`, for example a rule with no `ingress` or `egress` section) now fails the deploy as soon as Cilium reports it, with Cilium's reason, instead of after the readiness timeout with a timeout message.
- cert-manager, kubevirt, cdi, prometheus-operator, victoria-metrics-operator, and clickhouse-operator now deploy their CRDs before their controller. On a first deploy the controller no longer starts before the API server serves its kinds, so it no longer crashes and restarts while it waits for them.
- The in-cluster operator, and `kix deploy` when the previous build is not on disk, no longer run a finished setup Job again. Both compare the build with the live cluster, and a Job that had deleted itself after finishing looked like a missing resource.

## 0.6.0 - 2026-11-06

### Breaking (shows an error)

- A stateful package (`lifecycle = "stateful"`) now fails to build if it creates a custom resource whose type does not say whether it holds data. Kix uses this to tell a real data migration from a harmless swap of objects. To fix the build, add `holdsData = true` to each type whose objects hold data you would lose if they were deleted, such as a database or a storage pool. Add `holdsData = false` to the others, such as monitoring rules, certificates, or policies. Set it where the type is declared: the `scope.mkCRD`, `scope.mkCRDRef`, or `kix.mkImport` `crds` entry. Create those custom resources with `scope.mkCR`, so that they carry the setting. The packages in this repository already do this.
- `cnpg-cluster` no longer accepts `extraSpec.bootstrap.initdb.import`, and the build stops with an error. Use the new `import` option instead. It also sets up the dependency on the source database and the network policy to reach it.

### Breaking (no error)

- `filebrowser` now shows only a `files` folder at the top of its storage claim. Release 0.5 showed the whole claim. When you upgrade, move the files already on the claim into a new `files` folder at its top. Otherwise File Browser does not show them. File Browser now keeps its own database on the same claim, at `/data/database`, so its users survive a restart. Its Deployment now uses the `Recreate` strategy, because only one copy of File Browser can use the database file at a time.

### Upgrade notes

- The first deploy after the upgrade applies some objects again. You do not need to change your cluster definitions. Kix now adds a `kix.run/holds-data` annotation to some objects: `"true"` or `"false"` on custom resources whose type declares `holdsData`, and `"true"` on PersistentVolumeClaims, PersistentVolumes, and StatefulSets that create storage. Kix applies each of these objects again to add the annotation. It also applies again every object that depends on one of them, because Kix records each dependency's new hash. Only annotations change, so most pods do not restart. Pods in `grafana`, `valkey`, and `plausible` may restart once. Their pod templates carry a checksum of a ConfigMap or Secret, and that checksum changes when the ConfigMap or Secret depends on an annotated object.
- That first deploy is also the first time the new warning about fields Kubernetes did not keep (see Added) checks these objects. It may list fields that a CRD has been dropping for a long time.
- The `kix deploy --log-format json` log has a new type of line, `fields_not_kept`. A program that checks each line against the 0.5 schema rejects it. Check against the updated `cli/kix-cli/schema/deploy-log.schema.json`, or skip lines whose `type` you do not know.
- Each deploy now saves an index of the build's packages in the Activation record, under `status.packageIndex`. You do not need to do anything. Older Kix ignores the field, and records without it work as before.

### Added

- `cnpg-cluster` can copy databases from another PostgreSQL server when the Cluster is created, through the new `import` option and the `importSource`, `importPassword`, and `importCa` dependencies. Kix derives the network policy between the Cluster's pods and the source.
- The `service-ref` package names a Service Kix does not render, with the pod labels and ports network policy needs, so a server another tool installed can be a dependency.
- `kix plan` and `kix deploy` warn when Kubernetes would not keep, or did not keep, a field as the build sets it: a field a CRD's schema drops, or a value a mutating admission webhook changes. `kix plan` lists these fields in a new `not_kept` section, and `kix deploy` prints a warning after the apply (a `fields_not_kept` line in `--log-format json`). The in-cluster operator records a Kubernetes Warning event with reason `FieldsNotKept`. Neither stops the deploy.
- `filebrowser` creates or updates the users listed in the new `users` option on every start, with passwords from a `filebrowserUsers` secret, each scoped to a folder and with command execution off. The new `tokenExpirationTime` option sets how long a login lasts.

### Changed

- Security patch upgrades: `immich` 3.3.5, `cilium` 1.19.10, `grafana` 13.1.8, and `prometheus` 3.13.5.

### Fixed

- `kix diff` and `kix deploy` no longer report a data migration, and stop the deploy, when a stateful package removes one object and adds another that holds no data. Two examples are an import marker replaced by a PodDisruptionBudget, and a PodMonitor replaced by a PrometheusRule. Objects of different kinds now count as a migration only when both may hold data. Kix reads that from the object's `kix.run/holds-data` annotation. An object without the annotation, such as one an earlier release deployed, holds data when it is a custom resource or a built-in kind that declares storage. A renamed object of the same kind still counts as a migration.
- `kix diff` shows one changed value inside a list item as one change to that value, not as the item removed and a new one added. Lists of objects with a `metadata.name`, such as a VirtualMachine's `dataVolumeTemplates`, match items by that name, and `creationTimestamp: null` on one side no longer counts as a difference. In `-o json` output, the `path` of an added or removed list item now gives its real index in the list.
- `kix diff` and `kix plan` against the cluster no longer show changes to objects the build does not change, such as an empty `value` the API server dropped. `kix diff` now lists drift (fields someone changed on the cluster, and who changed them) on any machine, also when it finds no other difference, and says how many objects it could not check for drift (the new `drift_unchecked` field in `-o json`).
- `kix diff` and `kix plan` against the cluster no longer list an import marker (such as `secret-ref-*`) as a removed package after a failed deploy. The marker shows under the package that declares it.
- `kix diff` and `kix plan` against the cluster show an object that moved to another package and changed as removed from its old package and added to its new one, on any machine. This needs a deployed record written by this release. Against a record from Kix 0.5, the object shows only under its new package.
